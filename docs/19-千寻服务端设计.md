# 19 — 千寻服务端（qx-server）与在线能力平台设计（v5）

> 状态：设计稿 v5.2（2026-10-09）。v5：定位升级为「千寻服务端」（单一访问面 + rusqlite +
> 配置同步 + 工具端在线能力底座）；**v5.2：纯客户端化与零兼容**——千寻只连接不托管任何服务，
> 服务端形态唯一，旧 LAN 面直接删除（operator 指示，见 §13）。
> v3 评审定案与 v4 资源治理全部吸收；架构变更见 §1.2 与 §13 变更记录。
> 真实域名/端口/地址见 git 忽略的 `.local/servers.md`；本文档只出现占位符。

## 0. 结论（TL;DR）

- 新 crate `src-tauri/crates/qx-server`：**独立服务端二进制，形态唯一**——部署在哪
  （本机 / 局域网机 / 云端 VPS）只是连接地址不同。千寻桌面端是**纯客户端**：只连接、
  不托管、不启动任何服务（operator 指示 2026-10-09）；桌面外壳的回环 listener 是壳内管道，
  不属于访问面。
- **单一服务器端口原则**：千寻桌面端对外的访问面只有「服务器」一个；不再有
  「LAN 直连 + 中转兜底」双路径，手机永远只跟服务器说话。
- **服务端有状态**（operator 指示）：rusqlite（SQLite）保存实例表、设备注册表、配对码、
  **配置同步数据**、审计与指标。鉴权与配对上收到服务端（边缘鉴权），千寻侧 Router 只管会话内容。
- **配置同步**是第一公民：多设备（桌面千寻 × N、未来移动端）之间的配置 LWW 同步 + 历史留档。
- **发散定位**：server 是以后工具端的在线能力底座——同步、信箱、通知、私有插件通道、产物分发、
  API 令牌（§8 路线图，按需立项）。实施规格、兼容矩阵与决策清单见 §12（v5.1）。

## 1. 定位与原则

### 1.1 从「中转」到「服务端」

v1-v4 把服务器当**无状态字节管道**（凭据都在千寻侧）。v5 起，服务器是**有状态的千寻组件**：
它拥有设备注册表与配对（SQLite），拥有同步数据，未来承载信箱/通知/分发。理由：

1. operator 明确要求配置同步与 rusqlite——状态必须在服务端；
2. 自托管信任边界下（v3 §9 已明示），边缘鉴权上收让配对更简单（千寻离线也能完成配对兑换）；
3. 工具端愿景（手机/CLI/agent 都消费同一边缘）要求一个稳定的、有身份体系的入口。

### 1.2 单一访问面（替代「LAN + 中转兜底」）

```
 手机浏览器/PWA ──HTTPS/WSS──> ┌───────────────────────────────┐
 未来移动 App   ──HTTPS/WSS──> │ qx-server（独立二进制，形态唯一）│
 CLI/脚本       ──HTTPS──────> │  边缘鉴权·路由·同步·治理·SQLite  │
                               └───────────────┬───────────────┘
                                               │ 出站隧道（地址决定加密）
                                               │  ws://127.0.0.1:23100     本机/局域网
                                               │  wss://<relay-host>       云端（反代 TLS）
                                千寻桌面端 = 纯客户端：Router + DSH 宿主 + 隧道客户端
                                （不启动、不托管任何服务；外壳回环 listener 仅为壳内管道）
```

- **服务端形态唯一**：`qx-server serve` 一个二进制跑在任何地方。本机/局域网机绑
  `0.0.0.0:<port>` 直连（明文 WS/HTTP，安全模型与今日 LAN 网关同级）；云端绑回环由
  openresty 前置 TLS（配置见私有文档）。**地址即模式**：URL 的 scheme 说明一切（ws/wss）。
- **千寻是纯客户端**（operator 指示）：`remote/online.rs` 只做连接——出站隧道、退避重连、
  状态上报、settings 防抖推送钩子；不管理任何服务生命周期。
- **协议统一**：同一套控制帧与 yamux 数据面；`tokio::io::duplex` 载体降级为**仅测试用**
  （crate 内集成测试不起端口跑全量协议）。
- 既有 LAN listener（bindIp socket）与 `remote.bindIp/devices` **直接删除，无兼容期**
  （operator 指示：不考虑兼容；既有数据一次性手工处置，见 §12.5）。

## 2. 备选与边界

| 命题 | 判定 | 理由 |
| --- | --- | --- |
| 保留 LAN 直连作兜底 | **否**（operator 指示） | 单一访问面；本地服务器模式已覆盖局域网场景，且通配绑定更稳 |
| 服务器直连 DSH（千寻只供 TCP 隧道） | 否 | dsh_upstream 的 cookie/改写/注入逻辑在千寻进程内最安全，搬走等于重写网关 |
| frp / cloudflared / tailscale | 否 | 无注册表/同步/治理语义，第三方依赖（v2 已论证） |
| 服务端持有明文 token | 否 | 只存 **SHA-256 哈希**；手机持明文，边缘常数时间比对哈希 |

## 3. 数据面：边缘鉴权上收 + Router 承载会话

### 3.1 路径布局与路由键（继承 v3 评审 #1 定案）

| 路径 | 用途 |
| --- | --- |
| `/qx-ws` | **统一 WS 端点**（角色在 hello 声明，§4.5）：千寻=instance 注册自己并供会话；移动 App/PWA（未来）=device 单连接消费 |
| `/qx-pair` | 配对静态页 + 提交一次性码（服务端签发、**服务器级**，见 §4.4） |
| `/`（无 cookie） | **舰队/配对首页**：已配对 → 实例列表（名称/在线/版本）；未配对 → 仅配对引导（不泄漏实例明细） |
| `/i/<instance_id>/*` | **会话入口**：set-cookie `qx_iid`（vhost 根域、HttpOnly、1 年）后 302 回 `/` |
| `/`（有 cookie，DSH 全部根相对路径） | 按 cookie 路由到对应实例隧道（会话页） |
| `/qx-fleet` | 舰队首页显式地址（会话中切换设备用；会话页经 /qx-mobile 定制层注入「切换设备」悬浮按钮） |
| `/api/fleet` | 实例列表 JSON（**需设备 token**；舰队页可见时 10s 轮询） |
| `/api/config/*`、`/api/devices/*` | 同步与设备自助 API（设备 token 鉴权，未来移动 App/CLI 复用） |
| `/metrics`、`/healthz` | 仅回环 |

### 3.2 边缘鉴权（v5 变更：从「千寻校验 qx_token」上收到服务端）

- 手机凭 cookie `qx_token`（或 `?token=` 兜底）到服务端；服务端查 `devices` 表
  （存哈希，常数时间比对）确认**服务器级设备身份**；目标实例取自 `qx_iid` cookie（§3.1）——
  设备对全部预置实例可见可达（单 operator 模型），开对应隧道流转发。
- 服务端**剥离并重写**身份头：`X-QX-Device: <id>` 注入，入站同名头一律丢弃（防伪造）。
- 千寻 Router 对隧道流的请求：**跳过设备 token 校验**（边缘已完成），
  但 **Host 断言中间层保留**（§4.3，双保险不变）；Origin/Sec-Fetch 改写逻辑不变（dsh_upstream 既有语义）。
- 设备撤销 = 服务端一行 UPDATE，**即时生效**（边缘就是执法点）；千寻 UI 的撤销走
  `device.revoke` 帧下发。千寻不再保存设备 token（只留展示用的设备清单副本）。

### 3.3 千寻侧会话服务（继承 v3 评审 #2/#9/#10 定案）

- RouterHandle = `Arc<ArcSwap<Router>>`：网关重建/DSH revive 后发布新 Router，
  隧道**每流**取最新（长流升级前已过边缘鉴权，与现状语义一致）。
- 每条流用 `hyper_util ... serve_connection_with_upgrades` 服务——`/api/remote.mux` 的
  WS 升级必须活（评审 #9）；逐跳剥离 `Sec-WebSocket-Extensions`（axum ws 无 deflate）。
- Duplex 载体（仅测试）与 WS/WSS 载体承载同一套逻辑——crate 内集成测试不起端口跑全量协议。

### 3.4 启动时序：两条连接互不依赖（可行性结论）

千寻桌面端启动时涉及的「移动端两条连接」——**千寻→服务端隧道**与**手机→服务端**——互为独立：
服务端是不动点，各自建立、各自保活，服务端按请求桥接，**谁先谁后、谁在谁不在都成立**。

| 时刻 | 千寻→服务端 | 手机→服务端 | 手机体验 |
| --- | --- | --- | --- |
| t0 千寻进程起 | connecting（服务端不可达则退避 0.5s→32s） | 任意时刻可入 | — |
| t1 Router 就绪（先于 DSH；壳内回环同源） | **online**（hello/welcome，心跳 20s） | 流可开到千寻 | 会话页能开；DSH 未就绪 → 上游转发短暂 502，页面重试 |
| t2 DSH ready：cookie 兑换 → RouterHandle 发布 | 保持 online（**无需重连**） | 新流取最新 Router | 会话全通（SSE/WS） |
| 千寻重启 | 新 hello **抢占**旧连接（§4） | 存量流断、页面重试 | 秒级恢复 |
| 千寻离线 | 服务端标记实例离线 | 新请求 502 + `Retry-After: 2` | 明确「桌面离线」 |

- 依据：网关本就「DSH 未跑时照常监听」（commands.rs:265），上游转发失败自动重试
  （启动时 ensure_cookie 一次 + 转发期重试）；隧道在线与否不影响壳内回环——桌面外壳零感知。
- 手机侧两条**逻辑面**同源：会话面（cookie 路由 → 隧道 → 千寻 Router）与服务面
  （`/api/config`、配对）指向同一 vhost、按路径分流（§3.1），不需要第二条物理连接；
  浏览器侧并发（页面 WS + SSE + 子资源）由 §5 分级闸门覆盖。
- 千寻同一时刻只连**一个**服务端（`settings.server.url` 单值）。「手机存多服务端档案
  （家里本地 + 外出云端）」可行：各服务端注册表独立、各配对各持 token，入口页选择即可
  （v2 打磨自动择优）；千寻同时双上联（本地+云端）列为 §8 演进项，不进 v1。
- **连接纪律（operator 指示 2026-10-09，设计不变量）**：手机常驻连接 = **1×WS + 1×HTTP(H2)**。
  WS 唯一（`/api/remote.mux`——DSH 本就是单 WS mux，gateway.rs:144-147；SSE 走 HTTP 不另开口）；
  HTTP 一条 H2 承载页面/静态/SSE/`/api/*`/舰队轮询，服务面**不另开第二条 WS**。舰队实时性
  v1 = 仅舰队页可见时 10s 轮询；v2 = Web Push（推送不占连接）。本地明文形态无 H2——页面
  加载期的浏览器并行是瞬时自限行为，常驻连接数不变（仍 1 WS + HTTP 池空闲收敛）。
  移动 App/PWA（未来）经 `device` 角色连 `/qx-ws`，达成字面意义的**单连接**（§4.5）。

## 4. 控制协议（统一帧表；载体 = WS/WSS 文本帧，测试另有 Duplex）

`v` 为协议主版本，不匹配即断。帧 = JSON。

```jsonc
// ---- 注册与心跳（统一端点 /qx-ws；角色在 hello 声明）----
{ "v": 2, "type": "hello", "role": "instance", "instanceId": "…", "instanceToken": "…",
  "meta": { "qianxun": "0.9.0", "dsh": "…", "hostname": "…" } }
{ "v": 2, "type": "hello", "role": "device", "deviceToken": "…" }   // 移动 App/PWA：单连接形态（§4.5）
{ "v": 2, "type": "welcome", "serverVersion": "…", "heartbeatMs": 20000,
  "features": ["sync","push","device-ws"] }
{ "v": 2, "type": "ping" } / { "v": 2, "type": "pong" }        // 千寻单侧发起
// ---- 舰队（设备列表与状态；HTTP 投影 = /api/fleet）----
{ "v": 2, "type": "fleet.get" }
{ "v": 2, "type": "fleet.snapshot", "instances": [
    { "id": "…", "name": "…", "online": true, "qianxun": "0.9.0", "dsh": "…" } ] }
{ "v": 2, "type": "fleet.changed" }                            // 实例上下线/元信息变化 → 推送
// ---- 配对（v5：服务端签发，千寻离线也能兑换）----
{ "v": 2, "type": "pair.create" }                               // 千寻→服务端：请求上架配对码
{ "v": 2, "type": "pair.offered", "code": "…", "expiresAt": 0 } // 服务端生成一次性码（哈希落库）
{ "v": 2, "type": "pair.granted", "deviceId": "…", "name": "…" }// 手机兑换成功 → 推给千寻（更新清单副本）
{ "v": 2, "type": "pair.denied", "code": "…", "reason": "expired|used|unknown" }
// ---- 设备治理 ----
{ "v": 2, "type": "device.revoke", "deviceId": "…" }
{ "v": 2, "type": "device.list" } / { "v": 2, "type": "device.snapshot", "devices": […] }
// ---- 配置同步（§6）----
{ "v": 2, "type": "config.push", "namespace": "…", "key": "…", "baseVersion": 7, "value": … }
{ "v": 2, "type": "config.accepted", "namespace": "…", "key": "…", "version": 8 }
{ "v": 2, "type": "config.conflict", "namespace": "…", "key": "…", "version": 9, "value": … }
{ "v": 2, "type": "config.pull", "since": { "namespace": "…", "version": 3 } }
{ "v": 2, "type": "config.delta", "items": [ { "namespace": "…", "key": "…", "version": 9, "value": … } ] }
{ "v": 2, "type": "config.changed", "namespace": "…", "key": "…" }   // 服务端→千寻：远端有更新
// ---- 错误 ----
{ "v": 2, "type": "error", "code": "unknown_instance|bad_token|over_instance_limit|…" }
```

- **同名实例抢占**：新 hello 替换旧连接；配对码/设备表在 SQLite，与连接无关，抢占后存续。
- 断线退避 0.5s→32s 封顶；隧道断开时手机新请求 → 502 + `Retry-After: 2`。
- 版本协商：`features` 数组让旧千寻连新服务端平滑降级（无 sync 能力就不同步，不影响会话）。

### 4.4 配对流程（服务端签发版）

```
千寻远程页            qx-server                     手机
   │──hello(注册)──────>│                              │
   │──pair.create──────>│ 生成一次性码(哈希入库, 5min)    │
   │<─pair.offered──────│                              │
   │  二维码: https://<server>/qx-pair?code=…          │
   │                    │<──打开配对页 + WSS 提交 code──│ ← 扫码
   │                    │ 校验→签发 deviceId+token(哈希库)│
   │                    │──{token,instanceId}──────────>│ localStorage+cookie 引导
   │<─pair.granted──────│                              │
   │  (千寻更新设备清单副本, 即使此刻手机已能访问)          │──GET /（cookie 路由）→ 会话页
```

- 手机端把 token 同时存 localStorage：cookie 被清后入口 JS 自动重打 `/qx-gate?token=` 自愈。
- 千寻离线时配对码仍可兑换（服务端有库）——设备「先配对、桌面上线即用」。
- **配对是服务器级**（operator 指示 2026-10-09）：一次配对 = 全部预置实例可见可达（单 operator
  模型）；`pair.create` 可由任一在线千寻发起，零千寻在线时用 `qx-server admin pair-create` 兜底。
  per-instance 细粒度授权（grants 表）留 v2。

### 4.5 一个端点、两种角色（operator 指示 2026-10-09）

`/qx-ws` 是**唯一的 WS 端点**，角色在 hello 里声明，同一条连接因角色而产生不同作用：

| 角色 | 谁用 | 这条连接上的作用 |
| --- | --- | --- |
| `instance` | 千寻桌面端 | **注册自己**（hello/心跳/在线状态，fleet 元信息由此而来）+ 作为会话**提供者**：hub 在其连接上开 yamux 流服务会话 |
| `device` | 移动 App / PWA（未来） | **获取设备列表**（`fleet.get` + `fleet.changed` 推送）+ 配对/同步；**点选实例后，会话子流走同一条连接**（hub 把 device 流路由到目标 instance 连接）——字面意义的「一个连接」 |

- **协议对称**：两个角色用同一载体（yamux over WS），区别只是流的**发起方向**——instance 被动提供、
  device 主动消费；hub 做双向路由。注册、发现、会话三件事收拢在这一个端点上。
- **浏览器（v1）走 HTTP 投影**：DSH 会话页不能改协议，手机浏览器用 REST 投影消费**同一套 hub 能力**：
  `/api/fleet` = `fleet.get`、`/api/pair/submit`、`/api/config/*` = config 帧；会话仍走 cookie 路由 +
  `/api/remote.mux`。连接纪律 1×WS + 1×HTTP 不变（§3.4）。
- **实施节拍**：M1 = instance 角色 + HTTP 投影；`device` 角色（单连接手机端）随移动端立项，
  `welcome.features` 已预留（`device-ws`），旧客户端自动降级到投影。
- **治理键扩展**：device 角色直连的流闸门按（实例 × 设备）双键计数；浏览器 HTTP 路径维持按实例。

## 5. 资源治理（v4 原样继承，适用于一切宿主形态）

### 5.0 原则（为什么不是「并发 N 流」）

流数这条轴既不充分也不必要：N 条 bulk 流可无限期占满出口带宽（流数管不到带宽），
浏览器 6 并行 + DSH 常驻 3 流又让小限额弄坏正常页。v4 = **流量分级准入 +
资源三轴硬闸（内存/带宽/CPU）+ 压力按序降级**。

### 5.1 流量分类（服务端内部记账，协议零改动）

| 类 | 识别 | 准入与整形 |
| --- | --- | --- |
| **interactive** | `Upgrade: websocket` / 响应头 `text/event-stream`（响应头可见时升格） | 硬上限 8/实例、16 全局；idle 600s；**降级序中永不主动断** |
| **page** | 其余普通请求 | 令牌桶 40 次/s、突发 40（整页加载一次通过）；在途硬顶 64/实例（病态防护） |
| **bulk** | 请求体 >256KiB 或累计传输 >4MiB（动态降格） | 并发 2/实例 + 慢桶 512KiB/s（突发 4MiB）；idle 300s；最先被 shed |

### 5.2 三轴硬闸与降级序

| 轴 | 闸门 | 默认 |
| --- | --- | --- |
| 内存 | cgroup `MemoryMax` | 192M（正常水位 ≈4MiB） |
| 带宽 | 每实例 2MiB/s 持续（突发 8MiB）+ 全局 4MiB/s | 配置 |
| CPU/任务 | `CPUQuota=30%`、`TasksMax=64` | systemd（云端形态） |

降级序：RSS>80% 或全局带宽桶饥饿 >5s → shed bulk → 再 page → **interactive 永不主动断**。
本机/局域网裸进程形态无 systemd，等价护栏由进程内限额（interactive/page/bulk 上限 + 带宽桶）承担。
`/metrics`（仅回环）按 实例×类 出 admitted/shed/bytes/桶水位。

### 5.3 超时与上限端到端矩阵（云端形态含反代）

| 环节 | 值 |
| --- | --- |
| 反代 WS/SSE idle（`proxy_read_timeout`） | 650s（> 千寻 WS 桥 600s） |
| 反代请求体（`client_max_body_size`） | 16m（与服务端 `max_body_bytes` 对齐） |
| 反代 SSE | `proxy_buffering off` |
| 服务端普通流 / 升级流 / bulk idle | 120s / 600s / 300s |
| 隧道心跳 | 20s（千寻单侧发起） |

## 6. 状态层：rusqlite（operator 指示）

### 6.1 使用策略

- `rusqlite = { features = ["bundled"] }`（服务器自包含编译，无系统 SQLite 依赖）。
- **单写者 actor**：一条专用线程 + mpsc 收闭包，天然串行化写事务；读走 `spawn_blocking` +
  WAL 模式（并发读不阻塞写）。不引连接池/ORM——规模（≤4 实例 × ≤十级设备）用不上。
- 迁移：`PRAGMA user_version` + 代码内顺序迁移步骤；启动时自动升级，向后兼容旧库。
- 数据目录：云端 `/var/lib/qx-server/`；本地模式 `<千寻数据目录>/qx-server/`（随千寻生命周期）。

### 6.2 v1 模式（SQLite DDL 纲要）

```sql
PRAGMA journal_mode=WAL;
instances(id TEXT PRIMARY KEY, name, token_hash, created_at, last_seen_at, meta_json);
devices(id TEXT PRIMARY KEY, name, token_hash,          -- 服务器级身份：不绑实例
        created_at, last_seen_at, revoked INTEGER DEFAULT 0);
pair_codes(code_hash TEXT PRIMARY KEY, issued_via,       -- 发起者（实例/admin）仅审计用
           expires_at, used_at);
config_items(namespace TEXT, key TEXT, version INTEGER, value BLOB,
             updated_at, updated_by, PRIMARY KEY(namespace, key));
config_history(namespace, key, version, value, updated_at, updated_by);  -- 每版留档
audit(id INTEGER PRIMARY KEY, at, instance_id, device_id, event, detail_json);
metrics_hourly(at, instance_id, klass, admitted, shed, bytes);           -- §5 指标落库
```

- 敏感数据纪律：**只存哈希**（instance_token、device_token、pair_code 均 SHA-256）；
  配置明文存储（自托管信任边界，云端 E2E 列为 §8 演进项）。

## 7. 配置同步（operator 指示：如 DSH 的配置内容）

### 7.1 模型

- **命名空间 + 键** 的 LWW 同步：`config.push` 带 `baseVersion` 做 CAS；版本冲突回
  `config.conflict`（附当前值），由端上决定覆盖或采纳——默认策略「新时间戳胜」，
  每版进 `config_history` 可手工找回。
- 触发：千寻 `settings::update` 后防抖推送；连接建立时 `config.pull` 增量拉齐；
  远端变更经 `config.changed` 实时下发（多桌面互同步）。
- 未来移动 App 走 `/api/config/*`（设备 token 鉴权）复用同一引擎。

### 7.2 v1 命名空间（白名单制，宁缺毋滥）

| 命名空间 | 内容 | 说明 |
| --- | --- | --- |
| `qianxun.settings` | settings.json 主体 | **过滤字段**：server.instanceToken、devices 明细、一切凭据不同步 |
| `qianxun.mobileui` | mobile-access 的 custom.css/js | 手机定制层跨设备跟随 |
| `dsh.profile.<name>.config` | DSH profile 配置白名单（模型选择、镜像源等） | **凭证类（credentials/cordis.patch 里的密钥）绝不入同步** |
| `plugins.pinned` | 插件钉版清单 | 多机插件一致性 |

白名单之外的键服务端拒收（`config.rejected`）——防止未来某端手滑把秘密推上来。

                                # 状态上报、settings 防抖推送钩子

### 12.2 传输载体：一套协议，生产一种、测试一种（协议层逐字节同构，含 yamux）

- `TunnelTransport` 就是一条全双工字节流（`AsyncRead + AsyncWrite`）：
  - **Ws/Wss（生产唯一）**：`tokio-tungstenite`（**必须补 TLS feature**，现状硬缺口）承载，
    Binary 帧即隧道字节。地址 scheme 决定加密：`ws://` 本机/局域网，`wss://` 云端（反代 TLS）。
  - **Duplex（仅测试）**：`tokio::io::duplex(64KiB)` 成对内存管道，crate 集成测试不起端口
    跑全量协议（配对/同步/治理/抢占）。
- 控制帧（JSON）与数据面（yamux）在两种载体上**逐字节相同**——测试与生产只差 TLS 与反代两层，
  杜绝「测试能过、真机跑不了」的分叉。

### 12.3 千寻端命令面与配置

- `settings.server = { url: "ws://127.0.0.1:23100" | "wss://<relay-host>", instanceId,
  instanceToken }`——**一个地址字段**，scheme 即加密语义，无 mode 枚举；
  `settings.remote.*`（enabled/bindIp/port/devices）**直接删除，无兼容期**（§12.5）。
- IPC 命令（走 contract.test.ts 对齐门禁）：`server_status`（地址/连接态/实例/最近错误/在线设备）、
  `server_configure`、`server_pair_create`（返回二维码内容）、`server_device_list`、
  `server_device_revoke`。
- fingerprint 增加 server 维度：url 变更 → Router 重建并发布（RouterHandle，§3.3）。
- `backup_export` 过滤：`instanceToken` 剔除；设备明细迁出 settings 后，备份自然不含 token。
- supervisor 日志：状态机翻转（off/connecting/online/backoff/invalid_config）必记。

### 12.4 本机/局域网部署形态（standalone，与千寻生命周期无关）

- `qx-server serve --bind 0.0.0.0:23100 --data <dir>`：谁拉起都行（手动 / 服务管理器），
  千寻不管、也不因它产生任何防火墙提示（提示只会落在 qx-server.exe 上，一次）。
- 绑 `0.0.0.0` 通配——对网卡改名/增删免疫（v0.8 两类脆断根的根治版）。
- 手机 `http://<任一网卡IP>:23100`；明文与今日 LAN 网关同级；远程页展示当前服务端地址与配对二维码。
- 备份语义：同步走命名空间白名单（§7.2），**库文件本身不入备份**。

### 12.5 一次性数据处置（零兼容代码；operator 指示：导入由 agent 手工完成）

- **直接删除，无兼容期**：LAN listener、`settings.remote.*`（enabled/bindIp/port/devices）、
  PairCodes 的 LAN 配对流程。旧 settings 键由 serde 默认值静默忽略，不写任何迁移逻辑。
- **既有已配对手机**：默认处置 = **重新扫码一次**（注册表签发新 token，成本一次扫描）；
  例外（token 必须保留）= agent 手工导入：
  `qx-server admin import-device --instance <iid> --name <n> [--token <t>]`
  （一次性 CLI，不进产品 UI 与迁移逻辑）。
- **既有配置**：无迁移——配置同步从零起步（首启 `config.push` 打全量基线）。
