# 16 · 马里奥 v2 与 Laya 推理提速:搜索优先、System 1 瘦身

> 本文是 2026-10-05 的一轮改造记录。起因是一次在线调研(见 §1),结论是
> **选型没错、架构没错,瓶颈在"把 System 1 当策略用"和"把 System 2 当启发式用"**。
> 改造分两条:游戏侧把 System 2 从启发式换成 rollout 搜索(§3);
> 推理侧把 ORT 该开的开关全开、并把 state 编码压瘦(§4)。
> **所有性能数字都是本机实测,不是引用;测不出来的都写明测不出来(§4.5)。**

## 1. 调研纠正了三个前提(2026-10-04 在线核实)

| 原来的认知                           | 核实后                                                                                                                                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Jev 是开源模型,可找替代              | **Jev 闭源**。TypeSafe AI 2026-09-15 发布的托管 API(`api.typesafe.ai/v1/systemone`),无权重、无 HF 仓库、架构与参数量未披露。**开源的那个是 Laya**(Convai Innovations,Apache-2.0,发布于 Jev 三天后) |

## 2. 游戏侧:补齐的机制(全部有单测)

v1 只有一个 Goomba 怪、一种形态、一个即时触发的"win"。v2 补成完整的一局:

| 机制                          | 实现要点                                                                                                  | 测试                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **变身** small → big → fire   | 碰撞盒以**脚底为锚**(`marioBox`),改形态只改 `power`,`y` 不动即站得住;big/fire 高 26px、small 14px         | `big 受伤降级为 small,small 再受伤才死`                 |
| **受伤 / 无敌窗口**           | fire→big→small→死;`invuln=96` 期间免疫二次伤害,renderer 同步闪烁                                          | `受击后无敌窗口内不再二次受伤`                          |
| **道具** 蘑菇 / 火焰花 / 吐币 | 从 ?块**顶上**升起(不是块体内——否则道具一出生就踩在自己脚下,永远走不下去,这是实测踩到的坑)                | `蘑菇 ?块:顶出蘑菇 → 追到它 → 变大`                     |
| **砖块**                      | small 只顶;big/fire 顶碎(tile 置空 +50 分)                                                                | `big 顶碎砖块` / `small 顶砖只顶不碎`                   |
| **火球**                      | 边缘触发(`fireLatch`,按住不连发)、上限 2 颗、**触地弹跳**——不弹的话火球 30 tick 就埋进地里,够不到任何敌人 | `fire 形态可发射火球…火球弹地砸死 Goomba`               |
| **乌龟 / 龟壳**               | 踩→壳;侧踢→滑行(3.2px/tick);滑行壳撞死其他敌人(链式清场);壳 420 tick 后复活                               | `踩 Koopa → 变壳;侧踢 → 滑行` / `滑行龟壳撞死 Goomba`   |
| **食人花**                    | 管口升降;**马里奥贴近管子时不伸出**(经典规避);接触扣血                                                    | `食人花:伸出时碰到马里奥 → 受伤` / `马里奥贴近时不伸出` |
| **连击**                      | 滞空连踩,第 n 踩 = 100×n,上限 8 连;落地清零                                                               | `连踩连击:分越踩越高`                                   |
| **通关序列**                  | 旗杆下滑 → 走向城堡 → 消失 + 时间奖励 ×50。`phase` 仍是 `'won'`,序列状态放在 `win.stage`,不破坏既有断言   | `通关序列:旗杆下滑 → 走向城堡 → 消失 + 时间奖励结算`    |
| **第二关 1-2**                | 全新增布局:4 处坑、12 根管道(高低组合)、3 根食人花、空中浮砖带、5 只乌龟、5 只 Goomba、末段双阶           | `autopilot 通关 1-2`                                    |

物理常量对三种形态**保持一致**(不做"变大跳更高"),`JUMP` 表因此对所有形态同时有效,规划器可达性推理不必分叉。

## 3. System 2:从"扫第一个危险"换成 rollout 搜索

### 3.1 为什么换

v1 的 `nextIntent` 是"向前扫描,取第一个危险,按危险类型给候选集",`autopilotInput` 是一组起跳触发窗 + 一套贴墙后撤启发式。它能通关,但:

- 触发窗是**人工标定**的常数,换关卡就要重标;
- 只有"第一个危险",没有多步推理;
- 拿不到"每个候选动作各自会导致什么"的信息——而这正是 System 1 需要的候选集依据。

### 3.2 做法:rollout 策略 + 单步策略改进

```
for 每个候选动作 a:
    sim ← 深拷贝当前局
    前 commitTicks 步执行 a,之后交给基线策略 rolloutInput 跑满 horizon
    score ← evaluateState(原局, sim)          // 死亡 -1e6 / 通关 +1e6 / 其余加权
取 Top-K
```

- `rolloutInput` 是**无递归**的基线策略:一律向右助跑,脚下前方 1.6 瓦是坑 / 有墙 / 有敌人就起跳。它本身很笨(不理解食人花与龟壳),**正是搜索要改进的基线**。
- `evaluateState` 的关键设计:**死亡是 -1e6、通关是 +1e6**,其余(进度 ×1000、分数 ×20、敌人清理 ×120、贴地 +6、贴脸危险负塑形)只在不死的候选之间比较。这让"必达"成为目标函数的性质,而不是靠调参保证。
- 引擎是确定性纯函数,所以搜索结果可复现、可单测;代价是每拍 O(候选 × horizon) 次 `step`。

新增 policy 沙盒字段(agent 可调,`dim: 'search'`):

| 字段            | 默认 | 值域   | 含义                                                                                 |
| --------------- | ---- | ------ | ------------------------------------------------------------------------------------ |
| `searchHorizon` | 45   | 12–90  | 每个候选的 rollout 总 tick                                                           |
| `searchTopK`    | 3    | 2–5    | 送进 Laya 的候选数。**硬压住**:Laya 在 >20 选项时急剧退化(Banking77 77 类只有 0.425) |
| `searchLookPx`  | 176  | 64–320 | 意图层前扫距离                                                                       |

`nextIntent` 新增 `scores: number[]` / `best: Action`,renderer 把它画成**左上角候选动作得分条**(`S2 得分` 按钮可关),让"规划器为什么选这个"在画面上可见。

### 3.3 结果

| 验证                                          | 结果                    |
| --------------------------------------------- | ----------------------- |
| `autopilot 全程通关`(1-1,含食人花 + 乌龟)     | ✅ 确定性仿真通过       |
| `autopilot 通关 1-2`(全新布局,agent 从没见过) | ✅ 确定性仿真通过       |
| `e2e/mario-loop.test.ts 自驾头面会话`         | ✅ 确定性通关并产出复盘 |

`autopilotInput` 现在就是 `nextIntent(...).best` → `actionInput`,**触发窗启发式与后撤记忆全部删除**。搜索结果按 `(state, tick, 搜索参数)` 缓存(WeakMap)——autopilot 每 tick 调一次、叠加层还要再调一次,没有缓存就是每帧一次完整 rollout。

### 3.4 顺手修掉一个真实性能 bug

`MarioLab.svelte` 原来在**每帧**调 `nextIntent(s, world)` 画目标框。换成搜索之后,那等于每帧 12×45=540 次 `step`,主循环必然被打爆。现在:autopilot 模式靠上面的缓存零开销;reflex 模式按 `intervalMs` 节流。语义反而更诚实——画的是"上一次真正用于决策的那一帧"。

## 4. 推理侧:ORT 开关 + 编码瘦身

### 4.1 改了什么(`laya-engine/src/engine.rs`)

| 项                  | 改前             | 改后                   | 理由                                                                                                                                                                      |
| ------------------- | ---------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `intra_op_spinning` | (未设 = ON)      | **OFF**                | ORT 的 intra-op 线程池默认在请求之间自旋吃满 CPU。sidecar 每 250ms 才来一次请求,绝大部分时间在空转,还和 UI 线程抢核。Manticore 生产部署称这是他们整个分支里最大的单项收益 |
| `flush_to_zero`     | (未设)           | **ON**                 | attention 的 softmax 产出大量 denormal,x86 上走微码路径                                                                                                                   |
| `approximate_gelu`  | (未设)           | **ON**                 | ORT 文档:约 10% 更快且无数值质量损失                                                                                                                                      |
| `intra_threads`     | 固定 4           | **0 = ORT 取物理核数** | 桌面 sidecar 没有别的活可干                                                                                                                                               |
| 模型图选择          | 只认 `laya.onnx` | **量化候选优先**       | `resolve_model_file()`:显式指定 > `laya.int8/q8/quant.onnx` > `laya.onnx`                                                                                                 |

`laya-server --threads` 默认从 4 改成 0;`/health` 新增 `graph` / `threads` / `spinning` / `quantized` 四个字段;`laya-server` 启动时打印实际生效的图与开关。

> **rc.13 的 API 注意**:`with_flush_to_zero()` / `with_approximate_gelu()` 是**无参**开关(只能开不能关),要关就整段不调用。`with_intra_op_spinning(bool)` 才带参数。

### 4.2 量化:int8 是**唯一还没兑现**的大杠杆

`resolve_model_file` 的管子已铺好(纯函数 + 6 个单测锁优先级),但**仓库里还没有 int8 图**——生成它需要 Python 侧 `onnxruntime.quantization`,超出本次范围。规则已写进代码注释:

- **per-tensor,不 per-channel**:Laya v0.3.23 实测 per-channel 把输出一致性压到 **32%**,官方已回退 per-tensor;
- x86-64 用 **S8S8 + QDQ**,**不要 S8S8 + QOperator**(ORT 文档明示后者在 x86-64 慢);
- 动态量化用于 transformer,静态用于 CNN;
- **上线前必须跑 parity 比对**,不能只看延迟。

### 4.3 编码瘦身(v2-obs → v3-obs)

实测本机延迟与序列长度近似线性(见 §4.4),于是压 token:

- profile 从"逐列数字"改 RLE 游程(`13*12 9*2 5`),无损;
- 键名从 `progress`/`profile16`/`threats`/`subgoal` 改成 `p`/`prof`/`th`/`sub`;
- 姿态只留档位量纲 `v2 a0 R`,删掉全部小数点;
- 进度只留百分比 + 关键计数,删掉可由百分比反推的 `x=1234/3392`;
- 指令模板与 `TERSE_HINTS` 同步压短;`obsHintStyle` 默认由 `full` 改 `terse`。

### 4.4 实测曲线(本机 i9-14900HX,fp32,无量化)

新旧两个 `laya-server` 同时跑,同一批 payload,各 8 次取 p50:

| 场景                        | 旧(threads=8,自旋 ON) | 新(threads=auto,自旋 OFF + ftz + 近似 gelu) | 倍数      |
| --------------------------- | --------------------- | ------------------------------------------- | --------- |
| 马里奥完整 state(217 token) | **178 ms**            | **141 ms**                                  | **1.26×** |

序列长度→延迟标定(新引擎,合成填充,3 选项):

| tokens   | 36  | 41  | 49  | 61  | 86  | 136 |
| -------- | --- | --- | --- | --- | --- | --- |
| p50 (ms) | 35  | 37  | 41  | 47  | 58  | 85  |

拟合 **≈ 17 ms 固定 + 0.5 ms/token**。

### 4.5 测不出来 / 与预期不符的(诚实记录)

1. **我最初"砍 100 token 省 80 ms"的推算是错的。** 第一版 v3 把 state 压瘦了,却把指令和选项描述写得更长,净 token 反而从 217 涨到 220,延迟纹丝不动。真正压瘦指令+描述后,217 → 165 token,延迟 141 → 132 ms,**只省了约 9 ms(6%)**。
2. **合成填充的线性外推对真实文本偏乐观。** 136 token 落在拟合线上(85ms),但 165 token 实测 132ms(外推只有 99ms)。真实句子比 `aaaa…` 贵,大致是词表分散度带来的开销。**结论:不要用 token 数单独外推延迟。**
3. **int8 的收益仍未测量**(§4.2),文献上 BERT 系在 VNNI 机器上 int8 相对 fp32 常报 1.4–6×,但那是别人的模型;本项目必须自己测。
4. **本机没有 AVX-512**(13/14 代消费级被 Intel 关闭),只有 AVX2 + VNNI。所以 ORT 的 `reduce_range` 不需要(ORT 文档:VNNI 机器上不需要)。

### 4.6 与调研预期的差距(保留意见)

调研声称的"ORT int8 最高 6×"、"int8 是 2–3×"在本机上**只兑现了 1.26×,且那 1.26× 全部来自三个运行时开关,与量化无关**。int8 兑现之前,不要对"毫秒级"做任何承诺。

## 5. 现状与下一步

**已经做到的**

- 游戏从"演示"变成"一局游戏":变身/受伤/道具/碎砖/火球/龟壳/食人花/连击/通关序列/第二关;

- System 1 的输入从 218 token 压到 165 token,ORT 三个开关全开;
- 131 个 mario 单测 + 全仓 261 个测试全绿,`clippy -D warnings` 与 `cargo fmt` 干净。

**明确还没做**

1. **int8 量化图**(最大的一块,需要 Python 工具链 + parity 验收);
2. **蒸馏**——`docs/10 §5` 的 Phase 2 未动。调研证据(中文 20/64 vs 64/64)说明零样本不可用,`conftest` 默认阈值仍靠 System 2 兜底,System 1 在 reflex 模式下目前**从不真正"赢"**;
3. **闭环**:ESCALATE 后搜索的结果没有回灌给 System 1,现在是单向的"移交",不是"移交 + 学习";
4. 1-1/1-2 之外的关卡、Warps、地下房。
