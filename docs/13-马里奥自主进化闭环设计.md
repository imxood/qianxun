# 13 — 马里奥自主进化闭环设计

> 承接 docs/11(马里奥实验室)与 docs/12(双脑架构)。本文定义**运行模式下**的
> 配置生命周期、局末与本地 agent 的交互协议、以及"每一局都在优化"的收敛机制。
> 约束前提(架构红线):Laya + Qwen 只用**本地模型**;云端编码代理只改代码/重编译;
> 本地 agent 运行时只能动**策略沙箱**(`policy.ts`),永不碰代码。

## 1. 闭环总览与三条不变量

```
加载(局前) → 冻结快照(局内) → 规则复盘(局末,同步,毫秒级)
           → Qwen 精炼(异步,不阻塞下一局) → 候选补丁
           → 试跑评估(K 局中位数) → 提交 / 回滚 → 审计落盘
```

三条不变量,所有子设计服从它们:

1. **一局之内配置不可变**。开局对 policy 做快照,局内任何更新只影响"下一局"。
   否则同一局的复盘数据不可归因(分不清第几分钟改的参数起了作用)。
2. **规则复盘在前,LLM 精炼在后**。确定性统计(死因/卡点位/门控分布)是事实;
   Qwen 只做"基于事实的假设生成",只看压缩后的复盘文档,不碰原始遥测流。
3. **补丁是"候选"不是"命令"**。Qwen 产出的 patch 必须经试跑评估才能转正——
   "成功概率越来越高、耗时越来越短"是**测量出来的**,不是模型自己宣称的。

## 2. 加载侧:配置的单一事实源

### 2.1 存储位置(收敛后)

| 环境                          | 路径                                           |
| ----------------------------- | ---------------------------------------------- |
| 千寻 debug(`pnpm dev`)        | `~/.qianxun_dev/mario/`                        |
| 千寻 release                  | `~/.qianxun/mario/`                            |
| 无头闭环(`e2e/mario-loop.ts`) | 默认同 debug 根(共享 champion),`--dir=` 可覆盖 |

UI 经 Tauri IPC 读写(webview 无文件能力);无头闭环直接 fs。
**localStorage 降级为纯 web dev(无 Tauri)环境的 fallback**,不再是主存储。

### 2.2 加载优先级链

```
DEFAULT_POLICY(代码内置兜底)
  ↓ 被覆盖
policy.json(持久化 champion,进化产物)
  ↓ 被覆盖
用户设置面板的显式调整(本次会话)
  ↓
getPolicy() —— 全系统唯一读取出口
```

### 2.3 版本化与校验

- `policy.json` 带信封:`{ version, updatedAt, source, policy }`。
  版本不匹配走迁移;迁移不了回退默认并记录 issue。进化是长期过程,字段必然增删。
- **加载即 sanitize**:`sanitizePolicy` 同时应用于"文件加载"与"Qwen 补丁"两个
  入口——不信任任何外部来源,包括自己昨天写下的文件。旧版扁平 JSON 自动识别迁移。

## 3. 局末交互侧:与本地 agent 的协议

### 3.1 触发器(有新信息才调 Qwen)

| 触发            | 说明                                        |
| --------------- | ------------------------------------------- |
| 通关            | 成功经验也要沉淀(巩固手册)                  |
| 新死因/新卡点位 | 与上次分析过的失败签名不同才升级            |
| plateau         | 连续 N 局 maxXCol 无进展,主动求助           |
| ~~每局都调~~    | 噪声大、浪费本地推理;规则复盘足够覆盖平淡局 |

**幂等**:每局有 `runId`,同一 runId 的 Qwen 分析结果只接受一次——防止
"死亡瞬间连点重开"造成重复分析、重复打补丁。

### 3.2 两阶段时序(异步、不阻塞)

```
游戏结束
 ├─ 同步(毫秒级): buildPostmortem → 规则复盘 → 会话 JSONL + UI 复盘浮层
 └─ 异步(秒级,后台): refineViaQwen(复盘 + 手册 + 近5局 + 当前策略)
      ├─ 成功 → 候选 patch + 新手册 → 进入评估队列(不直接生效!)
      ├─ 失败/离线 → 仅记录,规则复盘已是完整产物,游戏照常
      └─ 用户已开新局 → 照样完成,patch 标记作用于"下一局"
```

### 3.3 有界上下文

发给 Qwen 的:手册(≤1600 字滚动上下文)+ 近 5 局摘要 + 本局规则复盘 +
当前 policy 值 **+ 各字段合法值域**。把沙箱边界写进 prompt,既减少被钳制次数,
也让钳制日志(issues)成为 agent 的学习信号。

## 4. 更新侧:收敛机制(核心)

单局噪声极大(同一策略两局 maxXCol 可差 30 格)。每局按单局结果改配置 =
策略空间随机游走。收敛靠「候选-评估-提交」协议 + 四个防振荡机制。

### 4.1 协议

```
Qwen 产出候选 patch
  → 与 champion 对比,差异为空则丢弃
  → 试跑评估:候选跑 K=3 局,取中位数
  → 判定:candidate 中位分 > champion 中位分 × (1+ε)  ?  提交 : 回滚
  → 无论成败,追加写入 evolution.jsonl(谁提的/改了什么/分数/是否采纳)
```

### 4.2 四个防振荡机制(按重要性)

1. **中位数 + 最小提升阈值 ε(默认 5%)**——没有统计显著性的"改进"一律视为噪声。
2. **变更幅度限制**——每次 patch 最多改 2–3 个字段;数值字段步进 ≤20%。
   大步跳进容易跳出甜区,小步爬山可回溯。
3. **冷却期**——某字段的改动被回滚后,M=5 次迭代内禁止再改它,
   防止 Qwen 在同一参数上来回横跳。
4. **滞回(hysteresis)**——提交阈值 +5%,回滚阈值 −10%,涨跌不对称吸收噪声。

### 4.3 评估指标

```
主指标: 通关率(K 局赢几局)
次指标: 通关局的中位 ticks("耗时越来越短")
平局裁决: maxXCol 中位数
约束指标(一票否决): 非自然死亡数上升 / veto 率暴涨 → 视为退化
```

陷阱:单纯压 ticks 会让策略变激进、死亡率上升,所以约束指标必须参与判定。

## 5. 存储布局

```
mario/                       # 数据根下(见 §2.1)
├── policy.json              # 当前 champion,信封带 version/source 元信息
├── playbook.md              # 滚动手册(≤1600字),Qwen 维护,人类可读
├── evolution.jsonl          # 只追加:每次迭代的完整审计记录
└── history.json             # 逐局曲线(近 50 局,UI 画图/判定 plateau 用)
```

`evolution.jsonl` **只追加不改写**——审计链是回答"它为什么变成这样"的唯一依据。
规则复盘文档仍随会话 JSONL 落 `logs/laya-sessions/`(laya-server 侧),
批量汇总由 `e2e/mario-postmortem.ts` 产出 `INDEX.md`。

## 6. 关键决策(已拍板)

| 决策          | 结论                                                                                 |
| ------------- | ------------------------------------------------------------------------------------ |
| 自动化程度    | 开发期:UI 候选补丁需确认(试用/丢弃);无头闭环全自动 champion 更替。稳定后 UI 可切自动 |
| 试跑成本      | K=3 中位数(本地一局 30–90s,可接受);`--eval-runs` 可调                                |
| Qwen 调用时机 | 仅"新信息":新死因/新卡点/通关/plateau                                                |
| UI 与无头关系 | **共享同一 champion**:无头闭环是训练场,UI 是展示场                                   |
| 手册所有权    | Qwen 起草维护;人类可编辑,Qwen 在下一版中应保留人工段落                               |

## 7. 落地路线

1. **统一存储**——Rust IPC 读写 mario 状态目录;policy 信封版本化;
   消除 localStorage 主存储地位。(纯重构,无行为变化)
2. **局内快照 + runId 幂等**——归因地基。
3. **候选-评估-提交协议**——K=3 中位数 + ε + 冷却期 + 滞回,替换单局 keep-best。
4. **触发器细化**——新死因才调 Qwen;plateau 检测。
5. **审计与可观测**——`evolution.jsonl` + UI 进化面板
   ("它为什么改了这个参数"可视化)。

风险最大先做 1、2(地基);体验提升最明显是 3(消除随机游走)。

## 8. 一句话总结

把 Qwen 从"每局结束直接改配置的玩家"降级为"**提交候选补丁的提案者**",
把真正的进化逻辑(评估、提交、回滚、防振荡)收回到确定性规则代码里——
**LLM 负责创意,代码负责纪律**。这样"越来越优"才是可证明的。
