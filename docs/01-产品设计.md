# 01 · 产品设计

状态：草案 v1（待确认）

## 1. 定位

**千寻是个人开发者的工作台**，围绕三件事：

1. **托管 DSH** —— 环境检测、安装、启动/停止/守护，让 DSH 像"一直在那儿"一样存在；
2. **承载工具** —— 终端、截屏、搜索、笔记，日常开发中高频的小工具收进一个窗口；
3. **连接远近** —— 通过 EasyTier 虚拟局域网，手机与远程机器访问同一台 Host 上的 DSH 与工具。

千寻**不替代 DSH 的界面**：DSH 的 Web GUI 始终由 DSH 自己的服务提供，千寻把它装进 iframe，
并作为它的进程守护者与工具侧翼。

## 2. 用户与场景

单人使用（作者本人）。典型场景：

- **日常**：开机 → 打开千寻 → DSH 已在运行（或被拉起）→ 在内置终端干活 / 在 DSH 界面与 agent 协作；
- **收集**：截屏标注贴图、随手记笔记、文件名与内容检索；
- **整理**：把零散笔记丢给 DSH 里配置的模型，整理成结构化需求文档；
- **远程**：人在外面，手机通过 EasyTier 打开 Host 上的 DSH 与笔记，继续工作。

### 与外部 DSH 实例共存（硬约束）

作者日常同时运行另一个 DSH 实例（占用端口 10000，且正在承载工作会话）。千寻必须：

1. **默认端口 17300**，与 10000 永不冲突；端口校验对 10000 给出专门提示；
2. **只管理自己拉起的子进程**：停止/重启/回收仅作用于千寻 spawn 的进程树，
   绝不按进程名或端口杀任何非自有进程；
3. **DSH_HOME 隔离**：千寻托管的 DSH 使用应用数据目录下的独立 DSH_HOME，
   与系统 `~/.dsh`（外部实例正在使用）互不干扰；设置里可切换为系统目录（带冲突警告）。

## 4. 起步范围（v0.1：基础框架 + 核心托管）

**v0.1 · 基础框架**（已交付）：

1. Tauri 2 + Svelte 5 工程骨架，质量门禁（lint/测试/检查脚本）就位；
2. 移植基础底座：settings、paths、error、logging、tray、窗口、单实例；
3. 外壳骨架：标题栏、侧栏导航、主题、状态栏、设置页空壳。

**v0.1 · 核心托管**（已交付）：

1. 移植 Rust 核心：`node-runtime`、`proc-guard`、harness supervisor（改造为固定端口）；
2. 外壳 UI：环境检测/安装页、控制台、DSH iframe 承载；
3. 设置项：DSH 端口（固定）、npm/Node 镜像源、随软件自启 DSH、关闭行为（退出/到托盘）。

起步时未包含（已在 v0.1 内补齐，见功能地图）：终端、笔记、搜索、截屏、远程、同步、DSH 插件桥。

## 5. 非目标（Non-goals）

- **不 fork DSH**、不 vendor 其源码，不改它的界面——扩展一律走 DSH 自己的插件系统；
- **不做公网中转**（frp/隧道/端口映射）——远程访问只走 EasyTier 虚拟局域网；
- **不做账号体系、云服务、多人协作**——单机优先，数据归本地文件；
- **不做通用 IDE**——终端/搜索/笔记服务于"围绕 DSH 的开发流"，不与 VS Code 竞争；
- **不做插件市场**——个人插件走本地构建注入（super-injector 生产线）。

## 6. 体验原则

1. **外壳要"无聊"**：托管逻辑稳定压倒一切，界面不抢 DSH 的戏；
2. **每一行提示都是可操作的**：检测不到环境时，那行字本身就是安装按钮；
3. **数据是文件**：笔记、截图、配置尽量落在纯文件上——同步、备份、AI 直接读写的共同前提；
4. **失败要显式**：端口被占、下载校验失败、DSH 启动失败，都给出原因与下一步，不静默重试到底。
