# 12 · 双脑架构:Qwen 慢思监督 × Laya 反射的完全本地自主游戏

> 呼应 docs/11(马里奥实验室)。在 Laya(System 1 反射)+ 规划器(System 2 安全执行)
> 之上,引入 `环境` 页已有的 **Qwen 本地推理服务**(llama.cpp `llama-server`,
> OpenAI 兼容,默认 `127.0.0.1:17230`)作为 **System 2.5 慢思监督者**,
> 并兼任 **离线分析师**——整条链路(反射/规划/慢思/复盘)全部本机闭环,零云端。

## 2. 控制栈:三层闭环 + 一个分析师

```
频率轴  层级                职责                              失败语义
────────────────────────────────────────────────────────────────────────
60Hz    L0 引擎/驱动        物理仿真、输入量子持有、守卫      确定性,无失败
2~7Hz   L1 Laya 反射        看编码状态选动作(约束候选集)    低conf→RE-SENSE→ESCALATE
亚秒级  L1.5 规划器         waypoints、候选约束、安全机动    ESCALATE 的执行者,必达
秒级    L2 Qwen 慢思监督    策略路由、风险旋钮、门控微调、   超时/出错→丢弃本轮,游戏不停
                            卡死仲裁、失败归因(事件驱动)
离线    L3 Qwen 分析师      读 JSONL → 复盘报告 → 编码/阈值   可缺席,只影响改进速度
                            建议 → 蒸馏数据策展
```

关键认知:**9B 模型(秒级延迟)永远不进反射回路**。L2 只做"tick 之间、
安全边界上"的慢决策;空中/贴坑时刻的安全执行永远属于 L1.5 规划器。
这是把"LLM 参与实时控制"从风险变成收益的结构性保证。

## 3. L2 监督者设计

### 3.1 触发器(事件驱动,不轮询刷屏)

| 触发           | 条件                              | 频控            |
| -------------- | --------------------------------- | --------------- |
| `on_death`     | 死亡(附死亡归因 + 最近 3 次死因)  | 每 attempt 1 次 |
| `on_stuck`     | 5s 内 Δx < 2 瓦且 on_ground       | ≥10s 间隔       |
| `on_spike`     | 30s 窗内 ESCALATE 占比 > 40%      | ≥30s 间隔       |
| `on_milestone` | 通过 checkpoint(管道/坑群/台阶)   | 自然稀疏        |
| `periodic`     | 兜底心跳(默认关,CPU 机器不建议开) | ≥60s 间隔       |

### 3.2 输入上下文(紧凑,总 prompt ≤ 1.5k token)

系统提示固定为**稳定前缀**(命中 llama-server 前缀 KV 缓存,prefill 提速),
用户消息拼装:进度摘要 + 威胁表 + 规划器 waypoints + Laya 近窗统计
(avg conf / escalation% / QPS)+ 近 3 次死亡归因 + 当前旋钮值。
数据全部来自已有 JSONL 行与内存统计,不需要新的感知面。
死亡/里程碑触发时可附**当前帧截图**(引擎自绘 PNG,~2KB)——视觉通道实测与约束见 §3.5。

### 3.3 输出契约(有界授权,结构化约束)

**有界授权**是本设计的安全阀:Qwen 只能动 4 个旋钮,不能碰逐帧输入。

```jsonc
// llama-server: response_format = { type: "json_schema", json_schema: <下述 schema> }
// (实现时校验版本;旧版回退 GBNF grammar,再回退提示词约束 + 宽松解析)
{
  "route_hint":  "top | balanced | bottom",   // 有岔路时规划器 waypoint 偏好
  "risk":        0.0 .. 1.0,                  // 规划器裕度:助跑要求/踩敌vs绕行
  "gate_bias":   -0.05 .. +0.05,              // Laya EXECUTE 阈值微调(硬边界)
  "advice":      "≤40 token 英文祈使句",       // 注入 Laya state 的 language→reflex 通道
  "rationale":   "一句话理由(日志/UI 展示)"
}
```

应用时机:`on_ground && phase==='running'` 的 tick 边界一次性生效;
每条落 `supervisor` 日志行(prompt hash / 响应 / 延迟 / 旋钮 before→after / applied)。
`advice` 是最有实验价值的通道——**用大模型的语言编译成小模型的 state 文本**,
直接检验"语言能否遥控反射"(见 §6 RQ8)。

### 3.4 延迟工程(真机实测校准)

实测环境:`Qwen3.5-9B-Q6_K` @ llama.cpp b11063,单槽,温度 0,探针 `.tmp/qwen-vision-bench.mjs`:

| 探针                         | 结果                                                 |
| ---------------------------- | ---------------------------------------------------- |
| 纯文本 64 tok 短答           | 1.57s(decode ≈25ms/tok)                              |
| 图像 prefill(384×240 PNG)    | **~350ms**(视觉编码 + 图像 token,共 ~150 tok)        |
| 完整图像简报 220 tok(禁思考) | **1.4~4.4s**(前缀缓存命中 → 1.4s;未命中 → 4.4s)      |
| 默认放任思考                 | **15s+ 仍未出答案**(800 tok 全耗在 reasoning,被截断) |
| 提示词 `/no_think`           | **无效**,照样思考——不能用提示词抑制                  |

**结论:`chat_template_kwargs: {enable_thinking: false}` 是延迟工程的硬开关。**
由此确定 Qwen 的两个档位:

| 档位 | 配置                       | 延迟   | 用途                                   |
| ---- | -------------------------- | ------ | -------------------------------------- |
| 快档 | 禁思考 + 小 JSON(≤100 tok) | 1.5~4s | L2 监督者:死亡验尸/卡死仲裁/旋钮微调   |
| 慢档 | 允许思考(10~30s+)          | 无所谓 | L3 离线复盘:对局结束后的深度归因与策展 |

其余工程规则:

| 项     | 做法                                                              |
| ------ | ----------------------------------------------------------------- |
| 降频   | EWMA 监督延迟;超阈值自动收窄触发集(仅 on_death),CPU-only 友好     |
| 熔断   | 单次 >8s 丢弃记 `supervisor_timeout`;连续 3 次失败本局静默        |
| 缓存   | 固定 system 前缀 + 稳定指令模板(实测重复前缀 prompt 仅重算 6 tok) |
| 并发   | 单槽串行排队,不并发打;L3 批量分析才考虑 `--parallel 2`            |
| 不阻塞 | 请求异步,游戏循环零等待;结果只在安全边界(着地静止 tick)生效       |

### 3.5 视觉通道:能用,但只做语义级

实测(思考自述 + JSON 对照):9B 视觉能正确识别**场景语义**——两块地面、
坑的位置(±1 瓦)、金币/?块/管道、可行路线;但 **tile 级坐标不可靠**
(坑实际宽 3 瓦,模型报 8)。因此:

- 图像问"**什么样**"(地形类型、威胁类别、路线建议、死亡画面归因)——Qwen 强项;
- 精确坐标问"**引擎**"(状态编码与规划器数据精确到像素)——Laya/规划器强项;
- 视觉调用只发生在**冻结窗口**(死亡停顿/检查点/开局简报)或离线复盘,
  快档 1.5~4s 完全放得下;实时对局中绝不为等视觉而暂停物理。

### 3.6 基准汇总:两脑延迟对照(真机)

同一台机器,laya-server(`laya-rl-agent` @ laya-multilingual-onnx)与
llama-server(Qwen3.5-9B-Q6_K)各自实测。探针:`.tmp/laya-bench.mjs`、
`.tmp/qwen-bench3.mjs`(会话临时脚本,数据落 `.tmp/*-results.json`)。

**Laya(/predict,各 5 次)**

| 状态规模                     | state | 题  | min~max   | p50    |
| ---------------------------- | ----- | --- | --------- | ------ |
| L1 极小(2 候选)              | 78B   | 1   | 62~87ms*  | ~75ms  |
| L2 Tetris hex(3 候选)        | 271B  | 1   | 216~280ms | ~250ms |
| L3 马里奥 v1-profile(3 候选) | 262B  | 1   | 211~260ms | ~240ms |
| L4 = L3 + threat score       | 262B  | 2   | 314~380ms | ~350ms |

\* L1 首拍预热 1766ms 已剔除——服务冷启动第一拍必须预热
(游戏开局先发一次探活预测),生产同理。

**Qwen(/v1/chat/completions,旋钮决策实况形状)**

| 形态                      | 总耗时        | 备注                         |
| ------------------------- | ------------- | ---------------------------- |
| 快档纯文本(47 tok JSON)   | 0.9~1.4s      | 前缀命中 0.9s;冷 prompt 1.4s |
| 快档 + 384×240 帧(73 tok) | 1.4s(命中)    | 未命中约 4.4s                |
| 慢档(允许思考)            | 15s+ 仍无答案 | 仅限 L3 离线                 |

**合成结论:决策节奏分工**

| 层        | 有效节奏             | 依据                             |
| --------- | -------------------- | -------------------------------- |
| Laya      | ~4Hz(250ms 间隔)     | p50 240ms;第二题 +100ms,默认单题 |
| Qwen 快档 | 事件驱动 ≈ 0.1~0.5Hz | 0.9~4.4s,只在冻结窗口/事件触发   |
| Qwen 慢档 | 离线                 | 深度换准确,时间免费              |

Laya 比 Qwen 快档快约 **4~18 倍**、比慢档快 **60 倍以上**——两脑节奏相差一个
数量级以上,这是「反射/慢思」分层在工程上成立的实证基础,也再次否决了
"Qwen 进反射回路"的任何方案。

附带观察(单样本,不下结论):v1-profile 状态 Laya 给出 conf=0.59,明显高于
Tetris hex 的 0.13——马里奥编码可能比棋盘 hex 更贴近 Laya 舒适域,M5 校准
阶段用批量数据验证。

## 4. L3 分析师(完全本地的自改进闭环)

```
对局 JSONL ──▶ Qwen 分析(本地)──▶ 结构化发现 ──▶ 人工确认 ──▶ 下轮参数
   │              │ death 聚类、卡点定位、                │  编码模板 v1-profile→v1-both
   └ 同一份文件    │ 编码缺陷假设、阈值偏移、              │  门控阈值 / 风险默认值
                   │ 蒸馏数据切片建议(state,action)      │  蒸馏子集导出
```

- 输入 = docs/11 §10 的既有 JSONL(可附关键帧截图);输出 = 固定 schema 的发现列表
  (每条含证据行号 + 建议 + 预期可证伪指标)。**L3 允许开思考(慢档)**——
  离线时间免费,用深度换准确。
- 分析师**只建议、不自动改配置**(确认权在人),但蒸馏数据切片可直接导出——
  呼应 docs/10 §5 的微调路线,马里奥因此成为可再生训练环境的"策展人"。

## 5. UI(剧场式增量,浮层承载)

docs/11 §7 已裁定剧场式舞台布局(顶栏 + 舞台 + 遥测条 + 浮层,舞台 ≈92% 面积),
Qwen 以三个**低存在感**元素融入,不占常驻布局:

- **顶栏状态点**:Laya 点旁并列 Qwen 点(sky 色,只读探活);未启动时对应
  模式入口置灰并提示「请在 release 版 · 环境页启动」——游戏页无启停按钮。
- **遥测条 Q 段**:单行最新监督结果——`✦Q risk 0.30→0.55 · "走上层绕坑" · 0.9s`,
  点击 [▸] 打开 **SUPERVISE 浮层面板**(玻璃拟态):rationale 全文、旋钮
  before→after 历史、触发类型与延迟、快/慢档开关、「监督者」总开关
  (正交于模式,human 模式自动隐藏)。
- **舞台气泡**:Qwen 发言时舞台左上角 DOM 浮层(sky 描边玻璃底),一句话
  rationale,3s 淡出,与 Laya 品红目标旗一眼区分"谁在说话"。

监督者关闭/未就绪时,三个元素整体隐藏(不是置灰占位)——布局零残留。

## 7. 开发闭环:运行结果 → 千寻代码优化(与云端 Agent 协作)

控制栈的第四层是**开发时层**:游戏产生的每一次对局,都是给云端 Agent
(千寻/DSH 背后的编码 Agent)的"实验读数";Agent 的产出不是游戏动作,
而是**千寻仓库的代码修改与优化**。本节定义这条回路的数据契约与协议。

### 7.1 闭环总览与三档速度

```
对局(run) ──▶ var/mario/sessions/<id>/ 落盘 ──▶ BRIEF.md + summary.json
   ▲                                                        │
   │                                       用户递交云端 Agent / 本地 Agent 直读
   │                                                        ▼
   └──── 新一轮对局验证 ◀── 代码修改 ◀── 假设 + 主指标 + 优先级
```

| 回路     | 路径                                                     | 时延   |
| -------- | -------------------------------------------------------- | ------ |
| 快回路   | Agent 改代码 → debug 构建 + CDP 探针无头跑 N 局 → 读结果 | 分钟级 |
| 日常回路 | 用户在 release(双脑服务就绪)跑批 → 简报交 Agent 分析     | 小时级 |
| 蒸馏回路 | 轨迹导出 → LoRA 微调 → `models/laya-*` bundle → 重测     | 天级   |

### 7.2 数据契约(为 Agent 而设计)

落盘目录 `var/mario/sessions/<ts>-<mode>-<enc>/`(实现时在 `.gitignore` 追加
`var/`;**不用 `.tmp/`**——那是易失的 agent 草稿区,实验数据要可追溯):

| 文件            | 内容与约束                                                                                                                |
| --------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `manifest.json` | **配置指纹**:git sha(或 dev 标记)、物理常量、门控阈值、决策间隔、编码模板版本、视口瓦数、模型名——没有指纹的对比都是伪对比 |
| `session.jsonl` | 逐拍 decision/event 行(沿用 laya-server `/session/*` 既有协议)                                                            |
| `summary.json`  | ≤2KB KPI 头部:通关率、maxX p50/p90、死因堆叠、escalation%、QPS、门控分布、各 waypoint 通过率                              |
| `BRIEF.md`      | ≤4KB,**给 Agent 的标准入口**:①指纹表 ②KPI 与上轮 diff ③Top3 异常(如"坑2 死亡集中→助跑不足")④建议关注的文件指针            |

生成器:`scripts/mario-brief.ts`(tsx CLI,读 JSONL → summary + BRIEF),
同时作为 e2e 探针的输出端。`var/mario/latest` 固定指针文件指向最新 session,
用户与 Agent 都不必报路径。

### 7.3 Agent 的修改面(有界授权,镜像 L2 旋钮思想)

| 目标文件      | 可改                         | 证据要求                  |
| ------------- | ---------------------------- | ------------------------- |
| `world1-1.ts` | 物理手感常量、关卡数据       | 死因分布 + 人玩体验       |
| `brain.ts`    | 门控默认阈值、编码模板 v1→v2 | 编码消融数据(RQ3)         |
| `planner.ts`  | 候选动作策略、waypoint 评分  | waypoint 通过率、死亡热图 |
| `driver.ts`   | 决策间隔、输入持有策略       | QPS vs stale 率           |

**修改纪律**:每次修改 = 一个假设 + 一个主指标;改前改后同指纹各跑 ≥10 局;
不达标即回退(诚实数据文化,docs/10 §4)。禁止无证据重写与跨层大爆炸改动。
Agent 侧工程纪律沿用仓库规范:`pnpm all:check`、Conventional Commits 多笔拆分、
结论回写 docs。

### 7.4 快回路:CDP 无头验证(debug 构建)

- 复用既有基建:debug 二进制内置 Playwright CDP 端口 10222(docs/07);
- `e2e/probe-laya-mario.ts` 扩展:进入游戏页 → 设定模式/视口 → 跑 N 局 →
  按 §7.2 契约输出 summary;
- Agent 迭代循环:`改代码 → pnpm dev(或 e2e:build)→ npx tsx e2e/probe-laya-mario.ts --episodes 10 --mode autopilot → 读 summary → 判定假设 → 提交或回退`;
- 边界:autopilot/human 探针**不依赖任何服务**,Agent 可独立验证引擎/规划器;
  reflex/pure 需 laya-server——**Agent 无权代启**,由用户在 release 环境页启动
  (docs/11 §1.1)。

### 7.5 交互协议(用户 ↔ 云端 Agent 怎么说、怎么回)

- 用户指令模板:「读 `var/mario/latest/BRIEF.md`,给 3 条假设,实施最优一条,
  用探针验证后汇报」;
- Agent 回执固定结构:**修改列表 + 验证数据(改前/改后同指标)+ 是否回退 +
  docs 更新点**——形成可审计的决策链;
- 分工:L3 分析师(Qwen,本地)做**局内诊断**(JSONL 找异常、给参数建议),
  云端 Agent 做**代码进化**(改仓库)。两者输入同源、输出分层、结论都落 docs
  可互相引用。

### 7.6 隐私与边界

- `var/` 数据不出本机;`BRIEF.md` 是唯一的云端摘要面(路径脱敏、不含用户
  目录信息),由用户决定是否递交;
- Agent 不碰用户数据目录、不代启服务、不 kill 非自己启动的进程(仓库红线);
- 这个闭环本身即是"Laya 能力外推"的第一个真实域:**游戏成为 Agent
  自动化开发闭环的试验台**——感知(简报)→ 决策(假设)→ 执行(改码)→
  验证(探针),与游戏内 SENSE→DECIDE→ACT 同构。

## 8. 风险与对策

| 风险                        | 对策                                                           |
| --------------------------- | -------------------------------------------------------------- |
| CPU-only 机器 Qwen 过慢     | 禁思考硬开关 + EWMA 降频至仅 on_death;超时熔断;游戏永不等 Qwen |
| 输出不可解析                | json_schema(回退 GBNF/提示词约束)+ 宽松解析 + 丢弃即安全       |
| 过度干预(旋钮抖动)          | 有界授权 + 频控 + before→after 全落盘可回放                    |
| 与 Tetris 共用 17230 无冲突 | 端口已与 Laya/DSH 错开;游戏只读状态,启停权仍属环境页           |
| "假自主"(其实全靠规划器)    | 归因遥测:每局统计 L1/L1.5/L2 各自贡献占比,诚实呈现             |

## 10. 结论

- **零新增基建**:`qwen.rs` 侧车、OpenAI 端点、EnvPage 管理、JSONL 全部现成,
  新增的只有 `supervisor.ts`(触发器 + 契约 + 旋钮应用)与一块 UI 卡片。
- **结构性安全**:9B 慢思被关进"有界授权 + 事件驱动 + 安全边界应用"的笼子里,
  反射与规划层保证任何时刻断供都不掉线——这正是未来把同一栈推向
  RPA/桌面自动化时最需要的容错形态。
- **探索价值**:RQ8(语言→反射通道)与 RQ9(本地自改进闭环)是 Laya×Qwen
  组合独有的命题;若成立,"小模型执行 + 大模型战略"就是完全本地自主体的通用范式。
- **第四层**:开发闭环(§7)把云端 Agent 接入为"开发时层"——游戏内
  SENSE→DECIDE→ACT 与仓库侧"简报→假设→改码→探针验证"同构,
  千寻由此同时验证 Laya 的**运行时**与**开发时**两种外推形态。
