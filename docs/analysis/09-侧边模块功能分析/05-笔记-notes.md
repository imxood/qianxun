## 1. 模块定位与设计意图

`docs/01-产品设计.md:42` 把笔记定位为三大支柱之一「承载工具」的主力：_「Markdown 笔记库（纯本地文件夹 + frontmatter）· 编辑器 · 检索」_，v0.1 交付。设计原则落在 `docs/01-产品设计.md:86`「数据是文件」——同步、备份、AI 直接读写的共同前提。

代码内的意图注释与之一致：

- `src-tauri/src/notes/mod.rs:3-4`：「一个目录 = 一个库，`.md` 文件 + YAML frontmatter。所有写入走原子替换；不做隐藏数据库」。
- `src/features/notes/NotesPage.svelte:2-8`：「列表 | CodeMirror 编辑 | Markdown 预览。纯文件库（ADR-006）；保存走原子写；删除入 .trash 可救。v0.2：编辑器容器常驻…自动保存（1.5s 防抖+失焦+Ctrl+S）、对话框组件化（去 window.prompt/confirm）」。

**v0.2 之前的历史缺陷已修复**（`docs/05-功能深化设计-v0.2.md:13,57-61` 记录的两个致命项）：

| 历史致命项                                               | 现状                                                                     | 证据                                                                                                                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| CodeMirror `parent: host!` 游离视图，页面完全不可输入    | 已封装 `NoteEditor.svelte`，挂载生命周期跟随 `$effect(() => host)`       | `NoteEditor.svelte:30-52`；`NotesPage.svelte:548-561`（容器常驻 DOM，预览只切 `hidden`）                                               |
| 读剥 frontmatter、写不拼回 → **首次保存即丢 title/tags** | 已统一：Rust `compose_frontmatter` 与 `parse_frontmatter` 同源，单测互逆 | `notes/commands.rs:60-77`（`notes_save` 收结构化 title/tags）、`:270-291`（compose）、`:329-345`（`拼装与解析互逆且保留created` 单测） |

**结论：设计意图明确，v0.2 列出的两项致命缺陷均已闭环，不是「占位骨架」。**

## 3. 实现分析

### 3.1 架构与数据流

```
                ┌──────────────── 桌面外壳 (tauri.localhost) ────────────────┐
  用户编辑 ──────▶ NotesPage.svelte（列表/过滤/元数据输入/对话框/AI 面板）  │
                   │  ├─ CodeMirror: NoteEditor.svelte（doc ⟷ onDocChange）  │
                   │  └─ call('notes_*')  ←→  src/lib/ipc/contract.ts        │
                   └───────────────────────────┬────────────────────────────┘
                                               │ Tauri IPC
  ┌─────────────────────────── Rust (src-tauri/src) ─────────────────────────┐
  │ notes/commands.rs  notes_list / notes_read / notes_save /                │
  │                     notes_create / notes_delete / notes_init             │
  │        ↓ 拼装 / 剥 frontmatter（同源实现，单测互逆）                     │
  │ atomic::write  tmp → write_all → fsync → remove(旧) → rename            │
  └───────────────────────────────┬────────────────────────────────────────┘
                                  ▼
                    <vaultDir>/*.md（+ .trash/）
                                  ▲
  ┌──────────────── DSH Host 进程（Node）· qx-bridge 插件 ──────────────────┐
  │ note_search / note_read / note_write（agent 工具，index.js:252-342）      │
  │ POST /qx/notes/organize（ctx.inject webServer+llm，:504-552）             │
  └─────────────────────────────────────────────────────────────────────────┘
```

两套 frontmatter 语义（Rust `parse_frontmatter` 与 JS `parseFrontmatter`）是**手写重复实现**，靠约定保持一致（`index.js:131` 注释「与千寻 Rust notes::commands 语义一致」）。当前实现确实等价（都只认 `---` 开头、`\n---` 收尾、`title:`/`tags: [a, b]`），但没有跨语言回归测试兜底。

### 3.2 前后端契约

契约声明在 `src/lib/ipc/contract.ts:58-63`（6 个 notes_*）、类型 `NoteMeta`/`NoteContent`（`contract.ts:885+`），Rust 侧 `#[serde(rename_all = "camelCase")]`（`notes/commands.rs:13,27`）——**命名映射正确**。

| 命令           | 入参                               | 出参                       | 关键语义                                                                                                                                           |
| -------------- | ---------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `notes_list`   | `vault: String`                    | `NoteMeta[]`               | 全库 walk；`updated` 来自 mtime，`size` 来自 `stat.len()`；`NoteMeta.size` 前端**未使用**                                                          |
| `notes_read`   | `vault, path`                      | `NoteContent{meta, body}`  | body 已剥 frontmatter                                                                                                                              |
| `notes_save`   | `vault, path, title, tags[], body` | `NoteMeta`                 | **必须文件已存在**（`note_path` 校验 `is_file()`，`notes/commands.rs:151-153`）；`created` 字段原样保留（`:68-70`）                                |
| `notes_create` | `vault, title`                     | `NoteMeta`                 | 文件名 = `YYYYmmdd-HHMMSS-<sanitized>`；`title` 字段用**原始** title 写 frontmatter（`:87`），文件名用安全化版本（`:83-85`）——两者故意不同，是对的 |
| `notes_delete` | `vault, path`                      | `()`                       | 移入 `.trash/<ts>-<原名>`                                                                                                                          |
| `notes_init`   | `vault: Option<String>`            | `String`（库目录绝对路径） | `None`/空 → 默认目录                                                                                                                               |

**契约健康度**：读/写两侧 frontmatter 同源（v0.2 缺陷已闭环）；但 `notes_save` 不能创建新文件、不能改路径，是隐式契约（前端 `create` 后 `open` 再自动保存，路径永远来自 `activeNote.meta.path`，`NotesPage.svelte:215-221`）——当前调用方自洽，无 bug，但契约未文档化。

### 3.3 数据安全与持久化

| 环节         | 实现                                                                                                     | 评价                                                                                                                                                                                                      |
| ------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 写入原子性   | `atomic.rs:12-35`：同目录 `.json.tmp` → `write_all` → `sync_all()` → 目标存在则 `remove_file` → `rename` | fsync 在 rename 之前，掉电不会拿到「rename 已完成但数据未落盘」的中间态，**这一点做得对**（`atomic.rs:25-27` 有注释说明）                                                                                 |
| 临时文件命名 | `path.with_extension("json.tmp")`（`atomic.rs:21`）                                                      | 笔记 `x.md` → `x.json.tmp`，不与 `.md` 混淆，且 `collect_notes` 只收 `.md`（`notes/commands.rs:168`）、`index.js:200` 同款过滤 → 不会被误列为笔记。**结论：无冲突风险**（与"看起来像 bug"相反，特此核实） |
| 崩溃窗口     | `remove_file(path)` 与 `rename(tmp, path)` 之间崩溃 → **原文件已删、新文件未就位**                       | `atomic.rs:5-6` 与 `:30-33` 都承认此窗口，理由是「读取方只认正式文件名」。对 settings.json 无所谓，**对笔记 = 整篇丢失且无备份**（§4 P2-1）                                                               |
| 软删         | `.trash/<时间戳>-<原名>`（`notes/commands.rs:109-113`）                                                  | 命名带时间戳，重复删除同名笔记不会互相覆盖；`.trash` 被 `name.starts_with('.')` 跳过（`:163`）→ 不污染列表                                                                                                |
| 越界         | `note_path` 拒绝绝对路径与 `..` 分段（`notes/commands.rs:147-149`）                                      | 有单测（`:354-360`）；桥侧 `index.js:172-184` 独立实现同一规则（`/^[A-Za-z]:/` 也拦）                                                                                                                     |
| 编码         | `read_to_string` / `write(bytes)`                                                                        | **非 UTF-8 的 .md 文件在 `collect_notes` 里被 `unwrap_or_default()` 静默跳过**（`:169`），在 `notes_read` 则直接报错（`:48-49`）。行为不一致但都不损坏数据                                                |
| 备份/历史    | 无                                                                                                       | 单篇覆盖写，无 `.bak`、无版本栈                                                                                                                                                                           |

### 3.4 错误处理

- 前端：所有 IPC 调用统一 `try/catch` → `errorText`（`NotesPage.svelte:168,197,228,241,256,301,324`），底部红条展示（`:574-576`），不静默。
- 后端：全部 `Error::Notes("中文原因：{cause}")`（`notes/commands.rs:49,73,91,104,115,130`），符合「失败要显式」原则（`docs/01-产品设计.md:87`）。
