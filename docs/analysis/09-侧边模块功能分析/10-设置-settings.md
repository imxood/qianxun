### 值得称道的部分

- **设置合并逻辑只做一份**：`stores/settings.svelte.ts:4-6` 注释是关键设计决策——「update 把补丁发过去，用返回的完整设置替换本地状态，避免前后端两套深合并互相漂移」。这是很多项目踩坑的地方，这里从架构上规避了。
- **热键注册顺序正确**：先 `shots_set_hotkey` 试注册（占用/非法立即报错），**成功才落设置**（`SettingsPage.svelte:229-234`）。反过来写会留下「设置显示已保存但实际没注册」的幽灵状态。
- **`app_restart` 的「不返回」语义处理**：`SettingsPage.svelte:412-420` 明确写了「restart 不返回：走到这里说明重启没有发生，提示用户手动重启」，两条路径都给用户可见反馈。
- **热键录制防呆**：`accelFrom` 要求至少一个修饰键 + 一个普通键（`:206-207`），避免吞掉单键输入；裸按键（Ctrl/Shift/Alt/Meta）返回 null 忽略。
- **滚动联动尊重 `prefers-reduced-motion`**（`:92`），且用 `spyPinned` 解决「点击锚点后联动把高亮翻掉」的经典问题（`:94-96` 有完整解释）。
- **还原前自动停 DSH**（`:399-402`）+ 还原前自动快照（`restoreReport.preRestoreBackup`）+ 插件缺失一键补装（`:889-903`）——危险操作的防御链完整。

## 1. 模块定位与设计意图

设置页不是单一功能域，而是**三个横切域的汇聚点**：

| 职责                                | 归属                      | 证据                                   |
| ----------------------------------- | ------------------------- | -------------------------------------- |
| 应用偏好（主题/窗口/DSH/镜像/联网） | `settings.rs`             | `settings_get` / `settings_update`     |
| 数据备份与还原                      | `backup/commands.rs`(728) | `backup_export/inspect/restore`        |
| 笔记 git 同步（S1）                 | `sync/`                   | `sync_status/init/pull/push`           |
| 插件清单补装（还原后修复）          | `market`                  | `market_sync_pinned`（`:313`）         |
| 截屏热键注册                        | `shots`                   | `shots_set_hotkey/clear`（`:230-232`） |

**信息架构**：6 个分区（外观/通用/DSH 环境/联网/数据/关于），左侧 sticky 分区导航 + 滚动联动（`:483-511`），窄窗口（`<lg`）自动退化为单列（`:483` `hidden ... lg:block`）。

这违反了常见的「设置项按功能模块分散到各页面」做法，但对这个项目是**合理的**：DSH 相关设置（数据目录/端口/锁定版本/Node 源/npm registry）高度耦合，集中一处反而清晰。

## 3. 实现分析

### 3.1 架构与数据流

```
App.svelte onMount
  └─ await settings.load()        ← 决定是否 show()（startMinimized）
       └─ 失败也继续（finally 里兜底 show）

设置页每次改动
  └─ save(patch) → settings.update(patch)
       └─ IPC settings_update → Rust 深合并 → 落盘 → 返回完整 Settings
            └─ 前端整体替换 this.current    ← 单一合并逻辑（Rust 侧）

主题联动
  └─ onTheme → theme.set() + save({theme})   ← 立即生效（乐观）
  └─ App.svelte $effect: settings.current 变化 → theme.set(settings.current.theme)
       └─ 权威态回写（双通道但方向一致）
```

**关键设计**：`settings.update` 不用乐观更新，等 Rust 返回完整设置再替换。虽然多一次往返，但彻底消除了「前端猜的合并结果」与「Rust 实际落盘」不一致的可能。对设置这种低频操作，这个取舍完全正确。

### 3.2 前后端契约

- `settings_get` / `settings_update` / `app_meta` / `backup_*` / `sync_*` 均在 `contract.ts:13-21,102-105` 声明，受 `contract.test.ts` **命令级**门禁保护。
- `Settings` 嵌套深（`window`/`dsh`/`web`/`mirrors`/`hotkeys`/`notes`/`tools`/`plugins`），`SettingsPatch` 是字段级部分更新（`contract.ts:290`）。
- ⚠️ **`Settings` / `SettingsPatch` 未进 `RESPONSE_TYPES`**（`contract.test.ts:92-107`），这个全应用最重要的类型反而没有字段级门禁。`nested patch` 的语义（浅合并还是深合并）在 TS 端也没有类型保障。

### 3.3 性能与资源

- `SettingsPage.svelte` 948 行单文件，是前端第二大组件（仅次于 `MarioLab.svelte` 1828 行）。内部有 6 个分区、~15 个独立功能块。
- 滚动联动用 `getBoundingClientRect()` 遍历 6 个 section（`:117-120`），且绑在 `passive: true` 的 scroll 上——每次滚动 6 次 rect 读取，实测无感（元素数固定为 6）。
- `theme.test.ts` 与 `sync.test.ts` 覆盖了 store 层的关键逻辑。

### 3.4 错误处理

- 三层错误各自独立可见：`settings.loadError`（整页红框 + 重试按钮，`:447-455`）、`saveError`（顶部 alert，`role="alert"`，`:457-464`）、各功能的局部错误（hotkeyError / syncError / backupError / pinBackMessage）。
- `dshRunning()` 查询失败时**不拦截**备份操作（`:334-344` catch 返回 false）——注释说「状态查询失败不拦截备份操作」，这是有意的降级选择。
- `restartNow()` 的「不返回」双路径都提示手动重启（`:412-420`）。
