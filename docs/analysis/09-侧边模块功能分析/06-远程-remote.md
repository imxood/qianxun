## 1. 模块定位与设计意图

`docs/01-产品设计.md:11,44-45` 把「连接远近」列为三大支柱之一：_「通过 EasyTier 虚拟局域网，手机与远程机器访问同一台 Host 上的 DSH 与工具」_，并把 **Capacitor Android 壳（加载网关地址）** 也算进 v0.1 范围。硬非目标（同 `:77`）：**不做公网中转、不做账号体系/云服务/多人协作**。

代码内的架构声明（`remote/mod.rs:1-11`）把边界讲得很清楚：网关是 DSH 的唯一远程暴露面；DSH 永不听非回环；`/qx-gate` 是唯一免鉴权入口；其余路径要求 cookie/query 命中未吊销 token；`enabled=false` 时「零监听」。

v0.2 之前的历史致命项是 `sync()` 的幂等判断只看「任务在跑」而不比较配置指纹，导致**配对后新 token 不生效（扫码 401）、吊销后旧 token 不断**（`docs/05-功能深化设计-v0.2.md:16,169-174`）。

**该缺陷已修复**：`GatewayHandle.fingerprint`（`gateway.rs:51`）+ `fingerprint()` 覆盖 `enabled/bind_ip/port/devices/upstream/dsh_url` 六个维度（`commands.rs:244-262`）+ `sync()` 指纹比对保留/重建（`commands.rs:305-337`）。且**不仅修了文档里写的 4 个维度，还把 `upstream` 与 `dsh_url` 也纳入指纹**（`commands.rs:236-243` 注释说明原因：DSH 就绪/ revive 后不重建会永远指向上游占位 `127.0.0.1:0`），单测 `指纹随任一配置维度变化`（`commands.rs:415-539`）逐维度验证了这点。**这是本模块工程质量最高的一段。**

## 3. 实现分析

### 3.1 架构与数据流

```
 手机浏览器 / Android 壳(WebView)
        │  http://<EasyTier IP>:23090/…
        ▼
┌──────────────── remote::gateway（一个 axum Router，两份 clone）────────────────┐
│  ① 自己的路由（优先于兜底，不转发 DSH）                                        │
│     /qx-mobile/{info,version,bootstrap.js,custom.css,custom.js,*}               │
│     /qx-shell/links.js        ← 仅回环可取                                     │
│     /api/remote.mux           ← WS 双向桥                                     │
│  ② 兜底 handler（按 Host 头分流）                                              │
│     回环(127.0.0.1/localhost/[::1]:port) → access_allowed 栅栏 → 注入桌面外壳层   │
│     其它 Host                          → /qx-gate 配对 or authorized → 注入移动层 │
└────────────────────────────────┬──────────────────────────────────────────────┘
                                 │ dsh_upstream::forward / upgrade_ws
                                 ▼  Origin/Sec-Fetch-Site 合成为上游同源；
                                    cookie 换成服务端持有的 dsh-auth-*；
                                    qx_token 绝不外泄
                        DSH（永远 127.0.0.1:<dsh-port>）

  启动侧：settings.remote（enabled/bindIp/port/devices）
      → commands::sync（sync_lock 互斥 → fingerprint 六维比对）
      → gateway::start（回环必绑；LAN 首绑失败降级 + lan_serve_loop 30s 重试）
      → GatewayHandle{shutdown, task, lan_addr(watch), loopback_addr, fingerprint}
```

监听地址通过 `tokio::sync::watch` 共享（`gateway.rs:44-52,185`），所以「LAN 网卡掉线/恢复」能同时反映到 `remote_status`（`commands.rs:67-73`）、自检（`commands.rs:153-166`）与日志——**这个设计是对的**，避免了状态分裂。

### 3.4 错误处理

**做得好的**：所有拒绝路径都有中文原因 + 日志（`gateway.rs:299,316,321,341,348`）；注入失败绝不破坏页面（`gateway.rs:528-537` 非 UTF-8 时**原样透传**并落日志，`:542-554`，注释明确「绝不能拿错误页顶掉正常页面」）；上游不可达返回 502 + 中文提示（`dsh_upstream.rs:357-363`）；LAN 失败节流日志避免刷屏（`gateway.rs:258-267`）。

**缺口**：

1. **启动失败不显式**（`commands.rs:389-391` 只落 warn；UI 只显示「未监听」，`RemotePage.svelte:245-246`）。直接违反产品原则「失败要显式：端口被占…都给出原因与下一步」（`docs/01-产品设计.md:87`）。**端口被占是最典型的远程失败场景，用户却只能去翻日志。**
2. **无状态推送**：`lan_serve_loop` 每 30s 可能让 LAN 从「不可用」变「已监听」（`gateway.rs:276-278`），但 UI 只在窗口聚焦时刷新（`RemotePage.svelte:181`）→ 用户点完开关后盯着「未监听」，其实 30s 后就好了，界面不会告诉他。
3. **前端两处 catch 静默**：`refresh()` 失败设 `status=null`（`RemotePage.svelte:70-72`）、`loadInterfaces()` 失败设 `interfaces=[]`（`:78-80`），都不给 `error`。其中后者会让「未检测到 EasyTier」的引导条**永远不显示**（`easytierAbsent` 要求 `interfaces.length > 0`，`:40-42`）→ 枚举失败被误呈现为「一切正常」。
4. `harness`/DSH 侧与网关相关的失败处理不在本模块范围（`harness::proxy`），未展开。
