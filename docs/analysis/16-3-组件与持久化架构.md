## 1. EvolutionChat 组件设计

### 1.1 布局归属:常驻主列,不进 FloatingPanel

| 维度 | FloatingPanel 现状 | 聊天主列需要 | 冲突 |
| --- | --- | --- | --- |
| 定位 | `position:fixed` 浮层 + 拖拽,目标是"不占主内容、可挪开" | 与游戏区并排、固定占宽 | **语义相反**;拖走后位置持久化,用户再也找不回 |
| z 序 | 模块级 `zTop`/`activePanel` 全局单值,点击置顶 | 主列不可被 pm/settings 遮盖 | 参与置顶竞争即错误 |
| 高度 | body `p-3` 随内容涨,内滚靠内容自己 max-h | 列高=视口高、body flex-1 内滚、锚定底部 | 需给通用组件开"高度受控"特例,污染全应用复用 |
| 持久化 | x/y/folded | 宽度占比/折叠态 | 拖拽与位置逻辑全部作废 |
| 小视口 | <900px 退化为底部浮窗 | 应退化为游戏区下方堆叠 | 两套退化逻辑并存,不如一条 flex 换向 |
| ARIA | `role="dialog"` | 主内容列不应是 dialog | 语义错误 |

**推荐**:EvolutionChat 作为 MarioLab 根布局的常驻 flex 列(360–420px,可折叠为窄条只显最新一条+未读徽标)。复用 FloatingPanel 的只有**约定**而非组件:`qx.mario.panel.chatDock` 折叠态键、折叠徽标交互。聊天是主界面,辅助窗机制(z 序/拖拽/单窗退化)对它是纯负担。

### 1.2 消息类型与 Props

数据所有权不在组件:仿照 store.ts"只搬运字节、解析在纯函数"的分层,新建 `chat.ts` 纯模块定义 `ChatMessage`、append、重建(可单测),MarioLab 负责在各事件点投递消息。

```ts
type ChatMessage =
  | { id: string; kind: 'run-start';  runId: string; mode: DriveMode; iter: number; ts: number }
  | { id: string; kind: 'death';      runId: string; attempt: number; cause: string; col: number }
  | { id: string; kind: 'analysis';   runId: string; phase: 'start'|'ok'|'fail'; key: string;
      reason: string; latencyMs?: number; err?: string }
  | { id: string; kind: 'diagnosis';  runId: string; key: string; text: string }        // Qwen 正文
  | { id: string; kind: 'insight';    runId: string; text: string }
  | { id: string; kind: 'proposal';   runId: string; patch: Patch; kind: 'numeric'|'design';
      issues: string[]; gated: boolean }
  | { id: string; kind: 'verdict';    runId: string; verdict: 'commit'|'rollback'|'restore';
      reason: string; score: number | null }
  | { id: string; kind: 'run-end';    runId: string; won: boolean; ticks: number; maxXCol: number };

interface Props {
  messages: readonly ChatMessage[];   // 父级注入,组件不拥有数据源
  status: { phase: Phase; mode: DriveMode; layaOk: boolean; qwenOk: boolean;
            queueDepth: number; analyzingKey: string | null };
  onstepadvance?: () => void;         // 提案卡「下一步 ▸」上抛(单步放行)
  onresetpolicy?: () => void;
  onopenpostmortem?: (runId: string) => void;  // DataCard「查看全文」→ pm 浮窗
}
```

要点:**run-start/run-end 只存摘要 + runId 引用**,复盘全文已在 `runs/<runId>.json`,消息里不重复存(单行 64KiB 预算的大头省掉);diagnosis 正文超长时截断并注明"全文见 runs/"。

### 1.3 内部 $state 与滚动锚定

```ts
let atBottom = $state(true);      // 锚定开关(距底 <24px 视为在底)
let visibleCount = $state(200);   // 窗口化:只渲染尾部 N 条
let folded = $state(false);       // 列折叠,持久化 qx.mario.panel.chatDock
let unseen = $state(0);           // !atBottom 期间的新消息计数(浮标用)

const groups = $derived.by(() => { /* 顺序扫描 messages,按 runId 切组 */ });
$effect(() => {                   // 锚定:只依赖 length,不依赖消息内容
  messages.length;
  if (atBottom && scrollEl) { scrollEl.scrollTop = scrollEl.scrollHeight; unseen = 0; }
  else if (!atBottom) unseen += 1;
});
function onScroll(): void {       // 程序化赋值也触发 scroll:赋值处先同步 atBottom=true 防回环
  const el = scrollEl!;
  atBottom = el.scrollHeight - el.scrollTop - el.clientHeight < 24;
}
```

### 1.4 子组件职责边界

| 子组件 | props | 职责 | 不做 |
| --- | --- | --- | --- |
| `MessageItem` | `{ msg }` | 按 kind 渲染气泡(角色色/图标映射),纯展示 | 无内部状态、不感知滚动 |
| `DataCard` | `{ patch, issues, kind, gated, verdict, score }` + 回调 | 提案卡(from→to 字段表)/判定卡(徽标+分数)/单步放行按钮 | 不自己改状态,动作全部上抛 |
| `StatusStrip` | `{ ...status }` | 列顶固定单行:运行态/探活点/队列 n·在途 key | 高频 stats 走**单值覆盖**,绝不追加消息(§5.6 决策拍教训的推广) |

分组渲染:`{#each groups as g (g.runId)}` 组头「第 N 局 · 模式 · 死亡 x 次」→ 内 `{#each g.msgs as m (m.id)}`。

## 2. 聊天历史持久化:三方案对比

### 2.1 先校准两个 IPC 事实(易被"1MiB"误导)

- `mario_state_write` 整文件上限 **1MiB** + 原子替换;`mario_state_append` 上限是**单行 64KiB,文件总量无上限**——append 型文件根本不撞 1MiB 墙。
- `mario_state_list` **只列根目录文件,不含 runs/ 内容**:方案 B 重建必须先读 `runs/index.jsonl`(裸名可读)拿 runId 清单,再逐个 `read runs/<runId>.json`。
- 白名单允许裸名 `chat.jsonl`;e2e(mario-loop.ts)直写同一数据根,双侧同构 append 可行。

### 2.2 对比

| 维度 | A:chat.jsonl append | B:从 evolution.jsonl + runs/ 重建 | C:仅会话内存 |
| --- | --- | --- | --- |
| 写入约束 | 单行 64KiB(单条 ≤2KB,余量 30×) | 无新写入 | 无 |
| 数据完整性 | 全量,含 Qwen diagnosis 正文 | **缺核心内容**:diagBySig 是内存 SvelteMap 不落盘,审计行只有 key/reason/latency | 重启全丢 |
| 呈现契约 | 自有稳定 schema | 绑死审计行格式——对账格式一改,聊天即坏 | — |
| 启动成本 | read 1 个文件(3–7MB/百局,parse 数十 ms) | read index + N×runs(100–400KB/局),IO 放大严重 | 0 |
| 时序还原 | 天然有序 | 审计行有 phase 时序,但需二次翻译成文案 | — |
| 用户诉求"每轮失败都有" | ✓ | 勉强(半成品) | ✗ 直接违背 |

### 2.3 推荐:A 为主 + B 降级兜底

- **运行时**:每条消息 `store.append('chat.jsonl', JSON.stringify(msg))`,**写失败静默不重试**——聊天是呈现层,事实源始终是 evolution.jsonl + runs/;呈现可丢,审计不可丢(与现有 persist* 同纪律)。
- **启动**:read chat.jsonl 渲染历史;文件缺失/损坏(旧版本升级首启)→ 从 evolution.jsonl 尾部解析**降级重建"简史"**(只有事件骨架,无诊断正文),UI 标注"历史由审计重建,不含分析全文"。
- **不选纯 B 的根因**:重建出的聊天流缺 Qwen 说了什么(diagnosis 未落盘)——要补齐就得把 diagnosis 写进审计或新文件,绕回 A;且把呈现层绑死在对账格式上是双向耦合。
- **不选 C**:与 §9b"数据要多不要少"的已拍板口径相悖。

### 3.4 回归风险清单(按易坏程度)

1. **键盘冲突**:`svelte:window` onKeyDown 全局吃 Enter(重生)/P(暂停)/方向键 preventDefault——聊天列若加输入框必须 stopPropagation 或判 `e.target`;当前需求无输入则无此险(列为开放问题)。
2. **log-stream 文本断言**:evolve 档迁走后 laya 浮窗日志变少,涉及 e2e 断言必断,第 3 步前置 grep。
3. **testid 层级**:e2e 若用"panel-evo 内找按钮"的嵌套定位会断;保持 testid 唯一与顶层可达。
4. **analysisGate 时序**:聊天消息在 runAnalysisQueue 内产生,推送逻辑勿改 gate 的 resolve 条件;start 按钮 disabled 只看 analysisPending,与聊天渲染严格解耦。
5. **canvas 自适应**:游戏区让宽后 `viewTiles = clientWidth/clientHeight×15`(钳制 16–56)在窄区出怪比例;ResizeObserver 已有,需 4 模式×3 倍速人工过一遍。
6. **Escape 语义**:openPanels 缩为 [laya,settings,pm];确认焦点在聊天列时 Escape 不误关浮窗(activePanel 机制沿用)。
7. **persistKey 残留**:`qx.mario.panel.evo` 成死键(无害,第 4 步清理);chatDock 新键勿撞名。
8. **高频快照**:stats/lastDecision 严禁追加为消息(§5.6 刷屏教训),只走 StatusStrip 单值覆盖。

## 4. 性能与容量

### 4.1 量级估算

每局 = run-start 1 + death ≤3 + analysis(start/ok|fail)×(1–4 任务)×2 + insight 0–2 + proposal 0–1 + verdict 0–1 + run-end 1 ≈ **15–35 条**;100 局 1.5–3.5k 条。单条 ≤2KB → chat.jsonl 约 30–70KB/局(与 runs/ 的 100–400KB/局同量级)。DOM:3.5k 条 × 3–5 元素 ≈ 1.5 万节点,全量渲染首屏与滚动吃力。

### 4.2 虚拟滚动判定:**不上**

使用频率是"偶尔回看"而非高频滚动;气泡高度不定,虚拟滚动需动态测量,复杂度与收益不匹配。替代:**窗口化渲染**——初始只渲染尾部 200 条(按 id 找起点组),顶部「加载更早(还有 N 条)」每次 +200;200 条 ≈ 1k 节点,首屏 <50ms。上限即消息总量,不设滑动窗口淘汰。

### 4.3 key 策略

消息创建时即分配 `id = ${runId}#${seq}`(seq 模块内单调),each 全部 keyed。禁止:数组下标(重建历史前插会错位重渲染)、`t+text` 拼接(现 log-stream 的做法,同毫秒同文本可碰撞,聊天量级下必炸)。

### 4.4 滚动锚定三态

1. **跟随**:atBottom 为真 → 新消息 `scrollTop = scrollHeight`(用 instant;smooth 在连续追加时会排队抖动)。
2. **锁定**:用户上翻 → atBottom=false 停止自动滚,右下浮标「↓ N 条新消息」(N 累计,回底清零)。
3. **恢复**:点浮标或手动滚回底部 → 重新锚定。

实现纪律:锚定 effect 只依赖 `messages.length` + atBottom(verdict 卡原位更新不触发滚动);程序化赋值先同步 atBottom 防止 scroll 事件回环;列折叠展开后强制回底。
