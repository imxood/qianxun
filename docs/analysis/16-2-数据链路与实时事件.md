# 16-2 数据链路与实时事件(聊天式进化窗 · 设计评审)

> 范围:只做设计分析,未改任何源码。聊天式进化窗 = 每局失败后,把 Qwen 分析的
> 过程/优化/结论以消息流呈现,并显示运行状态与必要数据。所有结论基于对
> evolution.ts / qwen.ts / machine.ts / driver.ts / store.ts / commands.rs /
> MarioLab.svelte(runAnalysisQueue 等)的通读核实。

## 0. 结论摘要

1. 现有链路已有一个"天然事件总线":`MarioLab.audit()`(MarioLab.svelte:279)。
   全部进化事件(propose/commit/rollback/restore/analyze start|ok|fail)都从这里
   过,同时进 `auditTail`($state,仅 10 条)与 evolution.jsonl。聊天流的最小接线
   = 在此事件流上做"投影 + 展开",不引入第二条事实源。
2. Qwen 四类内容的可获取性差异很大:playbook 全文、补丁 from→to、insight 结构体
   在 `runAnalysisQueue` 的成功分支里"路过即得",只是没有被推给聊天窗;diagnosis
   明细只进内存 `diagBySig`(SvelteMap,不落盘、不进 UI),**重启即失,历史局不可
   重建**——这是最深的一个缺口。Qwen 原始 JSON 文本在 refineViaQwen 内被直接丢弃。
3. 实时性:纯事件驱动即可,零轮询、零新增回调面。Qwen 流式输出建议一期不做
   (输出是单个 JSON 对象,流式增量不可直接渲染;二期用"原始流文本 + 完成后
   切结构化卡片"的低成本方案)。
4. 一致性:聊天流定位为**审计的投影视图**(视图含审计没有的"展开数据"),不是
   独立流。重连/刷新从 evolution.jsonl 重建;历史局按 `runs/index.jsonl` +
   evolution.jsonl 按 runId 分组合并;诊断明细类展开数据一期接受"未归档占位"。

## 2. Qwen 四类内容"在哪一步可被 UI 拿到"(重点核实)

- **playbook 全文**:`runAnalysisQueue` 成功分支 MarioLab:869 `playbook = r.playbook`。
  值此刻就在手上,直接 emit 即可;唯一陷阱是多个任务连续覆盖同一 `$state`,聊天窗
  必须在赋值**之前**把当轮文本快照进消息,否则历史气泡内容漂移。
- **补丁 from→to**:最终形态在 `pendingCandidate.patch`($state)与 propose 审计行,
  两者都可得。任务级 `accPatch` 的中间态只在内存(还写进了 `patchBySig` 供
  death-repeat 载荷),不建议展示中间态——run 级合并才是真正被试用的东西。
- **diagnosis 明细**:MarioLab:880 `diagBySig.set(...)` 是唯一去向。UI 无渲染、
  evolution.jsonl 无记录、runs/<runId>.json 无归档 → **当前唯一可获取时机就是
  ParseRefineResult 返回的那一瞬**,错过即永久丢失,历史局重建不可能。
- **insight 内容**:结构体在 `r.insight`,但立即被 `appendInsight` 折叠进滚动文档
  (近重复 Jaccard≥0.55 时只在旧行上追加 `‖确认@iter`,不产生新行)。聊天窗若要
  "本局学到一条经验"的独立气泡,必须在折叠前 emit 原始对象。
- 附:分析**输入侧**(死亡载荷 buildDeathPayload 的 ①-⑤ 段)不落盘;但因组装是
  纯函数、原料(report/session/sent)都存进了 runs/<runId>.json,输入可确定性重建;
  不可重建的只有 `lastDiagnosis/prevPatch` 上下文(依赖内存 diagBySig/patchBySig)。

## 3. 缺口与最小改动清单(只建议,不动手)

- **G1(MarioLab.svelte)**:新增 `chat = $state<ChatMsg[]>([])` 与 `emitChat(msg)`
  统一出口;在 audit() 成功分支之外,补四处 emit:局末局报、任务排队、诊断明细、
  insight 原始对象、playbook 快照。每处 ≤3 行,数据全在既有局部变量里。
- **G2(qwen.ts)**:`ParseRefineResult` 增加可选 `raw: string`(refineViaQwen 里把
  `content` 带出来),供聊天窗"查看原始输出"折叠块与调试;不影响任何现有调用方。
- **G3(evolution.ts,二期)**:`AuditEntry` v3 为 analyze ok 行增加可选
  `result?: { diagnosis: DeathDiagnosis[]; insight: LayaInsight | null }` 摘要字段
  (受 64KiB append 上限约束,摘要足够),使诊断/经验可对账、可重建;v1/v2 行
  白名单解析已兼容,不破坏旧文件。
- **G4(MarioLab.svelte)**:暴露熔断态(如 `breakerTripped = $state(false)`,在
  `breaker.fail()` 返回 tripped 时置位),聊天窗显示"连续 3 败已熔断,等待探活"。
- **G5(store.ts 或 Rust commands.rs,二期)**:`mario_state_list` 不列 runs/ 内容,
  但 runs/index.jsonl 已是完整索引,一期前端只读 index + 逐个 read 即可,**无需
  新 IPC**;仅当要按前缀检索归档时才加 `list_runs` 命令。
- **G6(MarioLab.svelte,顺手)**:persistRunSnapshot 写 index 行时 `tasksOk: 0`
  从不回填(分析发生在快照写之后);队列跑完后 append 一行修正或改为启动对账,
  否则"计划/成功分析数"对账永远显示 n/0(见 §5)。
- 明确**不需要**改:driver.ts(onDecision/SentRow/sessionSnapshot 已够,聊天窗
  不消费逐拍数据)、machine.ts(队列规则不变,聊天只是视图)、store.ts 一期不动。

## 4. 实时性方案(Svelte 5 runes)

### 4.1 接线:事件 → 消息数组,零轮询

```ts
type ChatMsg = {
  id: string;
  kind:
    'run' | 'queue' | 'phase' | 'diag' | 'insight' | 'playbook' | 'patch' | 'verdict' | 'status';
  ts: string;
  runId: string | null;
  text: string;
  data?: unknown;
};
let chat = $state<ChatMsg[]>([]);
const pushChat = (m: Omit<ChatMsg, 'id' | 'ts'>) =>
  (chat = [...chat.slice(-199), { ...m, id: crypto.randomUUID(), ts: new Date().toISOString() }]);
```

- 单一权威触发点:**每个数据更新的函数调用现场**,不设任何 setInterval/定时读盘:
  1. `genPostmortem()` 局末 → 局报 + 排队消息(tasks 数组在此处拿到);
  2. `audit()`(既有必经之路)→ 按 action/phase 映射 phase/patch/verdict 消息,
     一处改动覆盖 start/ok/fail/propose/commit/rollback/restore 全部;
  3. `runAnalysisQueue` 成功分支 → diag/insight/playbook 三类"展开消息"(emit 后
     再写 diagBySig/insights/playbook,保证快照不被覆盖);
  4. `driver.probe()` resolve、`analysisGate` 的 finally、breaker 翻转 → 状态条。
- `$state` 深响应,`{#each chat as m (m.id)}` keyed 渲染;自动滚动用 `$effect`
  监听 `chat.length`。上限滚动(如 200 条)防止长会话内存膨胀,持久事实在审计,
  UI 丢了可重建。
- 排队用的 `taskQueue/taskBacklog` 保持普通 let 即可(它们是内部调度状态);
  聊天窗只消费"入队/出队"这两个事件瞬间,不直接读队列数组,避免把非响应式状态
  暴露给模板。

### 4.2 Qwen 流式输出:一期不做,二期低成本做

- **一期不做**:①现在一次性返回约 9-13s,聊天流用"开始 → 计时徽标 → 结论分键
  卡片(playbook/补丁/诊断/经验)"三段式,信息密度已够;②输出是**单个 JSON 对象**,
  流式增量半截 JSON 不可直接渲染,要自写容错的部分解析,复杂度与收益不成比例;
  ③分析是后台队列(分析硬门保证不阻塞开局),用户注意力在游戏画面,打字机效果
  非刚需;④60s 超时与熔断逻辑都按"整次调用"建模,流式中断的失败语义要重定义。
- **二期做(低成本路径)**:本地 Qwen 走 OpenAI 兼容 `stream:true`,前端只做
  **原始文本累积展示**(不解析),完成后再整体 `parseRefine` 切结构化卡片;即
  "打字机显示 JSON 源文"的观感,零增量解析风险。仅当用户反馈"等 13s 无反馈太
  闷"时再上。另注意 enable_thinking 已关,流式首个 token 延迟应尚可。

## 5. 一致性:聊天流与审计的关系

### 5.1 定位:审计的投影视图,不是独立流

- 每条聊天消息必须能指回一条审计行(phase/key/latency/patch/score 字段齐全)或
  一条 runs/ 派生数据;聊天流自身**不落盘**。审计是唯一事实(evolution.jsonl 只
  追加),"宁可缺行不可崩"的解析纪律已经兜底。
- 例外是"展开消息"(诊断明细/insight 原文/playbook 快照):一期它们只活在内存
  聊天数组里,重启后对应气泡降级为审计行摘要("析 r#2 · 12.3s · 诊断 2 条
  [明细未归档]")。要消除降级,走 §3-G3 的审计 v3 摘要字段。

### 5.2 掉线/刷新后的补齐

- 聊天窗是内存 $state,webview 刷新即空。重建路径与现有 auditTail 同源但更全:
  `parseAuditLines(store.read(EVOLUTION_FILE))` 取**尾部 N 行**(不是现在的 10 条),
  经同一 `mapAuditToMsg` 投影回放,再按最新 evo.counters 对账显示"已析 x/计划 y"。
- 无新增协议:审计行自带的 `iter/runId/ts/action/phase/key` 足以恢复顺序与分组;
  分析中掉线(ok 行缺失)自然显示为"未完成",与幂等键"失败不占、backlog 重试"
  的既有语义一致。

### 5.3 历史局聊天重建

1. `runs/index.jsonl` 提供局序列(runId/won/ticks/tasksPlanned);
2. 对目标 runId:`store.read('runs/<runId>.json')` 得 report/session/sent/policy/design;
3. 过滤 evolution.jsonl 中 `e.runId === runId` 的全部行(analyze/propose/commit/
   rollback/restore;死亡级 key `runId#attempt` 天然按局分组),与局报按 ts 合并
   即成该局的完整聊天序列;
4. 对账检查:`analyze ok` 行数 vs `counters.qwen.deathAnalyses+runAnalyses` vs
   index 行 `tasksPlanned/tasksOk`(G6 修复前 tasksOk 恒 0,只能单向核对)。

- 已知不可重建项:诊断明细、每轮 playbook 快照、insight 原始对象(原因同 §2);
  Qwen 输入载荷可由 runs/ 原料重放 buildDeathPayload 确定性重建(调试场景够用)。

## 6. 开放问题

1. index 行 `tasksOk` 恒 0:是队列跑完后 append 修正行,还是改为启动时用审计
   重放对账回写?涉及 runs/index.jsonl 是否保持"只追加"语义。
2. 诊断/insight/playbook 快照的归档载体选型:审计 v3 摘要字段(§3-G3)vs 并入
   runs/<runId>.json 的 `analyses[]` 数组 vs 独立 `runs/<runId>.chat.jsonl`?
   三者在 1MiB 写上限、64KiB 追加上限下的取舍需实测。
3. Qwen 原始 `raw` 文本(G2)是否长期保留:调试价值大,但含死亡轨迹回显,存档
   有体积与隐私考量;只进内存聊天折叠块是否足够。
4. 聊天窗是否允许用户向 Qwen 追问(例如"为什么这个补丁被回滚")?一旦允许,
   它就不再是审计的纯视图,需要独立的输入通道与会话管理,超出本次数据链路范围。
5. evolution.jsonl 无限增长:重建读"尾部 N 行"的 N 取多少、是否需要轮转/压缩,
   与 docs/15 §9 数据留存策略合并决策。
6. 多任务合并提案(一局 3 死 = 3 次分析 = 1 个候选)在聊天窗的粒度:每任务一张
   诊断卡片 + 汇总一张补丁卡片,还是全部拍平?影响 ChatMsg.kind 的设计。
