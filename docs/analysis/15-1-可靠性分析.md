# docs/analysis/15-1 · §6「每死全量 Laya 数据分析 v3」可靠性分析

> 评审视角:可靠性与健全性。准则:自进化系统必须**健全、可靠、不断进化**——
> 单次分析可以降级,但**状态不能错、死因证据不能丢、失败必须可见**。
> 结论均经落地核实:docs/15 §6 草案 + docs/13 §1 / docs/14 + evolution.ts /
> qwen.ts / driver.ts / policy.ts / brain.ts / store.ts / src-tauri/mario/commands.rs /
> MarioLab.svelte / e2e/mario-loop.ts。

## 结论摘要

1. **「触发即标记」是现存 bug,v3 会放大它**:UI 在发起分析前就 `recordRun(..., analyzed=true)`(MarioLab.svelte L512),之后 `qwenRefineAfterRun` 失败也不回滚标记 → 该 run **永久失去分析机会**。v3 的 deathKey 幂等若沿用此写法,「每死必析」退化为「每死只有一次机会」。
2. **Qwen 调用没有超时**:`refineViaQwen` 无 AbortSignal;本地服务挂起 = UI `qwenRefining` 永久占锁、后续分析全被静默丢,e2e 主循环整局卡死。超时 + 重试上限 + 连续失败熔断是 v3 队列的硬前置。
3. **队列溢出 = 永久丢死亡**:deathKey 只在局末触发一次,溢出即永久丢失(没有任何补触发点)。cap 6 只能是「内存在途」上限,溢出必须落盘 backlog,不能丢。
4. **championScore 会被状态损坏清零**:`parseEvoState` 损坏即整体重置 → championScore=null → 下一候选按「无基线直接转正」跳过 K 局评估(evolution.ts L262)。基线必须可从 history/audit 重建,且「无基线直转」应收紧到 iteration=0。
5. **两套写入器、两种原子性**:UI 走 IPC 原子写(tmp+fsync+rename)✓;e2e `saveState` 是裸 `writeFileSync` ✗——撕裂 → 解析失败 → 全重置 → 撞上第 4 条。UI 与 e2e 还共享 `~/.qianxun_dev/mario`,跨进程并发写无任何仲裁。
6. **裁剪顺序必须反着定**:死因证据(③死前 12 拍 / ④异常行)是 v3 的核心增量;§8「超限裁剪顺序①→⑤」语义含糊且可能裁掉最该保的块。应「⑤→②→① 依次缩,③④⑥ 保底」,并附裁剪元数据。
7. **death 级诊断与 run 级补丁要显式缝合**:分析失败/跳过后,death-repeat 载荷里的「上次诊断+补丁」不能是空串,必须注入「上次分析失败(原因)」,否则 Qwen 在回答一个不存在前提的问题。
8. **3 死 = 3 份补丁提案会冲垮试用管线**:K=3 评估在途时新提案必须排队(只审计不入队),同 run 的 3 份 diagnosis 应合并为 1 个 patch,否则 pendingCandidate 相互覆盖、归因错乱。
9. **补丁落盘要做快照-rebase**:分析任务以入队时 champion 为基准,完成时 champion 可能已被用户设置或另一进程改写;必须对当前值重算 diff,无差异则 skip 并审计。
10. **失败必须一眼可见**:审计加 `analyze(ok|fail)` 行,counters.qwen 加 failed/timeout/badJson/queueHighWater;审计是唯一事实源,counters 必须可由其重放校验。

## 关键防护的具体设计(伪代码级)

### D1 AnalysisScheduler:串行、持久化 backlog、有界重试、熔断

```text
type Task = { key: deathKey|runKey, kind: 'death'|'win'|'plateau', sig?, attempts, payload }

enqueue(t):
  if 存在同 key pending: 合并(保留最新 payload, merged++) ; return
  if queue.length < 6: queue.push(t)                 // 内存在途上限
  else: state.pendingAnalyses.push(t)                 // 溢出落盘,不丢
runLoop():                                             // 局间串行槽;绝不阻塞仿真
  if breaker: return
  t = backlog 首个 ?? queue.shift()
  audit(analyze, 'start', t.key)
  try r = await refineViaQwen({ ...t.payload, signal: timeout(60s) })   // attempts≤2 内部重试 1 次
    ok:  analyzedKeys.push(t.key); counters.deathAnalyses++; audit(analyze,'ok',...)
    fail: t.attempts++; t.attempts<=2 ? 重新入队 : (audit(analyze,'fail',errClass); counters.failed++)
  连续失败 ≥3 → breaker=true(UI 红标;下一次探活成功自动复位)
```

### D2 幂等标记时序(修 R6/R8)

```text
// 错(现状):trigger.invoke 就 recordRun(analyzed=true)
// 对:
outcome = await scheduler.run(task)
analyzed = outcome.ok
recordRun(state, report, runId/deathKey, analyzed)      // 只有成功才占幂等键
persist 顺序:audit append → state.json 写(崩溃后由审计重放补齐)
启动恢复:state.pendingAnalyses 重新入队;analyzedKeys 与 audit analyze-ok 行对账,缺的补
```

### D3 state.json 一致性(修 R7/R8)

```text
saveState:一律 tmp+rename(e2e 与 UI 同纪律;UI 已由 Rust atomic::write 保证)
loadState 修复:
  if championScore==null && audit 存在 evaluate 行: championScore = 最后一条 evaluate.champion
  if championScore==null && iteration>0: flag requireBaseline=true(judgeCandidate 拒绝直转)
  counters = replay(audit) 对账,不一致以 audit 为准并告警
```

### D4 补丁快照-rebase(修 R11/R12)

```text
入队:task.base = { updatedAt: envelope.updatedAt, policy: champion }
完成:
  if current.updatedAt != task.base.updatedAt:        // champion 已被改(用户/另一进程)
    rebased = sanitize+limitPatch+applyCooldowns( 以 current 为基准重算 )
    if diffPatch(current, rebased) 为空: audit('propose-stale'); return
  否则按原提案走候选管线
写 policy.json 前再比对 updatedAt,不一致 → 放弃本次写并告警(防 R12)
```

### D5 载荷裁剪:确定性 + 证据保底(修 R10)

```text
预算按字符(24k chars ≈ 6k token),不用分词器 → 同输入必同输出
PROTECTED(只降密度,不归零):③死前12拍(最低8拍)/④异常行/⑥上次诊断+补丁/近3条insight
TRIMMABLE(依次裁):⑤其它attempt摘要 → ②轨迹采样(step=ceil(n/120),idx=k*step,保首8行+全部异常行) → ①digest压缩
每块附裁剪元数据 `(sampled 120/450)`;全部裁完仍超 → 任务标 overBudget-failed,不送脏载荷
```

### D6 观测性(修 R15 及一切「静默失败」)

```text
counters.qwen += { deathAnalyses, runAnalyses, failed, timeouts, badJson, overLength,
                   retries, merged, droppedByCap(应恒为0), queueHighWater, emptyInsight, avgLatencyMs }
audit action 扩 'analyze':{ phase:'start|ok|fail', key, errClass, latencyMs }
UI:队列面板常显「待 n · 在途 · 最近失败原因 · 熔断中」;e2e 汇总行加 分析 ok/fail/backlog
校验:启动与 --verify 时 counters == replay(evolution.jsonl)
```

## 开放问题

1. Qwen 实际 ctx 长度未测:③ 保 12 拍还是 8 拍由实测定,但 D5 的裁剪顺序不应依赖实测结果。
2. backlog 重试时机:局间槽先清 backlog 再收新任务(倾向),还是探活恢复即刻?前者实现简单、节奏可控。
3. 跨进程并发(R12):上文件锁成本高,是否直接文档化「UI 与 e2e 不得同时跑」+ updatedAt 比对兜底?需拍板。
4. 「无基线直转」(§8 已列为风险)建议收紧为仅 iteration=0 一次;与 §3 全自动化的组合风险需产品确认。
5. analyzedDeathKeys cap 200 FIFO 淘汰后,跨重启 backlog 的 key 幂等判定是否改以 audit 的 analyze-ok 行为准(建议是:cap 只管内存,持久判定看审计)。
6. UI 连续玩时「局与局之间」的串行槽不稳定:是否允许分析与下一局并行(补丁仍只在局界生效)?需确认不破坏不变量①。
