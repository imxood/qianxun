# 08 - 插件清单与自动恢复设计

> 状态：**已实现**（§9 切分落地；§11 三态 profile 为第二轮评审新增）
> 日期：2026-02
> 设计原则：**不过度设计**。不做 Journal 崩溃恢复、不做 receipt 证据链、
> 不做多注册源管理。只做「成功记录 → 清单随备份走 → 缺失可一键补装 → 单个失败不拖垮批量」，
> 以及「默认 profile → 已知良好快照 → 最小安全环境」的启动失败三级递进（§11）。

---

## 1. 目标与非目标

### 1.1 目标

| #   | 目标                   | 一句话验收                                                        |
| --- | ---------------------- | ----------------------------------------------------------------- |
| G1  | 安装成功的判定有依据   | pnpm 退出码 0 **且** 反向校验 node_modules 落盘版本一致，才叫成功 |
| G2  | 成功后记录到设置       | `settings.json` 新增 `plugins.pinned`，装上/卸下都同步维护        |
| G3  | 清单可自动补装         | 一个命令按清单逐个装，返回逐项结果                                |
| G4  | 单个失败不影响批量     | 第 3 个失败，第 4 个照样装；报告里列出谁失败了                    |
| G5  | 清单随导出/导入走      | 备份包天然携带（settings.json 已整包进出），还原后可一键补装      |
| G6  | 插件导致启动失败可自救 | 默认失败→快照恢复重试；快照也不行→最小安全环境兜底（§11）         |

### 1.2 非目标（明确不做，防止过度设计）

- ❌ **Journal 崩溃恢复**（变更前全量文件镜像 + 哈希校验 + 启动自动回滚）。
  理由：千寻的变更面只有两个文件（package.json + pnpm-lock.yaml），且 backup 还原
  本身已有 pre-restore 回滚包兜底。断电极端场景交给用户重装即可。
- ❌ **receipt 文件 / integrity 证据链**。清单只记 `name@version`，够定位、够重装。
- ❌ **多注册源管理**。沿用 `settings.mirrors.npmRegistry` 单一注册源。
- ❌ **启动时静默自动安装**。网络环境不可控，启动变慢且难排查；只提供
  「还原后提示」和「手动按钮」两个触发点。
- ❌ **启用/禁用（disabled）状态**。bundles 数组语义已够，禁用是另一个需求。
- ❌ **全屏恢复中心页面**。恢复入口内联在环境页失败态（§11.5），
  不新开全屏页面；千寻状态面小，用不着一个专门的中心。
- ❌ **启动失败自动归因到具体插件 / 自动卸载坏插件**。归因不可靠（可能是插件组合炸
  而非单个），猜错比不猜更糟；只做「隔离现场 + 保住可用状态」（§11.1）。

## 2. 数据形状

### 2.1 settings.json 新增字段

```jsonc
{
  // ...现有字段不变...
  "plugins": {
    "pinned": [
      { "name": "dsh-plugin-foo", "version": "1.2.3" },
      { "name": "@vendor/dsh-plugin-bar", "version": "0.4.0" },
    ],
  },
}
```

Rust 侧（`src-tauri/src/settings.rs`）：

```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(default, rename_all = "camelCase")]
pub struct PinnedPlugin {
    pub name: String,     // npm 包名，非 @deepseek-ai/ 前缀（内核包不入清单）
    pub version: String,  // 安装时的精确版本（来自 registry detail 复核）
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(default, rename_all = "camelCase")]
pub struct PluginsSettings {
    pub pinned: Vec<PinnedPlugin>,
}

impl Default for PluginsSettings {
    fn default() -> Self { Self { pinned: Vec::new() } }
}
```

- `Settings` 结构体加 `pub plugins: PluginsSettings` 字段，`#[serde(default)]` 保证
  旧 settings.json 无此字段时零迁移。
- **schema_version 不动**：字段走 serde default，老文件可读；新文件被老版本读到会
  因 `#[serde(deny_unknown_fields)]` 未启用而忽略未知字段（现状即如此，已验证 settings.rs
  没有开 deny）。
- **去重与排序**：`pinned` 按 `name` 小写排序、写入前去重，保持文件 diff 干净。

### 2.2 为什么记在 settings 而不是 profile 旁的独立文件

- settings.json **已经是备份包的成员**（backup/commands.rs `SETTINGS_ENTRY`），清单随
  包走是免费的，G5 自动成立。
- profile 的 package.json 由 pnpm 管理，往里塞自定义字段等于和 pnpm 抢文件。
- 独立清单文件需要额外进备份收集规则，多一处漏同步的风险。

## 3. 安装成功的判定（G1）

现状缺口：`market/mod.rs market_install` 在 `run_pnpm` 成功 + `mutate_bundles` 成功后
直接报成功，**没有反向校验** node_modules。

新增轻量校验函数（`market/mod.rs`）：

```rust
/// 反向校验：node_modules/<name>/package.json 存在且 version === 期望版本。
fn deployed_version(profile: &Path, name: &str) -> Option<String> {
    let manifest_path = profile.join("node_modules").join(name).join("package.json");
    let body = std::fs::read_to_string(manifest_path).ok()?;
    let value: serde_json::Value = serde_json::from_str(&body).ok()?;
    value.get("version")?.as_str().map(str::to_owned)
}
```

`market_install` 成功路径改为：

```
pnpm add 成功
→ mutate_bundles 成功
→ deployed_version(profile, &name) == Some(version)   // 新增：反向校验
   ├─ 一致   → 写 settings.pinned + supervisor 日志「已记入插件清单」→ 返回 Ok
   └─ 不一致 → 返回 Err("安装完成但落盘校验失败：期望 x.y.z，实际 …")
              （此时 bundles 已含该包——保留现状不动，让用户用卸载清理；
               不做自动回滚，见 §1.2）
```

`market_remove` 成功路径对称：`mutate_bundles` + `pnpm remove` 都成功后，
从 `settings.pinned` 移除该项。

**为什么清单只记 name@version、不做 receipt**：receipt 的价值在 provenance（来源审计、
integrity 防篡改）。千寻是单用户桌面工具，registry 复核（现有 `registry::validate`）
已经挡了弃用/不兼容，清单只需回答「曾经装过什么版本」——name@version 足够。

## 4. 自动补装（G3 + G4）

### 4.1 新命令 `market_sync_pinned`

```rust
/// 逐项结果：前端逐行渲染。
#[derive(Serialize)]
#[serde(rename_all = "camelCase")]
pub struct SyncItemResult {
    pub name: String,
    pub ok: bool,
    pub skipped: bool,   // 已在清单且已落盘 → 跳过（不算失败）
    pub detail: String,  // 成功：版本；失败：错误摘要
}

#[tauri::command]
pub async fn market_sync_pinned(app: AppHandle) -> Result<Vec<SyncItemResult>> { ... }
```

流程（顺序执行，**不并发**——pnpm 对同一 profile 并发写锁会互相踩）：

```
读 settings.pinned
→ 逐项：
    1. deployed_version(profile, name) == Some(pinned.version)？
       → 是：skipped = true，进下一项（幂等：重复点同步不重装）
    2. registry::detail + validate（复用 market_install 现有门槛）
    3. run_pnpm add name@version
    4. mutate_bundles push
    5. 反向校验
→ 单项任何一步失败：记录 { ok: false, detail: 错误 }，**continue 下一项**（G4）
→ 全部跑完返回 Vec<SyncItemResult>
```

- 返回值 `Result<Vec<SyncItemResult>>`：外层 Err 只在「profile 不存在」「读设置失败」
  这类**整体性**失败时用；单插件失败**不**冒泡为 Err，而是体现在元素里。
- 每项的 pnpm 输出照旧进 supervisor 日志，前端日志面可回看。
- 超时沿用 `run_pnpm` 现有 IDLE/TOTAL_TIMEOUT，不需要新机制。

### 4.2 触发点（两个，刻意不加第三个）

| 触发点         | 入口                                | 说明                                             |
| -------------- | ----------------------------------- | ------------------------------------------------ |
| 备份还原完成后 | 还原结果条上的「补装插件（N）」按钮 | 还原报告（§5）里带 pinned 缺失计数，N > 0 才显示 |
| 插件页手动     | 已安装 tab 顶部「同步清单」按钮     | 随时可点，幂等；换机器/重装系统后手动恢复用      |

**不做启动自动同步**（§1.2）：启动路径保持零网络依赖。

## 5. 导出 / 导入（G5）

### 5.1 导出：零改动

settings.json 已在备份包里，`plugins.pinned` 自动随包。manifest 新增一个展示字段：

```rust
// BackupManifest 加：
/// 插件清单条数（settings.plugins.pinned.len()，读取失败计 0）。
plugin_count: usize,
```

前端 `backup_inspect` 摘要显示「含 N 个插件记录」。仅展示，不影响兼容
（老包读出来是 0）。

### 5.2 导入：还原报告带缺失计数，不自动执行

`BackupRestoreReport` 加字段：

```rust
/// 还原的清单里，当前 profile 未落盘的插件个数（需要补装的量）。
pub plugins_missing: usize,
```

计算方式：还原完成后读新 settings 的 `pinned` × `deployed_version()` 对账。

- `plugins_missing == 0`：无事发生。
- `> 0`：前端结果条提示「清单中有 N 个插件未随包还原（node_modules 未覆盖或版本
  不符），点击补装」→ 调 `market_sync_pinned`。

**为什么 node_modules 在备份包里还可能缺失**：dsh-home 整包备份确实含 node_modules，
但存在两个洞——a) 用户导出后插件在源机器升级了，版本与 pinned 记录不一致；
b) 只导入设置类轻量包的未来形态。补装逻辑对两个洞都生效，且 skipped 幂等保证
「其实没缺」时是空操作。

### 5.3 schema_version

不 bump。settings.json 是整文件进出，未引入新包内条目；manifest 加的是纯展示字段，
旧版千寻读新包会忽略未知字段（serde 默认），旧包读新代码走 `#[serde(default)]`。

## 7. 边界与守护

| 场景                                          | 行为                                                                                                                                                                                               |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pinned 里的包后来下架                         | registry detail 404 → 该项 ok=false「registry 无此版本」，继续下一项                                                                                                                               |
| 内核包（@deepseek-ai/）混入 pinned            | 记录时已挡（install/remove 都过 BUILTIN_PREFIX 检查）；sync 时再挡一层，跳过并报「内核组件不走清单」                                                                                               |
| pinned 条目格式非法（手工改坏 settings）      | sync 跳过该项报「清单条目无效」，不整体失败                                                                                                                                                        |
| 同步进行中用户又点单个安装                    | 后端 busy 位（**本设计新增一个 AtomicBool**）：只挡 market 域并发，不做跨窗队列                                                                                                                    |
| settings 写失败                               | install/remove 成功但清单写失败 → 返回 Ok 但 supervisor 记 warn「清单未更新」。**不因清单失败回滚安装**——插件本体已可用，清单是增强信息                                                            |
| 版本漂移（node_modules 版本 ≠ pinned）        | sync 视为缺失，按 pinned 版本重装（pnpm add 精确版本天然收敛）                                                                                                                                     |
| **安装成功后 DSH 启动失败**                   | pinned **保留**（安装事实成立）；走 §11 三级递进：快照恢复重试 → 安全模式兜底。快照恢复后 bundles 已不含坏插件，且 `deployed_version` 幂等跳过保证 sync **不会自动把坏插件装回来**（防 boot loop） |
| 快照恢复救不了的故障（node_modules 本身损坏） | manifest 恢复后依然启动失败 → 停在明确失败态，用户手动点「安全模式」（§11 第三层存在的意义）                                                                                                       |

## 10. 设计取舍速览

| 机制                                       | 取舍                              | 理由                                                    |
| ------------------------------------------ | --------------------------------- | ------------------------------------------------------- |
| Journal 式崩溃恢复（全量文件镜像 + 哈希）  | ❌ 不做                           | 变更面小，backup 已有 pre-restore 回滚；成本收益不匹配  |
| receipt（integrity/provenance/收据 ID）    | ❌ 不做，settings 记 name@version | 单用户桌面工具无审计需求；registry 复核已挡篡改入口     |
| 变更事务化编排（失败自动回滚全部步骤）     | ⚠️ 简化版：成功路径加一步反向校验 | 校验失败即报错，让用户卸载重装；不做自动回滚            |
| 全屏恢复中心 UI                            | ❌ 不做，内联按钮 + 逐行结果      | 恢复入口只有失败态一个场景，内联够用                    |
| 重试漂移检测（generation/依赖图比对）      | ❌ 不做                           | 没有重试队列就没有漂移；sync 每次都是新鲜 registry 复核 |
| 多注册源管理                               | ❌ 不做                           | 沿用 mirrors.npmRegistry 单源（用户明确要求）           |
| 子进程防挂死                               | ✅ 已有等价物（run_pnpm 超时）    | 无需新做                                                |
| 三态 profile（候选 / 已知良好 / 安全环境） | ✅ 采纳，适配为 §11 三级递进      | 启动失败自救的核心；见 §11.3 关键规则                   |

## 11. 三态 profile 与启动失败恢复（第二轮评审新增）

> 背景：用户多次遭遇「安装插件成功 → DSH 重启失败 → 卡死循环，无逃生通道」。
> 千寻只有一个 DEFAULT profile，没有「回退到另一个 profile」的选项——
> 这正是踩坑无处可逃的根因。本节把三态思想降维到单 profile。

### 11.1 核心语义：三个状态，各司其职

| 状态                 | 存什么                                           | 回答什么问题                    |
| -------------------- | ------------------------------------------------ | ------------------------------- |
| **默认 profile**     | 真实 `package.json` + node_modules（现状，不变） | 现在装了什么                    |
| **known-good 快照**  | 上次成功启动时的 manifest 副本（几 KB 文件）     | 上次能跑的时候装载的是什么      |
| **最小安全 profile** | 独立目录 + 最小 bundles 栈（独立 node_modules）  | 连快照都救不回来时的 DSH 可用性 |

三者互不干扰：**pinned 记「想装什么」，快照记「上次能跑什么」，安全模式保证
「永远有一个能进的地方」**。

### 11.2 状态机

```
                     ┌─ 启动成功 ──→ 更新快照（known-good = 当前 manifest，原子写）
默认 profile ────────┤
（bundles + 插件）    └─ 启动失败 ──→ ① 自动：用快照恢复 manifest，重试默认 profile
                                      ├─ 成功 → supervisor 提示「已回退到已知良好配置；
                                      │        坏插件仍安装但未加载」（pinned 不动）
                                      └─ 失败 → 停在明确失败态，显示「安全模式」按钮
                                                 ↓（仅用户手动点击）
最小安全 profile ──── 独立目录，最小 bundles 栈
（只读逃生舱）        └─ 启动成功：不写快照、不改默认 profile、不改 pinned
```

### 11.3 关键规则（评审已确认）

1. **快照只在默认 profile 启动成功时更新**（DSH ready 检测点挂钩子）。
   失败路径、安全模式路径一律不写。
2. **安全模式启动成功永不更新快照**——它健康是必然的，不构成新信息；更新反而会
   把「用户真实环境的快照」冲掉，逃生舱用一次就丢了恢复能力。安全模式是**纯只读通道**。
3. **快照恢复后不会自动重装坏插件（防 boot loop）**：恢复后 bundles 已不含坏插件，
   但 node_modules 还在 → `market_sync_pinned` 的 `deployed_version` 幂等判定命中
   skipped，不会把坏插件自动装回来。想要它必须先卸载再装，用户的显式动作。
4. **安全模式内冻结插件变更**：`market_install / market_remove / market_sync_pinned`
   在安全 profile 激活时直接拒绝（「逃生舱内不进行插件变更，请先恢复默认 profile」）。
5. **安全模式是手动按钮，不做自动升级**。自动链只走一步（默认失败 → 快照恢复重试）。

### 11.4 实现要点

**known-good 快照**

- 位置：`<dsh-home>/profiles/default/package.json.good`——放在 profile 目录内，
  backup 整包已含 dsh-home，**快照随备份走是免费的**（放数据根反而要改备份收集规则）。
- 写入：DSH 启动成功钩子处，读当前 `package.json` → 原子写 `.good`（临时名 + rename）。
- 恢复：新命令 `harness_recover_known_good`——校验 `.good` 存在且为合法 JSON →
  覆盖回 `package.json` → 返回恢复摘要（哪些插件从 bundles 里被移除）。
  `.good` 不存在 → 明确报错，不产生半写状态。

**最小安全 profile**

- 目录：`<dsh-home>/profiles/qianxun-safe-mode/`，固定名 + 所有权标记文件
  `.qianxun-safe-mode`（标记内容 `qianxun-safe-mode-v1\n`）。同名用户 profile 无标记
  → 拒绝复用、绝不吞并（防误伤用户数据）。
- 内容：最小 bundles 栈——仅 DSH 运行必需的内核包，无任何用户插件，独立 node_modules。
- **预热**：首次 DSH 安装成功后后台静默构建（装一次最小栈），此后每次启动成功钩子
  顺带校验其存在。逃生舱不该有等待——真正需要它时若还要现场下载安装就失去意义。
- 启动命令 `harness_safe_mode_start`：停当前进程 → prepare（校验标记 + 复位为最小栈）
  → 以安全 profile 启动。**用户默认 profile 的文件一个字节不动**。

### 11.5 前端入口

| 位置                                      | 元素                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------- |
| 环境页 DSH 启动失败态                     | 「恢复到上次能启动的配置」按钮（快照存在才显示）+ 失败原因 + 恢复摘要 |
| 环境页 DSH 启动失败态（快照恢复也失败时） | 「安全模式启动」按钮                                                  |
| 环境页运行态（安全模式激活时）            | 徽标「安全模式中」+ 「返回默认 profile」按钮（就是一次普通启动）      |
| 插件页（安全模式激活时）                  | 安装/卸载/同步按钮置灰 + 冻结说明                                     |

不做全屏恢复中心：千寻的恢复入口只有失败态一个场景，内联按钮够用。

### 11.6 边界诚实声明

快照恢复救不了 **node_modules 本身损坏**（磁盘问题、杀毒误删、pnpm 半写被断电）。
这种情况 manifest 恢复后依然启动失败，才会走到安全模式按钮——这正是第三层存在的
意义，三层刚好覆盖递进的三种故障深度：

1. 插件/manifest 层故障（最常见，用户多次遭遇的）→ 快照恢复；
2. 快照也失效/manifest 之外的状态损坏 → 安全模式（DSH 仍可用，用户可读日志、卸载插件）；
3. 安全 profile 也建不起来（磁盘/网络彻底坏）→ 明确报错，超出软件自救范围。
