# 11 · Laya 马里奥实验室:实时平台跳跃的 System 1 控制设计

> 目标:在千寻「游戏」页新增 **超级马里奥 1-1(致敬复刻)**,人工可玩 + Laya 驱动。
> 这是 Laya 从**回合制**(俄罗斯方块)走向**实时控制**的第二块试金石——
> 一旦 SENSE→DECIDE→ACT + 置信度门控在实时域成立,同一套运行时就能外推到
> RPA / 桌面自动化 / 监控响应等真实领域。

---

## 1. 为什么马里奥对 Laya 议程重要

| 维度     | 俄罗斯方块(已落地)     | 马里奥 1-1(本设计)              | 对现实域的意义           |
| -------- | ---------------------- | ------------------------------- | ------------------------ |
| 决策节奏 | 回合制,一步一决策      | 60fps 实时,Laya 只有 2~7Hz      | **时间尺度压缩**是核心题 |
| 状态空间 | 10×20 棋盘,全信息      | 滚动世界 × 物理 × 运动敌人      | 部分可观测、流式感知     |
| 动作语义 | 离散且幂等(移一格)     | 连续输入(方向/跳跃有 hold 时长) | 输入量子化 → 宏动作      |
| System 2 | Dellacherie 枚举 0.2ms | 路径规划器(跳距可达表 + BFS)    | 规划器兜底保障任务必达   |
| 失败代价 | 一步次优,可挽回        | 掉坑/撞敌 = 死亡重来            | 风险门控语义真实可见     |

核心研究问题(实验都在这台"仪器"上做):

- **RQ1** Laya 的 choice 原语能否胜任实时控制?(pure 模式生存距离分布)
- **RQ2** 规划目标写入 state(reflex)比裸感知(pure)提升多少?
- **RQ3** 哪种状态编码单位 token 信号最强?(高度剖面 vs 位图 vs 实体清单,可消融)
- **RQ4** 时间域的 RE-SENSE(起跳前一刻再感知)是否比俄罗斯方块的静态再感知更有价值?
- **RQ5** 自动驾驶 + 人玩回放产生的 `(state, action)` JSONL 能否蒸馏出游戏域 Laya(呼应 docs/10 §5)?

### 1.1 服务启动约定(release 启动,游戏页只读)

laya-server 与 qwen-server 是**用户在 release 版「环境」页主动启动**的本地服务
(实测环境:`:10230` laya-rl-agent、`:17230` Qwen3.5-9B-Q6_K):

- 游戏(GamesPage/MarioLab)对两个服务**只探测、不启动**:HTTP 探活
  (`:10230/health`、`:17230/health`)+ 只读状态 pill;**debug 构建下绝不调用
  `laya_start` / `qwen_start`**——侧车进程归 release 应用管理,debug 侧重复
  spawn 会撞端口且进程所有权混乱。
- 服务未启动时:Laya/双脑相关模式入口置灰并提示「请在 release 版 · 环境页启动
  laya-server / qwen-server」;human 与 autopilot(规划器)不依赖服务,照常可玩。

## 2. 总体架构

```
GamesPage(注册表加一行)
  └─ Laya Jump · 超级马里奥 1-1(MarioLab.svelte)
       ├─ world1-1.ts   关卡数据:ASCII 瓦片图 + 实体出生点 + 物理常量(纯数据)
       ├─ engine.ts     确定性引擎:step(state, input) 纯函数,固定步长 60Hz,可单测
       ├─ renderer.ts   Canvas 2D:关卡离屏缓存 + 实体层 + Laya 叠加层
       ├─ planner.ts    System 2:路面图 BFS + 跳跃可达表 → waypoints + 候选动作约束
       ├─ brain.ts      Laya 决策端:state 编码 + questions + 置信度门控三分支
       ├─ driver.ts     循环编排:决策定时器、动作量子应用、过期丢弃(代次守卫)
       └─ MarioLab.svelte  剧场式 UI:顶栏 + 舞台 + 遥测条 + 浮层面板(§7)
```

与 Tetris 的同构与差异:

- **同构**:brain 的 `{state, questions}` → `/predict` 契约、EXECUTE/RE_SENSE/ESCALATE
  三分支、reflex/pure/solver(此处叫 autopilot)/human 四驱动模式、session JSONL 落盘——
  全部沿用,UX 与心智模型一致。
- **差异①**:引擎状态**不进 Svelte 响应式**。Tetris 回合制,`$effect` 重绘无压力;
  马里奥 60fps,引擎用普通可变对象 + rAF 绘制,HUD 以 10Hz 快照进 `$state`。
- **差异②**:Laya 决策与仿真**异步解耦**,决策结果作为"动作量子"在下一个 tick 边界生效,
  过期决策按代次丢弃(继承 Tetris pieceGen 教训,推广为 attempt+pose 守卫)。

## 3. 引擎设计(engine.ts + world1-1.ts)

### 3.1 确定性优先

- 固定步长 `TICK = 1000/60`,rAF 累加器驱动,每帧最多补 5 步(防死亡螺旋);
  速度滑杆(0.5×~3×)只改累加器消费速率,不改物理。
- `step(state, input): Event[]` 纯函数:同输入序列必得同状态哈希(vitest 锁定)。
  确定性 = 可单测 + 可回放 + 可批量生成蒸馏数据,是 RQ5 的前提。
- 随机源(敌人行为无随机,砖块出币固定)——v1 全关确定性,种子系统留待 Phase 2。

### 3.2 关卡数据:ASCII 即关卡

```ts
// world1-1.ts(节选示意)
export const LEVEL_1_1 = `
......................................................................
........?b................b?b?b..............................b?b......
......................................................................
..X................=======.................XX====XX..........===..F..
..X.....o?o.......==......==....o.....................o....==.....P..
XX....XXXX.......==........==.......X==X.........===.......==...####.
`; // X=地面 #=台阶 =砖 ?=问号 o=金币 F=旗杆 P=管道, 敌人/出生点单独表
```

- 瓦片 16px,1-1 全长约 220 列(3392×240px 世界);相机只进不退(SMB 原作规则,
  顺带把规划器问题简化成 DAG)。
- v1 实体集:Goomba(直线行走、可踩)、砖块/问号块(顶出金币)、管道、坑、旗杆。
  **明确砍掉**:蘑菇变大、Koopa 龟壳、地下房、Warp——小马里奥碰敌即死重生,
  碰撞状态机减半,死亡遥测反而更纯净(见 §9 里程碑)。

### 3.3 物理(v1 简化 SMB 手感,常量集中在 world 文件)

- 水平:加速/摩擦/走跑两挡(run 键);垂直:重力 + 起跳初速,长按跳更高
  (松开或下落时截断上升)→ 天然的变高跳。
- 碰撞:AABB 对瓦片网格,先水平后垂直分轴解算;实体间只做
  Mario×敌人(踩踏判定:下落中且脚在敌上半部)、Mario×金币、Mario×旗杆。
- 跳跃可达表:由物理常量推导 `MAX_JUMP_H`(格)、`RUN_JUMP_D`(格)、
  `WALK_JUMP_D`(格),单测锁定;planner 与 UI 提示共用同一张表——
  保证"规划器认为能跳的,引擎一定跳得过"。

## 4. 时间尺度:动作量子(本设计的关键决策)

Laya 单次 predict 约 26ms(短 state)~~300ms(长文本),决策频率 2~~7Hz;
马里奥是 60fps。**不让 Laya 逐帧按键,而是让它下达"输入指令",由 driver 以宏方式持有**:

```
Laya 决策(每 150~500ms)          driver(每 tick)
─────────────────────────         ────────────────────────────────
choice: "jump_run_right"   ───▶   Input{right:1, run:1, jump:1}
                                  ……持续持有,直到下一次决策替换……
choice: "right"(松跳)      ───▶   Input{right:1} → 跳跃被截断 = 短跳
```

- **跳高由下一次决策隐式控制**:长按时长 = 决策间隔,离散选择因此获得连续表达力;
  无需为 Laya 建模"按多少帧"。
- driver 保证两次跳跃之间至少插入 100ms 无输入窗(SMB 不允许空中二段跳)。
- 过期守卫:决策携带 `(attempt, snapshotPoseHash)`,应用时马里奥已死亡/重生/
  位姿漂移 > 阈值 → 丢弃并记 `stale` 日志(Tetris gen 教训的推广)。
- v1 动作集(9 个,语义即输入向量):

| 动作                             | Input 向量  | 典型用途        |
| -------------------------------- | ----------- | --------------- |
| `idle`                           | 全空        | 观望/等敌人走近 |
| `left`/`right`                   | 单方向      | 微调站位        |
| `run_left`/`run_right`           | 方向+run    | 赶路/长跳助跑   |
| `jump`                           | 原地跳      | 顶砖/原地越敌   |
| `jump_left`/`jump_right`         | 方向+跳     | 短距越坑/踩敌   |
| `jump_run_left`/`jump_run_right` | 方向+run+跳 | 越宽坑、跨管道  |

**v2(预备案,不进 v1)**:技能层宏(`walk_to(x)`、`clear_gap(gap)`),
Laya 选技能、执行器展开成帧输入——当 v1 实测"hold 语义跳不准坑"时启用。

## 5. System 2:路径规划器(planner.ts)

马里奥没有 Dellacherie 式 0.2ms 枚举求解器,但静态关卡 + 可预测敌人让规划可行:

1. **路面图**:从瓦片图抽取可站表面(GroundSpan),建边:
   `walk`(同面)、`fall`(面缘跌落)、`jump`(跃距 ≤ RUN_JUMP_D 且助跑足够,
   或上跳 ≤ MAX_JUMP_H)。相机不回退 ⇒ 图是 DAG,一次性正向 BFS 即得全关路途。
2. **waypoints**:Mario 所在面向前,输出有序子目标
   `{type: 'walk'|'jump_gap'|'stomp'|'avoid'|'climb', targetX, gapWidth?}`。
3. **候选动作约束**(reflex 模式核心,直接复用 Tetris 约束解码经验):
   每 tick 由当前子目标生成 2~3 个"朝目标合法"的动作进 criteria。
   例:接近 w=2 的坑且助跑达标 → `[jump_run_right, jump_right]`;
   敌人在前方 5 格 → `[run_right, jump_right, idle]`。
   未蒸馏 Laya 在 9 动作全集上接近噪声(Tetris 实测教训),约束后"选哪个都不会变坏"。
4. **ESCALATE 语义**:conf 低于阈值 → planner 直接接管**一个子目标**的安全执行
   (不是俄罗斯方块的"瞬移放置",而是自动输入一个跳跃/绕行机动)。
   保证演示永远成立,门控语义可见:"Laya 不自信的一步交给规划器"。
5. **正确性验收**:autopilot(planner-only,不经 Laya)必须 10/10 通关 1-1——
   这是 System 2 的出厂标准,也是给 Laya 的"教师轨迹"。

## 6. SENSE:状态编码(brain.ts)

目标:**每步 state ≤ 300 token**,贴着 26ms 短文本档而不是 280ms 长文本档。
编码模板带版本号(`encoding=v1-*`),JSONL 里可分组对比(服务 RQ3 消融)。

```
progress : x=1234/3392 36%  coins=7  time=284  life=3  attempt=2
mario    : vx=+1.5 vy=0 on_ground=1 pose=run
profile16: 0 0 0 3 3 0 0 2 0 0 0 0 4 4 0 0   ← 前方16列首次实心高度(坑=0)
threats  : gap dx=3 w=2 | goomba dx=5 dir=toward | pipe dx=9 h=2
subgoal  : jump_gap x=57 w=2 (reflex 才有;pure 时为 none)
```

- `profile16`(高度剖面)是默认编码 `v1-profile`:16 个数字概括坑/管道/台阶,
  对小模型比 16×12 位图更友好;`v1-bitmap`、`v1-both` 作为消融开关存于配置。
- 敌人威胁用**命名实体清单**而非像素:dx、方向、是否可踩窗口,文本化直接给结论线索。
- questions(默认单题控延迟,Tetris 实测教训):

```jsonc
{
  "action": {
    "type": "choice",
    "instructions": "Mario reflex step…",
    "criteria": { "jump_run_right": "…", "jump_right": "…" },
  },
  "threat": { "type": "score", "instructions": "rate danger 0-10", "criteria": ["0", "5", "10"] }, // 可选第二题,默认关闭,实测开关
}
```

- 门控:沿用三分支,阈值默认 0.16/0.12(与 Tetris 同款起点),**必须 M5 实测重校**
  并保持 UI 滑杆可调。RE-SENSE 在时间域的新语义: commitments(已起跳/贴近坑缘)时
  中置信 → 立即再感知一次(时序敏感),其余场景沿用防抖上限 2 次。
- 健康可视:brain 暴露最近一次请求的原始 JSON,UI 一键展开"STATE 预览"——
  所见(Laya 眼中)即所玩,调试与信任都靠它。

## 7. UI / 交互设计:剧场式舞台(内容为王)

> 设计裁定:**不沿用 Tetris 三栏布局**。游戏舞台占满内容区,遥测全部**降维**为
> 「单行状态 + 点击弹出浮层」。精致来自克制:发丝线、留白、等宽数字、
> 一次性的微动效——而不是堆砌面板。

### 7.1 布局:三明治结构,舞台吃掉一切

```
┌──────────────────────────────────────────────────────────────────────┐
│ 顶栏 40px   ←  Laya Jump · 1-1    人玩|反射|纯反射|自驾   ▶⏸↺ ⚙ ●● │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│                                                                      │
│                    舞 台 STAGE(占满全部剩余高度)                    │
│                                                                      │
│        画布铺满舞台:宽度优先铺满,整数倍像素缩放                   │
│        游戏 HUD(分数/金币/时间/命)→ 画进 canvas,像素字体        │
│        Laya 叠加 → 画进 canvas:品红目标旗 / 决策涟漪 / 输入芯片     │
│        Qwen 气泡 → DOM 浮层:舞台左上角,3s 淡出                     │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│ ▔ 关卡进度条 3px(贴舞台下缘:马里奥●/死亡×/waypoint∘/旗杆▮)      │
├──────────────────────────────────────────────────────────────────────┤
│ 遥测条 44px  ⌁L  jump_run_right · 58% · EXEC · 240ms      [详情 ▸] │
│              ✦Q  risk 0.30→0.55 · "走上层绕坑" · 0.9s     [详情 ▸]  │
└──────────────────────────────────────────────────────────────────────┘
```

- 1080p 视口下 chrome 总高 ≈ 90px(顶栏 40 + 进度 3 + 遥测 44 + 发丝线),
  **舞台可用面积 ≈ 92%**——第一眼看到的是马里奥,不是面板。
- **画布铺满舞台全宽全高(用户裁定)**:不做 16:9 letterbox。垂直方向锁定
  15 瓦世界高度,水平可视瓦数随宽高比自适应(16:9≈24 瓦,更宽窗口看得更远);
  相机以马里奥为锚点,整数倍像素缩放防走样。可视瓦数记入 manifest 指纹
  (对比实验要求同视口,docs/12 §7)。
- 常驻 chrome 只有两条细带,遵循 8px 栅格与发丝线分隔(`border-line`)。

### 7.2 三个浮层面板(点击才出现,玻璃拟态)

| 面板      | 入口            | 内容                                                                          |
| --------- | --------------- | ----------------------------------------------------------------------------- |
| LAYA 决策 | 遥测条 L 段 [▸] | 9 动作概率条、置信度仪表、EXEC/RE/ESC 统计、决策日志流、原始 state JSON(折叠) |
| QWEN 监督 | 遥测条 Q 段 [▸] | rationale 全文、旋钮 before→after 历史、触发与延迟、快/慢档开关、监督者总开关 |
| 参数设置  | 顶栏 ⚙          | 速度 0.5~3×、决策间隔、门控阈值滑杆(改即生效,applyTimers 模式)                |

- 浮层 = `bg-surface/95 + backdrop-blur + border-line + shadow-xl + rounded-xl`,
  锚定触发点下方;**单开互斥**,`Esc`/点击外部关闭;进入 160ms(淡入+4px 上移),
  退出 120ms(退出更快);浮层内控件保留可见焦点环。
- 设置收进浮层后,常驻界面没有任何滑杆——舞台视觉零干扰。

### 7.3 舞台内部(游戏自洽,HUD 不是 DOM)

- **游戏内 HUD 画进 canvas**(像素字体、8px 内边距):分数/金币/时间/命,
  随暂停/死亡一起淡出——它是游戏的一部分,不是仪表盘控件。
- **Laya 叠加画进 canvas**:品红目标旗标(虚线)、决策涟漪(新决策到达时
  一次脉冲;`prefers-reduced-motion` 降级为静态描边)、输入量子芯片
  (舞台右上角小徽章,显示当前被持有的输入,如 `→⇧A`)。
- **Qwen 气泡**:舞台左上 DOM 浮层(sky 描边玻璃底),一句话 rationale,
  3s 淡出,同时最多 1 条。
- **死亡/通关卡片**:舞台中央玻璃浮层——死因归因(pit/goomba/time)、maxX、
  attempt 数、「再来一次 ⏎」。它同时是实验数据确认框,不是 game over 装饰。
- **关卡进度条**:3px 贴舞台下缘;悬停分段 tooltip(第几坑/敌群)。
  死亡×打点常驻——诚实的失败遥测。

### 7.4 视觉规范(OLED 剧场黑 × 千寻令牌)

| 维度   | 规范                                                                                          |
| ------ | --------------------------------------------------------------------------------------------- |
| 背景   | 舞台区真黑(`#0b0b10`,OLED 剧场感);chrome 沿用 `bg-surface`                                    |
| 线条   | 只用 1px 发丝线;层级靠留白与明度差,不靠粗边框                                                 |
| 字体   | 微标签 `text-[10px] uppercase tracking-[0.08em] text-muted`;数字一律 `font-mono tabular-nums` |
| 语义色 | Laya=emerald(执行)+magenta(目标);Qwen=sky;门控 EXEC/RE/ESC=emerald/amber/red(沿用既有语义)    |
| 图标   | 全 SVG(lucide 线性,16px/1.5px 描边);**禁用 emoji 与字符图标**(▶⏸↺ 一律不用)                   |
| 动效   | 仅一次性微动效(门控徽章 pulse 180ms、进度平滑插值);`prefers-reduced-motion` 全部降级静态      |
| 对比   | chrome 文字 ≥4.5:1;遥测摘要用 `text-muted`,关键数值用前景色                                   |
| 焦点   | 所有可点元素 `focus-visible` 环;浮层内焦点圈闭(Trap),关闭后焦点归还触发点                     |

### 7.5 交互细节

- **键盘**:←→ 移动,Z/空格 跳,Shift 跑,P 暂停,⏎ 死亡后重试,Esc 关浮层;
  窗口失焦自动暂停。人玩模式不跑决策循环;Laya 模式忽略游戏键。
- **服务状态**:顶栏右侧两枚只读状态点(Laya/Qwen:绿=就绪/黄=加载/灰=未启动,
  沿用 EnvPage 语义),悬停显示端口与说明;**未启动时对应模式入口置灰**,
  提示「请在 release 版 · 环境页启动」——游戏页**没有**启停按钮(§1.1 约定)。
- **错误**:不再用横幅挤压布局——错误折叠为顶栏状态点的红色态,点击弹出
  浮层说明(含 laya-server 启动指引)。舞台永不被错误条推挤。

### 7.6 为什么这样是「精致」

1. 92% 面积给游戏,chrome 只有两条细带;
2. 信息没有消失,只是**降维**:常驻=单行摘要,细节=点击浮层——符合
   "90% 的时间不需要盯遥测"的真实使用分布;
3. 发丝线、等宽数字、大写微标签、一次性微动效,同一套小手法处处重复形成
   秩序感;霓虹/扫描线/辉光标题一概不用——辉光只给"活"的元素(检索结论:
   OLED 暗色,minimal glow,high contrast)。

## 8. 性能预算与工程要点

| 项        | 预算/做法                                                               |
| --------- | ----------------------------------------------------------------------- |
| 帧时间    | < 2ms @60fps(集显);关卡整图一次性绘入离屏 canvas(~3MB),每帧仅 blit 视口 |
| 实体      | 视口剔除;热循环零分配(复用数组);精灵预渲染到离屏                        |
| Svelte    | 引擎状态不进 $state;HUD 10Hz 快照;$effect 只做画布尺寸自适应            |
| 决策链路  | 与仿真解耦:in-flight 决策 ≤1,done 后在下一 tick 边界应用,过期即弃       |
| Laya 延迟 | 实测 p50 ≈ 240ms(v1-profile 单题,docs/12 §3.6);决策间隔 250ms ≈ 4Hz     |
| 反射短路  | trivial tick(直路无威胁且已对齐)免推理直通——计入日志,标 `shortcut`      |
| 页面隐藏  | `visibilitychange` 自动暂停累加器,后台不烧电不漂移                      |
| 资源      | 零新增依赖、零二进制资源;关卡/精灵全部代码内 ASCII 定义                 |

## 10. 遥测与实验方法

- 复用 laya-server `/session/start` + `/session/log`(`game: 'laya-mario'`),
  三类行:`decision`(stateHash/candidates/probs/conf/gate/latency/applied/stale)、
  `event`(death+归因/coin/stomp/flag)、`episode`(attempt/maxX/cause/duration)。
- 实验协议:每配置 ≥10 局,报 maxX 分布、通关率、死亡归因堆叠、escalation%。
  reflex vs pure vs autopilot 三线对照,编码 v1-profile/bitmap/both 消融。
- 蒸馏通路(RQ5):autopilot + 人玩轨迹导出 `(state, action)` JSONL →
  LoRA 微调(复用 docs/10 §5 栈与 `models/laya-*` bundle 流程)→ 纯反射重测 Δ。
  **马里奥因此不只是游戏,而是 Laya 域适应的可再生训练环境。**
- 运行结果反哺千寻代码的**开发闭环**(Agent 协作协议、数据契约、快回路)见 docs/12 §7。

## 12. 结论

- 架构上**零新增基建**:laya-server、session JSONL、GamesPage 注册表、
  剧场式舞台 UI 全部在既有体系内;新增的是**实时域的两个机制**——动作量子
  (输入保持)与路径规划器(可达表+BFS)。
- 实验上首次把 Laya 推进**时间敏感控制**域,产出 RQ1-RQ5 的可测答案与蒸馏数据集,
  为"Laya 走出游戏"提供第二块、也是更难的一块拼图。
- 双脑扩展(Laya 反射 × Qwen 慢思监督,完全本地自主)见 docs/12。
