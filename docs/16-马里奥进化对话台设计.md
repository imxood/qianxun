# 16 · 马里奥进化对话台设计(聊天式 Qwen 复盘)

> 需求原话:"每一轮失败,都需要有一个类似聊天的窗口,进行 qwen 的分析、优化过程,
> 以及结论,同时还要在其中显示运行的状态,以及各种必要的数据,其他的页面就可以
> 简化或者取消。"
> 评审输入:docs/analysis/16-1(交互与信息架构)/16-2(数据链路与实时事件)/
> 16-3(组件与持久化架构)。冲突已由 Lead 裁决合并。

## §0 目标与非目标

- **目标**:每局结束(失败/通关)后,Qwen 的分析过程、优化提案、结论以**聊天消息流**
  呈现;运行状态与必要数据嵌入聊天列;现有面板大幅简化。
- **非目标**:不向 Qwen 开放自由提问(二期);不改分析硬门语义;不动逐局归档 runs/。
- **文案宪法**:标签 ≤6 字 / 消息 ≤30 字 / 说明 ≤2 句。

## §0.1 核心需求校准(v2 修订,收录用户反馈)

用户两条反馈:①UI 必须漂亮美观简洁、文案不罗嗦;②紧扣核心需求,不做没必要的功能。

**核心需求一句话:看 AI 进化。** 用户要盯住的链条只有一环:
`失败 → Qwen 怎么想(诊断) → 改了什么(补丁) → 有没有用(判定)`。
其余一切(状态、统计、明细)都只是让这一环**可信、可查**的辅助,不该抢戏。

**v2 削减清单(相对 v1 合并稿)**:

| 砍掉                     | 理由                                              |
| ------------------------ | ------------------------------------------------- |
| 斜杠命令体系与命令输入框 | 从未被要求;重置=工具条小按钮+二次确认,手册=小按钮 |
| 局开始独立消息           | 局分隔符已含(局号·模式·结果)                      |
| 独立经验消息             | 并入分析卡元数据行(`经验+1`)                      |
| 熔断/不可达消息          | 列头状态点表达(Qwen 点变红+悬停文案)              |
| 硬门提示消息             | 开始按钮 tooltip 表达                             |
| 通关独立消息             | 并入终局分隔符                                    |
| emoji 图标               | SVG/文字标签(检核项:emoji 当图标=反模式)          |
| 「加载更早」分批         | 当前量级不需要,数据涨了再说                       |
| 判定独立卡               | 判定一行挂该局块末尾+提案卡原地更新角标           |

收敛后聊天只有 **5 种元素**:局分隔符 / 死亡行 / 分析卡(占位→结论原地变身) /
提案卡(判定角标原地更新) / 列头常驻条(非消息)。消息类型 12 → 5。

### 1.3 三层分发(防聊天仪表盘化)

| 层                      | 承载                                                | 刷新                                   |
| ----------------------- | --------------------------------------------------- | -------------------------------------- |
| 画布 HUD                | score/coins/time/门控徽标/IN                        | 10Hz 实时                              |
| 聊天列头常驻条(≤7 字段) | 局# · 模式 · 队列 k/n · 胜率 · 最远列 · 冷却 · 三态 | 事件驱动(胜率/最远列局末沉淀,不中途刷) |
| 消息数据卡              | 死亡/终局/结论/提案/判定                            | 事件一次性沉淀,不可变                  |

取舍六条:每秒变的数字不进聊天;一次性事件才可入聊天;卡片只带读得懂故事的字段
(全量明细走 runs/ 角标);常驻条超 7 字段即砍;删一条消息不损失决策依据=不该存在;
实时项仅两处(列头队列深、占位气泡耗时)。

### 1.4 视觉规范(v2,Swiss 极简;沿用应用既有 token)

原则:**留白即层级,色彩即语义**。整个聊天列只允许 4 种色彩语义,其余全灰阶。

| 语义           | 色(token)     | 用在哪                           |
| -------------- | ------------- | -------------------------------- |
| Qwen/进化      | violet-400    | 分析卡左侧 2px 竖条 + actor 标签 |
| 成功/转正      | emerald-400   | 转正角标、通关徽标               |
| 警示/回滚/失败 | amber-400     | 回滚角标、失败条                 |
| 中性           | slate-400/500 | 其余一切文字、分隔符、时间       |

- **卡片,不是气泡**:无头像无圆角气泡堆;每条事件是一张细边卡
  (`bg-surface/60 border border-line rounded-lg`,内边距 10-12px),
  卡间距 8px——安静、对齐、像变更日志不像微信。
- **字体层级**:正文 13px sans(slate-200);actor 标签 11px 大写宽字距
  (slate-500,如 `QWEN · 析#1`);**数字一律 mono**(得分/列号/耗时/字段名)。
- **留白**:列内边距 12px;分隔符行上下各 16px 空隙 + 细分隔线——局与局
  之间靠空白呼吸,不靠重色块。
- **动效只两处**:新消息 150ms 淡入+上移 4px;「分析中」卡顶部细进度条
  微光循环。其余零动画;`prefers-reduced-motion` 全部静默。
- **状态点**:列头两枚 6px 圆点(Laya/Qwen),绿=在线,红=断;悬停出原因。
- 禁止:emoji 图标、渐变、阴影堆叠、每卡不同颜色、10Hz 闪烁数字。
- 空状态一行:`跑一局,Qwen 的复盘会出现在这里`(slate-500 居中)。

## §2 聊天消息模型(v2:5 种元素)

组织方式:**连续时间线 + 局折叠单元**(不做一局一会话块——试用→判定差一局、
冷却 5 局、回归守卫跨局,硬切块会割裂因果链)。历史局默认折叠为分隔符摘要行,
当前局展开,可点开回看。

| 元素     | actor | 触发点                  | 形态                                                                               |
| -------- | ----- | ----------------------- | ---------------------------------------------------------------------------------- |
| 局分隔符 | 系统  | 局末(genPostmortem)     | 单行:`#5 · 反射 · 3死 · 78列` 或 `#6 · 反射 · 通关 · 1180分`;折叠=复盘全文         |
| 死亡行   | 规则  | death 事件              | 单行:`第2死 撞龟@52 · 54%`                                                         |
| 分析卡   | Qwen  | 任务出队→ok/fail        | 占位(分析中…计时)原地变身结论卡或失败条;**每死恰好一张**                           |
| 提案卡   | Qwen  | propose                 | patch from→to 表 + 判定角标原地更新(试用后标 ✓转正/✗回滚);stepGated 时带「装填 ▸」 |
| 判定行   | 规则  | commit/rollback/restore | 单行挂该局块末尾:`转正 · 1180 vs 1024 · ↩#5`                                       |

规则:

- **分析卡原地变身**:占位(琥珀呼吸点+耗时)→ 结论卡(紫竖条)或失败条——
  不追加不重复,"每死一张卡"呼应幂等键"成功才占位"。
- **经验/手册增量是分析卡的元数据行**,不是独立消息;近重复确认(`‖确认@N`)
  显示为计数徽标。
- 熔断/断连只动列头状态点;硬门只动按钮 tooltip——都不产生消息。

文案示例(全部 ≤30 字,无 emoji):

```text
第2死 撞龟@52 · 54%                          (死亡行)
◌ 第1死 分析中… 8.2s                         (分析卡占位)
QWEN · 析#1 · 12.4s                          (结论卡标签,11px 宽字距)
连续两局在52列同一乌龟处撞龟;提前半拍起跳即可越过。(结论卡正文,一句)
手册+140字 · 经验+1 · ▸ 收发明细               (结论卡元数据行)
改 gateExec .16→.12 · 装填下局 ▸              (提案卡)
转正 · 1180 vs 1024 · ↩#5                    (判定行)
回滚 · 未过+5% · 已冷却                       (判定行,amber)
```

## §3 数据链路(零轮询,事件驱动)

### 3.0 即死即析(v2.1 用户确认:每次死亡后必须 Qwen 实时交互)

死亡瞬间(第 1/2/3 死,无一例外)→ 聊天立即出现该死的占位卡,Qwen 立即开始
分析(~10s),占位卡原地变身结论卡;游戏自动重生继续跑,分析并行不打断。
局终只补 run 级任务(通关/平台期)+ 局分隔符;硬门语义不变(下一局开始前
队列必须清空,大多在局内已消化)。

- 触发点从 `genPostmortem` 移到**死亡事件处理**;每死任务即刻入串行队列。
- 死亡即析载荷从收发环按 attempt 切片组装(`buildDeathPayload` 增纯 sent 变体
  `buildDeathPayloadFromSent`,不再依赖局末 report;死前 12 拍上下文天然在环内)。
- 额外收益:同局连续同死因时,第 n 死的载荷能带上第 n-1 步刚产出的诊断
  (diagBySig 实时可见)——同局 repeat 是最强信号,局末批量做不到。
- 死后**不暂停等待**(重生照旧,分析并行);"死→析完→重生"作为独立产品决策再议。

### 3.1 定位与接线

聊天流是**审计的投影 + 展开数据的归档**(§5 持久化裁决后)。单一权威触发点:

1. `audit()`(必经之路)→ 按 action/phase 投影 phase/patch/verdict 消息,
   一处覆盖 analyze start|ok|fail、propose、commit/rollback/restore 全部;
2. **死亡事件(即死即析,§3.0)** → 占位卡 + 任务入队;局分隔符与局摘要
   在 genPostmortem(局终);
3. `runAnalysisQueue` 成功分支 → **先 emit 再落库**:diagnosis 明细/insight 原始
   对象/playbook 快照三类展开消息必须在此刻快照进聊天,否则被后续覆盖/折叠漂移;
4. `probe()` resolve、`analysisGate.finally`、breaker 翻转 → 状态点/状态条。

```ts
let chat = $state<ChatMessage[]>([]);
const emitChat = (m) => {
  chat = [...chat.slice(-199), m];
  void store.append('chat.jsonl', JSON.stringify(m)).catch(() => {});
};
```

### 3.2 Qwen 四类内容可获取性(核实结论)

| 内容               | 现状                                               | 结论                                    |
| ------------------ | -------------------------------------------------- | --------------------------------------- |
| playbook 全文      | `r.playbook` 在成功分支"路过即得"                  | 直接 emit,先快照后赋值                  |
| 补丁 from→to       | propose 审计行 + `pendingCandidate.patch` 完整可得 | 投影即可;任务级中间态不展示             |
| **diagnosis 明细** | **只进内存 diagBySig,不落盘不进 UI,重启即失**      | emit + 随 chat.jsonl 归档( deepest gap) |
| insight 对象       | 立即被 appendInsight 折叠(近重复合并)              | 折叠前 emit 原始对象                    |

一期**不做**(输出是单个 JSON,半截不可渲染;三段式"开始→计时→结构卡"已够;

## §4 组件架构

- **chat.ts 纯模块**(新):`ChatMessage` 判别联合(kind 对齐 M1–M11)、append、
  审计降级重建、`mapAuditToMsg` 投影——全部纯函数可单测;MarioLab 只负责投递。
- **EvolutionChat.svelte**(新,常驻列):props `messages/status` + 回调
  `onstepadvance/onresetpolicy/onopenpostmortem`;数据所有权在父级。
- 子组件:`MessageItem`(纯渲染)/`DataCard`(提案表/判定徽标/装填按钮,动作上抛)/
  `StatusStrip`(列头一行,高频值单值覆盖,绝不追加消息)。
- **key 策略**:消息真 id `${runId}#${seq}`(模块内单调 seq);禁下标、禁时间戳拼接。
- **滚动锚定三态**:跟随(atBottom→自动到底)/锁定(上翻→浮标「↓ N 条新消息」)/
  恢复(点浮标回底);锚定 $effect 只依赖 `messages.length`+atBottom;程序化赋值
  先同步 atBottom 防回环。
- **不上虚拟滚动**:窗口化渲染尾部 200 条 +「加载更早 +200」;200 条 ≈1k 节点,
  首屏 <50ms。消息量级:每局 15–35 条,100 局 1.5–3.5k 条,chat.jsonl 约
  30–70KB/局(append 单行 64KiB 上限内,单条 ≤2KB)。

## §5 持久化(Lead 裁决:方案 A 为主 + B 降级)

- **A(主)**:每条消息 `store.append('chat.jsonl', JSON.stringify(msg))`,
  **写失败静默不重试**——呈现可丢,审计不可丢(与现有 persist* 同纪律)。
  展开(diagnosis/insight/playbook 快照)随聊天流落盘,天然解决"重启即失"。
- **B(降级兜底)**:chat.jsonl 缺失/损坏(旧版首启)→ 从 evolution.jsonl 尾部 +
  runs/index.jsonl 重建"简史"(仅事件骨架,无分析正文),UI 标注"历史由审计重建"。
- 不选纯 B:diagnosis 未落盘时重建缺 Qwen 结论原文(违背"每轮失败都有"诉求),
  且呈现层绑死审计格式是双向耦合。不选纯内存 C:违背 §9b"数据要多不要少"。
- 事实源仍是 evolution.jsonl + runs/;聊天文件是呈现与展开数据的归档层。
- 审计 v3 摘要字段(16-2 G3)降为二期可选——聊天已归档,审计不必重复。
