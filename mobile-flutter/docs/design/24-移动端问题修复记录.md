## 1. 文件不弹框：为什么 RN 端能用、Flutter 端不能

两端都是「WebView 承载 DSH 页面」，页面里的「+ -> 文件」是**原生 file input**：

```js
// dsh-client-ui-conversation/lib/client.js 的 installDraftFilePicker
open: () => {
  fileInputRef.current?.click();
};
```

Android WebView 上，file input 的弹框**唯一**入口是 `WebChromeClient.onShowFileChooser`。两端差别在宿主：

| 宿主                                                | onShowFileChooser  | 结果                       |
| --------------------------------------------------- | ------------------ | -------------------------- |
| `react-native-webview` ^13.16.0（RN 端，`mobile/`） | **内置实现**       | 直接弹系统选择器，一直好用 |
| `webview_flutter` ^4.14.1（Flutter 端）             | 需**显式注册**回调 | 未注册 -> 静默不弹框       |

RN 端的证据（2026-11-05 用户提供的真机截图）：在 RN 端点「+ -> 文件」，弹出的是 **Android 系统照片选择器**（相机 / 摄像机 / 照片和视频 / 更多），选完直接作为附件发给 DSH——整条链路正常。Flutter 端同一步骤**完全没有反应**。

RN 端的壳代码极简（`mobile/src/surfaces.tsx:20-33`），没有任何文件选择相关处理——这反过来证明「能力来自 `react-native-webview` 本身」，不是 RN 端自己写的。

`webview_flutter_android` 的 Java 侧（`WebChromeClientProxyApi.java`）：

```java
private boolean returnValueForOnShowFileChooser = false;   // 默认 false
...
public boolean onShowFileChooser(...) {
  final boolean currentReturnValueForOnShowFileChooser = returnValueForOnShowFileChooser;
  api.onShowFileChooser(..., reply -> {
    final List<String> value = Objects.requireNonNull(reply.getOrNull());
    // 只有 returnValue 为 true 时，返回的 URI 才会喂给页面的 File 对象
    if (currentReturnValueForOnShowFileChooser) { ... filePathCallback.onReceiveValue(filePaths); }
    return null;
  });
  return currentReturnValueForOnShowFileChooser;   // false -> WebView 认为无人处理
}
```

`setOnShowFileSelector(cb)` 会把 `returnValueForOnShowFileChooser` 置 true —— 这是**唯一**的开关。

### 1.1 权限问题？——不是

- manifest 只有 `INTERNET`（`android/app/src/main/AndroidManifest.xml:3`）。
- 系统文件选择器走 SAF（`ACTION_OPEN_DOCUMENT` / `ACTION_GET_CONTENT`），**不需要任何运行时权限**；用户选中的 URI 由系统临时授权给 App。
- 所以症状是「点了完全没反应」而不是「提示需要权限」——这与「未注册回调」的表现一致。

### 1.2 URI 回传：`file://` 而非 `content://`

`file_picker` 11.0.3 的 Android 实现（`FileUtils.kt`）把选中的文件**复制到 app 私有 cache**：

```
context.cacheDir.absolutePath + "/file_picker/" + <timestamp> + "/" + <fileName>
```

返回的 `path` 是**真实文件路径** -> 转 `file://` URI。WebView 与 App 同 UID 同进程，可直接读，**不需要 URI 权限授予**（`content://` 则需要）。

### 1.3 两个 Dart 侧的坑（都踩过）

1. **`webview_flutter_android` 必须是直接依赖**：只写 `webview_flutter` 时，`AndroidWebViewController` 类型不可见，`is` 检查后的类型提升失效 -> 编译报「The method 'setOnShowFileSelector' isn't defined for the type 'WebViewController'」。
2. **类型提升在这里不适用**：`AndroidWebViewController` 继承 `PlatformWebViewController`，与 `WebViewController` **没有继承关系**（只是实现同一接口）——Dart 的 `is` 提升规则要求有继承/实现关系时才生效。所以必须用 `as` 强制转换：

```dart
if (controller is! AndroidWebViewController) return;
final androidController = controller as AndroidWebViewController;
await androidController.setOnShowFileSelector(...);
```

3. **版本约束**：本机 Flutter SDK 3.47.9 要求 `webview_flutter_android: ^4.12.0`（钉 4.14.1 会解析失败）；`setOnShowFileSelector` 在 4.12.0 即存在，API 形状相同。

## 2. 顶栏多一行

不是 DSH 页面的问题，是**壳自己画的**：

```
┌─────────────────────────┐
│ ← maxu-pc-msi           │  ← Flutter AppBar（合理）
├─────────────────────────┤
│ 正在检测定制层…          │  ← AppBar.bottom 的 28px 状态条（多余）
├─────────────────────────┤
│ DSH 页面自身头部…        │  ← 页面自己的
```

那条状态条是**恒显**的：定制层 10-31 已下线，`_customLayerReady` 永远为 `null` -> 永远走「正在检测定制层…」分支。RN 端没有这条。

修法：删掉 `AppBar.bottom`（加载失败已有整屏 `_ErrorView` 承载，不再叠条）。

### 5.1 顺带修的存量构建缺陷（AGP 9 与 Flutter 3.38 不兼容）

首次构建 APK 失败，根因**与本次改动无关**（存量问题）：仓库里
`settings.gradle.kts` 声明的是 **AGP 9.1.0 + Kotlin 2.4.0**，但本机只有
**Flutter 3.38.10**，而 Flutter 3.38 的 Gradle 插件只支持**旧 DSL**。

#### 坑 1：`kotlin {}` 块解析成插件坐标声明

```
e: build.gradle.kts:42:5: Unresolved reference 'compilerOptions'.
e: build.gradle.kts:43:9: Unresolved reference 'jvmTarget'.
   ^ None of the following candidates is applicable:
     fun DependencyHandler.kotlin(module: String, version: String? = ...)
```

`kotlin {}` 落到了 Kotlin DSL 内置的 `DependencyHandler.kotlin`（**插件坐标声明**），
拿不到 `KotlinAndroidProjectExtension`。

#### 坑 2：应用 Kotlin 插件会被 Flutter 直接拦下

```
[!] Starting AGP 9+, the default has become built-in Kotlin. This results in a
    build failure when applying the kotlin-android plugin
```

Flutter 权威文案（`flutter_tools/lib/src/android/gradle_errors.dart:672,680`）：
「**AGP 9.0 起 `org.jetbrains.kotlin.android` 插件不再需要**」——
Kotlin 支持已**内置**，所以 AGP 9 下两个插件名都不能写。

#### 坑 3：顶层 `compilerOptions` 不可用

Kotlin DSL 的顶层 `compilerOptions` 来自 `KotlinTopLevelExtension`（纯 JVM 插件），
Android 模块用的是 `KotlinAndroidProjectExtension`——故仍需 `kotlin { }` 包裹。

#### 坑 4：`android { kotlinOptions { } }` 在 AGP 9 也被移除

```
e: build.gradle.kts:43:9: Unresolved reference 'jvmTarget'.
```

#### 坑 5：Flutter Gradle 插件与新 DSL 不兼容（**决定性的一条**）

```
> Failed to apply plugin 'dev.flutter.flutter-gradle-plugin'
> java.lang.NullPointerException (no error message)
```

AGP 9 强制 `android.newDsl=true`，Flutter 3.38 的 Gradle 插件依赖旧 DSL 类型。
Flutter 给的两条路（`gradle_errors.dart:704-706`）：「**update flutter**」或
「**opt out of `android.newDsl`**」。

**但退路实际不可用**——实测 `android.newDsl=false` 在 AGP 9.1.0 下无效。
jar 字节码佐证：

| AGP 版本 | `newDsl` 出现在                                                                     |
| -------- | ----------------------------------------------------------------------------------- |
| 8.13.1   | `DeprecationReporter` / `BooleanOption`（= 仍可识别的废弃开关）                     |
| 9.1.0    | `AppExtension` / `BaseExtension` / `AbstractAppExtension`（= 语义已变，强制新 DSL） |

#### 最终决策：**AGP 9.1.0 -> 8.13.1**（Kotlin 2.4.0 -> 2.2.20）

理由：

1. 升级 Flutter SDK 是**跨项目**的重动作（`pub get` 已提示需要 3.47.9，
   本机只有 3.38.10），而 AGP 是**本项目局部**的开关；
2. AGP 8.13.1 是 8.x 最新版，**完全支持 compileSdk 35**（compileSdk 与 AGP
   版本是两件事）——不影响「用较新的 Android SDK」这个目标；
3. 本机 Gradle 缓存里已有 `gradle-8.13.1.jar` 与 `kotlin-gradle-plugin 2.2.20`，
   离线可解析，无需下载。

#### 最终形态

```kotlin
// settings.gradle.kts
id("com.android.application") version "8.13.1" apply false
id("org.jetbrains.kotlin.android") version "2.2.20" apply false

// app/build.gradle.kts
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")   // AGP 8.x 需要它（AGP 9 才不用）
    id("dev.flutter.flutter-gradle-plugin")
}

android {
    compileSdk = 35
    kotlinOptions { /* 已移除，AGP 9 才有 */ }
    ...
}

kotlin {                                     // 项目级块（Kotlin 插件提供）
    compilerOptions {
        jvmTarget.set(org.jetbrains.kotlin.gradle.dsl.JvmTarget.JVM_17)
    }
}
```

`android/gradle.properties` 里的 `android.newDsl` / `android.builtInKotlin`
两行已删除（AGP 8.13 下只剩废弃告警价值）。

#### SDK 版本（按 operator 指示）

手机是 **Android 16**，但按「支持较新版本即可，不要是最新」的口径，选 **API 35**：

| 项           | 值                | 理由                                                                    |
| ------------ | ----------------- | ----------------------------------------------------------------------- |
| `compileSdk` | 35                | 较新且稳定；本机 build-tools 35.0.0 / 36.0.0 都在，将来要 36 改一行     |
| `targetSdk`  | 35                | 与 compileSdk 对齐                                                      |
| `minSdk`     | 26（Android 8.0） | 覆盖绝大多数在用机型，满足 file_picker / webview_flutter_android 的下限 |
| `ndkVersion` | 28.2.13676358     | 必须与本机已装 NDK 一致，否则报「NDK not found」                        |

不再用 `flutter.compileSdkVersion` / `flutter.targetSdkVersion` / `flutter.minSdkVersion`
——那三个值跟着 Flutter SDK 走（本机 Flutter 3.38 对应的默认值远低于 35），
会让新装的 SDK 白装。

### 6.3 顶栏「额外换行」：**已修**（web 端 CSS，立即生效）

> ⚠️ 本节最初写成「当前不存在」，那是**误判** —— 误判源于探针抓错了 App
> （见 §6.6）。用户指出是「对话 | 轨迹」那一行的**上一行**，重新抓真机对照后
> 定位并修复。

#### 现象

- **Flutter 端**：DSH 会话头部占**两行** ->「对话 | 轨迹」那一行上方多出一整行
- **RN 端**：同一时刻只占一行

#### 根因（真机 DOM + computed style 实测）

设备 OnePlus PKB110 / Android 16 / 视口 **359×692 CSS px** / dpr **3.5**
（1256 物理像素 ÷ 3.5）。

DSH 的会话头部结构（`data-slot` 是稳定契约；class 是构建期哈希，不可依赖）：

```
[data-slot='conversation.session.header']   display:contents
└─ div.wSkVaW_titleRow      display:flex  flex-wrap:wrap  w=311  h=96  ← 96px = 两行
   ├─ div.wSkVaW_titleCluster    flex-grow:1  min-width:0  overflow:clip   w=307 h=56
   │  ├─ nav.wSkVaW_crumbs       w=85   ← 会话标题「移除千寻软件UI样式处理」
   │  │  └─ span.wSkVaW_crumb    text-overflow:ellipsis  white-space:nowrap
   │  └─ div.wSkVaW_headerActions w=187  ← 「智能体团队」+「2 个后台任务运行中」
   ├─ div.wSkVaW_headerUtilities w=77  flex-shrink:0   ← 被挤到第二行
   └─ div.wSkVaW_headerCorner    w=28  flex-shrink:0   ← 被挤到第二行
```

**算术**：标题 86px + 状态区 187px + 按钮 105px = **378px > 311px 可用**
-> `flex-wrap: wrap` 把后两个按钮挤到第二行。

**触发条件是「会话标题」**：RN 端当时那个会话**标题为空**，187 + 105 = 292 <= 311
-> 排得下 -> 只有一行。所以不是端差异，是**内容差异**。

#### 修法（`mobile/examples/minimal-input/custom.css` §4）

```css
@media (max-width: 560px) {
  [data-slot='conversation.session.header'] > div {
    flex-wrap: nowrap !important;
  }
  [data-slot='conversation.session.header'] > div > div:first-child {
    flex-wrap: nowrap !important;
    min-width: 0 !important;
    flex-shrink: 1 !important;
  }
  [data-slot='conversation.session.header'] > div > div:first-child > * {
    min-width: 0 !important;
    flex-shrink: 1 !important;
    overflow: hidden !important;
    white-space: nowrap !important; /* ⛔ 不加会逐字竖排 */
    text-overflow: ellipsis !important;
  }
  /* 状态区内部文本容器同样禁止换行 */
  [data-slot='conversation.session.header'] > div > div:first-child > * > * {
    min-width: 0 !important;
    overflow: hidden !important;
    white-space: nowrap !important;
    text-overflow: ellipsis !important;
  }
}
```

实测结果：`titleRow` 高度 **96px -> 30px**，三个子项回到同一行：

```
[方块] 移除干…  👤  ○ 2 个  [📁∨]  ⋯  [方块]
对话    轨迹    ⋯                       ← 多出的那行消失
```

#### 两个踩过的坑

| 坑                         | 现象                                               | 根因                                                                                                          |
| -------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 绝对定位 + `padding-right` | `titleCluster` 从 56px **涨到 104px**              | `padding-right` 落在 content-box 上 -> 307 + 127 > 311 -> 内部被迫折行。**改用 flex 收缩，别用 padding 让位** |
| 只加 `flex-wrap: nowrap`   | 「2 个后台任务运行中」变成**逐字竖排**（一列单字） | 中文在窄容器里会逐字换行 -> 必须同时 `white-space: nowrap` + `overflow: hidden` + `text-overflow: ellipsis`   |

### 6.6 探针抓错了 App —— 一条会骗人的教训

本轮前半段所有「两端一致 / 顶部无差异」的结论**全是错的**，因为探针抓的
根本不是两个不同的 App。

**根因**：`adb shell am start -n com.qianxun.mobile/.MainActivity` **静默失败**。
RN 端 Activity 的类名包前缀是 `com.qianxunmobile`，不是 `com.qianxun.mobile`
（真值：`adb shell cmd package resolve-activity --brief -c android.intent.category.LAUNCHER`
-> `com.qianxun.mobile/com.qianxunmobile.MainActivity`）。`.MainActivity` 简写
只在包名与类名前缀一致时成立 -> 解析成了不存在的 `com.qianxun.mobile.MainActivity`
-> 命令不报错、前台也不动。

于是「RN 端」那份数据其实抓的是仍在前景的 **Flutter 端** —— 两边数据一模一样
是必然的，我却据此得出「两端结构一致」的结论。

**教训（写进探针 `scripts/probe_top_compare.py`）**：

1. `am start` 之后**必须校验前台包名**（`dumpsys activity activities` 的
   `topResumedActivity`），不匹配就报错；
2. 用 `am start -S`（force-stop 后启动）或先 `force-stop` 另一个 App，
   再**轮询**等前台真的切过去 —— RN（Expo）冷启动慢，固定 sleep 不够；
   固定 sleep 不足时，后续 tap 会落到**桌面图标**上（实测把「天气」App 打开了）；
3. Activity 名要用 `resolve-activity` 查，**不要凭 `.MainActivity` 简写猜**。

修正后拿到真实对照：

| 项               | RN 端   | Flutter 端 |
| ---------------- | ------- | ---------- |
| WebView 起点 y   | 322     | 336        |
| **「对话」行 y** | **462** | **707**    |
| 会话标题         | 无      | 有（86px） |

## 7. 出包链路上踩的两个「假故障」

装不上 / 装了没变化，都**不是**代码问题，而是出包链路的问题。两条都已固化成自动闸门。

### 7.1 发布出去的包是旧的（装上了但没变化）

`build/app/outputs/flutter-apk/` 里**同时躺着旧的 release 包和新的 debug 包**，
而 `publish_apk.py` 只按文件名拷贝、不看新旧 -> 手机下载到 arm64 release，
装上去却是改动之前的代码（「怎么没生效」）。

修法（`publish_apk.py`）：**新鲜度闸门** —— 产物比源码旧就拒绝发布，
并打印该跑什么构建命令。实测拦下效果：

```
⚠️ 以下产物比源码旧，**不发布**（装了会看不到改动）：
   app-arm64-v8a-release.apk  比源码旧 42813 分钟
   请重新构建：flutter build apk --release --split-per-abi
```

### 7.2 versionCode 降级（新包装不上）

Android 提示「**已安装更高版本"千寻(0.3.0)"**」= `INSTALL_FAILED_VERSION_DOWNGRADE`
—— **新包 versionCode 低于已装包**，不是签名问题。

versionCode 的真实算法（Flutter gradle 插件 `FlutterPlugin.kt`）：

```
split-per-abi：versionCode = ABI偏移×1000 + buildNumber
                armv7 +1000 / arm64 +2000 / x86_64 +4000
不 split：    versionCode = buildNumber
```

对上实际产物：

| 包                      | pubspec buildNumber | 实际 versionCode |
| ----------------------- | ------------------- | ---------------- |
| 0.3.0 arm64             | +1                  | 2001             |
| 0.3.1 arm64（首次发布） | +2                  | 2002             |
| 0.3.1 arm64（修正后）   | +30000              | **32000**        |

手机上那个 0.3.0 的 versionCode **> 2002**（历史构建序号曾更大），
所以 2002 被判为降级。**根因是我的版本策略有错**：改了功能版本号 Z，
却把构建序号 N 从头数，撞上了历史峰值。

修法：

1. `pubspec.yaml` 的 buildNumber 提到 **30000**（arm64 包 versionCode=32000）；
2. `publish_apk.py` 加 **versionCode 门槛**（`< 30000` 不发布）——
   与「装不上」这种故障直接对齐；
3. `build_and_publish.py` 复用同一门槛常量（单一规则来源，避免漂移），
   并在验证段打印每个包的 versionCode 与判定。

### 7.3 顺带修的构建期坑

- **`flutter` 在 Python 子进程里找不到**：Windows 上 PATH 里的是 `flutter.BAT`
  （**大写扩展名**），`subprocess` 走 `CreateProcess` **不补** `.bat`/`.cmd`
  扩展 -> `FileNotFoundError`。在 PowerShell 里能跑、换宿主就炸的典型坑。
  `build_and_publish.py` 改从 `android/local.properties` 的 `flutter.sdk`
  推导绝对路径。
- **`flutter.versionCode` 由工具写入 local.properties**（`changeIfNecessary`，
  值不同就改），所以改 pubspec 后不需要手工清 local.properties。

## 9. 软键盘弹出「发滞」：分析、已交付的优化、以及根治路线

> 用户反馈（2026-11-05）：「输入框点击后，输入框向上移动，底部输入法显示出来。
> 但是 输入法向上的过程 似乎有点 迟滞的感觉」。

### 9.1 客观数据（`scripts/probe_keyboard.py`，rAF 帧间隔采样）

设备 OnePlus PKB110 / Android 16 / 视口 359×692 CSS px / dpr 3.5。

```
平时                11ms/帧（90fps）
键盘动画期间        连续 8~9 个 >32ms 的长帧，最长 71~77ms
                    （键盘动画总时长约 280ms，期间只出了 ~9 帧 -> ~20fps）
```

### 9.2 根因

1. `adjustResize` 模式下，**键盘动画是拖着 App 窗口一起动的** ——
   App 每帧渲染慢，键盘动画就直接看起来卡；
2. Flutter 的 `Scaffold` 默认 `resizeToAvoidBottomInset: true` ->
   键盘弹出期间 **WebView 的渲染表面尺寸每帧都变** ->
   Chromium 必须**整页重新光栅化** -> 抢渲染线程；
3. 实测 `visualViewport.height ≈ window.innerHeight`（693/692 -> 393/392），
   说明布局视口随键盘一起缩小，**输入框本来就是跟手的**
   （与视口底边间距恒定 83px）—— 所以**不是**「输入框没躲开」的问题。

### 9.3 A/B 实测：掉帧确实来自 resize

在真机上把壳改成 `resizeToAvoidBottomInset: false`，重新构建安装后复测：

| 壳配置                                          | 键盘动画期间长帧 | 最长帧 | 输入框                       |
| ----------------------------------------------- | ---------------- | ------ | ---------------------------- |
| `resizeToAvoidBottomInset: true`（每帧 resize） | **8~9 个**       | 77ms   | 跟手可见（贴在键盘上沿）     |
| `resizeToAvoidBottomInset: false`（尺寸不变）   | **0 个**         | 15ms   | **被键盘完全盖住 —— 不可用** |

`false` 这一侧掉帧归零，但 **Flutter 吞掉了 IME inset**：
WebView 的 `visualViewport` 不再更新 -> 页内 `100dvh` 不收缩 ->
输入框留在文档流末尾（= 屏幕底部）-> 被键盘盖住。
截图确认：键盘弹起、DSH 内容没有被顶上去、输入框不可见。

**所以 `false` 这一侧被否决**（可用性优先），壳已回滚为 `true`。

顺带排除一个看似可行的方案：`content-visibility: auto`（让屏外消息跳过布局）
—— 实测长帧数与最长帧**与基线完全一致**，说明成本**不在 DOM 布局，
而在渲染表面尺寸变化后的整页光栅化**。该规则未采纳。

### 9.4 本轮已交付的优化（定制层，web 端，立即生效）

旧写法本身就有三处会造成迟滞：

| 旧写法                                | 问题                                                                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `setTimeout(..., 250)` 固定等待       | 落在键盘动画**进行中**（实测动画 t≈117ms 起、t≈423ms 止）-> 滚动动画与键盘动画**叠加**             |
| `scrollIntoView({behavior:'smooth'})` | 二次平滑滚动；且 `block:'center'` + `scroll-margin-bottom:50vh` 把目标推到视口中部，滚动量放大数倍 |
| 无条件滚动                            | 本机根本不需要（输入框已跟手），纯属多余的二次运动                                                 |

新写法（`mobile/examples/minimal-input/custom.js`）：

1. **等键盘动画稳定**再动作 —— 用 rAF 连续两帧 `visualViewport.height` 不变
   作为「稳定」信号（800ms 兜底），不再猜时长；
2. **按需补偿** —— 只有输入框**确实被键盘遮住**（`getBoundingClientRect().bottom`
   超出 `visualViewport.height`）时才滚动；本机永远不触发；
3. **非平滑 + 最小位移** —— `block:'nearest'` + `behavior:'auto'`；
4. CSS `scroll-margin-bottom` 由 `50vh` 收到 **12px**。

实测：键盘动画总时长 **306ms -> 281ms**，`scrollY` 恒为 0（补偿未触发），
输入框轨迹完全由键盘驱动。

### 9.5 根治路线（架构级，需另立议题）

要同时拿到「跟手」与「不掉帧」，必须让**输入框不依赖 WebView resize**：

- **方案一（推荐）**：Flutter 侧画**原生输入框**，WebView 只负责对话区，
  键盘弹出时对话区用 padding 让位。原生布局轻量，不触发整页光栅化；
  代价是要重做输入框 UI 与附件选择。
- **方案二**：DSH 页面把输入框改成 `position:fixed`，壳保持 WebView 尺寸不变，
  由页内 `transform` 跟手上移。代价：WebView 整体上移会**裁掉顶部内容**
  （会话标题行会消失），需要产品确认是否接受。

### 9.5 根治实施：壳通道 + 页内 transform 跟手（2026-11-05 已落地）

「方案二」的改良版最终胜出 —— **只 transform composer，不 transform 整页**，
配合壳的**逐帧 IME 高度通道**：

**壳侧（`dsh_page.dart`）**

- Android 上 `resizeToAvoidBottomInset: false`：WebView 表面尺寸全程不变，
  键盘动画由系统独立绘制；
- `build()` 里读 `MediaQuery.viewInsetsOf(context).bottom`，变化超过 0.5px 就在
  postFrame 回调里 `runJavaScript('window.__qxKb(h)')` 推给页面
  （Android 11+ 的 inset 动画逐帧上报，设备 Android 16 实测每帧都到）；
- 非 Android 维持 Scaffold 默认行为。

**页面侧（`custom.js` §1.5）**

1. `window.__qxKb(h)` 收到高度后 rAF 合帧，只做**compositor-only** 的操作：
   composer 座位 `translateY(-kb)`（座位 ~127px，独占小图层，GPU 合成，
   不触发布局/光栅化）；
2. 座位**运行时推导**：从 `[data-slot='conversation.composer']` 向上找第一个
   `overflow:auto/scroll` 的滚动容器，再取它与滚动容器之间的那个子元素
   （DSH 的 composer 槽是 `display:contents`，座位是哈希 class，都不能写死）；
3. 键盘高度**稳定后**（复用 afterKeyboardSettled）给滚动容器一次性补
   `padding-bottom: kb` 并**清掉 transform**：
   - 补 padding 是为了「滚到底」时消息尾行停在 composer 上方（座位是滚动
     容器的流内末尾元素，不补的话流式输出的最新内容会滚进
     「键盘+composer」遮挡带后面）；
   - ⚠️ **必须同时清 transform**：padding 已把座位的流内位置推到键盘上沿，
     transform 再叠一层就是二次位移（实测 composer 被推到 y=-34，
     藏进顶栏后面 —— 一次真实翻车，靠设备端 DOM 快照定位）；
   - 切换前后 composer 视觉位置完全一致（都停在键盘上沿），无缝。

**实测结果（同口径 rAF 帧间隔采样）**

| 方案                                        | show 长帧 | hide 长帧 | 最长帧   | 视觉                                     |
| ------------------------------------------- | --------- | --------- | -------- | ---------------------------------------- |
| resize=true（基线）                         | 8~9 个    | 未测      | 77~121ms | 输入框跟手，但动画发滞                   |
| resize=false（无通道，已否决）              | 0 个      | 未测      | 15ms     | **输入框被盖住，不可用**                 |
| **resize=false + 通道 + transform（当前）** | **0 个**  | **0 个**  | **17ms** | composer 贴键盘上沿，头部/对话区全程静止 |

settle 后 DOM 快照：座位 `t=266 b=393`，键盘上沿 `693-299.7 ≈ 393` —— 完全重合。

**附带收益**：头部（会话标题行、对话|轨迹 tabs）与对话区内容全程静止
—— 旧 resize 方案里它们每帧跟着键盘上蹿，这也是「发滞」观感的一部分。

**两个教训**

1. **transform + padding 叠加 = 二次位移**：settle 后 padding 接管定位时
   必须清 transform（见上）；
2. **脚本切除要跑语法门禁**：本次用 Python 按标记切除临时探针，把
   `onFocusIn`/清理函数/收尾括号一起切掉了 -> 整个 custom.js 语法错误 ->
   register 不执行 -> 自举 CSS 和键盘通道同时失效（截图上头部换行 + composer
   被键盘盖住，两个症状一个根因）。修复后 `node --check` 已过；
   **以后删代码块后必须 `node --check`**。

**第三个教训（hide 路径的状态机，2026-11-05 用户真机复测发现）**

「输入法消失时输入框向上弹了一下」—— 根因：applyKb 对任何 `kb>0` 的帧
无条件重挂 `translateY(-kb)`。settle 后 transform 已清空（padding 接管），
hide 动画**第一帧**就把 composer 从键盘上沿瞬移回「屏幕底-kb」（向上弹一个
键盘高度），随后再滑回来，kb=0 时再跳到底 —— 三段式跳变。

修法：transform **按模式计算**，不再无脑 `-kb`：

| 状态                        | transform                   | 效果                                                         |
| --------------------------- | --------------------------- | ------------------------------------------------------------ |
| padding 未加（show 动画中） | `translateY(-kb)`           | composer 从屏幕底爬升                                        |
| padding 已加（settle/hide） | `translateY(kbPadKey - kb)` | hide 时 ty 从 0 连续长到 +pad，composer 贴着键盘上沿同步下降 |
| kb = 0                      | 同帧清 padding + transform  | composer 正好落在流内底部，与前帧视觉无缝                    |

真机抓帧验证：hide 中途帧 composer 处于下降途中（无上跳），结束帧与
无键盘基线布局逐像素一致。BACK 键在输入框聚焦时正常收起键盘
（此前「BACK 不收起」的记录是 false-build 误读，见 9.3）。

## 10. 顶栏返回与系统返回双双失效（2026-11-05 已修）

**现象**：DSH 页内，顶栏返回箭头与手机返回手势都**毫无反应**（实测连点 6 次
页面纹丝不动；输入框聚焦时第一次 BACK 仍能正常收起键盘——键盘与路由是
两条独立通道，坏的是路由那条）。

**取证**：

1. 顶栏按钮与系统返回走**同一条代码路径**
   （`PopScope.onPopInvokedWithResult` -> `_handleBack()`），一起失效指向公共路径；
2. 定制层探针实测 WebView 侧 `history.length === 1` 恒定、`redirectCount = 0`、
   零 `pushState` —— **网页历史是干净的**，`webHistory` 分支无辜；
3. 路由表（`lib/app/app.dart`）：`/dsh` 与 `/dsh/:id` 是**顶层路由**，
   与 `/`（设备列表）平级。深链 `qianxun://app/dsh` 冷启动/恢复时，
   GoRouter 的栈只有 `[/dsh]` 一层，**`/` 不在栈底** ->
   `navigator.canPop()` = false -> `decideBackAction` 走 `exit` ->
   `navigator.maybePop()` 在根上是 no-op（代码注释里「交给系统退出 App」
   的假设不成立）-> 返回彻底失效。

**修法**：把 `dsh` / `dsh/:connectionId` **嵌套到 `/` 之下**（子路径不带
`/` 前缀）。任何方式进入 DSH 页（深链 / 进程恢复 / 点卡片 push），
栈都变成 `[/ -> /dsh/...]`，返回自然弹回设备列表。

**真机验证（三个场景全过）**：

| 场景                       | 修复前       | 修复后         |
| -------------------------- | ------------ | -------------- |
| 深链进入 DSH -> 返回       | 6 连点无反应 | 一次回设备列表 |
| 点卡片进入 -> 返回（回归） | 正常         | 正常           |
| 键盘 -> BACK 收起 -> 返回  | -            | 两段都正常     |
