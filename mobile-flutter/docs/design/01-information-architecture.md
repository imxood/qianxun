## 0. 先把代码里已经确定的事实摆出来

设计不能凭空假设。这一节列的是我在写这份文档时从代码里读出来的硬事实,
后面每一条设计决定都落在这些事实上。

### 0.1 会话列表能拿到什么

`lib/data/models/session.dart` 的 `SessionSummary` 是 `session/list` 的完整映射:

| 字段 | 用途 | 注意 |
| --- | --- | --- |
| `sessionId` | 身份 | 唯一可靠的主键 |
| `updatedAt` | 排序 | 毫秒时间戳 |
| `running` | 「agent 现在在跑」 | **冷会话 / 未附着会话恒为 false** |
| `blank` | 一轮都没跑过 | 参考客户端用它过滤掉空会话 |
| `parentSessionId` | 子 agent 判定 | 非空即子会话 |
| `cwd` | 项目识别 | 完整绝对路径 |
| `agentPreset` | 预设名 | 顶层优先,缺失时取投影 |
| `agentAvailable` | 是否还能进去 | `false` = 点进去进不去(子 agent 跑完) |
| `projections['title']` | 标题 | **标题只存在于投影,顶层没有 `title` 字段** |
| `projections['turnOutline']` | 每轮「问了什么 / 答了什么」 | 宿主的现成摘要 |
| `projections['sessionStats']` | turns / steps / llmMs / toolMs / ttftMs | |
| `projections['tokenUsage']` | 输出 token 等 | |
| `projections['contextPressure'].projectedTokens` | 上下文占用 | |

**关键缺失:列表里没有任何「这个会话正在等用户回答」的字段。**
`running` 只表示 agent 在跑,不表示它卡住了。等答状态只能从事件流里合成,
见 §0.2。这是本设计里最大的一个风险点。

### 0.2 待答交互是连接级的,不是会话级的

`lib/features/workspace/application/interaction_controller.dart` 的注释写得很直白:

> `$events` 上的 waterfall 是**全连接范围**的,不属于某个会话,所以这个状态挂在
> 连接级,而不是会话级:哪怕用户正在看 A 会话,B 会话的审批请求也必须能弹出来。

waterfall 帧的形状(`README.md` 与 `stream_mux.dart`):

```
event = approval/request | user-questions/request
eventId
agentId          <-- 注意:不是 sessionId
request          <-- { toolName, callId?, reason? } 或 { questions[] }
```

回应只有四个结局:审批 `allowed-once` / `rejected` / `cancelled` / `unavailable`;
提问必须**逐条**给出应答,否则宿主整份拒收,工具会永远挂着。

**`agentId` 能不能对上 `sessionId`,决定了整份设计的成败。**
参考客户端 `TerminalPanel.kt:186` 直接把 `sessionId` 塞进 `agentId` 字段
(`put("agentId", JsonPrimitive(key.sessionId))`),说明那套 harness 里两者同值。
我们这套网关没写明。§10 里这是第一条待验证项,并且我给了一个降级方案。

### 0.3 当前实现已经是路由栈,不是标签页

`lib/app/app.dart`:

```
/                      ConnectionsScreen
/workspace             SessionsScreen
/workspace/:sessionId  SessionScreen
/logs                  LogsScreen
```

注释里已经记下了一个踩坑:必须用 `push` 而不是 `go`,否则返回键没有可 pop 的页面,
Android 直接杀进程,表现就是「一按返回就退出程序」。本设计在这套栈上做加法,不推翻它。

### 0.4 现有的待答提示条已经是「抢占焦点」的定位

`pending_interaction_bar.dart` 的文件头注释:

> 固定贴在底部、压在输入框之上。这是整个 App 里**唯一**允许抢焦点的…

它已经区分了两种待答:审批用实心方块(阻断),提问用描边(可延后)。
本设计沿用这个区分,但把它的**呈现形态**从「一条会消失的提示」改成「一个不会消失的驻留条」,
理由见 §5.4。

### 0.5 设计令牌已经定调,不要推翻

`qx_tokens.dart` 的自我定位:

> 这是一台**放在口袋里的开发机控制台**,不是消费级 App。

已有:状态四色(运行=青、等待=琥珀、完成=蓝、失败=赤、离线=灰)、暗色画布
`#0B0F14`(非纯黑)、8dp 间距刻度、小圆角克制、三档动效。
类型:display 32 / title 20 / body 15.5 / caption 13 / micro 11.5 / code 13 / ident 12。

这份文档不改这个基调,只在它上面做**信息结构**的决定。

## 1. 核心洞察 (The core insight)

千寻移动端不是一个聊天客户端,它是**一台正在干活的机器的遥控器**,而手机唯一的
本职是让人的在场**在必要时精确出现**:没事的时候彻底安静,agent 卡住的时候无法被忽略。
用户不在手机上读东西,用户只在手机上**确认、回答、纠偏**。

由此推出三条贯穿全文的原则:

1. **注意力是最贵的资源,不能平均分配。** 屏幕上任何一处会动的东西都在花用户注意力。
   只有两种东西该动:agent 真的在产生新事件,或者 agent 真的卡住了。其余全部静止。
2. **状态要能被一眼扫过,而不是被读出来。** 「20 条会话里哪条需要我」必须在
   1 秒内完成,这要求状态用**位置 + 形状 + 文字**三重编码,而不只是颜色。
3. **手机上唯一值得做的决定是「回答 / 不回答」。** 任何需要超过 3 次点击、
   或者需要看清长文本才能做的决定,都属于桌面端。

### 1.1 三个问题到结构的映射

用户只有三个问题,结构必须从这三个问题长出来,而不是从「有哪些页面」长出来。

| 用户的问题 | 需要的答案 | 结构上的归属 | 出现时机 |
| --- | --- | --- | --- |
| Q1 它现在在干什么 | 当前工具 + 上次进展时刻 | **行内状态轨**(§4)+ 详情页粘性活动条(§6) | 常驻 |
| Q2 它刚做了什么决定 | 最近一次**回复**,不是提问 | 行内第二行(§4)+ 转录(§3.4) | 常驻 |
| Q3 它卡住等我 | 谁卡住、要什么、怎么答 | **接管层**(§5) | 事件驱动 |

注意 Q2 的方向性:会话行第二行现在放的是 `turnOutline.last.prompt`,
也就是**用户自己刚说的话**。这是错的。用户已经知道自己说了什么,
他不知道的是 agent **据此做了什么**。所以第二行应该优先取
`turnOutline.last.response`,只有在它为空时才回落到 prompt。

这条改动看起来只是换一个字段,但它把整个列表从「用户输入的回声」变成了
「agent 产出的索引」。这是本设计对现有实现最重要的一处修正。

## 2. 信息架构 (Information architecture)

### 2.1 顶层:不要标签页,也不要抽屉

先排除两个常见答案。

**标签页(底部 2-3 个 tab)**:这个 App 只有**一个工作面**:某台电脑上的会话。
给一个单工作面的 App 配永久底栏,等于为「设置」这种一个月点两次的目的地,
永久付出每次会话列表的 56dp 高度和一次点击跳转。**代价常驻,收益偶发,不划算。**

**抽屉**:抽屉把列表**藏起来**。而这个 App 的核心动作恰恰是「扫一眼列表」。
把要被扫的东西收进抽屉,等于强迫每次检查都做两次开合。参考客户端把会话列表放在
抽屉里(`ChatListDrawer`),那是因为它的根是**单会话聊天**,会话列表是次要导航。
我们的根恰恰相反:**根就是列表本身**。所以不抄。

**结论:单栈 + 一层与导航正交的全局层。**

- 导航只有一条栈:连接 → 会话列表 → 会话详情。
- 待答、连接状态这两个东西**不属于任何栈上的位置**,它们是浮在栈之上的全局层。
  这是本设计里最重要的一条结构判断:待答不是一个页面,它是**横切切面**。

### 2.2 屏幕树

```
千寻 (App)
│
├─ 全局层 (Global layer,浮在导航之上,不属于任何屏幕)
│   ├─ 连接状态条 ...... 连接中 / 已连接 / 重连中 / 离线 / 需重新配对
│   └─ 待答队列 ........ 0..n 条,连接级,跨会话;驻留,不自动消失 (§5)
│
├─ /connections  连接与配对 (PC 选择器)
│   └─ 配对面板 ...... URL / 二维码 / 手填 host:port,做成底部弹层,不是独立路由
│
├─ /workspace  会话列表  ← 冷启动默认落点 (§2.3)
│   └─ /workspace/:sessionId  会话详情 = 转录
│       ├─ [弹层] 会话信息 ...... §3.5,右侧抽屉,带上下文分段计量条
│       ├─ [弹层] 步骤 ........... §3.5,按轮次的动作审计,不是顶层标签页
│       └─ [接管] 回答面板 ....... §5,模态,点外面不关闭
│
└─ /settings  设置 (从会话列表右上角 push 进来)
    ├─ 连接 ......... 跳 /connections
    ├─ 运行日志 ...... 跳 /logs
    ├─ 外观 ......... 跟随系统 / 常暗
    └─ 关于 ......... 版本、传输方式说明(明文 + VPN)
```

日志**不进**设置页的正文,直接跳 `/logs`,但入口只在设置里。
理由:日志是排障工具,不是设置项;把它和「外观」并列会暗示它是可配置的。

### 2.3 冷启动的 2 秒:落点必须是会话列表,不是连接页

现有实现把 `/`(ConnectionsScreen)当启动落点,这是**每天都要错一次**的决定。
用户的实际动作是:掏出手机,打开,看自己那个 agent 还在不在跑。
他不会想「先选一台电脑」。只要上次那台还在、还能连上,
App 就应该**直接落在会话列表**,把连接页完全跳过。

落点规则,按顺序判断:

| 条件 | 落点 |
| --- | --- |
| 有且仅有 1 台已保存电脑,且 3 秒内连上 | `/workspace`(自动选中它) |
| 多台电脑,上次用的那台还在线 | `/workspace`(选中上次用的) |
| 多台电脑,上次用的那台离线 | `/connections`,并在顶部直接说哪台掉线 |
| 一台都没有 / 全部配对失效 | `/connections` + 自动打开配对面板 |

「3 秒内连上」这个阈值是刻意的:连接很快时先显示列表再让它就绪,
用户看到的是骨架行然后填满内容,这个过程本身就是状态信息(§3.2);
连接很慢时先显示连接页,用户至少知道 App 没死。

**第一屏要回答的,按顺序,只有这三件事:**
1. 我的 agent 现在有没有卡住(顶部待答队列,哪怕为空也占位显示状态)。
2. 有几条在跑(筛选芯片上的计数)。
3. 最近动过的那条在干什么(列表第一行)。

标题、副标题、欢迎语一律不要。参考客户端的连接页上写着
「DSH Mobile mirrors the DeepSeek Harness running on your computer」,
这句是在复述 App 名字,不回答上面任何一个问题,删掉。

## 3. 逐屏设计 (Screen-by-screen design)

### 3.1 /connections

**回答的问题**:我连的是哪台电脑?怎么加一台?

**布局**:一个列表,不是表单页。

```
┌─────────────────────────────────┐
│  ‹                              │   ← 返回,仅当栈深 > 1 时出现
│  连接                           │
│                                 │
│  ●  台式机              在线    │   ← 状态点 + 名称(16/600) + 状态字(12)
│    192.168.1.23:23090           │   ← host:port(等宽,12,弱化)
│                                 │   ← 整行可点,进入 /workspace
│  ◐  笔记本              连接中  │
│    100.88.12.4:23090            │
│                                 │
│  ○  家里那台            离线    │
│    离线于 2 小时前              │
│                                 │
├─────────────────────────────────┤
│                                 │
│  ＋ 添加电脑                    │   ← 48dp 高,主色描边按钮,不是 FAB
│                                 │
└─────────────────────────────────┘
```

- 不做品牌区、不做 logo、不做欢迎语、不做「Preview」这类按钮。参考客户端的
  `home.png` 上半屏(巨大 logo + 产品名 + 复述句 + Preview 按钮 + 橙色警告条)
  占掉约 45% 的竖屏空间,一条有效信息都没有。全部砍掉。
- **警告条要重新定位。** 参考客户端把「harness 没有鉴权,只连信任的网络」做成
  橙色警告条挂在首页。我们的传输同样是明文 HTTP + WebSocket、只靠 VPN 兜底,
  但这句话的正确位置是**添加电脑时的确认页**和**设置里的关于页**,
  不是每一次打开都吼一遍。第一次配对时讲一次,之后只在设置里留着。
  常驻警告条会让真正的警告(比如「配对已失效」)失去力量。
- 添加电脑 → 底部弹层,三个 tab:`扫码`(默认) / 粘贴链接 / 手填`。
  手填只留 `host` 与 `port` 两个字段(参考客户端也是这样,是对的),
  多余的开关全部删掉:「Wi-Fi 自动连接」「自动重连上次」这类开关,
  对一个只有一两台电脑的用户是配置负担。自动重连默认开着,做成行为而不是开关。

**状态**:

| 状态 | 标题 | 说明文案 | 动作 |
| --- | --- | --- | --- |
| 一台都没有 | `还没有连接电脑` | `千寻电脑端在运行时,手机扫码就能加上。` | `添加电脑` |
| 扫码中 | `把电脑上的二维码对准这里` | `二维码在电脑端千寻的「手机连接」里。` | `手动输入` |
| 配对链接无效 | `这个链接用不了` | `可能已经过期了。在电脑上重新生成一次。` | `重新输入` |
| 全部离线 | `连不上这些电脑` | `手机和电脑不在同一个网络里。确认电脑端千寻在运行。` | `重试` |

### 3.2 /workspace 会话列表

**回答的问题**:有哪几条在跑?哪一条卡住等我?最近动的那条在干什么?

这是主屏,详细设计在 §4,这里只给整体骨架。

```
┌─────────────────────────────────┐
│  台式机                    ⓘ  ⋮ │   ← PC 名(可点=切换电脑) + 筛选 + 更多
│  3 条运行中 · 1 条等你          │   ← 一行状态摘要,永远占位,不因空而消失
├─────────────────────────────────┤
│  🔍 搜索会话                     │   ← 已在用 session/search,保持
├─────────────────────────────────┤
│ [全部 24] [等我 1] [运行中 3]     │   ← 筛选芯片带计数,横向滚动
├─────────────────────────────────┤
│▎等你回答 · Bash · 已等 12 分钟   │   ← 被卡住的行:形态与普通行不同(§4.4)
│▎拒绝执行 rm -rf build/          │
│▎台式机  18 轮 · 412k ctx      刚刚│
├─────────────────────────────────┤
│▎● 第 12 轮 · 4 秒前             │   ← 在跑的行
│▎Bash :: cargo build --release   │
│▎iot_tool_cloud  31 轮 · 365k  2 分│
├─────────────────────────────────┤
│  补齐 CDP 探针文档               │   ← 空闲的行,状态轨是 40% 不透明中性
│  已经在 events 里打印 waterfall │
│  mobile-flutter  7 轮 · 88k    2 小时│
└─────────────────────────────────┘
```

**筛选芯片是这一屏的关键装置。** 有了它,3 条和 300 条会话的差别就只是默认排序
和分组的问题,而不是信息结构的问题。它带计数,所以芯片本身就回答了「有几条在跑」,
不用滚列表去数。

### 3.3 待答队列条(全局层,常驻)

它浮在**每一屏**的底部,在会话列表上压住列表底部,在会话详情上压住输入框之上。
高度 56dp。

```
┌─────────────────────────────────┐
│ ⛔ 等你回答 · Bash · 已等 12 分钟 │ 56dp,琥珀,实心方块图标
│                      [ 回答 ]   │   48dp 高按钮
└─────────────────────────────────┘
```

**空的时候也占位**,但变成中性 28dp 的一行:
`没有待答请求`,或者干脆不显示,只在有内容时出现。我倾向后者:
一条写着「没有待答」的条是纯噪音,它在视觉上把重要状态稀释了。
但**位置必须固定**(不能有内容时把它挤到别处),否则用户学不会去看那里。

多于 1 条时,显示最紧急的一条 + 计数:`等你回答 · 3 条待处理`。

### 3.4 /workspace/:sessionId 会话详情

**回答的问题**:它刚做了什么决定?卡住时具体要我答什么?

**布局(自上而下)**:

```
┌─────────────────────────────────┐
│  ‹  补齐 CDP 探针文档        ⓘ  │  ← 返回 + 标题 + 信息按钮(抽屉)
├─────────────────────────────────┤
│● 第 12 轮 · Bash · 4 秒前 [停止] │  ← 粘性活动条,§6
├─────────────────────────────────┤
│                                 │
│  [转录,见下]                     │
│                                 │
├─────────────────────────────────┤
│ [待答队列条,全局层]              │
├─────────────────────────────────┤
│  给 agent 发消息…          ↑    │  ← 输入栏
│  [排队 ▾]                        │
└─────────────────────────────────┘
```

**转录的行类型与视觉权重**,按「用户在地铁上要不要读它」排序:

| 行类型 | 默认状态 | 视觉处理 | 理由 |
| --- | --- | --- | --- |
| assistant 消息 | 展开 | 全宽无气泡,`prose` 15.5/1.55 | **这是结论,是 Q2 的答案** |
| user 消息 | 展开 | 右对齐气泡 + 淡主色底 | 「我刚说了什么」需要可定位 |
| todo 列表 | 展开 | 紧凑卡,`3/7` 计数在标题右侧 | 待办是「进度条」,agent 正在推它 |
| tool 调用 | **折叠** | 单行 `> Bash :: cargo build --release` | 一次 grep 可能 300 行输出,不该滚过去 |
| reasoning | **折叠** | 单行 `> 思考 14 行` | 内心戏不是结论 |
| turn 分隔 | 折叠成细线 | 只在长会话里显示 `第 12 轮` | 结构,不是内容 |
| command notice | 展开 | 中性小字一行 | 低频 |

**这里我不同意参考客户端。** 看它的 `chat.png`:整个 Chat 标签页是 19 行
`> Bash :: ...` 展开行,一条 assistant 结论都看不到。那不是 Chat,那是一份日志
被放在了 Chat 的位置上。对我们的用户,Q2 问的是「它刚决定/改了什么」,
答案在 assistant 消息里,不在工具名里。工具名只是通往结论的路。

所以:**一行工具调用不是内容,是一扇门。** 默认折叠是对的(参考这点做对了),
但一屏 19 行折叠的工具名,等于把「结论」藏到了这一屏之外。

我的处理,叫**轮次摘要**:每个 turn 分隔处渲染一行摘要,聚合这一轮做了什么。
摘要数据用现成的 `sessionStats.turns` 和 `turnOutline[i].response`,
不新增接口:

```
━━━ 第 12 轮 · 6 步 · 3 分 12 秒 ━━━━━━━━━━━━━━━━━━━
  ✓ 改了 disk.rs 的 rename_all 映射
  ✓ 加了 rename_all_fields 断言
  ! gradle build 失败:SDK location not found
```
✓/! 是形状 + 颜色 + 文字三重编码,不靠颜色单独承载。

只有当这一轮的 assistant 消息**很短**(比如只有一句「好的,已完成」)时,
才退化成 `6 步 · 3 分 12 秒`一行,让用户自己决定要不要展开。
默认视图因此始终是「结论优先」,而需要审计时点开摘要拿到全部工具行。

**信息按钮(ⓘ)打开右侧抽屉**,内容见 §3.5。

### 3.5 会话信息抽屉 / 步骤抽屉

**这两个是弹层,不是顶层标签页。** 理由见 §4.5 和 §9(我们要砍掉 Trajectory 顶层页)。

会话信息抽屉,采纳参考客户端的 `Title :: value` 排版装置,它是好东西:
一套克制的、扫得动的元数据语法。

```
┌───────────────────────────────┐
│ 会话信息                      │
├───────────────────────────────┤
│ 会话名称 :: 补齐 CDP 探针文档 │

│ 主机      :: 0.0.1            │
│ 会话 ID   :: ses_9f2a…(可复制) │
├───────────────────────────────┤
│ 上下文 :: 49%                 │
│ ▓▓▓▓▓▓▓▓░░░░░░░░░░░░         │

└───────────────────────────────┘

采纳的三点:
- `Title :: value` 的排版装置,全 App 统一用这一套元数据语法。
- 分段上下文计量条(System / Tools / Messages)+ 图例。我们手上有
  `contextPressure.projectedTokens` 和 `tokenUsage`,三段能凑出来。
- `▸` 展开行承载二级信息(子 agent、排队轮次、后台 job)。

**不采纳的**:参考客户端把 `TTFT 4.3s · 80 tok/s` 常驻在聊天页底部
(`chat.png` 最下面那行 `15 turns · 283 steps · TTFT 4.3s · 80 tok/s · Cache 99%`)。
这些是**你电脑上的引擎指标**,不是手机上 4 秒扫视能提取的信息。它们属于这里,
不属于会话页底部。搬过来。

### 3.6 /logs

**这是全 App 密度最高的一屏**,密度定位 90% 靠「原始工具」。

```

「传输方式」这一行是**故意留在设置里的**。它把一个安全事实写在用户随时能找到、

## 4. 会话行,重新设计 (The session row, redesigned)

这是主屏,所以写得最细。

### 4.1 现有版本错在哪

现在的每行(实测截图)是:

```
┌───────────────────────────────────────┐
│ ●  补齐 CDP 探针文档                  │  圆点 + 标题(2 行)
│    问一下 events 里 waterfall 的字段   │  2 行预览
│    空闲 · iot_tool_cloud · 7 轮 ·     │  一串会换行的元数据
│    365k ctx · ↑152k · 2 小时前         │
└───────────────────────────────────────┘
```

六个具体缺陷,逐条对上用户反馈里的「太简陋」:

1. **六样东西一个权重。** 状态、时间、cwd、轮次、token、预览全在正文灰度里,
   眼睛找不到该看哪一处。
2. **状态是元数据流里的第一个词,不是结构。** 「空闲」和「2 小时前」在同一个
   `Wrap` 里、同一个字号、同一个颜色槽位。视觉上它们是平级的。
3. **元数据会换行。** 一次 `Wrap` 之后,行高从 3 行变成 4 行,列表高度随机,
   扫视时行与行之间没有对齐的基线可循。这是「没有层级」的直接原因。
4. **卡片化。** 20 个圆角卡片 + 描边,每张卡都在喊「我是重要的」,结果没有一条
   是重要的。卡片是**同质内容的正确容器**,而会话列表是同质的。
5. **第二行是用户自己说的话。** 用户不需要读自己的回声(见 §1.1)。
6. **20 行里哪条卡住了,看不出来。** 运行中和空闲只差一个点的颜色和一个词。

### 4.2 新行:左侧状态轨 + 固定三格元数据 + 条件活动行

去掉卡片。改成分隔线列表,这是同质内容的原生答案,而且**每行省下约 14dp**。

**几何规格:**

```
┌─ 4dp 状态轨 ─┬─ 20dp 缩进 ───────────────────────────────┐
│              │                                          │
│  ●           │  标题 15.5 / 600 / 1 行 / 省略            │  1 行 22dp
│  (10dp 圆点) │  上次回复 13 / 400 / 1 行 / 省略 / 72%     │  1 行 19dp
│              │  meta 三格 11.5 / 500 / 1 行 / 不换行      │  1 行 16dp
│              │  活动行 12 / 等宽 / 1 行(仅运行/卡住时)    │  1 行 17dp
└──────────────┴──────────────────────────────────────────┘
行高:空闲 57dp + 1dp 分隔线 / 在跑或卡住 74dp
行内左边距 = 状态轨 4 + 间距 8 + 缩进 8 = 20dp
右边距 16dp
```

### 4.3 元数据三格:永不换行

这是修掉「一串换行元数据」的具体做法。**用 `Row` + `Flexible`,不用 `Wrap`。**

```
[ 项目名(cwd 末段,Flexible,先被压缩) ]  [ 7 轮 · 88k ]  [      2 小时前 ]
   ↑ 可缩到省略号,最少 8 字符              ↑ 不压缩         ↑ 固定 52dp,右对齐
```

三格都有上限,所以三格永远不会跑到第四行。当项目名太长被压缩时,
用户仍然看得到末尾的目录名,足够认出是哪个仓库。
等宽字体只给 token 数与时间(`QxType.ident`),项目名用正文字体。
理由:token 数和时间是**量**,项目名是**词**,用不同字形区分「量」和「词」,
比用颜色区分更快。

固定顺序,永远不变:`项目 · 轮次/上下文 · 时间`。
时间永远在最右,因为它是排序键,应该落在一条垂直线上,
用户上下扫的时候眼睛沿着右边缘走。

### 4.4 状态轨:形状 + 图标 + 文字,三重编码

硬规则:**不用颜色单独承载状态。** 每种状态同时有**形状**、**图标**、**文字**。

| 状态 | 轨道形状 | 符号 | 首行文字 | 第四行(活动行) |
| --- | --- | --- | --- | --- |
| **等你回答** | 3dp 实心琥珀条,**满高** | 实心方块 ⛔ | `等你回答 · 已等 12 分钟` | `拒绝执行 rm -rf build/`(等宽) |
| **在跑** | 2dp 实心青条,**随脉冲轻微明暗** | 实心圆点 ● | `第 12 轮 · 4 秒前` | `Bash :: cargo build --release`(等宽) |
| **已结束(子 agent)** | 2dp **虚线**中性条 | 斜杠圆 ⊘ | `子 agent 已结束` | 无 |
| **空闲** | 2dp 中性条,40% 不透明 | 无 | 时间只在 meta 行 | 无 |

四种状态在**缩略到 1/3 尺寸**时仍可区分:
虚线 vs 实线、满高 vs 细条、有无符号。这是「扫一眼」能成立的原因,
不依赖颜色。

**「等你回答」的形状必须与其他三种明显不同。** 它是满高的,其他是细的;
它是实心的,空闲是半透明的;它有唯一的方形符号。
用户在一屏 20 行里认出它,靠的就是「有一行比别的粗」。

### 4.5 排序与提升:不只是样式,是位置

给状态上色是不够的。**卡住的会话必须被提到列表最上面。**

默认顺序:

```
1. 等你回答        (按等待时长倒序,等最久的最急)
2. 在跑            (按 updatedAt 倒序)
3. 其余            (按 updatedAt 倒序)
```

三条待办记录的处理是有先后的:

1. **4 条以内**:不排序干预,保持 `updatedAt` 倒序,只靠形态区分。
   超过 4 条的会话列表本身就没有「顺序」语义,强行提升会让用户找不到他记得的那条。
2. **5 到 20 条**:提升卡住的和运行中的,分组之间加一行粘性小标题
   (`等你回答 (1)` / `运行中 (3)`),组内 `updatedAt` 倒序。
3. **超过 20 条**:不提升,靠筛选芯片。此时列表本身已经是工作区而不是收件箱,
   提升会破坏用户对位置的记忆。筛选芯片的计数仍然提示有卡住的。

**理由**:提升只在「卡住的数量与用户的心智容量匹配」时有用。
3 条卡住时,提升就是指路;30 条卡住时,提升就是一片红色的海洋,
用户还是要用筛选。

### 4.6 3 条 vs 300 条

| 会话数 | 布局 | 分组 | 搜索 |
| --- | --- | --- | --- |
| 1 到 4 | 扁平,行高可以放宽到 66dp,活动行常显 | 无 | 搜索框隐藏(没什么可搜的) |
| 5 到 20 | §4.2 默认 | 粘性小标题 | 搜索框显示 |
| 21 到 100 | §4.2 默认,恢复 57/74dp | 按 `cwd` 末段分项目,吸顶 | 搜索框显示 |
| 100 以上 | 同上,分页加载(`session/page`) | 同上 | 搜索框显示,并提示 `仅显示最近 100 条` |

**不做的事**:不按项目分组少于 21 条的列表。3 条会话按项目分组,
每组 1 条,分组标题比内容还高,纯噪音。

**不做的事**:不做无限滚动 + 虚拟列表之外的复杂化。`ListView.builder` 够用,
行高固定 57/74dp 让滚动性能没有压力。

### 4.7 行的可点区域与次级动作

- **整行可点**,进会话详情。48dp 最小高度已由行高 57/74dp 满足。
- **长按**出行操作菜单:`置顶` / `复制会话 ID` / `归档`。
  这是唯一的手势入口,不占用任何可见控件。
- **不**在行上放图标按钮。20 行乘 2 个按钮 = 40 个视觉噪声源,
  而且这些动作一个月用一次。参考客户端的会话行也是整行点开,这点是对的。

### 4.8 文案

会话行上不写任何解释性文字。四个位置上的字符串就是全部:

| 位置 | 取值 |
| --- | --- |
| 活动行(等回答) | `等你回答 · Bash · 已等 12 分钟` |
| 活动行(在跑) | `第 12 轮 · 4 秒前` |
| 第二行 | `turnOutline.last.response`,空则 `turnOutline.last.prompt` |
| meta 行 | `{cwd 末段}` `{N 轮} · {context} ctx` `{相对时间}` |

「已等 12 分钟」里的数字每 10 秒刷新一次,不需要用户下拉。

## 5. 被你卡住的流程 (The blocked-on-you flow)

### 5.1 为什么这个流程值得用最强的手段

我把「卡住」当成**整个产品里唯一允许抢焦点的事件**,理由有三条,都基于产品事实:

1. **代价是真金白银的时钟。** agent 阻塞时进度是**零**,不是变慢。
   用户在通勤,这一卡可能是 40 分钟。用户为了「不被打扰」而付的,
   是 PC 上白跑 40 分钟的任务。
2. **它是一次性且低频的。** 一个长任务里审批几次、提问几次。
   低频意味着打断不会疲劳,这是能安全使用强手段的前提。
3. **它同时是危险的。** 盲点「允许」可能放行一条 `rm -rf`。
   所以打断的强度要够,但**回答界面必须提供足够信息让人不盲点**(§5.5)。

第 3 点是对第 1 点的约束:我主张强打断,但**前提是不打断就无法做出安全判断**。
所以审批面板必须显示工具参数。如果网关给不出参数(见 §10.5),
那这个事件就应该**降级为弱打断 + 强制去桌面**,而不是让人在手机上盲点。

### 5.2 升级阶梯:四层,每层都有明确理由

| 层 | 触发条件 | 形态 | 强度 | 理由 |
| --- | --- | --- | --- | --- |
| **L0 应用外** | App 在后台,socket 仍活着 | 本地通知 + 应用角标 | 弱 | 明文 VPN 上没有可靠推送通道(§10.2),能做多少做多少 |
| **L1 应用内全局** | 任何一屏,任何位置 | 底部 56dp 驻留条 + 角标 | 中 | 保证「任何一屏都能看到」,不自动消失,不遮内容 |
| **L2 接管面板** | 用户正在**相关会话**里 | 模态底部面板,60% 遮罩,**点外面不关** | 强 | 人已经在现场了,这是完成任务的最后一步 |
| **L3 从不** | 任何情况 | 全屏警报 / 声音循环 / 震动 | 无 | 见下 |

**L3 为什么不做。** 一个未被回答的审批**不会过期**。
既然它不会消失,L1 的驻留条 + 角标已经保证了用户在移开视线之前会看到它。
再叠一层声音和震动,买到的是「用户被吓到后随手点允许」,
卖掉的却是「用户在整个 App 里的信任额度」。
一个每天要用几十次的东西,不能在上面撒谎式地喊。
L2 是我会给的最强手段:它在正确的位置,提供正确的信息,由**他自己的拇指**完成。

L2 的「点外面不关」要配一个显式逃生口:`稍后`(§5.4),
否则用户会被困住,下次就不敢开这个 App 了。

### 5.3 L1 驻留条的形态

```
┌─────────────────────────────────┐
│ ⛔  等你回答 · Bash · 已等 12 分钟 │  56dp
│                        [ 回答 ]  │  48dp
└─────────────────────────────────┘
   ↑ 3dp 琥珀左边条,与会话行的状态轨同一视觉语言
```

- **不自动消失。** 只有在对应 waterfall 收到 `cancel` 帧
  (别的客户端答了 / 宿主撤了)时才收走,并在原地换成一行中性提示 3 秒:
  `已由其它客户端回答`。
- **多条时**显示最紧急的一条 + 计数:`等你回答 · 3 条待处理`。
  审批优先于提问(审批挡住的是 agent 的动作,与现有实现一致)。
- 点击条身 ≠ 点击「回答」。点条身展开一个精简列表让你选是哪一条,
  点「回答」直接进面板。只有一条时两者等价。

### 5.4 L2 接管面板:审批

```
╔═════════════════════════════════╗
║  拖动条(不可拖关,只有按钮可关)  ║
╠═════════════════════════════════╣
║  ⛔  需要批准                    ║  标题 20/600
║      已等 12 分钟                ║  12/500,琥珀,与标题同一块
║                                 ║
║  工具                          ║  Title::value 语法
║    Bash                        ║
║  原因                          ║
║    agent 想清理构建产物          ║  prose,可换行
║  命令                          ║
║  ┌───────────────────────────┐  ║
║  │ rm -rf build/             │  ║  等宽 13,横向滚动
║  └───────────────────────────┘  ║  不换行,长命令换行就不可读
║  工作目录 :: deepseek-harness   ║
║                                 ║
╠═════════════════════════════════╣
║  [      拒绝      ] [ 允许这一次 ]│  两个 56dp,主操作在右
║                                 ║
║  稍后                          ║  文字按钮,48dp 命中区
╚═════════════════════════════════╝
```

要点:

- **`命令` 是这个面板的核心。** 如果只能显示工具名,那用户在手机上做的决定
  没有信息量,只能盲点。`ApprovalRequest.reason` 是可选的,
  所以能显示命令的唯一路径是从 `callId` 反查工具调用的参数(§10.5)。
  查不到时,面板必须**明说**而不是留白:
  `这次调用没有带参数,无法在这里判断。请到电脑上确认。`
  然后**只给「拒绝」和「稍后」**,把「允许」置灰。
  这是本设计里我唯一一处主动**减少**功能的地方,因为盲目授权的代价
  高于少一个功能。
- **`允许这一次`,不是「允许」。** 语义要对齐宿主的 `allowed-once`。
  手机上**不提供「始终允许」**(§9)。一次性的授权即使点错,伤害面也被限制在一次调用。
- **`拒绝` 不可撤销。** 点下去就发出去了。所以它做成次要样式(描边),
  主操作是「允许这一次」。同时拒绝后给一个 4 秒的撤销窗口是不诚实的,
  因为帧已经发出去了。我们不在这里撒谎。
- 面板**允许被拒绝后不关闭**地回到列表:如果用户点了「拒绝」,
  面板收起,驻留条消失,并在转录里插一行 notice:
  `你拒绝了这次调用 · 14:32`。历史必须留痕。

### 5.5 L2 接管面板:提问

提问和审批**强度不同**,因为提问不阻断执行,只阻断决策。
所以提问用同一个面板外观,但:

- 标题是 agent 的问题原文,**不给**「需要你批准」这类框架词。
- 单选:整行可点,48dp 高,选中态是**填充 + 勾** + 左侧 3dp 竖条(不靠颜色)。
- 多选:复选行 + 底部固定一个「提交回答(N)」,N 是已答条数。
- 自由文本:多行输入,`其他…` 固定在选项末尾。
- **必须能全部跳过**:宿主要求逐条应答(漏一条整份拒收,工具永远挂着)。
  所以未选择的项在提交时以**空选**提交,而不是不提交。
  按钮文案要说清这一点:`提交回答(2/3,未选按「无偏好」)`,太长,
  折成两行:`提交回答` + 下方 12px 灰字 `2/3 已答,未答按无偏好`。
- `关闭` 走 `rejected` + `code: cancelled`,**必须**是这个码,
  其他码会让等待一直挂着(现有实现注释已记录)。

### 5.6 阻塞状态下会话行的行为

卡住的会话在列表里必须表现出**它在等**,而不是「它在跑」。

对比:

| | 在跑 | 等你回答 |
| --- | --- | --- |
| 轨道 | 2dp 实心,脉冲 | 3dp 实心,**不脉冲**(它在静止地等) |
| 符号 | ● 圆点 | ⛔ 实心方块 |
| 首行 | `第 12 轮 · 4 秒前` | `等你回答 · 已等 12 分钟` |
| 活动行 | 当前工具(等宽) | 要批准的动作(等宽) |
| 倒计时 | 有 | **无**。审批没有已知时限,不要造一个假倒计时 |

最后一条是原则性的:没有过期机制的等待,显示倒计时就是在骗用户。

## 6. 实时活动设计 (Live activity design)

### 6.1 最有价值的那一条信息

不是「它在跑」(一个转圈就够了),而是:

> **它在跑什么工具,以及它多久没有新动作了。**

理由:「它在跑」只消除「它是不是死了」的焦虑,不能降低焦虑。
「它在 `cargo build`,已经 40 秒没有新动作」直接告诉你**该等还是该干预**,
这是可行动的信息。第二半尤其重要:
agent 卡在某个网络请求上五分钟,和一个正常跑 build 的五分钟,
在「转圈」这个 UI 下**长得一模一样**。

所以活动指示器的设计目标不是「证明它活着」,是「区分它在想、它在算、它卡住了」。

### 6.2 行内活动行(§4.2 的第四行)

格式固定为三段:`状态 · 工具 · 距上次事件时间`

```
● 第 12 轮 · Bash · 4 秒前
● 第 12 轮 · Edit · disk.rs · 1 分前
● 第 12 轮 · 等待中 · 90 秒没有新动作
```

- 三段用 `·` 分隔(与 `Title :: value` 是同一套分隔符语法)。
- 工具名用图标 + 名称,参数用等宽、弱化、末尾省略。
  直接采纳参考客户端的 `> Bash :: List GitHub workflows a…` 这个装置,
  它是对的:一行放下「哪个工具 + 干什么」。
- **「距上次事件时间」是这个设计的灵魂。** 它从 `updatedAt` 与事件到达时间算出,
  每 10 秒重算一次(不需要网络往返)。

### 6.3 静默阈值:90 秒

超过 90 秒没有新事件,活动行切到:

```
● 第 12 轮 · Bash · 90 秒没有新动作
```

同时状态符号从 ● 变成 ◐(半环),从青色降为琥珀色。
文字 + 形状 + 颜色三重编码,满足硬规则。

**为什么是 90 秒:** LLM 首 token 延迟(TTFT)在 4 到 5 秒量级,
工具调用(编译、装依赖、跑测试)在 10 秒到几分钟量级。
90 秒能区分「一个正常的长工具」和「真的不动了」,
同时短到不会在正常的长工具上误报。

**这个阈值应该可配。** 不同项目的 build 时间差一个数量级,
硬编码 90 秒一定会在某处误报。放设置里,默认 90 秒,给三个档:30s / 90s / 5min。

### 6.4 进度条:只在有事实时动

参考客户端聊天页底部有一条细的上下文条。**我同意它的位置(输入栏上方),
反对它的语义**:它现在显示的是上下文占用,一个跟「它在干什么」无关的量。

我的处理:那条上下文条**继续显示上下文占用**(它回答的是「还能聊多久」,
有价值),但活动行另外给一条 **2dp 的进度细线**,规则是:

- **只在收到真实事件时前进**(step/end、assistant 消息、tool/result)。
- 长时间没有事件时**静止**,并从青色渐变为琥珀。
- **永远不做不确定动画。** 一个自己转圈的进度条在说「有进展」,
  而我们其实不知道有没有。这是整个设计里最容易骗人的地方,不做。

进度线不给百分比数字。它是个信号,不是读数。

### 6.5 详情页粘性活动条

```
┌─────────────────────────────────┐
│● 第 12 轮 · Bash · 4 秒前   [停止] │
└─────────────────────────────────┘
```

- 贴在 AppBar 下面,转录滚动时**不动**(粘性)。
  用户的眼睛不需要来回找「它还在跑吗」。
- 右侧「停止」= 终止当前轮次,48dp 命中区,图标 + 长按提示说明。
  它在活动条里而不是只在 AppBar 里,因为「停止」和「当前在干什么」是同一个决定。
- 空闲时这条收成 28dp 的一行灰色:`空闲 · 上次 2 小时前`,
  **不消失**。消失会造成布局跳动,跳动会让用户在滑动中点错东西。

### 6.6 不做的

- 不做「agent 思考中…」的动画聊天气泡。这是消费级 AI 产品的语言,
  它暗示一种人格,而这里发生的是一次 RPC 等待。
- 不做实时打字机逐字渲染 assistant 消息。手机上流式逐字会让行高不停变化,
  用户点不到东西。整段到达、整段渲染,行高稳定。
  (流式本身仍然要接,只是 UI 上按块提交。)
- 不做每个会话独立的推送式动画。只有行内那个点是动的,别的地方一律静止。

## 7. 导航与返回 (Navigation & back behavior)

### 7.1 逐个决定

| 目标 | 选择 | 理由 |
| --- | --- | --- |
| 连接 / 配对 | **路由**,但只作落点,不是常驻 tab | 打开一次配一次。不配对就不看它,没理由常驻 |
| 会话列表 | **栈的根** | 90% 的使用时间在这里。它必须是「退不出去」的底 |
| 会话详情 | **push** | 明确的层级关系,返回=回列表,用户预期正确 |
| 会话信息 | **右侧抽屉** | 它是详情的补充,不是下一级。抽屉保留转录上下文,切换成本最低(采纳参考客户端) |
| 步骤 / Trajectory | **抽屉或详情里的筛选,不是顶层页** | 见 §9,这是我和参考客户端的主要分歧之一 |
| 运行日志 | **push 路由**,入口在设置 | 排障工具,不该和「外观」并列成设置项 |
| 设置 | **push 路由**,入口在列表右上角 | 低频目的地,不配底栏 |

### 7.2 返回的完整规则

「返回绝不能退出 App」这条要求,在每一层都要有明确行为:

| 所在位置 | 返回键的行为 |
| --- | --- |
| 接管面板(审批/提问) | 关闭面板 = `稍后`。驻留条**保留** |
| 会话信息 / 步骤抽屉 | 关闭抽屉 |
| 会话详情 | 回会话列表,**保留列表滚动位置和实时状态** |
| 会话列表 | 若有其他已保存电脑 → 打开 PC 切换器;否则回到 `/connections` |
| 会话列表(多台,当前这台离线) | 弹 PC 切换器,并把离线那台标出来 |
| `/connections`(栈底) | **才允许退出 App** |

关键点是最后两行:`/connections` 是唯一的根,是唯一允许退出的地方。
而 §2.3 的冷启动规则让用户**正常情况下根本不会停在 `/connections`**,
所以「返回退出」这件事在正常使用中不会发生。
现在的实现里返回会直接杀进程,那是因为 `go` 覆盖了栈;现在这套规则要求
**每一层显式接 `PopScope`**,不依赖默认行为。

### 7.3 通知与深链的栈构建

从通知点进来时,必须**构造栈**,不是替换:
`/connections > /workspace > /workspace/:id`,然后把会话详情放在栈顶。
用 `go` 直接落到详情页会让返回键无处可退,用户按一次返回就退出 App,
而他甚至还没看清任何东西。

### 7.4 PC 切换的位置

AppBar 上的 PC 名**就是切换器**,点击即展开 PC 列表弹层。
不另设一个图标按钮,也不进设置。理由:切换 PC 的频率比打开设置高一个数量级,
它必须在第一层可达。

## 8. 密度哲学 (Density philosophy)

### 8.1 我的位置:仪表盘,不是杂志,也不是终端

两个极端都成立过,都不对:

- **消费级大卡片**(等大圆角卡片网格、渐变、插画、模板化引导):
  每屏只能放 4 到 5 条信息,20 条会话要滚 5 屏,而且没有一处能承载状态。
  这正是我们现在的问题。
- **原始开发者工具**(满屏等宽、每行都是数据、无留白):
  能塞 30 条会话,但 assistant 的结论、审批的措辞、提问的选项
  这些**需要呼吸感的文本**被压成了数据行,人读不动。

我的位置是**仪表盘**:仪表盘的密度是按「这个控件要多快被读到」决定的,
不是全局统一的。转速表很密,车机导航的按钮很大,它们在同一个面板里共存。

**判断标准只有一个:这块内容是被「扫」还是被「读」。**
扫 → 密;读 → 松。同一屏里可以同时有两者,用形态区分。

### 8.2 每屏的落点

| 屏 | 密度 | 一句话理由 |
| --- | --- | --- |
| 会话列表 | **75% 密** | 纯扫视任务。一屏能放下多少条,就是多少条 |
| 会话详情(转录) | **50 / 50** | 结论要读(松),工具行要扫(密)。两种混排,靠形态区分 |
| 接管面板 | **30% 松** | 这是**决定**,不是阅读。参数要看得清,按钮要好按 |
| 会话信息抽屉 | **60% 密** | 元数据,扫的 |
| 运行日志 | **90% 密** | 它本来就是原始的,不做美化 |
| 设置 / 连接 | **40% 松** | 七个选项,不要挤 |

**转录那一栏 50/50 是本设计最实际的一处判断。** 它意味着转录**不能**统一成一种排版:
assistant 结论用 `prose` 15.5/1.55 带段间距,工具行用 `code` 13/1.5 单行折叠。
两个尺度并置,用户靠字号和字形自己就能区分「这是给我的」和「这是记录」,
不需要任何标签去解释。

### 8.3 等宽字体的纪律

这是「不滑向原始工具」的唯一有效手段:

**等宽只用于本来就是机器文本的东西:**
路径、命令、工具参数、session ID、token 数、日志行、时间戳。

**正文和标题永远不用等宽。** 会话标题是模型生成的自然语言,
用等宽会让它读起来像一行命令输出,这是「原始工具感」最主要的来源。

反过来,当前实现里 meta 行(`7 轮 · 365k ctx · ↑152k`)全部用正文字体,
这也是一种浪费:**token 数是量,应该用等宽**。等宽让数字对齐,
多行扫描时更容易比较大小。

### 8.4 从参考客户端采纳与拒绝的清单

**采纳(它们做对了):**

1. `> 工具名 :: 参数` 的单行工具展开行。密集、一行放下工具与用途。
2. `Title :: value` 的元数据排版装置,全 App 统一。
3. 分段上下文计量条 + 图例 + 行内指标。
4. 琥珀色 `Stopped` 状态胶囊(我们已有同源的四色语义,保留)。
5. 圆形发送按钮 + 细上下文条位于输入栏上方。
6. 侧滑抽屉承载会话信息(保留转录上下文)。
7. 会话行整行可点、不放图标按钮。
8. 连接页手填只留 `host` / `port`。

**拒绝(我认为它们错了):**

1. **Chat 标签页是一面工具行的墙。** 19 行折叠的 `Bash ::`,零条结论。
   Q2 的答案被埋在了这一屏之外。用「轮次摘要」替代(§3.4)。
2. **常驻的性能底栏**(`15 turns · 283 steps · TTFT 4.3s · 80 tok/s · Cache 99%`)。
   这是 PC 上的引擎指标,手机上 4 秒扫视提取不出信息量。搬进信息抽屉。
3. **Chat / Trajectory 两个顶层标签页。** 同一个会话两种顶层视图,
   把用户的去路变成两倍、转录的空间砍掉一半。Trajectory 降级为抽屉或筛选(§9)。
4. **连接页的品牌区**。巨大 logo + 产品名 + 复述句 + Preview 按钮 +
   橙色警告条 = 约 45% 的竖屏,零有效信息。全部砍掉,警告条移到配对确认与设置。
5. **标题栏三层堆叠**(会话名 + 模式选择器 + agent 计数 + 胶囊标签),
   在任何转录内容之前吃掉约 180dp。我们的标题栏只留:返回、标题、信息。

## 9. 我们要砍掉什么,以及为什么 (What we're cutting)

### 9.1 移动端不做子 agent 树

**参考客户端有完整的子 agent 抽屉**(`subagent.png`:12 个子 agent、名字 +
`Continuable` 状态)。我们**只做只读的一瞥,不做可下钻的树**。

保留:父会话行尾一个计数 `12 个子 agent`,点开是一个底部弹层,列出
名字 + 状态(在跑 / 已结束 / 可继续),像参考客户端那样。

砍掉:从子 agent 点进去看它的转录。

理由:用户在通勤时想知道的是「这 12 个子 agent 干完了吗,有几个卡住了」,
不是「3 号子 agent 第 7 步在干什么」。后者在手机上至少 5 次点击,
而且信息密度低到不值。父会话的轮次摘要已经包含了子 agent 的产出结论。
**树上最有价值的一层是计数,不是叶子。**

### 9.2 移动端不做模型切换与权限档位选择

参考客户端的输入栏有 `Full access ⌄` 加一个盾牌图标。我们**不提供任何修改**。

- `agentPreset` 在会话详情标题下方**只读**显示(比如 `iot_tool_cloud`),
  点它弹一个说明「在电脑上修改」并复制当前值。
- 理由:模型与权限档位改错了会让 agent 在接下来的几十轮里持续做错事,
  而这种错误**在手机上看不出来**(它只会表现为「怎么这么慢」)。
  这是典型的「需要看清全貌才能做的决定」,必须留在桌面端。
  配合 §5.4 的立场:手机只做「回答 / 不回答」,不做「改变策略」。

### 9.3 移动端不做工作区浏览

不查文件树,不搜仓库代码,不打开文件。理由:那是一个文件管理器,
和「我的 agent 现在在干什么」没有关系。用户要看代码,他在电脑上,
而且**代码要横着看**。同理,不提供 diff 视图。
真要确认 agent 改了什么,转录里的工具行已经告诉他改了哪个路径。

### 9.4 移动端不做后台任务列表

参考客户端有 `Background jobs` 的展开行。我们 v1 不做。

理由:后台任务没有「等用户回答」的语义(不阻塞任何人),
所以它不抢占我们的注意力预算;而它有「在跑 / 失败了 / 要重试」的语义,
后者确实值得看。但在 agent 会话的上下文里,失败会以 turn error 的形式
出现在转录里,已经在 §3.4 的行类型里了。
**等后台任务真的变成一个独立的、用户会主动来看的东西,再给它一个入口。**

### 9.5 不做「始终允许」

见 §5.4。在手机上、在明文链路上、离机器很远的地方授予一个长期权限,
是本产品里最坏的授权位置。四种结局里我们只用 `allowed-once`。

### 9.6 不做图片附件(与题面一致)

用户拍张截图给 agent 听上去很美,但:传输要走明文 VPN,
体积在移动网络上不可控,而 agent 是通过**它自己的文件工具**读文件的,
手机传上去的图对它只是一个附件引用。桌面端发图更直接。
**不是「以后做」,是「在手机上做这件事本身就是绕远路」。**

### 9.7 不做真正的推送

见 §10.2。产品事实是没有可靠通道,那就不假装有。L0 只做「App 在后台且 socket
活着」时的本地通知,并在通知里说清楚是哪个会话。

## 10. 开放问题与风险 (Open questions / risks)

按「如果我错了,会毁掉多少设计」排序。

### 10.1 `agentId` 是否等于 `sessionId`(最高风险)

**问题。** waterfall 帧带的是 `agentId`,不是 `sessionId`
(`README.md` §2.3 与 `stream_mux.dart:146`)。参考客户端
`TerminalPanel.kt:186` 把 `sessionId` 写进 `agentId`,说明那套 harness 同值。
我们这套网关没写明,而 `session.dart` 里 `SessionSummary` 根本没有 `agentId` 字段。

**如果不等**,§4.4 的「等你回答」行、§4.5 的提升排序、§5 的定位到会话
**全部落空**,只能退回连接级的泛化提示。这是整个设计里最大的单点依赖。

**怎么验。** 起一次真机审批,用 `probe_rpc.py` 抓一帧 `waterfall`,
把 `agentId` 和当时那个会话的 `sessionId` 比对。一条命令的事。

**降级方案(不等时的设计)。** 待答仍然全程可用,但归因降级:

- 驻留条文案改为 `有个 agent 在等你回答`,不给会话名。
- 列表顶部插入一条**独立的、无会话归属的**待答卡,排在所有会话之上,
  它自己没有标题,只有工具名与等待时长。
- 审批面板照常,面板顶部不显示「哪个会话」,只显示工具与参数。
- §4.5 的提升排序退化为「提升一条合成行」,不动会话顺序。

这个降级仍然满足 Q3(用户能回答,agent 能解冻),只是丢了「在哪」这一维。
**产品依然成立**,所以风险等级是「重要」而不是「致命」。但值得优先验证。

### 10.2 明文 VPN 上没有推送

**问题。** 产品事实:明文 HTTP + WebSocket,只靠 EasyTier 隧道。
原生推送(FCM / APNs)需要一个可达的推送中继或公网端点,这个产品都没有。
App 在后台被系统回收后,socket 死了,L0 就不成立。

**这意味着 Q3 的第一层在现实里经常缺席。** 用户可能是在 App 被杀掉、
agent 已经卡了 20 分钟之后才打开手机。这是这个产品最本质的局限,
应该在关于页写明,而不是假装推送能救。

**选项:**

| 方案 | 效果 | 代价 |
| --- | --- | --- |
| (a) Android 前台服务常驻 socket | 后台能收待答 | 常驻通知 + 耗电;iOS 上做不到 |
| (b) 承认只有 L1/L2 | 诚实 | Q3 的响应延迟完全取决于用户多久打开 App |
| (c) 家里跑一个中继 | 真正的推送 | 要多部署一个东西,与「零配置」冲突 |

我倾向 **(a) 做 Android,(b) 写进关于页,iOS 走 (b)**,
并且**不要**为了推送引入中继(v1 的整个价值主张是「装上就能用」)。
但这是个产品定位决定,不是我能单方面定的,需要用户拍板。

### 10.3 审批请求带不带得下工具参数

**问题。** `ApprovalRequest` 只有 `toolName` / `callId` / `reason`,且 `reason` 可选。
如果 `reason` 为空,而我们又拿不到 `callId` 对应的工具参数,
审批面板就只剩一个工具名,**用户在手机上无法做出安全判断**
(§5.4 的核心要求)。

**为什么这比看起来严重。** 这不是 UI 问题,是**能力缺口**。
如果 gateway 在 `approval/request` 里带上工具参数,
这个产品最好的功能就成立;如果带不上,手机上审批就退化成盲点,
那就应该**在产品上砍掉手机审批**,只保留问题回答 + 转录查看,
并诚实地把用户导流到桌面端。

**怎么验。** 让 agent 请求一次 `Bash` 审批,看 `request` 里 `reason` 实际填了什么。
若为空,试着用 `callId` 反查 `session/follow` 的历史。

**这条的答案可能改变 §5 的整个强度设计。** 我在 §5.1 已经写明了这个约束:
信息不足时不许盲授权,宁可弱打断。

### 10.4 `running` 在重连后的语义

**问题。** `session/list` 的 `running` 对「冷会话 / 未附着会话恒为 false」。
重连之后,这个标志是**宿主的实时内存状态**,还是**持久化的最后状态**?
如果是前者,手机重连的那几秒内所有行会显示「空闲」,用户会以为任务死了,
可能因此做出错误的干预(发消息、打断)。

**设计上的对策(不论答案如何都要做):** 保留本地已知的 `running`,
重连后**不立即把行降级为「空闲」**,而是先标成 `状态未知`(中性灰 + `?` 符号),
拿到第一次权威列表后才落定。
**永远不要在不确定的时候断言一个让人紧张的结论。**

### 10.5 `session/page` 的分页语义

**问题。** `README.md` 提到 `session/page` 存在,且 `explicitNulls = false`
(所以**绝不能发 `"cursor": null`**)。但游标格式、每页大小、
有没有总数字段都没验证。§4.6 的 100+ 会话策略依赖它。

**次要问题。** 更现实的风险是 `session/list` 一次返回 300 条时
在手机上的反序列化开销(每条带完整 `projections`)。
如果 `turnOutline` 很长,`session/list` 的响应体会相当大。
需要在真机上量一次「300 条会话的 `session/list` 响应多大、解析多久」。
超过 2 秒就应该直接切分页,不要先乐观地上。

### 10.6 需要用户研究的问题

这些不是我能从代码或截图里读出来的:

1. **他真的在手机上回答吗?** 还是只在手机上看、回到电脑前再回答?
   如果是后者,§5 的整个 L2 接管层可以降级成 L1,工作量差一倍以上。
   **这是最该先问的一个问题**,因为它决定最大的那块设计投入。
2. **同时最多会有几条 agent 在跑?** 决定 §4.5 的阈值(4 / 5 / 20)
   和筛选芯片的默认档。一个只有 1 条在跑的用户和一个并行开 8 个的人,
   需要的列表不是同一个。
3. **他通勤时看得懂 TTFT / tok/s 吗?** 如果他其实看得懂,
   我把它搬进信息抽屉的决定就是错的 (§8.4-2)。
4. **审批时他敢不敢在手机上点?** 需要知道他的风险直觉。
   如果多数人不敢,那 §5.4 应该反过来:手机上根本不提供「允许」,
   只提供「拒绝」和「打开电脑」。
5. **90 秒静默阈值准不准?** 需要拿他真实项目的 build 时间分布来校准 (§6.3)。
6. **中文文案还是英文?** 现有实现是中文,参考客户端是中英混排
   (`标准模式`、`1 steps`)。混排会破坏 `Title :: value` 那套装置的一致性。
   我这份文档按中文写,假设**全中文**,需要确认。

### 10.7 已知的取舍(不是风险,是故意)

记下来,免得后面有人当成 bug 修回去:

- 不做卡片化,会话列表永远是分隔线列表。
- 活动行的「距上次事件时间」是本地估算,不是服务端权威值。可能偏差几秒。
- 「等你回答」不显示倒计时(没有过期机制)。
- 手机上不提供「始终允许」。
- 进度细线永远不做不确定动画。
- 转录不做流式逐字渲染。
