# 15 · 移动端产品与实施规格

> **面向对象**：任何要在千寻（qianxun）上实现 / 接手这套移动端的人或 agent。
> 本文只写**已实测的事实**与**由此产生的规格**，不写设想。
> 数字全部可在真机上复现，复现方式见 §7。

---

## 0. 需求原文与不可违反的原则

### 0.1 需求原文

> DSH 的所有内容一般情况下都**不要修改**，只处理对于 mobile 不友好的**布局**。
> 如左侧菜单需要优化、对话的顶部显示不全。
> **功能要保留**，仅仅是改变 UI 布局，相当于在移动端的 UI 表现。
> 你需要自己考虑如何才能显示得让人很舒服。

### 0.2 三条原则（违反其一即为做错）

| # | 原则 | 判据 |
|---|------|------|
| P1 | **不改 DSH 的内容与功能** | 不新增字段、不删除入口、不改文案含义、不改数据流 |
| P2 | **只重排布局** | 允许：换行 / 换列 / 改尺寸 / 改间距。禁止：隐藏功能、合并入口 |
| P3 | **UI 要专业、美观、精致** | 不是「没坏掉」就算好；外来的元素必须与宿主视觉语言一致 |

### 0.3 范围

- **做**：移动端（窄屏）下 DSH 的导航形态、顶栏、会话列表、composer、状态条、长内容排版
- **不做**：移动端设置页（用户明确不要）、远程桌面 Surface（未实现，见 §8）
- **交付形态**：`<dsh_home>/mobile-access/custom.{js,css}` + Flutter WebView 壳

## 1. 架构与分工

```
Flutter 壳（mobile-flutter/lib/）
  └─ 只做四件事，不重画任何 DSH 界面
     1. 加载前注入 qx_token cookie
     2. 处理返回键
     3. 外部链接交系统浏览器
     4. 顶栏：返回 + 机器名

千寻网关注入（src-tauri/src/remote/mobile_ui.rs）
  └─ /qx-mobile/{info,version,bootstrap.js,custom.css,custom.js}
     bootstrap.js 定义 window.qxMobile.register，轮询 hash，5 秒热替换

定制层（mobile-flutter/qx-mobile/custom.{js,css}）  ← 界面改造都在这里
```

**为什么定制层在 WebView 内而不是 Flutter 侧**：
把 DSH 的会话列表在 Flutter 里重画一遍就成了**两套 UI**，且与桌面不同步。
方案 B 的核心是「壳只负责能不能打开，页面负责打开后长什么样」。

## 3. 三个「模拟器正常、真机坏掉」的坑（**最该记住的一节**）

这三个在模拟器上**界面完全正常**，只有真机能暴露。
它们不是玄学，各自有明确的成因。

### 3.1 DSH 界面语言不同 → 按钮 aria-label 不同

| | 模拟器 | 真机 |
|---|---|---|
| 展开侧栏 | `Open sidebar` | `打开侧边栏` |
| 收起侧栏 | `Collapse sidebar` | `收起侧边栏` |

按英文匹配的结果：在真机上点菜单按钮**完全没反应**，
而界面上看不出任何异常 —— 最容易误判成「按钮没插进去」。

**规格**：`findSidebarToggle()` 同时认中英两种，
且都找不到时退回「侧栏里的第一个按钮」（折叠态第一个按设计就是切换键）。
**行为闸必须有中文 label 的断言**，否则这个 bug 会从闸门底下溜过去。

### 3.2 侧栏展开后顶栏被换成 blank header，菜单按钮被顶出屏幕

实测 x=381 而视口 359，**整整 66px 在屏幕外**，一次审查报出 5 个 high 溢出。
根因：侧栏展开后 DSH 把对话顶栏换成 `headerBlank`，
而菜单按钮挂在 `[data-slot="conversation.header.leading"]` 空槽里。

**规格**：侧栏展开时菜单按钮 `display:none`。
它那时本来就没用 —— 工作区页自带收起键。

### 3.3 `custom.js` 的 5 秒热替换不可靠

实测：CSS 的 hash 变了会热替换，**custom.js 的不会**。
按钮里仍是旧的文本内容，DOM 里连新元素都没有；`location.reload()` 之后才换。

**规格**：手机上改 `custom.js` **必须整页刷新**才生效。
不要相信「5 秒自动生效」那句提示。

## 4. 选择器纪律（违反其一就会埋雷）

### 4.1 绝不写 class 名选择器改 DSH 的东西

DSH 的 class 是**构建期哈希**，每次构建都变：
`hHd-Xa_root` / `bhn1Oq_list` / `pI_x6G_frame` / `qianxun-wSkVaW_header` …

**只能用 `data-slot`**（Base UI 的部件标记，语义化、带版本）。实测 42 种：

```
root  sidebar  main  rightbar  shell.overlay
conversation.composer / .input.dock / .header / .session …
sidebar.workspaces / .panellist / .footer.action …
```

以及状态属性：`data-sidebar-collapsed`
（**展开时该属性是「不存在」而不是 `"false"`**，所以展开态 = `:not([data-sidebar-collapsed)`）、
`data-row-key`（`workspace:<uuid>` / `session:session-<uuid>`）、
`data-disclosure-row`、`data-composer-input`。

### 4.2 哈希类名读得出来，但写不进 CSS

排查时用哈希类名快速定位（比如 `qianxun-bhn1Oq_searchButton`），
但**最终产物里不能出现** —— 下次 DSH 构建就全失效。

### 4.3 需要「按行为找元素」时，用 JS 打标记 + CSS 改样式

class 不可用但结构又不稳时（例如「找出被省略号砍掉的行」），
由 `custom.js` 按**行为**（`scrollWidth > clientWidth`）找元素、打
`data-qx-*` 属性，再由 CSS 据此改样式。标记与样式分离，
class 怎么变都不影响。

### 4.4 行为判据的三条硬规矩（第 6 版踩出来的）

这一版加状态按钮时，判据连栽四次。四次犯的是**三类不同的错**：

| # | 犯的错 | 后果 | 规矩 |
|---|--------|------|------|
| 1 | 判据**依赖了另一条启发式的产物**（用 `[data-qx-clipped]` 找统计行） | 层级比想的多一层 → 一个都数不到 | **判据要独立**。别把 A 的产物当 B 的输入 |
| 2 | 判据**数一数还剩几个** | 自己 `display:none` 藏起来之后，计数随之漂移，标记跟着漂 | **判据不能依赖你隐藏掉的东西**。隐藏是单向不可逆的 |
| 3 | **自己造的元素进了「找 DSH 元素」的判据** | 药丸文字 `79%` 命中统计关键词 → 标记一路走到 composer 根 → **整个输入框消失** | **自己造的元素绝不能进判据**。第一行就 `if (b.closest('.qx-status-btn')) continue` |

**还有一条更普适的**：

> **判据要在「后果发生的那一层」再挡一次。**
> JS 判据误标了 composer 根（4 个孩子的启发式），
> 光靠「把 JS 写对」不够 —— CSS 侧还要有
> `[data-qx-status]:has([data-slot='conversation.input.left']) { 恢复显示 }` 这样的护栏。
> 这样即使 JS 再判错，最多状态条没被隐藏，不会把输入框一起弄没。

### 4.5 闸门的替身要像浏览器，不要逼产品代码写防御性判断

第 6 版给新功能补断言时发现：闸门的假 DOM 只认 `.class` 选择器，
其余 `return []` / `return null` —— **新逻辑一行都没被执行到，闸门照样全绿**。

修的三处（都在 `scripts/check_custom_js_runs.py` 的 HARNESS 里）：

1. 选择器引擎升级：认 `.class` / `[attr]` / `[attr="v"]` / `tag` / 后代 / `>` / 逗号并列
2. 两处替身覆盖改成**未命中时回落到引擎**（原来直接 `return []` / `return null`）
3. `getComputedStyle` 补齐 `flexDirection` / `gap` / `flex` 等，并补 `childNodes`

> 第 3 条尤其重要：`cs.flexDirection.indexOf(...)` 在缺字段的替身上会抛
> TypeError，症状看着像「产品代码坏了」。
> **正确做法是让替身像浏览器，而不是在产品代码里写 `cs.flexDirection || ''`。**

### 4.6 断言要用真值构造（含细节）

fixture 里只写 `aria-label` 不写 `textContent` —— 断言就变成
「测一个我编出来的结构」，因为真 DOM 里**两者都有**。
`findStatButtons` 读的是 `textContent`，于是 fixture 一条都匹配不到，
断言以「不报错」的方式悄悄失效。

同理，**替身的 `getBoundingClientRect` 默认 40×20**，
而 `findToolbarRow` 的判据之一是「行宽 ≥ 视口 70%」（真机 320/359）。
不喂真实宽度就永远认不出来。

> **断言失败得响，断言「通过」得更有理由。**

#### 4.6.1 「绿但其实是错的」—— 七次记录

这是本项目最贵的一类失败：**闸门全绿，真机是错的**。已发生七次：

| # | 绿的东西 | 真相 |
|---|---|---|
| 1 | fixture 只写 `aria-label` | `findStatButtons` 读 `textContent`，匹配 0 条 |
| 2 | A22 标记「成功」 | 只标了**最内层**祖先，外层一换就失效 |
| 3 | 对比度「全达标」 | 3 个根本没测到（覆盖率没强制） |
| 4 | 对比度报 2.35:1 | 深浅两套主题读的是同一份行背景 |
| 5 | 提示条断言 | 断言要求的 `.qx-hint-ctx` 已被删，断言形同虚设 |
| 6 | 对比度「全达标」 | 令牌块之外还有颜色字面量覆盖了令牌，实际渲染 2.88:1 |
| 7 | **CSS 热替换「成功」** | **从第 2 轮起一张表都没换过，每轮都报成功** |

第 7 次的教训比前六次都重要：

> **一个「成功」但没做事的工具，比没有工具更坏。**
> 它不会让你停下来，只会把你推向错误的怀疑对象 ——
> 我当时依次怀疑了特异性、`!important`、媒体查询，全是错的，真正坏的是工具本身。

由此定两条规矩：

1. **热替换工具必须自检**：查 href 里的时间戳，**不是查有没有跑**。
   查「跑没跑」永远通过，因为问题恰恰是「跑了但没换」。
2. **审查脚本自己新加的检查项，先证明它能抓到**：
   注入故障 → 必须变红 → 撤掉 → 必须变绿。
   ⚠️ 而「检查项不存在」和「检查项报 0」在结果里长得一模一样 ——
   这个坑当天踩了两次（调错入口、去 stdout 里找 JSON，
   而它 stdout 是给人看的摘要）。**所以输出里要有可断言的字段名。**

#### 4.6.2 夹具会悄悄丢掉 `!important`

假 `style.setProperty(k, v)` 把第三个参数直接扔了 ——
于是「写没写 `!important」在测试里毫无差别。

而第 9 轮查明的核心机制恰恰是：
**行内 `!important` 压过任何样式表规则**（哪怕特异性再高）。
也就是说，一条「值完全正确、真机上完全无效」的写法能骗过全部断言。

```js
setProperty(k, v, pri) { s.map[k] = v; if (pri) s.imp[k] = pri }
```

对应的变异测试第 8 条专门盯这个（**值对、真机无效，最危险的一类**）。

#### 4.6.3 「测到了什么」≠「系统是什么」——第 11 轮连错三次

第 11 轮只做测量、不改代码，三次判错，原因各不相同：

| 我下的结论 | 实际 | **为什么会是这个数** |
|---|---|---|
| 「点了不滚，控件是摆设」 | 它是**选中**控件，本来就不该滚 | 我先假设了用途，再拿它当证据 |
| 「右栏够不着，选中无处可看」 | 顶栏有 `Open right sidebar`（x=291） | 我只搜了 rightbar 内部，**没搜全页** |
| 「右栏开了但没有内容」 | 24 个节点，正常 | 它是 `display:contents`，**自己恒为 0×0** |

三条规律：

1. **先问「这个数为什么会是这个数」**，再决定它意味着什么。
   `getBoundingClientRect() === 0` 有两种可能：元素真的不可见，
   或者**它根本没有盒子**（`display: contents`）——量它的子元素。
2. **别在「已经知道它在哪」的地方找别的东西。**
   我认定「按钮在 rightbar 里」，就只搜了 rightbar ——
   而那个按钮在顶栏。
3. **测量之前先确定判据的前提。**
   「没滚动 ⇒ 没用」成立的前提是「它是跳转控件」，而这个前提是我脑补的。

> **一个只做测量、不改代码的轮次也是有效轮次** ——
> 前提是它诚实记录**测错了什么**。
> 把三次错判写成文字，比留一句「已验证正常」值钱得多。

**推论：没有桌面端基线，就不要给「可能正常」的控件加行为。**
「看着不对就改」正是前九轮反复犯的错。

#### 4.6.4 「断言了存在」≠「断言了存在且唯一」

第 11 轮实测 `document.querySelectorAll('.qx-layer').length === 2`
（自己的容器热重载泄漏），而原来的闸门照样 PASS：

```js
if (!layer) FAIL;                    // ← 只问「在不在」
```

| 要点 | 内容 |
|---|---|
| 产品侧 | mount 时先 `for (const stale of doc.querySelectorAll('.qx-layer')) stale.remove()` —— **只清自己的 class**，不碰任何 DSH 节点 |
| 闸侧 | 必须**真调 `registered()` 再跑一次**（不 dispose，模拟热重载竞态），断言层数 `=== 1` |
| 位置 | 放**文件末尾** —— 它会重装监听器，插在中间会污染后面依赖「监听器装了几个」的断言 |
| 基线 | **不要写死「此刻应有 1 个」** —— 前面的 dispose 幂等测试刚把层删光，基线是 0；要前后对比 |

⚠️ **最容易写错的一版**：在夹具里自己写一遍清理逻辑，再检查自己清得对不对。
那样测的是**闸门自己**，删掉 custom.js 那行它照样绿 ——
正是第 9 轮记的「闸门必须测产品代码，不是测替身」。

**为什么这个 bug 特别难发现**：这些层 `pointer-events: none`、零子元素，
所以肉眼看不出、截图拍不出、功能测试全绿 —— **只有数量会变**。

#### 4.6.5 第 7 次「闸门绿、真机红」，这次没查到真因

部署后真机仍量到 2 个层。按纪律先查部署：源文件与已部署文件**逐字节一致**
（52797 B），清理行两边都在 → 不是没部署。

随后 3 轮重载 × 3 次采样 = **9 次全是 1**，未复现。

> 前 6 次最后都查到了真因，这次没有。
> **查不到就说查不到** —— 如实记「未复现」，
> 比编一个听起来合理的机制有价值得多。
> 下一个怀疑对象应当是「测量时机早于新代码接管」，
> 而不是回头去改一个已经被 9/9 采样证实的修复。

#### 4.6.6 第 8 次「验证器自己撒谎」：判定方向写反了

第 12 轮收官脚本：

```python
for cond, msg in [(d["导航flex"] == "row", "导航没有变横排"),
                  (d["可滚px"] > 0,     "内容区仍然不可滚"),
                  (d["Close"]["命中"] == "自己 ✓", "Close 按钮点不到")]:
    print(("✓ " if not cond else "✗ ") + msg)   # ← 反了
    if cond: bad.append(msg)                     # ← 也反了
```

实测值**全对**（`flex=row` / `可滚 844` / `Close 命中自己`），
脚本却打印了四条 ❌ 并让退出码为 1。

> 前 7 次是**断言写错**（断言了不存在的东西，或断言的对象不是产品代码）。
> 这一次不同：**数据是对的，是「怎么解读数据」写反了**。
>
> 更值得记的是它为什么能一路溜到收官才暴露：
> 我看到满屏 ❌ 的第一反应是「修复没生效」，
> 而不是「判定方向反了」。
> **一个验证器报错时，先怀疑判定，再怀疑被测系统。**

#### 4.6.7 改动影响面必须**逐个量 + 和基线比**，不能只盯被改的那个

第 12 轮给所有 `[role=dialog]` 加了 `width: 100%` 来救 Settings。
复验时发现 Members 弹窗溢出 1 个元素 —— 但**溢出的是 Members，不是 Settings**。

单点复验看不出这类问题，因为注意力全在刚改的地方。正确做法是 A/B：

| | 首子盒宽 | 溢出 |
|---|---|---|
| 保留改动 | 339px | 21px |
| 撤掉改动 | 316px | 0 |

**差值本身就是根因线索**：`width: 311.143px` 却量到盒宽 339，
差的 28px 正好是 `content-box` 下被重复计入的 padding（14 + 9 加余量）。

两条硬规矩：

1. 改动一旦用了**跨组件选择器**（如 `[role=dialog]`），
   就要把它**匹配到的每一个实例**都量一遍，不是只量触发改动的那一个。
2. 和**撤掉改动的基线**比，不和「我印象里原来什么样」比。

> 同源的还有一条第 12 轮才补上的 CSS 陷阱，见 §5.7。

#### 4.6.8 第 9 次「验证器自己撒谎」：**零样本 = 假绿**

第 13 轮最严重的一次。第 13 轮的收官脚本扫了 30 个入口，
打印出 `✅ 第 13 轮全绿` —— 但它**一个菜单都没打开过**。

原因是循环里两处静默失败叠在一起：

```python
for entry in entries:
    r = click(entry)
    if not r:
        continue                      # ← 静默跳过，不计数
    ...
    if tag_failed:
        continue                      # ← 又静默跳过
problems = collect_problems()
print("✅ 全绿" if not problems else "❌ " + str(problems))
```

**0 个样本 → 0 个问题 → 打印「全绿」。** 失败率和正确率都是 0，
而「没有失败」被当成了「通过」。

#### 硬规矩：打印结论前先断言样本量

```python
if len(found) == 0:
    bad.append("零样本：没有量到任何菜单")
```

#### 配套的三条

1. **每次运行都打印样本账**：`扫描 N 个 / 点开 M 个 / 量化 K 个 / 跳过 J 个（原因）`；
2. **跳过必须有原因分类**，不能是空 `continue`；
3. **「没跑到」和「跑过了」在输出上必须长得不一样** ——
   前者打印「⛔ 未验证」，后者才允许打印「✅」。

> 这是第 12 轮以来第 9～12 次翻车里最危险的一次，因为
> **其他几次会报错，这一次安静地给了个假通过**。

## 5. 布局改造规格（现有规则的由来）

### 5.1 A1 侧栏展开 → 全屏浮层

```css
@media (max-width: 760px) {

    grid-template-columns: minmax(0, 1fr) 0px 0px !important;
  }

    display: flex !important; flex-direction: column;
    overflow-y: auto; overscroll-behavior: contain;
  }

```

`grid-template-columns` 是内联样式，必须 `!important` 才压得住。

### 5.2 A11 折叠态 rail **不能 display:none**

⚠️ **栅格是按顺序自动放置的。** 删掉第 1 项后 main 滑到第 2 列，
而第 2 列是 0px —— 实测整个主区被推出屏幕（main 在 x=412、w=0）。

正确做法是**保持它在流里，只把那一列压成 0**：

```css
[data-slot='root'] > [data-sidebar-collapsed] {
  grid-template-columns: 0px minmax(0, 1fr) 0px !important;
}
[data-slot='root'] > [data-sidebar-collapsed] [data-slot='sidebar'] > * {
  width: 0 !important; min-width: 0 !important;
  overflow: hidden !important; visibility: hidden !important;
}
```

用 `visibility` 而非 `display` —— 前者彻底断掉交互，
但 JS 的 `.click()` 仍然派发（菜单按钮要靠它打开工作区页）。

### 5.3 A10 顶栏换行：标题块独占一行

```css
[data-slot='conversation.session.header'] > div:has(nav) {
  flex-wrap: wrap !important; align-items: center; row-gap: 0;
}
[data-slot='conversation.session.header'] > div:has(nav) > *:has(nav) {
  flex: 1 1 auto !important; min-width: 0;
}
```

⚠️ **不能写 `flex: 1 1 100%`** —— 菜单按钮也在这个 flex 容器里，
100% 会把它挤到第二排去（实测它掉到了 📁 那一行左边）。

⚠️ 曾试过把中间层改 `display:contents` 让 tablist 与按钮并到一行（省 50px 高度），
**已放弃**：顶栏 chip 随会话变（普通会话 vs 开了团队多出「Agent Team」「Standard mode」），
`order` 方案要写死「第几个子级是什么」，换个会话就散架。
`flex-wrap` 不依赖元素个数。

### 5.4 触控目标的三种改法（**不能混用**）

| 元素类型 | 改法 | 理由 |
|---|---|---|
| composer / 工作区页按钮 | `min-height:44 / min-width:40` | 块级，直接补 |
| 转录里审批、工具行 | `min-height:44`（带宽度筛选） | 块级 |
| 正文里的行内链接 | **纵向 padding** | 行内元素的纵向 padding **不改变行盒高度**，加了不撑开段落 |
| 消息下方图标按钮 | **44×44**（第 9 轮修正） | 原来写「间距仅 40px → 只补 32×40」，见下方 ⭐ |

⭐ **最后一行原来是错的，第 9 轮已推翻。**
原结论：「间距只有 40px，补到 44 会互相重叠」。
实测那一行（y=520）**只占 200px**、视口 359、右边空 133px，
补到 44 后占 252 —— **根本不会重叠**。

错在**把「按钮之间的间距」当成了「可用宽度」**。
> 「32 会不会重叠」本来量一下就知道，不该推断。而推断的代价是一整轮。

**块级 vs 行内必须分开**。给正文里的行内链接加 `min-height:44`
会把整段文字撑成一片，比原来更糟。

块级元素的筛选条件（缺一不可）：
1. `display` 是 block/flex（排除行内）
2. 宽度 ≥ 45vw **或** 父容器高度 ≈ 自身高度（说明「整行都是它」）
3. 高度 < 44px

⚠️ **门槛必须按目标值写，不能按旧值写。**
第 8 轮写的是 `if (r.width >= 32) continue`，改完之后按钮**再也升不上去** ——
它已经是 32 了，下一轮直接跳过，**自指的死循环**。
而每次扫描都「跑过了」，日志里看不出任何异常。
正确写法 `if (r.width >= 44) continue`：幂等，且能把旧版留下的 32 一起救回来。

### 5.5 字号下限 12px

代码是要**照着抄**的内容，比正文更不该小。
但注意：`!important` 拼的是**特异性**不是顺序 —— 同为 `!important`，
DSH 的 `._markdown_ :not(pre) > code`（0,3,0）会压过我们的 `[data-qx-tiny]`（0,1,0）。

### 5.6 ⭐ 两条压过一切的 CSS 规则（第 9 轮查明）

这两条让**两条看起来完全正确**的规则连续失效，其中一条从第 3 版写到现在。

#### (1) `min-width` 压过 `max-width`

DSH 给消息流项写 `min-width: max-content`（桌面端的正确做法：按内容撑开）。
我的 A5 写 `min-width: 0; max-width: 100%` —— **看着就对，一个字没起过作用**：

```
DSH  min-width: max-content  → 936
我的  max-width: 100%         → 288
936 > 288  →  min 赢
```

结果：一条含代码块的消息把版面撑到 **1832px**，
代码块上的 `Copy` / `Wrap lines` 落在 x=1754 / 1802，**用户永远点不到**。

```css
/* 正确：只写 max-width 约束不住「按内容定尺寸」的元素 */
[data-slot='conversation.session'] * { min-width: 0 !important; max-width: 100%; }
```

#### (2) 行内 `!important` 压过**任何**样式表规则

A24 写 `[data-slot='conversation.chat.node'] button { min-width:44px !important }`，
规则在表里、选择器匹配、媒体查询也命中 —— **盒子纹丝不动**。
把规则用 `insertRule()` 插进真表、加更高特异性，照样不动；
只有 `b.style.setProperty('min-width','44px','important')` 才变成 44。

> 行内 `!important` 在层叠里的优先级高于全部作者样式表规则，
> **特异性再高、写几个 `!important` 都压不过** —— 除非也写进行内。

所以 `custom.css` 里的 A24 降级为**兜底**，真正让它生效的是 JS。
两边都留着：**JS 负责现在，CSS 负责将来。**

> **通用判据：这条规则是在哪里生效的？被谁压着？**
> 不知道就别写 —— 两条失效的规则都「看着完全正确」。

### 5.7 ⭐ `width: 100%` 不带 `box-sizing` 会把元素**撑破**

第 12 轮修 Settings 双栏，内容区写 `width: 100%`。
Settings 没事，但 Members 弹窗的 `VoX2oq_body` **溢出 21px**：

```
有规则   width=311.143px  盒宽=339   ← 差了 28
撤掉规则 width=288.143px  盒宽=316
```

原因：`VoX2oq_body` 是 `box-sizing: content-box` + `padding: 14px 9px`。
**content-box 下 `width: 100%` 只约束内容盒，padding 在它之外另加一遍**，
于是比父容器宽出一个 padding。

**规矩：凡是我写 `width: 100%` 的选择器，同一条规则里必须带 `box-sizing: border-box`。**

| 写法 | 结果 |
|---|---|
| `width: 100%`（content-box） | 比父容器宽出 padding ❌ |
| `width: 100%` + `box-sizing: border-box` | 等于父容器内容盒 ✅ |

> 和 §5.6(1) 的 `min-width` 压过 `max-width` 属同一族：
> **都是「你写的值和浏览器算出来的盒子不是一个东西」。**
>
> 两者的症状一样 —— 量出来的数比写的数大，
> 而且**看起来完全正常**，只有拿 `getBoundingClientRect` 去对
> `getComputedStyle().width` 才会露馅。

### 5.8 ⭐ 标签塌成 2px：`min-width: 0` **赢不了**固定的 `width`

第 13 轮查明。同一个页面上两个形状一样的菜单，
一个标签 124px、另一个**只有 2px**，差别只有一处：

| | 🔴 坏 | ✅ 好 |
|---|---|---|
| `role=menuitem` 的 **`width`** | **38px**（固定！） | 159.5px（auto） |
| `role=menuitem` 的 `min-width` | **38px** | 0px |

标签自己是 `flex-grow:1; flex-basis:0%; min-width:0; overflow:hidden` ——
**这种写法对父容器的内容宽度贡献为 0**，只有「父容器多出来的空闲空间」
才会分给它。

而 DSH 给那个菜单项写死了 `width: 38px`（正好等于「⋯」图标按钮的宽度）。
**按钮撑不开 → 没有空闲空间 → 标签停在 0 → `overflow:hidden` 裁成 2px。**

#### 三条由此推出的硬规矩

1. **`min-width` 只压 `min-width`。** 想让一个 flex 子项真正拿到宽度，
   必须动它的 `width`：
   ```css
   [role="menu"] [role="menuitem"] { min-width: 0 !important; width: 100% !important; }
   ```
   `width: 100%` 是**承重声明**，删掉它立刻退回「只剩图标」。

2. **`align-items: stretch` 只能拉伸「拉伸轴」上的尺寸。**
   垂直 flex 容器里它管的是**高度**，对宽度毫无帮助 ——
   实测把坏菜单的容器从 38px 拉到 136px，标签**仍然是 2px**。

3. **`overflow: hidden` + `flex-basis: 0%` 组合 = 静默吞掉内容。**
   两者都在时，文字不会「溢出」，而是**无声地缩成 0**。
   量的时候必须用 `Range.getBoundingClientRect()` 比对
   `getBoundingClientRect().width`，**不能只看有没有溢出**。

#### 为什么选侵入性最小的写法

修这个菜单先后试了四种定位策略（覆写 `left/right`、只限宽、
`margin-left:auto`、只修菜单项），**四种全部测得 0 问题**。
于是选**唯一不改 DSH 定位逻辑**的那一种：菜单宽度交回内容自己算，
实测自然长到 171px。

> 四种都能修好时，选侵入性最小的那个 —— 这样 DSH 下次改布局时，
> 我们的 CSS 不会挡住它的修复。

#### 配套：菜单必须有**不透明**底色

修完宽度才从截图上发现：**菜单只有一圈阴影，却完全没有底色**。

```
background-color: rgba(0, 0, 0, 0)
background-image : none
backdrop-filter  : none      ← 我以为有，实测根本没有
```

结果菜单浮在消息正文上方，底下的字直接透上来。
修法是**不透明底色 + 已有主题令牌**（`--qx-surface` / `--qx-ink-body`，
随 `prefers-color-scheme` 走），不是「半透明 + 毛玻璃」——
后者在这里**一个字都不生效**。

> **`backdrop-filter` 这类「我以为宿主已经做了」的属性，必须先量。**
> 写了半天毛玻璃，结果发现宿主根本没加。

> P0 两条**都已完成**（顶栏 164 → **102px / 15%**；状态条**已收进工具栏按钮 + 弹层**）；

### 5.9 ⭐ 省略号：`text-overflow` 加在 **flex 容器**上不生效

第 14 轮查明，也是一条「属性值对、效果不对」的坑（§5.10 汇总）。

`text-overflow: ellipsis` **只对 block 容器生效**。而会话标题的结构是：

```
nav (display:flex, overflow:hidden)
└── SPAN (display:flex)          ← 把 ellipsis 加在这里，无效
    ├── SPAN (display:block)     ← 真正装 #text 的在这
    └── DIV[slot=…lineage] (display:contents)
```

把 `text-overflow: ellipsis` 加在外层 flex 容器上时，
`getComputedStyle().textOverflow` **读回来就是 `ellipsis`**，
但**一个字都不会省略**。

#### 判定省略号真的生效，要看这一个数

```js
inner.scrollWidth > inner.clientWidth
```

| 状态 | scrollWidth | clientWidth | 溢出 | 省略号 |
|---|---|---|---|---|
| 加错层 | 241 | 241 | **0** | ❌ 没画 |
| 加对层 | 241 | **209** | **32** | ✅ 画了 |

**内层没有被裁，就没有东西可以省略。**
`overflow: hidden` 在外层，裁的是外层。

#### 配套三条

1. **`text-overflow` 之前先确认 `display` 是 block**（`display:block` 或
   表格单元格等会建立 BFC 的值）；
2. **`overflow: hidden` 不给省略号 = 硬切**，默认的 `text-overflow: clip`
   会把字切在半个笔画上，这是最难看的一种截断；
3. **改完必须看截图** —— 半行汉字和三点省略号在缩略图上极像。

#### 附：标题被压扁的根因是内层 `flex: 0 0 auto`

内层写着 `flex: 0 0 auto`（**不许缩**），所以它保持 241px 不变，
裁切全落到外层。完整修法是三层都给：

```css
[data-slot="conversation.session.header"] nav      { min-width: 0 !important; }
[data-slot="conversation.session.header"] nav > *  { flex: 0 1 auto !important;
                                                     min-width: 0 !important;
                                                     overflow: hidden !important; }
[data-slot="conversation.session.header"] nav > * > * {   /* ⭐ 真正装文本的这层 */
  flex: 0 1 auto !important; min-width: 0 !important;
  overflow: hidden !important;
  text-overflow: ellipsis !important; white-space: nowrap !important;
}
```

> ⭐ A/B 时**不要**顺手降字号。本轮试过「16px → 15px」，
> 结果与只加省略号**完全相同**（右缘都是 277px）——
> 拿可读性换一个零收益的改动，是净亏。


### 5.10 ⭐ 汇总：「属性值对」**不等于**「效果对」

已连踩两次，第三次一定会再来。

| 轮次 | 属性 | 读回来的值 | 实际效果 |
|---|---|---|---|
| 13 | `backdrop-filter` | （我以为有） | **实测 `none`** —— 写了半天毛玻璃，宿主根本没加 |
| 14 | `text-overflow` | **`ellipsis`** | **一个字没省略** —— 加在了 flex 容器上 |

共同点：**我量的是「属性是不是我写的那样」，而真正要回答的是
「它有没有让用户看到想要的效果」。**

#### 由此定下的判定规矩

| 想证明的事 | **必须**量的东西 |
|---|---|
| 省略号生效 | `scrollWidth > clientWidth`，**且**看截图 |
| 模糊/毛玻璃生效 | `getComputedStyle().backdropFilter !== 'none'` |
| 文字没被裁 | `Range` 的宽度 ≤ `clientWidth`（不是「没溢出」） |
| 元素可点 | `elementFromPoint` 命中它自己 —— ⚠️ 见 §7.5 的假阴性警告 |

> 一句话：**先量「效果是否发生」，再量「属性是否正确」。
> 顺序反过来就会写出「全绿但没修好」的补丁**——
> 第 14 轮就是这么干了一次。

2. **只跑「守护通过」证明不了它抓得住。**

   本轮 8/8 全抓，且还原后逐字节一致。

> **守护自己也会撒谎** —— 所以守护也要被测。
### 5.11 ⭐ 改主题之后**必须等它稳定**，否则量到的是过渡帧

第 15 轮查明。`--qx-*` 令牌跟着 `prefers-color-scheme` 走，
而 DSH 自己还有一层 `data-ds-theme-source` 主题判断，
**两层不是同一时刻翻转的**。

实测抓到的过渡帧：

| 字段 | 值 | 说明 |
|---|---|---|
| `matchMedia('(prefers-color-scheme: dark)')` | `true` | 媒体查询**已经翻了** |
| `body` 背景 | `rgb(255,255,255)` | DSH **还没重绘** |
| `--qx-surface` | `#12161d` | 令牌**已经翻了** |

结果就是**白底页面上浮着一个深色菜单**。
再等一会儿，页面自己变成 `rgb(21,21,23)`，三者一致。

> 过渡期间还读到过一次 `--qx-surface` = **空字符串**，
> 一度以为整个令牌块没加载 —— 查 157 个样式表才确认
> custom.css 好好地在那儿。那也是同一件事的另一个切面。

### 硬规矩

**任何可能触发主题重算的操作之后**（切 `uimode`、切前后台、
切系统深浅色、首次注入），**连续采样 3 次一致才允许开始量**：

```python
prev, stable = None, 0
for _ in range(20):
    s = probe()                      # 同时取 body 背景和令牌
    key = (s['bg'], s['surface'])
    if key == prev:
        stable += 1
        if stable >= 2:              # 连续 3 次
            break
    else:
        stable = 0
    prev = key
```

不这么做，**量到的可能是任何一帧** —— 而且过渡帧不会报错，
只会安静地给出一个看起来很有说服力的假数据。


### 5.12 ⭐ 截图和测量打架时，先分清是谁在骗你

第 15 轮踩的第二个坑：截图里菜单项小得像 4px，
测量却报每项 44px、填满整个卡片。

### 规矩一：截图文件名不许撞车

```python
# ✗ "More actions" 和 "More ways to open" 都得到 "more"，
#   第二张直接盖掉第一张，我因此看错了图
cdp.shot("r15-" + label.split()[0].lower())

# ✓ 用序号或全名
cdp.shot(f"r15-{i}-{label.replace(' ', '-').lower()}")
```

**看错图 = 看错结论。** 这一条比任何测量技巧都重要。

### 规矩二：`rect` 是人眼尺寸，`offsetHeight` 是布局尺寸

| API | 含 transform | 用途 |
|---|---|---|
| `getBoundingClientRect()` | ✅ 含 | **人眼看到的** |
| `offsetHeight` / `clientHeight` | ❌ 不含 | 布局尺寸 |
| `getComputedStyle().transform` | — | 看有没有 `scale()` |

两者对不上 = 有 transform 在缩放（比如展开动画）。
本轮实测 `141.71` vs `142`，**差 0.29dp** ⇒ 没有缩放
⇒ 那张小字图只能是**动画中途的合成帧**，不是缺陷。

### 规矩三：点开之后要等

菜单有展开动画。点完立刻截图，拿到的是动画某一帧的合成结果。
本轮固定 `time.sleep(2.6)` 之后再量再拍。

> 三条合起来：**看图 → 对不上 → 先怀疑自己的工具（撞名 / 时机 /
> transform），再怀疑产品。** 这个顺序能省掉一整轮假 bug 调查。

**闸门第一版是「绿的假的」**：7 项里 3 项写「未渲染，跳过」，

**抓到的真失败**：`.qx-hint-sparse` 深色 **3.81:1** / 亮色 **2.88:1**。
（§6 当年写的是 `.qx-hint-ctx`，实测最严重的其实是 `sparse`，
而它是**出现频率最高**的那条 —— 208/394 条会话都是稀疏的。）

**两条必须记住的结论**：

1. **不存在「万能灰度」。** 在 `#5a6672 ↔ #9aa7b4` 之间扫 28 档，

2. **能用宿主令牌就别自己造颜色。** 药丸「低」档写死 `#6f757c` 只有 2.52:1，

**两个 CSS 坑**：

- **令牌块必须挂 `body`，不能挂 `:root`。**
  `var()` 的替换发生在**它被声明的那个元素**上；
  DSH 把 `--dsw-alias-label-secondary` 定义在 body（实测 documentElement 取到空串）。
  在 `:root` 里引用 → 解析失败、落兜底值 → 「颜色变了一点但说不清为什么」。
- **半透明底色要沿祖先合成后再算比值**，不能拿 `backgroundColor` 直接比。

**顺带一条方法论**：深色截图里 header 下缘总有一行「半截文字」，
看着像内容透出。经过查证（DOM 里 not found / `elementsFromPoint` 只有 header /
字形语义不通 / **真机没有**）确认是**模拟器 GPU 合成伪影**。

> **「看着像坏了」要先证明它是坏的。**
> 判别信号：DOM 里没有 + 字形语义不通 + **只在某一个环境出现**。
> 否则很容易去动一条本来正确的规则，而且改完看不出差别、很难回退。

### 5.13 第 16 轮补充：弹窗（`role="dialog"`）的实测定论

**目标**：还掉「审批弹窗从未实测」这笔从第 12 轮欠到现在的债。

**结论一：本 DSH 构建里不存在独立的审批弹窗。**
`role:"dialog"` 在全部 6 个前端 chunk 里只出现 2 处，都在同一个通用 `Modal` 组件；
权限相关导出**只有 `PermissionIcon*` 图标族**，无任何 Approve/Deny/Approval 组件。
权限走 `Access mode` 选择器 + 图标。
移动端 36 个可见控件逐一点击，只有 **Settings** 与 **Add workspace** 能开 dialog。

**结论二：`> nav` 竖排规则（B10）对单栏弹窗无害，依据是 Add workspace。**
Add workspace **无 `> nav`**，正是单栏形态。custom.css 开/摘两组对比：

| | 摘除 | 开启 |
|---|---|---|
| Settings `> div` | `[212,24,**123**,643]` | `[24,95,**311**,572]` |
| Add workspace 弹窗 | `[24,96,311,500]` | `[24,96,311,500]`（逐项相同） |
| 不可达元素（两弹窗） | 0 | 0 |

⇒ B10 使 Settings 内容区宽度 **123 → 311px（×2.5）**，且无回归。

**结论三：弹窗内存在真·触控目标缺陷（第 16 轮发现，未修）。**

| 控件 | 尺寸 |
|---|---|
| `Increase font size` | **17×12** |
| `Decrease font size` | **17×12** |
| `Close` | 28×44 |

低于 Apple HIG 44×44 / Material 48×48。custom.css 开与摘两组均在
⇒ **DSH 原生问题，不是本项目 CSS 造成的**。
⚠️ 修复方案必须先过 A/B（「不可达元素不增」+「弹窗高 ≤ 视口高」），**不能直接加 min-height**。

**判准变更**：判「溢出」必须先看祖先链有没有 `auto/scroll/hidden`。
`role="dialog"` 根元素自带 `overflow: hidden`，旧判法会让真溢出恒为 0（永远绿灯）。
新判法：**超出弹窗边界且中途无可滚祖先能带它回来** = 不可达。

### 5.14 ⭐ 第 17+18 轮：「太宽松」的定论 —— 先量根因，别动那个「看着最松」的属性

这一节把第 17、18 两轮压成一条可复用结论。

第 17 轮（Settings 字号步进器）修的是「**从不绘制**」的元素，
第 18 轮（列表 / 设置页密度）修的是「**被换行换竖排**」的元素。
两者是同一类错误的两个变体：**属性回读全对，屏幕上什么都没变**。

#### 5.14.1 判据：「一屏多露几行」，不是「属性变没变」

> 判「太宽松」必须换算成「一屏多露几行 / 多露出几节内容」。
> 属性改对了但一屏行数没变 = **没修好**。

第 18 轮实测（359×691dp 视口，dpr 3.5）：

| | 修前 | 修后 |
|---|---|---|
| 侧栏可见行 | 6 / 20 | **7 / 20** |
| 侧栏树内容高 | 1122 | 1024 |
| Settings 内容高 | 1362 | **1160**（省 202px） |
| Appearance 主题区 | 3×258×83 竖排 = 264px | **3×82×62 横排 = 62px** |

#### 5.14.2 ⭐ 竖排不一定是 `flex-direction` 写错，可能是 `flex-wrap: wrap` 换出来的

第 18 轮最值钱的一条。Appearance 的三张主题卡实测：

```
容器 DIV[box 48,271,258,264]  方向 row  换行 wrap  间隙 8
  BUTTON «Light»  258×83  flex: 1 1 180px
  BUTTON «Dark»   258×83  flex: 1 1 180px
  BUTTON «System» 258×83  flex: 1 1 180px
```

`getComputedStyle(el).flexDirection` 读出来是 **`row`**，屏幕上是竖的。
真因：**每个子项 `flex-basis: 180px`，两个 180 就超过 258px 的容器宽，
于是被逐个换行；换行后每个再撑满整行 258px**。

⇒ **只加一条 `flex-wrap: nowrap`**，子项自带 `flex-shrink: 1` 就自动收成 82px。
实测省 202px，弹窗高（643）与可滚量（518）都不变 ——
省下的是**真内容**，不是把滚动藏起来。

> `flex-direction` 和 `flex-wrap` **必须一起读**。
> 只读方向就下结论，会把「wrap 造成的竖排」误判成「方向写反了」，
> 然后去改一个本来正确的属性。

#### 5.14.3 ⭐ 结构选择器落地前，先普查命中数

第 18 轮用的选择器：`div:has(> button + button + button)`（= ≥3 个直接 button 子项）。

| 弹窗 | 命中 | 后果 |
|---|---|---|
| Settings | **2** | 主题卡容器 + `> nav` 标签行 |
| Add workspace | **0** | 无误伤（其页脚按钮不是同父的 3 个直接子项） |

Settings 里那个多出来的命中是**我自己造成的回归**：
合并成一条规则后，**nav 标签行按钮被一起撑到 62px**
（盒从 `460×44` 变成 `283×67`）。
**是在 T1 的 A/B 里当场量到并揪出来的**，不是上线后才发现。
修法：给 `[role="dialog"] > nav …` 显式写**还原规则**，还原后实测 `96×44`。

> `:has()` 计数型选择器命中 >1 时，**要么加排除 / 还原规则，要么改用 custom.js 打标记类**。
> 「命中数 = 1」不是可选项，是前置条件。

#### 5.14.4 ⭐ `flex: 1 1 0%` 的树长不大，不是 bug，是 chrome 吃掉了它

侧栏根 5 个直接子块（实测 y / 高）：

```
[0,60]    logo 头
[64,48]   New Session
[124,100] Plugins / Automation tasks
[232,347] Workspaces + 树     ← flex: 1 1 0%
[579,112] Mobile access / Settings
```

树 `盒[8,276,337,303]`，`scrollHeight 1122`，`overflow-y: auto`。
树**已经是** `flex: 1 1 0%`，它长不大是因为 chrome 占掉 344px。
**压行高（48→44）只能换来 +1 行；想让树真正长高，必须先压 chrome。**
本轮只做了行高，**树高 303 → 305 几乎没动** —— 这是已知的未竟项，不假装解决。

#### 5.14.5 ⭐ 算行距前，先确认相邻两行是不是同父兄弟

第 18 轮曾量出「行间距 52px」并准备去改 gap。**量错了**：
那批 `[role="treeitem"]` 混了「项目行」和它**内嵌的会话行**，相邻两个未必是兄弟。
改口径（只在**同一个父分组**内量）后，组内间距只有 **2px**、组间 **4px** ——
**本来就很密，不是问题**。

> 量重复元素前先确认层级。跨层级混量会造出一个「看起来该修、其实没坏」的缺陷，
> 改了还要回滚。

#### 5.14.6 第 17 轮定论：给「从不绘制」的元素调样式前先 dump 可见性

Settings 的字号步进器（`[ 13 ][ ∧ ][ ∨ ] px`）连续三轮方案（T1–T4）全部「无效」：
`getComputedStyle` 如实读回新值、几何也全对，**但图上什么都没有**。根因三条：

1. ⭐ **主因 `opacity: 0`** —— 元素**从不绘制**，任何普通选择器都看不见它。
2. 16 单位 viewBox 的 svg 被压进 9px，**描边只剩 0.56px**，几乎不可见。
3. 容器 `position: absolute` + 右锚，退出右锚后**位置整体跑掉**。

修法 B14（`custom.css`）：`opacity: 1` + `position: static` + 退出右锚
+ svg 提到 18px + 按钮补到 `44×44`。
真触摸验证（`adb shell input tap`，**不能用合成 `.click()`**）：`13 → 14 → 15`，
且弹窗内 `<44px` 的按钮数 = **0**。

> **纪律**：给元素调样式前先 dump
> `opacity` / `visibility` / `transform` / 祖先 `overflow` / `elementFromPoint`。
>
> **纪律**：验证功能**必须用真触摸**。合成 `.click()` 后立刻读 DOM
> 会读出**假的「值没变」**——React 异步重渲染，读到的是点击前的旧树。

#### 5.14.7 配套的两条基础设施

1. **JS 语法错在本地用真解析器拦**（`node --check`）。第 18 轮两次栽在这
   （中文标识符 walrus、`/\s\/g` 少一个 `+`），**都被拦在本地**，
   一次 adb + CDP 往返都没浪费。
2. **Python `json.dumps` 之前，把 JS 里的计算字段放独立对象**。
   曾把派生字段挂到**数组**上，`JSON.stringify` 会把数组的额外属性**整个丢掉**，
   Python 端拿到纯 `list` 再 `.get()` 就炸。

#### 5.14.8 触控下限不因为「要紧凑」而让步

行高 48 → **44**，不是随手砍的：**44dp 是 iOS HIG 与 Material 都认可的触摸下限**。
同轮把弹窗内**所有**按钮补到 `min-width/height: 44px`（B14），
实测弹窗内 `<44px` 的按钮数 = **0**。
「更紧凑」和「更可点」在本项目里**必须同时成立**，冲突时以 44dp 为准。

#### 5.14.9 ⭐ 模拟器 dp ↔ 屏幕像素标定（`emulator-5554` / 359×691dp 视口）

真触摸验证依赖 `adb shell input tap`，坐标换算**必须钉死，不能靠估**。
第 18 轮曾因为在被缩放的截图预览上目测，误判这条公式有 90~120px 误差，
白白怀疑了一轮。三方对照后的定论：

| 证据 | 结论 |
|---|---|
| `wm density` = **560** | dpr = 560/160 = **3.5** |
| 359 × 3.5 = **1256** = 截图宽（`wm size` override 1256×2760） | 横向**无**系统栏 |
| 2760 − 343 = 2417 ≈ 691 × 3.5 = **2418** | 顶部 chrome **343px**，WebView 直抵屏幕底 |
| 真触摸 13→14→15，误差 0 | 公式可用 |

```
屏幕 x = dp_x × 3.5
屏幕 y = 343 + dp_y × 3.5        # 343 = 状态栏 + Flutter 原生标题栏（返回箭头 + 设备名）
```

> ⚠️ **`343` 不是常数，是这台模拟器当前状态的实测值**。
> 换 AVD、换设备、改原生壳高度都要**重测**：
> `wm size` 高度 − CSS 视口高度 × dpr = 顶部偏移。
>
> ⚠️ `y < 343px` 属 **Flutter 原生壳**（状态栏 / 返回箭头），
> **不在 WebView DOM 里**，`elementFromPoint` 查不到，只能 `adb shell input tap`。
>
> ⚠️ 拿截图**目测**像素时，先确认预览有没有被缩放 ——
> 本项目的 `read_image` 会返回 normalized 副本，坐标与原图不一致。
> **目测只用来发现异常，判坐标一律以 CDP 量到的 dp 为准。**

#### 5.14.10 ⭐⭐ 压哪里有用，和直觉完全相反（`flex: 1 1 0%` 的兄弟块吃掉全部余量）

第 18 轮留的未竟项（树高只从 303 动到 305）本轮还掉了。但过程比结果重要：

侧栏根是 column flex，块3 是 `flex: 1 1 0%`（**吃掉全部余量**），块4 是最后一项 `0 0 auto`。
所以 **`裁切线 = 视口高 − 最后一个 flex 项的高度`**。

| 压哪里 | 后果 | 实测 |
|---|---|---|
| 压块3 **上方**的块1/块2 | 块3 原样吃掉省下的空间 ⇒ **树一点不变** | 块1 48→44，树高 303→**307**（+4，白费） |
| 压块3 **下方**的块4 | 裁切线上移 + 块3 长高 ⇒ **树真长高** | 块4 112→96，树高 303→**319**（+16） |

> **要长高只能压最后一个 flex 项。压「上面看起来更松」的，纯属白费。**
> 这和「要紧凑就压间距」的直觉相反，也是第 18 轮会失手的根因。

**判准落到行数**（纪律 (s) 的第二次兑现，直接决定要不要再加 4px）：

| 组 | 树高 | 完整可见行 |
|---|---|---|
| 基线 | 303 | 6/21 |
| 压块4 | 319 | **6/21** ← 差 **1px** |
| 再压顶栏图标 | 323 | **7/21** ✅ |

7 行需要 `7×44 + 6×2 = 320px`。**319 差 1px，323 刚好过线。**

#### 5.14.11 ⭐⭐ `<style>` 里的非法选择器是**静默丢弃**

为了选中侧栏底栏，四个候选的结果：

| 候选 | 结果 |
|---|---|
| `div:has(> [role="tree"]) ~ div` | 合法，**命中 0**（树的直接父是唯一子元素） |
| `div:has(> div:has(> [role="tree"])) ~ div` | **整条非法** ⇒ 静默丢弃 |
| `nav ~ div:not(:has(> div > [role="tree"]))` | 合法，**命中 2**（没排掉块3） |
| **`nav ~ div:not(:has([role="tree"]))`** | **命中 1** ✅ |

第 2 行是本轮最贵的坑：它**不是「没匹配上」，是整条规则被浏览器丢掉**，
A/B 表现与「选择器写对了但不匹配」**完全一样**。
我当场误读成「`~` 要求同父」——**那个结论是错的，真因是语法非法**。

> ⚠️ A/B 出现「毫无反应」，**先怀疑语法，再怀疑匹配**。
> 排查：把候选丢进 `document.querySelectorAll()` 并 **try/catch**，
> 拿到 `DOMException` 才算数。
>
> ⚠️ **命中 2 且「恰好没炸」的选择器不上线**，哪怕当轮全绿。
> 排除条件要写到**最短也最直观**：「凡含树的都不是块4」。

#### 5.14.12 ⭐ 布局动画未结束时测得的是中间态

开局第一件事量到**树高 1070px**（自然高），5 秒后再量是 **303px**（被 flex 压住）。
差点误判成「B15 把 overflow 从 auto 弄成了裁切」——
拆 B15 三条规则逐条 A/B 后确认**没有回归**。

> 与「换主题必须等过渡结束」同源。
> 本轮起所有 A/B 固定 `sleep(2.0)` 再量。

#### 5.14.13 ⭐⭐⭐ 内联 `!important` 压过一切作者样式表规则

第 20 轮最贵的一条。把顶部药丸从 44 改到 40，**写了就是不改**：

| 试法 | 结果 |
|---|---|
| `[data-qx-sb-primary]{min-height:33px!important}` | **44** |
| `[x][x]{…!important}`（特异性 0,2,0） | **44** |
| 再叠 `button[x]` / 三重属性 / 放最后 | **44** |
| `el.style.setProperty('min-height','40px','important')` | **40** ✅ |

读 CSSOM 才看见真相：元素上有**内联** `min-height: 44px !important`。
**不是 custom.js 写的**（全项目 4 处 `min-height` 内联都在会话区 /
点触点修复 / 细图按钮里，够不到侧栏）—— **是 DSH 运行时自己写的**。

> **内联 `!important` 排在作者样式表 `!important` 之上，
> 且这一层与选择器特异性无关。** 叠多少遍 `[x][x]` 都一样。
> 这不是「特异性不够」，是**层不对**。

**连带推翻一个假成功**：第 19 轮 B16「把侧栏底栏压到 48」当时真的生效了 ——
但那是因为 **48 恰好等于内联值**，不是 B16 压过了谁。
现在改成 40 立刻打回原形。

> ⚠️ **别把「值恰好相同」当成「规则生效了」。**
> 与第 17 轮那条（"值为 0 是因为不绘制"）同类：
> **一个「看起来对了」的结果，先问「它凭什么对的」。**
>
> ⚠️ 排查口诀：**改不动尺寸时，先读一次 `getAttribute('style')`。**
> 这一步能省掉整条特异性排查链。

#### 5.14.14 换视觉语言 ≠ 压间距

用户诉求是「**不要传统移动页，要 VSCode 那样桌面级质感**」。
本轮换掉的是整套语言，不只是密度：

| | 修前 | 修后 |
|---|---|---|
| 树项行高 / 圆角 | 44 / **12px 药丸** | **34 / 4px** |
| logo 头 | 60 | **48** |
| 顶部大药丸 | 44 / 圆角 12 | **40 / 圆角 4** |
| Plugins / Automation | 48 | **36** |
| **树内填充药丸** | **1** | **0** |
| 时间戳 | 12px `normal` | **`tabular-nums`** |
| **完整可见行** | **7/20** | **10/20** |

⚠️ **只改一半反而更糟**：B17 只收紧树，结果树一密集，
**导航区成了新的「移动页」信号** —— 上下像两个产品拼在一起。
**桌面级质感的另一半是全局统一，不是把某一块改好。**

无障碍取舍（UI 库原文）：
「iOS 44pt / Android 48dp; **for web use the separate WCAG Target Size rule**」
「**Don't treat one unit or minimum as universal**」
⇒ WebView 内的 web 内容适用 **WCAG 2.2 AA 24×24 CSS px**，
树行 34px（9.0mm）达标；**一级导航仍保 44~48px**。
另补：`touch-action: manipulation`（去 300ms 延迟）、`:focus-visible` 焦点环、
`prefers-reduced-motion`、过渡统一 180ms。

#### 5.14.15 选择器考古的四个坑（第 20 轮连续踩中）

| 候选 | 结果 |
|---|---|
| `[data-slot="sidebar"] …` | **命中 0** —— 侧栏根**没有 `data-slot`** |
| `div[aria-label="New session"]` | **命中 0** —— 药丸其实是 `<button>` |
| `button[aria-label="New session"]` | **命中 2** —— 274×44 的 logo 区与 326×44 的药丸**共用同一个 aria-label** |
| `块.querySelector(...)` | **漏掉块1** —— 药丸**本身就是**那个 button |

与第 19 轮 `:has()` 三坑同源，结论升级为铁律：

> **① 选择器必须实测命中数，且 `querySelectorAll` 的每个候选都要验。
> ② 同一个 `aria-label` 可能挂在多个元素上。
> ③ `querySelector` 只搜后代，不搜元素自身 → 配 `matches()`。**
>
> 当结构判据超过 2 条还分不清，就**停止考古，改用 custom.js 打 `data-qx-*` 标记**
>（本项目既有约定：`data-qx-wsroot` / `data-qx-rowtitle` / `data-qx-nspill` / `data-qx-sb-*`）。
