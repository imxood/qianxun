## 2. 这一版做的六件事

### 2.1 顶栏「空白方框」修复（A16）

**症状**：顶栏第二行左边是一个**没有任何图标的圆角方框**，一眼像「资源没加载出来」。

**实测根因**：DSH 把 `[slot="…header.utilities"]` 的第一个 SPAN 设计成
**24px 高的分段控件外壳**（内层 DIV 是 `overflow:hidden`），
而 A3 给 header 里的按钮兜了 `min-height:48px`：

```
外壳 SPAN   [88, 70, 89, 24]   overflow:hidden
  BUTTON      [88, 70, 44, 48]  ← 被撑到 48
    IMG        [104, 88, 13, 13]  ← 图标在这里
外壳底边 y=94，图标底 y=101 → 只露出 6px
```

**连带**：外壳只有 24 高又在 48 高的行里 `align-items:center`，
整组下沉到 y=70，同行其它按钮在 y=58 —— **同一行差 12px，肉眼可见地歪着**。

**修法**：撑外壳，不撤按钮（按钮 44 是触控下限）。
实测修后：外壳 `[88,60,89,44]`、图标 `iconInsideShell: true`、行内 y 全部 = 60。

### 2.2 顶栏两行化：164px → 102px（A18/A19/A20）

P0。**算过才知道放不下**：

```
内容区 = 359 − 左 20 − 右 28 = 311
tabs ：Chat 44 + Trajectory 66 = 110，加左 padding → 占 20…150
工具 ：4×40 + 间距 12 = 172，右对齐 → 147…319
```

40px 宽刚好卡住；44 宽会重叠 7px。

**最终方案**：tabs 绝对定位到第二行左侧，工具行右对齐，
工具按钮宽度 44 → **40**（高度保持 44）。
实测 `gap = 5px`、`overlaps = 0`、`toolRight` 正好落在 331。

**关键决策：用 `display:contents` + 绝对定位，而不是搬运 DOM 节点。**
`[slot="conversation.session.header"]` 本来就是 `display:contents`，
tablist 已经是 HEADER 栅格的直接子项，钉一下就行 ——
**DOM 一个节点不动，React 的协调器毫无察觉**。
（对比：JS 搬运 DOM 会让 React 在下次渲染抛 NotFoundError。）

**窄屏兜底**：<350px 时这套并排放不下（内容区掉到 292 以下），
把 `position:absolute` 撤掉即可回到 DSH 原生三行 —— **宁可多占高度，也不要重叠**。

### 2.3 顶栏必须不透明（A20）

实测 `HEADER` 的 `background-color = rgba(0,0,0,0)`、`backdrop-filter: none`。
桌面没事（内容从下方开始），窄屏下 header 压到 102px、内容紧贴上来，
转录第一行**从 header 底下透出来、被下边缘切掉上半截** ——
屏幕上就是一行「只剩半截笔画」的字。

用 DSH 自己的令牌 `var(--dsw-alias-bg-base)` 而不是写死颜色，主题切换自动跟随（P3）。

### 2.4 状态条收进工具栏按钮 + 点击弹层（B10/B11/B12/B13）

**这是本版最大的一处产品改动**（也是用户明确要求的）。

**改之前**：底部那行占 48px，两颗药丸的文字被压成 3 行碎字。
**改之后**：工具栏里一个 `79%` 标签，点开是弹层，三条字段一个不少。

**按钮上只显示上下文占用**：它是那堆数里唯一「会随时间逼近上限」的量。

**踩到的坑（按发生顺序）**：

| # | 症状 | 根因 |
|---|---|---|
| 1 | 按钮掉到 composer 卡片底部，多出 104px 空白 | 工具行 `flex-wrap`，305 > 304，**差 1px 就换行** |
| 2 | `tools` 被压成 **5px** | 行里加第三个子元素后，`trailing` 的 `flex-grow` 把剩余空间全吃掉 |
| 3 | 整条工具栏 `flex-direction: row` 后 `tools` 变 16px | `align-self:flex-start` 作用于交叉轴 |
| 4 | 百分比显示成 **98%** | 宽泛匹配 `/(\d+)%/` 先撞上「Cache hit 98%」 |
| 5 | **整个输入框消失** | 我自己的按钮文字是「79%」，命中统计判据 → 标记一路走到 composer 根 |
| 6 | 药丸永远停在「—」 | `display:none` 让数据源量不到了 |

**最终解**：

- 行宽用 `flex-wrap` 的临界不可靠 → 改成**「透明 44px 热区 + 24px 可见标签」**
- 按钮插在 `tools` 与 `trailing` **之间**（不是行尾，否则读数落到发送键右边）
- 百分比用 `/^(\d{1,3})\s*%$/` **整段锚定**（只有上下文那个按钮的文字纯粹是一个百分数）
- `findStatButtons` **先排掉 `.qx-status-btn`**
  > **规律：自己造的元素绝不能进入「找 DSH 元素」的判据。**
- 统计区用 `position:absolute + height:0 + visibility:hidden` 收起
  > **`display:none` 会让数据源一起消失**；`visibility:hidden` 不清除布局盒，
  > 子元素照常排版、`getBoundingClientRect()` 仍返回真实宽高。
- CSS 侧再加一道护栏：含输入区的容器**一律不许被藏** ——
  这类「误判后果是整块界面没了」的问题，光靠 JS 判据不够。

### 2.5 composer 瘦身 212px → 120px（B13）

**本版第二大的收益，而且是「找出来才发现的」**。

实测工具栏行 `uV2eYG_row` 的**实际内容只有 44px**
（tools / 状态药丸 / trailing，全是 44 高的按钮），
但它的盒子是 **152px** —— 上下各空 50 多 px。

试过 `height:auto` / `fit-content` / `align-self:flex-start` —— **全都无效**（仍是 152）。
扫遍样式表也找不到任何设 `height` 的规则（`.uV2eYG_row` 只声明了
`flex-wrap` / `align-items` / `padding`）。

> **「没有规则解释得通，但写死一个值就成立」—— 这种只能靠实测确认，不能靠推理。**

写死 `height: 52px` 后：行 152 → **60px**，composer 212 → **120px**，
**正文白拿回约 92px**（视口 691 的 13%）。

代价与兜底：计划编辑器展开时需要更多高度，
所以 JS 在计划区有内容时打 `data-qx-plan`，CSS 据此放开 `height:auto`。

### 2.6 侧栏列表被推出屏幕（A22）

真机截图发现：工作区与会话列表**整体右移 200px**，
`egui_hikvision_ap`、`补充命令输入文件` 被切掉。

```
root [12,238,347,335]  display:flex  flex-direction:column  flex-wrap:wrap
  ├ sectionHeader [12,240,213,36]
  └ listArea      [217,238,245,622]   ← 右边缘 462，视口只有 359
```

**成因**：`column + wrap` 的 flex，**换行是往右边换一列**。
两个子元素高 36 + 622 = 658 > 容器 335，于是 `listArea` 被丢到第二列。

**修法用 grid 而不是 `flex-direction: row`**：
`row + wrap` 实测也能摆对，但它是**靠内容超高触发换行**才换下去的 ——
视口一高（真机 789dp）就可能不换行、问题复发。
「单列 grid」是**无条件**堆叠，不依赖任何测量值。
**这类「靠巧合成立的修法」不能要。**

修后：所有行 x=221 → **12**，右边缘 **335**，越界/截断列表清零。

### 2.7 顺手修的两个真问题

- **1×44 的图片缩略图按钮**：`R_Yw7q_frame` 盒子只有 1×44，里面的 `<img>` 是 0×43，
  但它 `cursor:zoom-in`、有 `onclick`、`tabIndex=0` —— **是真能点的控件，却永远点不中**。
  起因是那些 PNG 本身就是 1×1，DSH 按自然尺寸渲染就成了 1px。
  给最小可点尺寸后解决。
  > ⚠️ 它长得**非常像**文档 §7.4 记录的那个「1×44 占位元素」误报。
  > 区别只有一条：**里面有没有 `<img>`**。不查清楚就跳过，会漏掉一个真缺陷。

- **CSS 规则顺序**：A18 必须排在 A15 之后。
  同为 `!important` 时**后写的赢**，A15 的 `min-width:56px !important` 会压过 A18 的 44px。
  > `!important` 拼的是**特异性**，但**同特异性时拼的是顺序**。

## 2.8 第 7 轮：深色主题对比度统一（P1 完成）

新建 `scripts/check_qx_contrast.py` + `scripts/probe_contrast.js`。

### 为什么是「实测」而不是静态算

`check_contrast.py` 查的是 Flutter 令牌（声明式）。
但定制层的颜色**渲染出来才知道对不对**：

- `.qx-status-btn` 底色是 `rgb(127 127 127 / .12)` —— 半透明，
  真实对比度取决于**它下面压着什么**（composer 卡片 / 页面底色）。
- `.qx-hint-*` 挂在 DSH 自己的行里，背景是继承来的。

所以走 CDP 进页面量**真实 computed color**，
再沿祖先把半透明层**合成**出真实底色。

### 闸门第一版也是「绿的假的」

跑出来 `✓ 全部达标`，但 7 项里有 3 项写着「当前未渲染，跳过」——
**那三项根本没被量过**。

> **「没量到」不等于「没问题」。**
> 静默跳过会让闸门在元素根本没渲染时也报绿。

改成两件事：

1. 闸门**自己**把元素驱动到会渲染的状态（开弹层、开工作区页）
2. 任何目标整轮**一次都没量到** → 直接判失败

### 闸门抓到的 2 个真失败

| 元素 | 深色 | 亮色 |
|---|---|---|
| `.qx-hint-sparse` | **3.81:1** ✗ | **2.88:1** ✗ |

背景是实测的会话行底色（深 `rgb(27,27,28)` / 亮 `rgb(249,250,251)`）。

> ⚠️ 文档 §6 当时写的是「`.qx-hint-ctx` 的琥珀色在亮色下对比度不足」——
> **实测最严重的其实是 `.qx-hint-sparse`**（亮色 2.88:1），
> 而它是**出现频率最高**的那条（208/394 条会话都是稀疏的）。

### 一个不存在「万能灰度」的事实

在 `#5a6672 ↔ #9aa7b4` 之间扫了 28 档亮度，
**没有一档能同时在深浅两套主题下都 ≥4.5**：
深色底要亮字、亮色底要暗字，这是物理约束。

所以**必须每套主题各定一组令牌**，不能「一个值走天下」。
按文档 §6 的方向落成 B0 令牌块（`--qx-ink-hint` / `--qx-ink-ctx` / `--qx-ink-low|mid|high` / `--qx-surface*`）。

### 踩到的两个 CSS 坑

**① 令牌块不能挂 `:root`，得挂 `body`。**

CSS 自定义属性的 `var()` 替换发生在**它被声明的那个元素**上。
实测 DSH 把 `--dsw-alias-label-secondary` 定义在 **body**
（`getComputedStyle(documentElement).getPropertyValue(...)` 返回空串）。

于是 `:root { --qx-ink-low: var(--dsw-alias-label-secondary, #8794a0) }`
引用它 → **解析失败、直接落兜底值**，
深色下药丸显示成 `#8794a0`（3.78:1）而不是宿主的 7.81:1。

症状是「颜色变了一点但说不清为什么」，极难往回找。

**② 「能用宿主令牌就别自己造颜色」。**

药丸「低」档本来写死 `#6f757c`，深色下只有 **2.52:1**。
改回 `var(--dsw-alias-label-secondary, …)` 后是 **7.81:1** ——
宿主令牌本来就是对的，我们自己造的颜色反而不对。
这正是 P3 的「外来的元素必须与宿主视觉语言一致」。

### 顺带确认：那行「半截文字」是模拟器 GPU 伪影，不是缺陷

深色截图里 header 下缘总有一行「传，0/0 文件在 10ms 内退出人…**半截削**」。

按 §7.4 的纪律先查证，结论是**不是产品问题**：

| 检查 | 结果 |
|---|---|
| DOM 里搜这段文字 | **not found** |
| `elementsFromPoint` 该点 | 只有 header 与 tab |
| 字形 | 「传…出人…半截削」语义不通，**双重曝光特征** |
| 转录滚动容器 `overflow-y:auto` 起点 | 正好 **102**（header 底边）→ 结构上画不到 102 以上 |
| **真机（PKB110）截图** | **没有这行** |

最后一条是决定性的：**只在模拟器出现，真机没有**。

> **教训：「看着像坏了」要先证明它是坏的。**
> 若当时直接去加 z-index / 裁剪，动的就是一条本来正确的规则 ——
> 而且改完可能看不出差别，很难再回退。
>
> 判别伪影的三个信号：DOM 里没有、字形语义不通、**只在某一个环境出现**。

### 2.9 第 8 轮：列表里去掉上下文标签（用户明确要求）

> 原话：「在 Sessions列表中 不需要显示 `上下文 51%`」

**为什么本来就该去掉**（两条独立理由）：

1. **重复信息**：上下文占用已由 composer 工具栏里的「N%」标签承担，
   那个标签就在**输入框旁边** —— 「准备发消息时看还剩多少」才是它的使用场景；
   列表是「找会话」的浏览场景，两边都放是噪声。
2. **它本来就有布局缺陷**：`.qx-hint-ctx` 是 `position:absolute`
   定位在 `right:8px`，实测与标题**重叠 52px**。

实现上做了两层：

- JS 不再插入，并在每轮 `scan()` 里**清掉上一轮可能残留的旧节点**
  （`state.painted` 让同一行只加工一次，不清理就会在热替换后出现两个）
- CSS 加一道 `[data-slot='sidebar'] .qx-hint-ctx { display:none }` 兜底 ——
  页面未刷新的窗口里旧节点还在，这一条保证「就算它还在，也一定看不见」

**同时把断言方向反过来**：以前断言「BBB 必须有上下文提示」，
现在断言「**任何一行都不许再有上下文标签**」。
用户明确提过的要求，值得钉一条断言，否则重构时很容易又插回来。

### 2.10 工作区列表的两个连带缺陷

#### A22 的真正根因：标记取错了层级

第一次修完看着好了（列表回到 x=12），但那是**碰巧**。
后来发现标记打在了 `bhn1Oq_groupSection` 上，而真正制造偏移的
`bhn1Oq_listArea` / `bhn1Oq_treeBody`（x=217）**没被标到**：

```
从行往上：
  i0 _root_38jqx_3       [221,…]  行
  i1 bhn1Oq_groupSection [221,…]  ← 第一个合格的，改它没用
  i2 bhn1Oq_list        [217,…]
  i3 bhn1Oq_treeBody    [221,…]  ← 偏移从这里开始
  i4 bhn1Oq_listArea    [217,…]  ← 真正的病根
```

修法：**把整条链上所有合格的都标上**（对中间层无害，对根层才是修复）。

> **教训：「第一个匹配的」和「真正出问题的那层」经常不是同一个。**
> 更麻烦的是，第一次「修好了」如果是碰巧的，
> 换一次会话/换一个层级就会复发，而且很难联想到是这次改动。

#### A23：行宽收回视口后，标题没有收缩能力

A22 把行宽从 376 压回 323 之后，
`16(slot) + 320(title) + 14(time) = 350 > 323` → **整行换行成三排**，
48px 的行装不下。实测症状：长标题冲出卡片圆角、时间掉到下一排、
标题和提示**重叠成一团**。

修法：锁死行不换行 + 给标题 `flex:0 1 auto; min-width:0` + 省略号。

标题由 `markRowTitle()` **按行为标记**（「文字最多的那个非我们元素」），
不写死「第几个子元素」—— §5.3 记过：子元素顺序会随 DSH 版本变。

## 2.11 两条工具链事故（这一轮各踩了一次）

### ① PowerShell 的 `Get-Content | Set-Content` 毁了中文编码

```powershell
(Get-Content x.py -Raw) -replace ... | Set-Content x.py -Encoding utf8
```

在中文 Windows 上是**破坏性**的：
`Get-Content` 按系统 ANSI 编码（cp936/GBK）解码，
`Set-Content -Encoding utf8` 再把解出来的乱码按 UTF-8 写回，
**每个中文字符都变成「UTF-8 字节被当成 GBK 解释」的结果，且不可逆**。

损坏的是 `scripts/check_custom_js_runs.py`（28KB，含大量中文注释与断言文案），
严格逆转也失败（位置 33 出现私有区字符 `U+E511`），
只能 `git checkout` 后用脚本重做全部改动。

> **规矩：改任何含中文的源码，一律用 Edit 工具或 Python 脚本，
> 不要用 PowerShell 的 `Get-Content | Set-Content` 管道。**
>
> 全局规则也已更新：命令行操作统一用 Python + subprocess。

### ② 批量重放脚本「打印了 ✓ 却一点没生效」

恢复闸门时写了个重放脚本，逐条 `str.replace` 后再写文件。
它逐条打印「✓ 选择器引擎」「✓ childNodes」……
然后在第 7 条 `raise SystemExit`，而 `write_text` 在**脚本末尾** ——
**前 6 条已经改好的内容全部丢掉**，现象是「明明打印了 ✓ 却一点没生效」。

> **批量脚本：任何一步失败都不能提前退出。**
> 成功要记下来，失败要留下痕迹，但**绝不能丢掉已经做完的部分**。

顺带两条经验：

- **多行精确匹配一旦有一个空格/全角符号对不上就定位失败**，
  而失败信息里看不出差在哪。改成「锚点 + 行范围」更稳。
- 失败时**把匹配到的实际内容打出来**，光说「定位失败」等于没信息。

## 2.13 第 9 轮：追一个 32×40 的按钮，追出三个缺陷

这一轮的起点很小：消息下方的操作按钮只有 **32×40**，够不上 44 的可点下限。
结果从「改两个数字」变成「三处代码都是错的」，其中一个还**曾经绿着**。

### (1) 32×40 是我自己写的，而且理由是错的

第 8 轮我在 `markShortTapRows` 里写下：

```js
el.style.setProperty('min-width', '32px', 'important')
```

理由是「间距只有 40px，补到 44 会互相重叠」。

**这个理由从一开始就是错的**：我拿「按钮之间的间距」当成了「可用宽度」。
实测那一行（y=520）：

```
5 个按钮 32×40，间距 8，x 26 → 226   → 行宽只有 200，视口 359
右边空着 133px。补到 44 是 5×44 + 4×8 = 252，落在 26 → 278 —— 装得下
```

> **「32 会不会重叠」本来量一下就知道，不该推断。**
> 而且推断的成本很高：这一压就是一整轮。

### (2) 卡死：`>= 32` 的门槛让按钮永远升不上去

修的时候顺手发现，改完 32 之后按钮**再也回不到 44**：

```js
if (r.width >= 32) continue   // ← 按钮已经是 32 了，下一轮直接跳过
```

自指的死循环。改成按**目标值**判定：

```js
if (r.width >= 44) continue   // 幂等，且能把旧版留下的 32 一起救回来
```

> **门槛要按目标值写，不能按旧值写。**
> 按旧值写出的「幂等」，恰恰制造了一个上不去的死角 ——
> 而且每次扫描都「跑过了」，日志里看不出任何异常。

### (3) ⭐ 行内 `!important` 压过一切样式表规则

A24 我在 `custom.css` 里加了 `[data-slot='conversation.chat.node'] button { min-width:44px !important }`，
热替换也「成功」了，**盒子纹丝不动**。

逐步排查下来是这样：

| 手段 | 结果 |
|---|---|
| 规则在真样式表里（`hasA24: true`） | ✅ 在 |
| 选择器匹配到元素（`b.matches(...) === true`） | ✅ 匹配 |
| 在 `@media (max-width:760px)` 里（`matchMedia` 为 true） | ✅ 生效范围对 |
| `sheet.insertRule()` 再加一条更高特异性 + `!important` | ❌ **32×40** |
| `b.style.setProperty('min-width','44px','important')` | ✅ **44×44** |

原因：**行内 style 上的 `!important` 在层叠里高于任何样式表规则** ——
特异性再高、写几个 `!important` 都没用，除非也写进行内。

而这个行内 `!important` 恰恰是**我自己上一轮写进去的**。查了半小时的对手是我自己。

> **`custom.css` 里的 A24 保留，但降级为「兜底」**（万一哪天 DSH 不写行内 important）。
> 真正让它生效的是 JS。两边都留着：JS 负责现在，CSS 负责将来。

### (4) 🔴 热替换工具自己坏了三轮，还一直报成功

查 CSS 为什么不生效时，发现 `cssreload.py` **从第二轮起就没换过样式表**：

```js
const olds = [...有 data-qx-base 标记的 custom.css link]
for (const x of 所有 custom.css link) {
  const fresh = (olds.indexOf(x) === -1)
  if (!fresh) continue          // ← 第 2 轮起，上面那个永远是 false
  …
}
```

第 1 轮替换并打标记；第 2 轮起那张「有标记的」直接跳过 —— **一张都不换，但每轮都报告成功**。

于是我以为是特异性、以为是 `!important`、以为是媒体查询 —— 查了三个完全错误的方向。

修好之后给它加了自检（查 href 里的时间戳，**不是查有没有跑**）：

```
replaced 2
自检 {"总表数":1,"本轮新表数":1,"href":"=1791362215259"}
```

> **一个「成功」但没做事的工具，比没有工具更坏。**
> 它会让你把时间全部花在错误的怀疑对象上 —— 而且你不会怀疑它，因为它每次都成功。
> 这也是本项目第 7 次「闸门绿得像没这回事」，只不过这次绿的是工具。

### (5) ⭐⭐ 顺带挖出一个 high 级缺陷：代码块把版面撑到 1832px

按钮变成 44×44 之后，测量脚本报出一行看不懂的数据：

```
y=-1149  2 个  [1754, -1149, 44, 44] 'Wrap lines'   ← 视口才 359
          [1802, -1149, 44, 44] 'Copy'
```

顺着祖先链往上量：

```
div.EvIC1a_flowItem    宽 936   min-width: max-content   ← DSH 故意按内容撑开
  └ div.EvIC1a_column  宽 288
      └ …→ markdown body 1832 → 代码块 header 1792
```

**一条含代码块的消息把版面撑到 1832px**，代码块上的
`Copy` / `Wrap lines` 落在 x=1754 / 1802 —— **用户永远点不到**。

而我的 A5 规则（`min-width: 0; max-width: 100%`）**明明写着，一直没生效**：

```
DSH  min-width: max-content  → 936
我的  max-width: 100%         → 288
936 > 288  →  min 赢
```

> **CSS 里 `min-width` 压过 `max-width`。**
> 只写 `max-width` 约束不住「按内容定尺寸」的元素，必须直接改 `min-width`，
> 而且要 `!important`（DSH 那条优先级更高）。
> 这条规则从第 3 版写到现在，**一个字都没起过作用**。

修完：`min-width: 0 !important`。全页再无 >420px 的元素，
`Copy` 回到 x=258，可见。

### (6) 这个 high 级缺陷为什么审查没抓到

因为审查第 1 条路径开头是 `if (ancestorHandles(el)) continue` ——
而转录滚动容器是 `overflow-x: auto`，**整个撑宽的元素被当成「可横向滚动的正常内容」跳过了**。

可它横向根本不该滚：该滚的是**代码块自己**（`<pre>`，A4 已经让它 scroll），
滚整条消息是副作用。

补了 `content-blowout` 检查，并**先证明它能抓到**（注入 bug → 抓 → 撤掉 → 不报）：

| 状态 | 结果 |
|---|---|
| 正常（A5 已修） | high 0，撑宽 0 |
| 注入 `min-width: max-content` | **high 4，撑宽 45 个元素，最高 1381px** |
| 撤掉注入 | high 0，撑宽 0 |

> 审查脚本自己新加的检查项，**不先证明它能抓到真问题**，
> 那它和第 7 次那个静默跳过的分支一样只是个摆设。
> 而且「检查项不存在」和「检查项报 0」在结果里长得一模一样 ——
> 这个坑我今天踩了两次（第一次调错了入口，第二次去 stdout 里找 JSON，
> 而它 stdout 是给人看的摘要）。

### (7) 夹具补强：假 style 以前会丢掉 `important`

写第 21 条断言时发现，夹具的 `setProperty(k, v)` **把第三个参数直接扔了**。

也就是说：**写没写 `!important` 在测试里毫无差别** —— 而这恰恰是本轮的核心机制。
于是一条「值完全正确、真机上完全无效」的写法，能骗过全部 20 条断言。

```js
setProperty(k, v, pri) { s.map[k] = v; if (pri) s.imp[k] = pri }
```

## 3. 这一版暴露的方法论问题：闸门绿得像没这回事

新增功能做完，按 §8 的纪律补断言时才发现：
**闸门的假 DOM 只认 `.class` 选择器，其余一律返回 `[]` / `null`**。

于是 `findStatButtons` / `findToolbarRow` / `markWorkspaceRoot`
这些新路径**一行都没有被执行过**，闸门照样 15 项全绿。

三处具体问题：

1. `document.querySelectorAll` 被替身覆盖成「只认几种特征选择器」，其余 `return []`
2. `document.querySelector` 被覆盖成「只认两个选择器」，其余 `return null`
3. `document.querySelector('[data-slot="root"] > *')` 用了 **`>` 直接子级**，
   而解析器不支持 `>`

**修完后的做法**：

- 假 DOM 升级成能认 `.class` / `[attr]` / `[attr="v"]` / `tag` / 后代 / `>` / 逗号并列
- 两处覆盖都改成**未命中时回落到引擎**
- `getComputedStyle` 补齐 `flexDirection` / `gap` / `flex` 等
  （替身要像浏览器，**不要逼产品代码写防御性判断**）
- 补 `childNodes`（`readStats` 用了它）

> 这正是文档 §8 说的：每个新修复都要配一条**用真值构造**的断言。
> 这次连**断言本身**都一度是假的 —— fixture 里只写了 `aria-label` 没写文字，
> 而真 DOM 里两者都有，于是测的是一个「我编出来的结构」。

**新增断言（5 条）**：

1. 统计区被精确标记（**不含**输入卡片与 composer 根）
2. 状态按钮插在 tools 与 trailing 之间（发送键左边）
3. 按钮读数取的是上下文占用（79%），不是缓存命中率（98%）
4. 点按钮弹出统计层，三个字段一个不少
5. 自己造的状态按钮不会被算进统计区

**新增变异（4 个，全部被抓住）**：

| 变异 | 抓得住的原因 |
|---|---|
| 统计区退回「数按钮个数 + 取最内层」 | 断言 1：标记必须落在 dock 上 |
| 百分比去掉 `^…$` 整段锚定 | 断言 3：宽泛匹配会抓到 98% |
| 状态按钮 append 到行尾 | 断言 2：必须排在 trailing 之前 |
| `findStatButtons` 认自己的按钮 | 断言 5：自己的元素不进判据 |

> ⚠️ 第一个变异**第一版没抓住** —— 我写的变异体「一路覆盖成最外层」，
> 而那恰好与现在的实现等价，**变异体自己必须先确认真的改变了行为**。

## 4. 这一版最该记住的五件事

1. **「差 1px 就换行」的东西不能用「算准了正好放得下」来保证。**
   字体度量、dpr、系统字号差一点就复发。要么放宽阈值，要么换机制。

2. **上游的 flex 假设会限制你能插什么。**
   那一行的分配是按「恰好两个子元素」调的，插第三个就会把别的挤成 5px。

3. **判据不能依赖「自己藏起来的那个元素」。**
   隐藏是单向不可逆的，任何「数一数还剩几个」的判据在隐藏之后都会自己失效。

4. **自己造的元素绝不能进入「找 DSH 元素」的判据。**
   代价是整个输入框消失。

5. **闸门绿得像没这回事的次数，比产品 bug 还多。**
   断言自己也要用真值构造；变异体自己也要先确认真的改变了行为。
   —— **第 9 轮又添了一条：工具也会「成功但没做事」。**
   `cssreload.py` 连着三轮一张样式表都没换，却每轮都报成功，
   害我以为是特异性、以为是 `!important`、以为是媒体查询。
   **热的不是对象，换的是怀疑顺序。**

6. ⭐ **约束要写在「值真正起作用的那一层」。**
   CSS 里 `min-width` 压过 `max-width`（A5 从第 3 版写起，一个字没起过作用）；
   行内 `!important` 压过任何样式表规则（A24 写了等于没写）。
   两次都是「规则看着完全正确」。
   判据：**这条规则是在哪里生效的？被谁压着？** —— 不知道就别写。

7. **先量，再推断。**
   「间距 40px 所以补到 44 会重叠」这句话里，
   「间距」和「可用宽度」是两个量，我拿前者的数字当后者用，
   还为它压了整整一轮。真量一次：行宽 200、视口 359、右边空 133。

# 附录 · 第 10 轮：第一次去看 Trajectory 页

前九轮所有测量都在 **Chat 页**。这一轮第一次点开 **Trajectory 标签页**，
立刻撞上两处从来没发现过的问题 —— 而且都是**前九轮的审查完全看不到**的，
因为审查只在 Chat 页跑过。

## (1) Trajectory 页在 359dp 上不可用

实测（`emulator-5554`，视口 359×691）：

```
触控过小 20 个
  BUTTON  16×16 × 14   ←「跳到第 N 次请求」的唯一入口
  BUTTON  55×20        "Collapse turns"
  BUTTON  51×20        "Collapse calls"
```

那 14 个 16×16 的按钮，内部结构是：

```
BUTTON  16×16   透明背景 · 无子元素 · 无边框
  ::before   5×5 灰点          ← 唯一可见的东西
  ::after    "Request #1" 54×12 白底   ← 悬停标签
```

**它是「跳到第 N 次请求」的唯一入口**，而 16px 在手机上永远点不准。

## (2) 两处修法完全不同

### 请求标记：**对称负边距**

圆点是 `::before` **伪元素**，按钮自身完全透明 —— 所以放大按钮只会让热区变大，
那个 5px 的点不会变形。但直接补到 44 会把行高从 30 撑到 58，14 行就是 +392px，
滚动条明显变短，圆点还会挤成一列。

用**左右各 −14px 的对称负边距**把布局盒子拉回 16：

```js
el.style.setProperty('min-width',  '44px', 'important')
el.style.setProperty('min-height', '44px', 'important')
el.style.setProperty('margin-left',  '-14px', 'important')
el.style.setProperty('margin-right', '-14px', 'important')
el.style.setProperty('margin-top',   '-14px', 'important')
el.style.setProperty('margin-bottom','-14px', 'important')
```

实测（修复后）：


```js
// 闸门：真跑一次 mount（且**不 dispose 就再跑**，模拟热重载竞态）
dispose3 = registered({ document, window, root: makeEl('div') })
```

# 附录 · 第 13 轮：菜单是个空盒子，还没有底色

## (1) 现象

点会话顶栏的「More actions(⋯)」，弹出的菜单在 359dp 宽的屏幕上
是一个**几乎全空的白色圆角框** —— 只剩两个小图标，
「Download session log」和「Feedback」**一个字都看不见**。

实测（修复前）：

| 元素 | 位置 | 需要 | 缺 |
|---|---|---|---|
| 菜单 `DIV[role=menu]` | `[143,106,144,96]` | — | — |
| `role=presentation` | `[196,110,**38**,88]` | — | — |
| `role=menuitem` | `[196,110,**38**,44]` | — | — |
| 「Download session log」 | `[224,122,**2**,20]` | 127px | **125px** |
| 「Feedback」 | `[224,166,**2**,20]` | 56px | **54px** |

标签不是「被盖住」，是**真的只有 2px 宽**。

## (2) 根因：卡住的是按钮的固定 `width`，不是 `min-width`

页面上有两个形状一模一样的菜单，对比之后只有**一处**不同：

| | 🔴 More actions | ✅ More ways to open |
|---|---|---|
| 菜单 `align-items` | `center` | `normal` |
| `role=menuitem` **`width`** | **38px** | 159.5px |
| `role=menuitem` **`min-width`** | **38px** | 0px |
| 标签 | `[224,122,**2**,20]` | `[101,122,124,20]` |

标签自己是 `flex-grow:1; flex-basis:0%; min-width:0; overflow:hidden`
（两边**完全一样**）。这种写法意味着：**它对父容器的内容宽度贡献为 0**，
只有「父容器多出来的空闲空间」才会分给它。

而 `More actions` 的菜单项上有一条**固定的 `width: 38px`** ——
正好等于那个图标按钮的宽度（DSH 按「图标型锚点」给的）。
按钮撑不开 → 没有空闲空间 → 标签停在 0 → `overflow:hidden` 把它裁成 2px。

### 四个失败的假设（都记下来，因为它们看起来都很合理）

| # | 假设 | 实测 | 为什么不对 |
|---|---|---|---|
| 1 | 菜单 `align-items:center` 不拉伸子项 | `presentation` 38→**136px** ✅，标签**仍 2px** ❌ | 拉伸了容器，标签还是拿不到空间 |
| 2 | 给菜单 `width: max-content` | 菜单缩到 **46px**，标签仍 2px ❌ | `min-width:0` 拆掉了下限，按钮自己的 `min-width:38px` 接管 |
| 3 | `[role=presentation]` 也是 `center` | 两边 `align-items` **都是 `normal`** ❌ | 假设本身错了 |
| 4 | 按钮的 `min-width:38px` 卡住了 | 只加 `min-width:0` → 按钮**仍 38px**，标签仍 2px ❌ | `min-width` 赢不了固定 `width` |
| 5 | 菜单宽度不够 | 菜单给到 240px → 按钮**仍 38px**，标签仍 2px ❌ | 宽度压根没传导到按钮 |

**第 4、5 条合起来才是答案**：承重的是
`[role=menu] [role=menuitem] { min-width: 0; width: 100% }`。

## (3) 修了什么

```css
[role="menu"] { align-items: stretch !important;
                max-width: calc(100vw - 24px) !important; }
[role="menu"] [role="menuitem"] { min-width: 0 !important;
                                   width: 100% !important; }
```

**没有覆写 `left` / `right`。** 先后试了四种定位策略：

| 策略 | More actions | More ways to open | 问题数 |
|---|---|---|---|
| Y1 覆写定位 `right:12px` | ✅ | ✅ | 0 |
| Y2 只限宽 | ✅ | ✅ | 0 |
| Y3 `margin-left:auto` | ✅ | ✅ | 0 |
| **Y4 只修菜单项（采用）** | ✅ | ✅ | 0 |

四种全绿，就选**侵入性最小**的 Y4：菜单宽度交回内容自己算
（实测自然长到 171px），**DSH 的定位逻辑一个字都不动**。

修复后实测：

| 菜单 | 修复前 | 修复后 | 标签 |
|---|---|---|---|
| `More actions` | `[143,106,**144**,96]` | `[114,106,**173**,98]` | 2px → **127px**（正好够） |
| `More ways to open` | `[69,106,168,140]` | `[68,106,169,142]` | 124px，**未变**（没修坏） |

## (4) 修完截图才发现的第二个问题：菜单根本没有底色

B11 修完、截图一看，菜单是**半透明**的 —— 底下的正文
「adb/fastboot 进程：重启后立刻杀掉」直接透上来，
和菜单文字叠在一起，两边都难读。

实测菜单和菜单项全都是：

```
background-color: rgba(0, 0, 0, 0)
background-image : none
backdrop-filter  : none
box-shadow       : rgba(0,0,0,.04) 0 0 0 .5px ...   <- 有影没底
```

**一圈阴影，却没有底色。** 修法用已有的主题令牌（随 `prefers-color-scheme` 走）：

```css
[role="menu"] {
  background-color: var(--qx-surface) !important;   /* #12161d / #ffffff */
  color: var(--qx-ink-body) !important;             /* #e8edf2 / #141a21 */
  border: 1px solid color-mix(in srgb, var(--qx-ink-body) 14%, transparent) !important;
  box-shadow: 0 6px 24px color-mix(in srgb, var(--qx-ink-body) 18%, transparent) !important;
}
```

复验：`背景 rgb(255,255,255)` / `背景图 none` / `文字色 rgb(20,26,33)`，
两套菜单**标签全够宽、未越界、菜单项均 44px**。
浅色底 + 深色字对比度约 **16.9:1**。

> ⚠️ 这里本来就写了 `backdrop-filter`，但实测是 `none` ——
> **「我以为有的属性」也要先量**。所以选不透明底色，
> 而不是「半透明 + 毛玻璃」那种看着高级、实际不生效的写法。

# 附录 · 第 14 轮：省略号加了，但**加错了层**

## (1) 现象

会话顶栏标题「E:\git\c#\VioletToolBox 这个工具中,」在 359dp 宽下
被切掉一截，截图上最后是「这个工具」后面跟着**半个残缺字形**。

实测 `NAV[aria="Session hierarchy"] @[68,20,209,28]`，需要 241px。
右边 `Agent Team` 按钮左边界在 **287**，而标题实际右缘到 **309** ——
**压了 22px**。

## (2) 根因不是「宽度不够」，是三个属性凑在一起

| 元素 | 属性 | 值 |
|---|---|---|
| NAV | `overflow` | `hidden` ← 超出的被裁 |
| NAV | `text-overflow` | **`clip`**（默认值）← 裁的时候**不给省略号** |
| 内层 SPAN | `flex` | **`0 0 auto`** ← 不肯缩 |

所以裁切发生在 NAV 上，而且**裁得干干净净**，连「…」都没有。

## (3) A/B：四种策略，只有一种值得留下

判定标准事先写死：**标题右缘 vs `Agent Team` 按钮左边界 287**。

| 策略 | 标题右缘 | 结果 |
|---|---|---|
| T0 基线 | **309** | ⚠️ 压了 22px，硬切半个字 |
| **T1 让内层可缩 + 省略号** | **277** | ✅ 收住，带省略号 |
| T2 标题降到 15px | 277 | 与 T1 **完全相同** → 白改 |
| T3 收 padding | 277 | 与 T1 **完全相同** → 白改 |

T2/T3 一点效果都没有，所以**只做 T1**：
不降字号（拿可读性换一行标题不值），不加 padding（对结果零影响）。

## (4) ⚠️ T1 第一次也失败了：省略号加在了 flex 容器上

第一次部署 T1，量到 `text-overflow: ellipsis`、`overflow: hidden`、
右缘 277 —— **所有指标都是绿的**，脚本打印 ✅。

**但截图上那个残缺字形原封不动。**

查结构才发现是三层，我只改了前两层：

```
nav (display:flex, 209px, overflow:hidden)
└── SPAN (display:flex, 209px)          ← T1 加在这层，**无效**
    ├── SPAN (display:block, 241px)     ← 真正装 #text 的在这
    │   └── #text「E:\git\c#\VioletToolBox 这个工具中,」
    └── DIV[slot=…lineage] (display:contents)
```

**`text-overflow` 只对 block 容器生效。** T1 落在 flex 容器上，
属性值读回来确实是 `ellipsis`，**但一个字都没省略**。

决定性的证据是这个数：

| | 内层宽 | scrollWidth | **溢出** | 省略号 |
|---|---|---|---|---|
| 部署的 T1 | 241 | 241 | **0px** | **没画出来** |
| 补上第三层 | **209** | 241 | **32px** | ✅ 画出来了 |

**内层根本没有在被裁，裁的是它的外层 —— 所以它没有东西可以省略。**

加了 `nav > * > *` 之后，截图上是干净的
「E:\git\c#\VioletToolBox 这个...」，收在 `Agent Team` 按钮前面。

### 这一条是最值钱的教训

> **读回 `text-overflow: ellipsis` 不等于省略号画出来了。**

「属性值对」和「效果对」是两件事。要判定省略号真的生效，
必须看 **`scrollWidth > clientWidth`**（确实在裁），
而且**必须看截图** —— 半行汉字和三点省略号在缩略图上真的很像，
我就是这样被骗过去的。

这也和第 13 轮的教训同源：**「量到了某个属性」≠「这个属性在起作用」**
（那次是 `backdrop-filter: none`，这次是 `text-overflow: ellipsis` 但不生效）。

## (5) 静态守护：8/8 变异全抓，还抓出了守护自己的 bug

B13 加了两条守护。跑变异测试时发现一个**假阳性**：

```
✗ 菜单有底色：**缺 ['background-color: var(--qx-surface)']
```

**原文件上也报**。原因是守护用 `re.search`，只取**第一个**匹配的
`[role="menu"]` 块 —— 那是 B11 的块（只有 `align-items`），
而不是 B12 写底色的那块。**守护自己指错了地方。**

改成 `re.finditer`，要求「**存在某个**匹配块同时含有全部承重属性」。

改完的结果：

```
正向：rc=0 ✅
变异：8/8 全抓
  · 删 菜单项 width:100%      → 菜单项能展开 ✗
  · 删 菜单项 min-width:0     → 菜单项能展开 ✗
  · 删 菜单 align-items       → 菜单子项拉伸 ✗
  · 删 菜单背景色             → 菜单有底色   ✗
  · 删 标题内层 text-overflow → 标题内层省略 ✗
  · 删 标题外层 flex:0 1 auto → 标题外层可缩 ✗
  · 删 对话框 min-height:0    → 内容区可滚   ✗
  · 删 对话框 box-sizing      → 宽度不撑破   ✗
还原：逐字节一致 ✅
```

> 行为闸跑在 Node 夹具里，**没有布局引擎，测不到 CSS**。
> 所以「样式写对了」和「效果对了」之间，只能靠
> **设备实测 + 静态守护**两头夹住，中间没有缓冲。

# 附录 · 第 15 轮：十四轮都没量过深色模式

## (1) 为什么要专门做这一轮

B12 给菜单加的底色是 `--qx-surface`，它跟着
`prefers-color-scheme` 走；B13 的标题也用同一套令牌。

**也就是说第 13、14 轮修的两个缺陷，从头到尾只在浅色下验证过。**
深色值 `#12161d` 写在 CSS 里，但**一次都没有在屏幕上出现过**。
「理论上没问题」和「量过」之间隔着一次崩溃。

## (2) 先把主题逼出来

不能指望模拟器自己保持主题（第 13 轮它自己翻成了浅色）。直接下 adb：

```python
adb -s emulator-5554 shell cmd uimode night yes
adb -s emulator-5554 shell settings put secure ui_night_mode 2
```

两条都 rc=0，`matchMedia('(prefers-color-scheme: dark)').matches = true`。

## (3) ⚠️ 坑一：主题切换有**中间态**，量到的是假的

第一次量就抓到一个荒唐的结果：

| | 值 |
|---|---|
| `prefers-color-scheme: dark` | **true** |
| body 背景 | **`rgb(255,255,255)` 白** |
| `--qx-surface` | **`#12161d` 深** |
| 菜单背景 | **`rgb(18,22,29)` 深** |
| 菜单文字 | `rgb(232,237,242)` 浅 |

**白底页面上浮着一个深色卡片。**

差点当成 bug 记进文档。追下去才发现是**过渡中间态**：
媒体查询已经翻了，DSH 的重绘还没跟上。再等一会儿，页面自己变成了
`rgb(21,21,23)`，三者一致。

更糟的是过程中还读到过一次 `--qx-surface` = **空字符串**，
一度以为整个令牌块没加载。查了 157 个样式表才确认
custom.css 好好地在那儿（`?v=` 版本，63 条规则）—— 那也是中间态。

### 由此定下的规矩

> **改完系统主题 / 切前后台 / 任何会让主题重算的操作之后，

## 17.2 ⭐ 核心教训：给「从不绘制」的元素调样式，先 dump 可见性

|---|---|

1. ⭐ **主因 `opacity: 0`** —— 元素**从不绘制**。任何普通选择器写完，

> **纪律 (q)**：给元素调样式前先 dump
> `opacity` / `visibility` / `transform` / 祖先 `overflow` / `elementFromPoint`。
> `getComputedStyle` 回读成功**只证明你写进去了**，不证明**它被画出来**。

# 第 19 轮 · 压侧栏 chrome —— **压哪里有用，和直觉完全相反**（本项目第 19 轮迭代）

## 一句话结论

第 18 轮留的未竟项（树高只从 303 动到 305）本轮还掉了：
**完整可见行 6/21 → 7/21，树高 303 → 323，裁切线 579 → 595。**

但真正值钱的是**两条工具级结论**，都不是 UI 知识，是 CSS/测量知识。

## 19.1 ⭐⭐ 压哪里有用，和直觉完全相反

侧栏根是 column flex，块3 是 `flex: 1 1 0%`（**吃掉全部余量**），块4 是最后一项 `0 0 auto`。
所以：

```
裁切线 界 = 视口高 − 块4 高 = 691 − 112 = 579
```

| 压哪里 | 后果 | 实测 |
|---|---|---|
| 压**块3 上方**的块1/块2 | 块3 原样吃掉省下的空间 ⇒ **树一点不变** | 块1 48→44，树高 303→**307**（+4，无用） |
| 压**块3 下方**的块4 | 界上移 + 块3 长高 ⇒ **树真长高** | 块4 112→96，树高 303→**319**（+16） |

> **要长高只能压最后一个 flex 项。压「上面看起来更松」的那些，纯属白费。**
> ——这正好和「要紧凑就压间距」的直觉相反，也是第 18 轮会失手的根因。

## 19.2 ⭐ 判准用「完整可见行」，不是「树盒高」

| 组 | 树高 | 完整可见 |
|---|---|---|
| T0 基线 | 303 | 6/21 |
| T1 底栏 56→48 | 319 | **6/21** ← 差 1px |
| T2 + 顶栏图标 48→44 | 323 | **7/21** ✅ |

7 行需要 `7×44 + 6×2(行间距) = **320px**`。
T1 的 319 **恰好差 1px**，仍然是 6 行。

> 「树盒高 +16」和「树盒高 +20」在属性上只差 4px，效果却是 **0 行 vs +1 行**。
> 判密度**必须落到「一屏多露几行」**——这是第 18 轮纪律 (s) 的第二次兑现，
> 上一轮它救了我一次，这一轮它直接决定了要不要继续加 4px。

## 19.3 ⭐⭐ `:has()` 嵌套 + 兄弟组合器，在这个 Chromium **非法**

为了选中块4（底栏），踩了四个坑：

| 候选 | 结果 |
|---|---|
| ① `div:has(> [role="tree"]) ~ div` | 合法，但**命中 0**（树的直接父是块3 的唯一子元素，没有兄弟） |
| ② `div:has(> div:has(> [role="tree"])) ~ div` | **整条非法** → `<style>` 静默丢弃 |
| ③ `nav ~ div:not(:has(> div > [role="tree"]))` | 合法，**命中 2**（没排掉块3） |
| ④ `nav ~ div:not(:has([role="tree"]))` | **命中 1** ✅ |

**② 是本轮最贵的坑**：它不是「没匹配上」，是**整条规则被浏览器丢掉**。
A/B 表现和「选择器写对了但不匹配」**一模一样**，我当场把它误读成
「`~` 要求同父」——**这个结论其实是错的，真因是语法非法**。

> ⚠️ `<style>` 里写非法选择器 = **静默丢弃，无任何日志**。
> A/B 出现「毫无反应」时，**先怀疑语法，再怀疑匹配**。
> 排查手段：把候选丢进 `document.querySelectorAll()` 并 **try/catch**，
> 拿到 `DOMException` 才算数（第 19 轮 `.tmp/r19_sel.py` 就是这么定位的）。
>
> ⚠️ **③「命中 2 但恰好没炸」绝对不能上线**。排除条件写浅了一层，
> 只是因为块3 的子元素恰好不是能压的东西才没出事。收紧到 ④ 才落盘。

## 20.1 先量「现在长什么样」，再定「要改成什么样」

不靠印象改 CSS。把 `[role="tree"]` 里**所有非透明填充块**捞出来，只有一个：


VSCode 的 explorer 里**没有**这种大填充块。这是本轮的主攻目标。

## 20.2 药丸选不出来 ⇒ 按项目约定用 JS 打标记

它就是个普通 `[role="treeitem"]`，圆角/内距/子元素（`SPAN 16×20` + `SPAN 文本`）
与文件夹行、会话行**完全同构**。唯一区别是**文字是 "New Session"** —— **CSS 无法匹配文本**。

## 20.3 ⭐⭐⭐ 本项目最贵的一条教训：**内联 `!important` 压过一切 CSS**

B18 把顶部药丸从 44 改到 40，**写了就是不改**。阶梯测试：

| 试法 | 结果 |
|---|---|
| `[data-qx-sb-primary]{min-height:33px!important}` | **44** |
| `[x][x]{…!important}`（特异性 0,2,0） | **44** |
| 再叠 `button[x]` / 三重属性 / 放最后 | **44** |
| `el.style.setProperty('min-height','40px','important')` | **40** ✅ |

读 CSSOM 才看见真相：元素上有**内联** `min-height: 44px !important`。
**不是 custom.js 写的**（全项目 4 处 `min-height` 内联都在会话区 /
点触点修复 / 细图按钮里，够不到侧栏）—— **是 DSH 运行时自己写的**。

> **内联 `!important` 排在作者样式表 `!important` 之上，且与选择器特异性无关。**
> 叠多少遍 `[x][x]` 都一样。这不是「特异性不够」，是**层不对**。

**连带推翻一个假成功**：第 19 轮 B16「把侧栏底栏压到 48」当时真的生效了 ——
但那是因为 **48 恰好等于内联值**，不是 B16 压过了谁。
现在改成 40 立刻打回原形。

> ⚠️ **别把「值恰好相同」当成「规则生效了」。**
> 这和第 17 轮那条（"值为 0 是因为不绘制"）是同一类陷阱：
> **一个「看起来对了」的结果，先问「它凭什么对的」。**

解法：`relaxSidebarInlineHeights()` 在标记时摘掉这条内联，
尺寸改由 CSS 的 `data-qx-sb-*` 接管（2 秒轮询一次，抗 DSH 重渲染）。

## 20.4 导航区选择器考古：三次全错，第四次改用标记

|---|---|
| `[data-slot="sidebar"] …` | **命中 0** —— 侧栏根**根本没有 `data-slot`** |
| `div[aria-label="New session"]` | **命中 0** —— 药丸其实是 `<button>` |
| `button[aria-label="New session"]` | **命中 2** —— 274×44 的 logo 区与 326×44 的药丸**共用同一个 aria-label** |
| ⇒ 新增 `markSidebarBlocks()` | 打 `data-qx-sb-{logo,primary,panels,tree,footer}` |

第 3 条尤其坑：**同一个 `aria-label` 挂在两个元素上**，靠选择器分不开。
与第 19 轮的 `:has()` 三坑同源 —— **选择器必须实测命中数**。

顺带一个 `querySelector` 的边界：**它只搜后代，不搜自己**。
顶部药丸**本身就是** `<button aria-label="New session">`，
第一版只写 `块.querySelector(...)` 把整块漏掉，

Size rule」**「**Don't treat one unit or minimum as universal across platforms**」。

树行 **34px（9.0mm）**达标；**一级导航仍保 44~48px**（入口少、点击频率高）。

## 20.8 本轮方法论增量

1. **纪律 (y)**：**内联 `!important` 压过一切作者样式表规则**，与特异性无关。
   CSS 改不动 ⇒ 只能 JS `removeProperty` / `setProperty`。
2. **纪律 (z)**：**「值恰好相同」不能证明规则生效**。
   改尺寸前先读一次 `getAttribute('style')`。
3. **纪律 (aa)**：同一个 `aria-label` 可能挂在多个元素上；
   `querySelector` **不搜元素自身**，要配 `matches()`。
4. **纪律 (bb)**：**单点优化会让不一致更刺眼** —— 密度/风格调整必须全局一起做。

## 20.9 离 VSCode 还差什么（本轮没做）
