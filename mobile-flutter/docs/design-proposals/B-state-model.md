> **本文的立场一句话**：状态词不是「宿主现在怎么样」的转述，而是

## 0. 唯一主张：消极断言需要比积极断言更强的证据

竞品 Codex 的旗舰失败（B4）不是「文案写得不好」，是**断言的证据等级错了**：

```
Pursuing goal — 11h 35m     ← 积极断言：它正在跑
is reconnecting             ← 传输层事实
Error loading messages      ← 消极断言：消息读不出来（被当成一句提示，而不是一个状态）
```

Codex 的错误是把三件**等级不同**的事排成了三行并列的「事实」，让用户以为它们互相印证。
用户学到的不是「它坏了」，而是「这个界面在编」。

更严重的是：**我们自己的代码里已经有同一个 bug。**
`05 §0.1` 记录的 P0 缺陷 —— `interaction_controller.dart:207` 是 `autoDispose`，
用户停在别的页面时订阅被取消，此刻到达的审批根本看不见；而 `$events` 不重放
（`01-facts.md §2.1`）。于是：

> agent 永久挂在等待态 → 手机上零解释 → 用户回来看到的还是「空闲」

这是 B4 的**同构复现**，只是主角是我们自己。

### 0.1 由此得到的建模律（本方案的地基）

协议的两类投递能力**不对称**：

| 通道 | 语义 | 能证「有」 | 能证「无」 |
|---|---|---|---|
| `emit` 单向通知（24 条白名单里 22 条） | 尽力投递，**不重放** | ✅ | ❌ **完全不能** |
| 一元调用 / `waterfall` | 请求-响应 | ✅ | ✅（但只在成功之后、且只在保质期内） |
| 传输层（socket / RTT） | 客户端自证 | ✅ | ✅ 连续时间线 |

所以：

> **律 1（消极断言律）**
> 「它空闲」「它完成了」「它没在等我」这类**否定式**断言，
> 只能由**一次成功的请求-响应**（`session/list` / `session/projections` / `session/page`）
> 或**一段未中断的 waterfall 投递**来支撑。
> 由 `emit` 的「没收到」推导出的否定式断言，一律无效。

> **律 2（新鲜度律）**
> 每个状态渲染携带一个 `Evidence` 结构（§1.3）。超过该状态自己的阈值，
> 状态词必须降级；**离线态不渲染任何宿主活动态**（C1 的对称补全，见 §2.4）。

> **律 3（区分度律）**
> 两个状态若在「证据来源 / 证据年龄 / 合法动作」三元组上完全相同，
> 它们**必须**渲染成同一个词。凭空多出的区分度就是欠账，迟早变成谎。
> 反之，三元组任一不同，才允许不同的词。

律 3 是本方案对 B4 的正面回答：**界面上的每一处差异，都必须能指着说
「这是因为证据 A 和证据 B 在这一点上不同」。指不出来的差异，删掉。**

## 1. 证据分层与新鲜度模型

### 1.1 五层证据

| 层 | 内容 | 谁产生的 | 连续性 | 能否证否定 |
|---|---|---|---|---|
| **E0 传输层** | socket 状态、重连次数 N、最后一次成功 RPC 完成时刻、RTT | **客户端自证** | 连续，无空洞 | ✅ |
| **E1 事件层** | `api-session/status`·`activity`·`added`·`removed`·`error`、`turn/end`、waterfall 投递 | 宿主，经 emit | **仅本连接内**，重连即丢 | ❌ |
| **E2 拉取层** | `session/list`、`session/projections`、`session/page` 的返回值 | 宿主，经请求-响应 | 每次调用一个点 | ✅ |
| **E3 客户端事实** | 配对记录、本地 `requestId`、终端已开启标记、本地 `throughSeq`、本地持久化的待批记录 | **客户端自证** | 连续 | ✅（但只对客户端行为） |
| **E4 宿主内部** | 宿主此刻在推理 / 在跑工具 / 已死但 socket 还在 | — | — | ❌ **不可观测** |

**E4 永远不可观测**，这不是工程问题，是协议没有这个信号（无版本协商、无能力握手、
`dsh-remote-api.md §1.5`）。因此本方案**不存在任何声称知道 E4 的状态**。
所谓「压缩中」「思考中」「卡住了」全部落进 E4，见 §3。

### 1.2 六种新鲜度信号，逐个判定

| # | 信号 | 来源 | 可用于**年龄**？ | 可用于**时长**？ | 判定 |
|---|---|---|---|---|---|
| S1 | `receivedAt` | 客户端收到帧/RPC 完成的**本机**时刻 | ✅ **唯一合法年龄基准** | ✅ | 全案基石 |
| S2 | `projections.asOfSeq` | 宿主，标注这 20 个 `values` 字段「截至第几条」 | — | — | **免时钟的相干性锚**，见 §1.4 |
| S3 | `projections.kind` | 宿主自报新鲜度（样本值 `"cached"`） | — | — | ⚠️ **取值域未验证**，见 §1.5 |
| S4 | `updatedAt` / `sessionListMetadata.lastPromptAt` | 宿主时钟 epoch ms | ❌ **实测偏差 ≈ 9h55m** | ✅（差值） | **绝不渲染为年龄**，见 §1.6 |
| S5 | `subagentTiming.settledMs` | 宿主时钟测的宿主内时长 | — | ✅ **免偏** | C5 的合法时长源 |
| S6 | RTT（自测） | 客户端 | ✅（作为误差上界） | — | 用来给年龄声明误差界 |

### 1.3 `Evidence` 结构（每个状态渲染都必须携带）

```dart
/// 每个渲染出来的状态词背后都必须有且只有一个这样的结构。
/// 没有 Evidence 的状态词不允许出现在界面上（律 2）。
class Evidence {
  final Source   source;      // event | pull | transcript | clientOnly | none
  final int      receivedAtMs;// S1，我们的钟
  final int?     asOfSeq;     // S2，仅 pull 来源有
  final String?  projKind;    // S3，仅 pull 来源有
  final int?     hostUpdatedAt;// S4，仅 pull 来源有；**不可渲染为年龄**
  final int      rttMs;       // S6
  final bool     subscriptionHealthy; // 客户端不变量，见 §0.1 律 1
  final int      ageMs() => nowMonotonicMs() - receivedAtMs;
}
```

**年龄只用 S1。** 宿主时钟（S4）在本案实测中与真实时间差 9h55m，
任何把它换算成「多久以前」的渲染都会说错一个数量级。

### 1.4 `asOfSeq`：本案唯一免时钟的新鲜度原语（未被任何现有文档采用）

探针实测（`docs/probe/session-list-item.json`）：

```json
"projections": { "asOfSeq": 169, "kind": "cached", "values": { …20 个字段… } },
"running": false,
"updatedAt": 1791181073818
```

`asOfSeq` 说的是「这 20 个字段描述的是第 169 条为止的世界」。它给出三个免时钟的判据：

1. **相干性**：我们本地转录读到的最大 seq 记作 `S_local`。
   `asOfSeq == S_local` → 状态与转录**严格相干**，状态轨可以全功能渲染。
   `asOfSeq < S_local` → **我们比状态更新**：状态词已落后于我们自己读到的内容。
   `asOfSeq > S_local` → 我们落后，可 `session/page` 追到 169。
2. **免偏时长**：`S_local` 的增长是单调的，所以「第 169 条到第 200 条之间宿主干了什么」
   可以用**条数**表述而不是时间表述 —— 在一个状态不可信的场景里，
   `新增 31 条记录` 是比 `31 秒前` 诚实得多的说法。
3. **反证**：`running` 在样本里与 `running == false` 同时出现，而 `turnOutline[0].seq = 5`
   明显早于 `asOfSeq = 169`。**说明 `running` 与 `values` 来自不同步的两次求值** ——
   这就是为什么必须用 `asOfSeq` 做交叉核对，不能只看一个字段。

> **这是本文相对 05 的第一处增量**：05 §0.2.3 列了 14 个未读字段，
> 但没有把 `projections.asOfSeq` 与 `projections.kind` 当成**元数据**使用。
> 它们不在 `values` 里（已实测确认），是 20 个字段的**信封**，
> 而信封恰恰是唯一能告诉我们「这 20 个字段有多旧」的东西。

### 1.5 `kind`：宿主的自保新鲜度声明，以及为什么必须默认拒绝

`kind: "cached"` —— 宿主自己承认这批投影是缓存的。取值域**未验证**
（本部署只观测到这一个值；`live` / `fresh` / `stale` / `unavailable` 均未见过）。

处理规则（**默认拒绝**，不猜枚举）：

```
kind ∈ {已验证为「实时」的字面量}  →  values 20 字段可全功能渲染
kind == "cached" 或 任何其它值     →  values 20 字段按「缓存」处理
kind 字段缺失                       →  按「缓存」处理（缺失即不信任）
```

> ⚠️ 在拿到取值域之前，实现里**不得**出现 `if (kind == 'cached')` 之外的分支，
> 也不得因为「不是 cached」就当作实时。正确写法是白名单：一个 `LIVE_KINDS` 常量集合，
> 初值只含**已实测确认**的字面量；集合为空时全部按缓存走。
> 这条规则的价值在于：宿主哪天新增了一个 `kind` 值，我们会自动降级而不是自动撒谎。

### 1.6 宿主时钟：实测偏差，以及为什么它仍有用

```
探针 capturedAt（真机 UTC）   : 2026-10-05T16:12:33Z
宿主 updatedAt / lastPromptAt : 2026-10-05T06:17:53.818Z
偏差                          : −35,679 秒 ≈ −9h55m
```

两种解释我**无法区分**：(a) 宿主时钟慢了 9h55m；(b) 该会话确实静默了 9h55m。
单样本不可判定。**但两种解释导出同一条结论**：

> **S4 永远不渲染为年龄。** 它只有两个合法用途：
> ① **变化检测**：两次成功拉取之间 `updatedAt` 是否变了（相等 ⇒ 宿主自述「这段时间没变」）；
> ② **免偏差值**：`settledMs`、以及同一宿主时钟上两点之差。

风险与方向：宿主时钟若冻结，我们会错误地推出「没变化」。
所以 `updatedAt` 相等推出的否定式断言**只用于「扣住完成态」**（不宣称完成），
**绝不用于「宣称在跑」**——错误方向永远朝保守。
且该推断的有效期被 §2.1 的 F1（10 秒）卡死，宿主时钟冻结最多让我们多自信 10 秒。

### 1.7 `running` 不在缓存投影里

实测结构：`running` 与 `projections` **平级**，`kind:"cached"` 标注的是
`projections` 整体。因此 `running` 不受该 `kind` 直接约束。
但 `running` 是否同样受缓存影响**未验证**。
处理：仍然把 `kind != live` 的保守渲染施加到 `running` 上
（去流光、显示「最后信号 X 前」）。**最坏结果是我们少动画一点，而不是谎称在跑。**

### 1.8 时长律（C5 的合法形态）

| 想要的文案 | 合法来源 | 非法形态 |
|---|---|---|
| `本轮结束 · 用时 1 分 51 秒` | `subagentTiming.settledMs`（免偏，✅ 实测存在） | — |
| `在跑 · 11 小时 35 分` | 需要免偏起点。**`NO VERIFIED FIELD`**（`subagentTiming` 样本里只有 `lastTurnCompleted`+`settledMs`，无 `turnStartedAt`） | ❌ 用 `now - updatedAt` 算（偏差 9h55m） |
| 退化：`在跑 · 本次连接起 4 小时 20 分` | `now − 本连接首次收到 running:true`（S1，诚实但锚点是我们自己） | ❌ 省略「本次连接起」四字，让用户以为这是真实运行时长 |

**锚点必须写在文案里。** 这是本文对 C5 的一处收紧：
C5 想要 `在跑 · 部署测试环境 · 11h35m` 这一行三段式。
在 DSH 协议下，第三段**在运行中尚无合法来源**。
我们保留第一、二段，第三段要么用免偏值，要么明写锚点，**不写裸数字**。

## 2. 状态保质期阶梯

### 2.1 五级阶梯（每级都有依据，不是拍脑袋）

| 级 | 年龄 | 渲染变化 | 动作变化 | 依据 |
|---|---|---|---|---|
| **F0** | ≤ 10 秒 | 现状态，全通道 | 全部合法 | 手机上「看见→瞄准→点下」约 2–4 秒，10 秒是 2.5–5 倍余量。低于此值，渲染会跑在用户反应前面 |
| **F1** | ≤ 45 秒 | **去流光**（形状保留，运动移除）；标签加 `最后信号 38 秒前` | 全部合法 | 静默 45 秒的轮次极常见（长工具 / 推理 / 等待宿主 IO）。此时**不得改判状态**，只许停止运动。C1「静止是诚实的」 |
| **F2** | ≤ 90 秒 | 标签加 `状态可能已变`；写动作全部禁用 | 只读 + 停止 | 90 秒长到「它大概还在跑」是唯一站得住的读法，又短到用户会想手动核一下 |
| **F3** | ≤ 180 秒 | 详情页转 `3 分钟前的状态`；轨转虚线环 | **只读**。发送/插入/排队/审批/提问/中断/终端/文件全禁 | 直接采用 C1 的锚点数字 |
| **F4** | ≤ 900 秒 | 列表行降级为 `状态不明 · 15 分钟前` | 只读 | 直接采用 C1 的锚点数字 |
| **F∞** | 从未成功 | `从未成功读取`，**不渲染任何状态词** | 只读，且不可进入 | 无任何成功拉取 ⇒ 连消极断言都无从谈起 |

### 2.2 按通道的差异化阈值

同一条阶梯，不同通道的**否定式断言**保鲜期不同：

| 断言 | 证据通道 | 保鲜期 | 理由 |
|---|---|---|---|
| `在跑` | E2 `running==true` / E1 status | 词 F2、动画 F1、断言 F3 | 积极断言，宿主会改 `running` 并重发，漏一次只会晚点发现 |
| `无待答` | E2 `userQuestions.active==[]` **或** 连续未断的 waterfall 投递 | F2（拉取）/ 连接存续期（waterfall） | waterfall 是请求-响应，宿主会持有并重放，**不会静默丢**——这是全案最强的否定式证据 |
| `已完成` | E2 七条件全满足（§4.2） | F2 | 七条否定式断言叠加，任一失效即降级 |
| `本轮结束` | E1 目击 `turn/end` 或 E2 `running` 由 true→false | F3 | 转录里的轮次边界是持久事实，不随时间失效 |
| `有 N 条待发` | E2 `inbox.next-step/next-turn` | F3 | 队列是快照，队列会变 |

### 2.3 「否定式断言的证据是客户端不变量」——05 §0.1 的教训必须可见

`无待答` 之所以可信，靠的不是数据，是**我们的订阅没断**。
而 05 §0.1 证明这个不变量**曾经被一个 `autoDispose` 悄悄破坏**。

因此本方案要求一条硬性设计：

> **`subscriptionHealthy` 必须是可观测的，且必须在「运行日志」页首行显示。**
> 它一旦为 false，**所有依赖否定式断言的状态词立即降级为 `状态不明`**，
> 包括 `已完成` / `空闲` / `无待答`。

把不变量藏进代码里 = 允许它再次被破坏而无人知晓。
把它放进诊断页 = 下次它坏掉时，用户和我们在同一屏上先看到它。

### 2.4 C1 的对称补全：离线态不只禁「运行中」

C1 写的是「**离线态永不显示「运行中」**」。这条只写了一半。
按律 1，`空闲` / `已完成` / `无待答` 全都是**否定式断言**，
而链路的承载者正是那条会断的 socket。

> **离线（socket 非 CONNECTED）时，不渲染任何宿主活动态。**
> 不是「显示运行中」的问题，是**一个都不能显示**。

这不是收紧，这是把 C1 那条规则推到它的逻辑终点：链路断了，
我们关于宿主的一切断言都失去承载物。此时唯一诚实的词是 `状态不明`。

**降级渲染的确切形态**（C1 要求给具体形态，此处给死）：

| 位置 | F0–F1 | F2 | F3 | F4 / 离线 |
|---|---|---|---|---|
| 列表行轨 | 4dp 实心 + 3×3 追逐 | 4dp 实心 + **静止 3×3** | 虚线环 2dp | 虚线环 2dp |
| 列表行状态词 | `在跑` | `在跑 · 状态可能已变` | `在跑 · 最后信号 2 分钟前` | `状态不明 · 15 分钟前` |
| 详情页顶部 | 状态轨 | 加 `状态可能已变` | `3 分钟前的状态 · 下面是最后一次成功读取的内容` | 同左 + 输入框整体禁用 |
| 点进失败时 | — | — | **保留上一次成功的转录**，不显示 `Error loading messages` | 同左 |

最后一行是对 B4 第三行 `Error loading messages` 的正面反制：
**读不出来时，屏幕上必须留下上一次成功的内容**，
而不是一个错误句把用户正在读的东西顶掉。

## 3. 诚实未知：六种「我不知道」

Brief 点名六种：`startup` / `loading` / `reconnecting` / `retrying` / `compaction` / `stopping`。
MiniMax 把六种全塌缩成 `run`（C1 记「宁可说忙也不谎称空闲」）。

我的立场分三层，**塌缩与否由「它改变了哪些合法动作」决定，不由它发生在哪一层决定**：

> **律 4（塌缩判据）**
> 两种不确定，若导出**同一个合法动作集合**，就在**列表行**上塌缩为一个词；
> 若导出的合法动作不同，就在**详情页**上分开。
> 列表行是「扫」的产物（105 项决策里没有「区分 startup 和 compaction」这一项），
> 详情页是「决策」的产物。

### 3.1 逐个裁定

| # | 不确定 | DSH 侧可观测性 | 裁定 | 依据 |
|---|---|---|---|---|
| U1 | `startup` | ⚠️ **宿主的 startup 不可观测**（E4）。但**我们自己的 startup 完全可观测**（E0+E3） | **重贴标签**：不渲染宿主启动态，渲染**客户端**启动态：`正在连接` / `正在拉取 393 个会话`，带真实进度与已用秒数 | 这是本文对六种的一个纠正：MiniMax 的 `startup` 是 agent 的，我们的 startup 是链路的。**我们能诚实描述自己的启动，不能描述宿主的** |
| U2 | `loading` | 部分 ours（RPC 在途，E0）+ 部分 E4（宿主在算） | 拆两半。RPC 在途 > 2 秒 → `正在读取… · 已等 3 秒`。宿主在算什么 → **与 `在跑` 有意不可区分** | 协议无法区分「宿主在想」「宿主卡在工具上」「宿主已死但 socket 还活着」。宣称能区分 = B4 |
| U3 | `reconnecting` | ✅ **完全可观测**（E0） | 独立渲染，**必须显示第 N 次** | 02 §4 记录参考客户端 `ConnectionManager.kt:56` 有 `attempts` 却**从未渲染**，「重连第 1 次与第 47 次完全一样」。我们不重复这个缺陷 |
| U4 | `retrying` | ✅ 完全可观测（E3） | **不作为会话状态**，挂在**失败的那个动作**上 | 重试是某个动作的重试，不是会话的属性。放进会话状态会让用户以为会话出了问题 |
| U5 | `compaction` | ❌ **NO SOURCE AT ALL**。DSH 侧无任何字段；MiniMax 的 `state` 枚举不存在于 DSH（DSH 只有 `running: bool`） | **不渲染该状态**。只渲染它的**可测后果**，且只陈述事实不下诊断 | 见 §3.2 |
| U6 | `stopping` | ✅ ours（cancel 在途）+ 可被 E1 证伪 | 独占一个槽位，直到被反证或超时 | 02 §3 #9 记录参考客户端有「点停止后最后一帧仍显示在写」的竞态 |

### 3.2 U5 的诚实缺席：本方案最克制的一处

压缩是我们**能测到、但不能命名**的现象：压缩会表现为
`contextPressure.projectedTokens` 或 `contextBreakdown` 在轮次中途**突然下降**。

> 我们**不**渲染 `压缩中` / `正在整理上下文`。
> 我们渲染的是一条**纯事实差异行**：
>
> ```
> 上下文 92% → 41% · 原因不明
> ```
>
> 这是观测，不是诊断。它不声称知道原因，因此不会因为猜错而误导用户
> （猜错的后果是用户去调一个不存在的设置项）。

同样地，若 E2 `turn/end` 的 `reason.kind` 携带了压缩/取消/超时的分类
（`05 §2` 指出真实失败源是 `turn/end` 的 `reason.kind`，但**那是事件流里的东西，
`session/list` 快照里没有**），我们**在详情页**可以显示该分类（E1 有接收时刻），
**在列表页不行**（E1 不重放，列表尺度拿不到）。这正是律 4 的一个实例。

### 3.3 六种之外的第七种：必须承认

Brief 列了六种。协议还制造了两种它们没列、而我们**一定**会遇到的：

| # | 不确定 | 可观测性 | 裁定 |
|---|---|---|---|
| U7 | **读不到这个会话**（`session/projections` 返回 `null`） | ✅ 确证（API 文档：`session/projections` 返回「基线 或 `null`」） | 独立态 `这条会话已经不在了`。**与 `读不到状态` 严格分开**——前者用户该返回列表，后者用户该重试 |
| U8 | **读得到，但投影不可用**（`session/projections-unavailable`） | ✅ 错误码确证（`dsh-remote-api.md §4`） | 独立态 `读不到状态 · 会话还在`。理由同上：两种失败的**用户下一步不同**（返回 vs 重试），按律 4 必须分开 |

把这两个混成一个「加载失败」是典型的律 3 违规：三元组相同吗？
不同 —— 合法动作不同（返回列表 vs 重试）。所以必须分开。

### 4.2 C3「已完成」与 C4「已收工」：本方案与 C4 的对接（本轮结束 ≠ 活干完了）

C4 的原文依据是 MiniMax 的 `state=done ... background=1`。
**DSH 侧没有 `state` 枚举**（实测只有 `item.running: bool`），
所以不能照搬那套词汇。但 C4 的**原则**可以完整落地，
而且 DSH 提供了比 MiniMax 更好用的字段：`turnOutline`、`inbox`、
`agentTeam.tasks`、`plan`、`userQuestions`。

> **C3 `已完成` 的七条件（缺一即降级）**
>
> | # | 条件 | 字段 | 挡掉的是什么 |
> |---|---|---|---|
> | 1 | 传输层 `CONNECTED` | E0 | 断链时的完成幻觉 |
> | 2 | 轮次结束被**本连接目击** | E1 `turn/end` 或 E2 `true→false` | 漏掉 emit 后把「不知道」说成「做完了」 |
> | 3 | `subagentTiming.lastTurnCompleted == true` | E2 | 停住了（C5）被说成完成 |
> | 4 | `userQuestions.active == []` | E2 | 「它还在等我」被说成「做完了」 |
> | 5 | `inbox["next-step"]` 与 `inbox["next-turn"]` 均空 | E2 | 还有我排的活 |
> | 6 | `agentTeam.tasks == []` 且 `plan.pending == false` | E2 | **C4 的后台工作** |
> | 7 | 七项证据年龄 ≤ F2 | S1 | 用旧证据说新话 |

**C4 `已收工` 的取值（条件 6 不满足时）**：

```
已完成 · 4 轮                 ← 条件 1–7 全满足
已收工 · 1 个后台任务          ← 1–5、7 满足，条件 6 不满足
本轮结束                       ← 条件 1、2、7 满足，3/4/5 任一不满足
状态不明                       ← 条件 1 或 2 不满足
```

> ⚠️ **`已收工` 的计数来源只有 `agentTeam.tasks.length` 与 `plan.pending`。**
> 实测样本里 `tasks: []` 为空、`plan:{active:false,pending:false}`，
> **单样本无法确认 `tasks` 的元素形状，也无法确认 `phase` 的取值域**。
> ⚠️ 特别注意：样本里 `running==false` 且 `lastTurnCompleted==true` 的同时，
> `agentTeam.members[0].phase == "active"`。
> **所以 `phase=="active"` 不能当「还有活」的信号** —— 它与「本轮已结束」共存。
> 只有 `tasks` 非空与 `plan.pending==true` 算数。
> 在拿到更多样本之前，`已收工 · N 个后台任务` 的 N **只取 `tasks.length`**；
> `plan.pending==true` 而 `tasks` 为空时，文案写 `已收工 · 有未落地的计划`（不编数字）。

> **`job/*` 不用来出这个数字。** `job/list*{sessionId}` 是 per-session 流，
> 393 条会话开 393 条流不可行。列表尺度上**没有任何合法的后台作业计数来源**。
> 详情页可以为**当前打开的这一个**会话开 `job/follow*`，
> 但那时我们已经在 C3/C4 的判定里了，**`job` 面板本身仍是 05 §11 明确不做**。

### 4.4 等待时长的锚点规则

C6 要求每条待答带**阻塞时长** `已等 2h14m`。锚点必须诚实：

| 情形 | 文案 | 理由 |
|---|---|---|
| 本进程连续持有该 waterfall，且链路自收到起未断 | `已等 2 小时 14 分` | 我们真的连续观察了这么久 |
| 中途重连过 / App 重启过 | `至少已等 2 小时 14 分` | 我们知道它在那个时刻**已经**在等，这是下界 |
| 重连后**首次**收到，客户端无历史 | `等你回答`（**不显示时长**） | 无锚点。编一个 0 秒比不显示更糟 |

> 所以 waterfall 的 `agentId` 可直接映射到行，**归属判定零成本**。

## 5. 陈旧下的动作合法性

### 5.1 合法性判据：不是新鲜度，是幂等性

朴素做法是「数据旧了就全禁」。那是懒惰的，因为它把**只读**动作也一起禁了，
而只读动作恰恰是陈旧时用户最需要的。

> **律 5（幂等律）**
> 动作能否在陈旧下保留，只取决于**重试是否安全**：
> - **幂等**（`cancel`、读、`updateQueue` 的 remove）→ 永远保留。
> - **不幂等且可检测**（审批/提问的回答，同一 `callId` 二次提交必失败）→ 保留，但必须单发、必须显示未回执。
> - **不幂等且不可检测**（`session/prompt`）→ 按年龄分级降级（§5.2）。

### 5.2 动作合法性矩阵

| 动作 | API | 依赖的证据 | 幂等性 | F0–F1 | F2 | F3+ / 离线 | 陈旧时用户看到什么 |
|---|---|---|---|---|---|---|---|
| 排入下一轮 | `session/prompt{mode:'queue'}` | 传输 CONNECTED | 依赖 `requestId` 去重（**未验证**） | ✅ | ✅ **降级保留** | ❌ | 输入框可用，芯片只剩 `排到下一轮`，`插到当前轮` 置灰并写明原因 |
| 插到当前轮 | `session/prompt{mode:'steer'}` | + 会话状态 ≤ F2 | 不幂等，会打断未知轮次 | ✅ | ❌ | ❌ | 芯片置灰 + `宿主忙不忙我们不知道`（不写「它在跑」） |
| 停止 | `session/cancel` | 传输 CONNECTED | **幂等** | ✅ | ✅ | ❌ | F3+ 时输入框整体禁用，`停止` 仍在（幂等，值得保留） |
| 允许这一次 | waterfall 回应 | 链路存活 + `callId` 定位成功 | 不幂等但可检测 | ✅ | ✅ | ❌ | 离线时 `审批在断线期间不可用`（05 §9.2 已裁定） |
| 拒绝 | waterfall 回应 | 同上 | 同上 | ✅ | ✅ | ❌ | 同上 |
| 改/删队列 | `session/updateQueue` | 投影 ≤ F3 | 幂等（remove） | ✅ | ✅ | ❌ | 置灰 + `队列状态是 3 分钟前的` |
| 改模型 / 权限档 | `session/selectModel` | — | — | ❌ | ❌ | ❌ | **不做**（05 §11 已裁定） |
| 重命名 / 分叉 | `session/rename`·`fork` | 投影 ≤ F3 | rename 幂等 | ✅ | ❌ | ❌ | 抽屉内置灰 |
| **终端** | `terminal/*` | 仅传输 + 本地开启标记 | — | ✅ | ✅ | **✅ 保留** | 见下 |
| **文件浏览** | `workspaceFiles/*` | 仅传输 | 读，幂等 | ✅ | ✅ | **✅ 保留** | 见下 |

**最后两行是本表最重要的两行。** 它们证明这套模型是有分辨力的、不是一刀切：

- 终端与文件浏览**不依赖会话状态**，所以会话数据再旧也不影响它们。
  按 C9，终端入口独立于会话、需一次显式开启、开启时明写
  「终端不受审批保护，宿主上会真的执行命令」。
- 因此「会话状态 3 分钟没更新」**不会**波及文件浏览。
  一刀切禁用会让用户在最需要看文件的时候被无关地拦住。

### 5.3 陈旧时的输入框（确切形态）

```
F0–F1   [ 插到当前轮 | 排到下一轮 ]   说点什么…            [ 排入下一轮 ]
F2      [ 插到当前轮(灰) | 排到下一轮 ] 说点什么…          [ 排入下一轮 ]
        灰芯片下方一行小字：宿主忙不忙我们不知道
F3+     整个输入区替换为一行灰字：需要连接才能发送
        （C1 + 05 §9.2 裁定；不显示成一个可点但没反应的输入框）
```

> **B7 物理律的落地**：F0→F2 只是芯片置灰 + 追加一行小字，
> **输入框本身高度不变**；只有 F3+ 才整区替换。
> 「芯片变灰」不推动转录，「整区替换」只在链路已断时发生一次。

### 8.1 与 05 冲突的两处（必须由人拍板）

> **冲突 1（重要）**：05 §2 的 5 态表里，`已完成` 的判定是
> **`running == false` 且不是其它三态**。
> 本文认为这条**不成立**，因为 `running == false` 只证明「本轮不在跑」，
> 不证明「活干完了」—— 而这正是 C4 要求区分的那件事。
> 在实测样本里，`running==false` 的会话同时有 `userQuestions` 待答、
> `inbox` 排队、`agentTeam.tasks` 的可能性，05 的判据会把它们全标成「已完成」。
> **建议修正为 §4.2 的七条件**，并新增 `本轮结束` / `已收工` 两态（05 的 5 态变 7 态）。
> 代价：状态词多了 2 个，元信息行更挤。收益：这是 C4 的全部意义。

> **冲突 2（次要）**：05 §9.2 的离线态四条行为里，没有一条说「禁止显示什么」。
> 本文补上 §2.4 的对称禁令（离线不渲染任何宿主活动态）。
> 若不补，05 的「缓存最后一次会话列表，离线时可读」会连带把
> `已完成` / `空闲` 一起留在屏幕上 —— 那就是 B4 的第一行换个马甲。

### 9.3 学习曲线

用户要学的**新概念只有 3 个**：`状态不明`、`已收工`、`至少已等`。
前两个是本方案新增的（05 的 5 态里没有），第三个是一个永久的限定词。
参照物全部是日常词，没有一个是协议词 —— 我们**不把** `running` / `cached` /
`asOfSeq` / `projections` 任何一个暴露给用户。

### 9.4 拿不到数据时的退化阶梯

| 缺失 | 退化 | 最终形态 |
|---|---|---|
| `kind` 取值域未知 | 全部按缓存渲染（去流光） | 少动画，不撒谎 |
| `asOfSeq` 缺失 | 退回纯 S1 年龄判据 | 阈值不变，精度下降 |
| `settledMs` 缺失 | 时长改 `本轮已用 X`（自测） | 锚点写进文案 |
| `turnOutline` 缺失 | 第二行不渲染摘要 | **不渲染**，不用别的东西凑 |
| `userQuestions` 缺失 | `等你` 退化为**仅** waterfall | 覆盖率下降，但不会误报 |
| `asOfSeq` 与本地 `S_local` 不可比 | 关闭状态轨流光 | — |
| **`approval/request` 在列表尺度不可得** | D2 只能靠本地持久化记录 | 见 §10 阻塞项 3 |

## 11. 阻塞项（开工前必须先答的 5 个问题）

| # | 阻塞 | 为什么阻塞 | 最小验证动作 |
|---|---|---|---|
| **1** | `assistant-stream` 的 delta 文字字段名 | S2 的「在跑」活动行内容依赖它；05 §0.3 已标为唯一探针动作，优先级高于一切视觉工作 | 抓一帧 `assistant-stream` 的 `chunk` |
| **2** | `projections.kind` 的完整取值域 | §1.5 的白名单为空时全部按缓存走。若实际有 `live`，F1 阈值可放宽一档 | 多拉几次 `session/list`，在**正在跑**的会话上采样 `kind` |
| **3** | `approval/request` 在**列表尺度**是否可得 | `userQuestions.active` 只覆盖提问（实测字段名即如此）。**审批没有对应的列表级字段**。若不可得，`等你` 区的覆盖率存在缺口，重启 App 后只能靠本地持久化记录 | 在一个真发生审批的会话上比对：`userQuestions.active` 是否含审批项 |
| **4** | `session/prompt` 对 `requestId` 是否去重 | 决定「发送」能否安全重试。若不去重，网络超时后重发会**产生两个轮次** —— 这是本方案唯一可能造成不可逆损害的未知项 | 连发两次相同 `requestId`，看是否产生两个 turn |
| **5** | 宿主时钟偏差到底是 (a) 还是 (b) | 只影响 `updatedAt` 的可读性（我们已禁用它做年龄），但影响 §1.6 变化检测的置信度 | 对一台刚跑完的会话立刻重拉，比对 `updatedAt` 与本机时间 |

### 11.1 顺带记录的一处文档不一致

Brief B2 与 05 §0.2.3 均称 `projections.values` 有 **19 个字段**；
实测 `docs/probe/session-list-item.json` 的 `values` 有 **20 个键**：

```
agentPreset, agentTeam, contextBreakdown, contextPressure, goal, imageLimits,
inbox, modelSelection, permissions, plan, sessionListMetadata, sessionStats,
subagent, subagentCatalog, subagentTiming, title, todos, tokenUsage,
turnOutline, userQuestions
```

多出的是 `contextPressure`（C10 的数据源）与 `sessionStats` / `tokenUsage` / `turnOutline`。
**本方案按 20 个字段设计**（`contextPressure` 是 §4.3 G1 的唯一来源）。
建议就地修正 Brief B2 与 05 §0.2.3 的计数，避免后续按 19 实施时漏接一个字段。

### 11.2 一句必须留下的提醒

`05 §0.1` 那个 `autoDispose` 缺陷之所以能活到今天，是因为
**它不产生任何报错**。它只是让一个「否定式断言」失去了证据，而界面照旧显示「空闲」。

本方案的所有阈值、所有 `NO FRESHNESS SIGNAL`、所有「不渲染」，
**都不会让界面变差，只会让它变穷**。这是刻意的取舍：
一个穷的界面不会训练用户不再相信它，而一个富的、会骗人的界面会。
