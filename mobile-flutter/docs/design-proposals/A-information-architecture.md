> 立场：本文从**用户的前三个问题**倒推结构，API 是约束不是生成器。
> 参照文档：`../research/03-design-brief.md`（下称「约束书」）、

## 0. 脊椎：地铁上的三秒

### 0.1 三个问题，是三个**不同形态**的答案

用户掏出手机，不是在「浏览」，是在**确认**。约束书 A 说它是遥控器。遥控器开机
之后从不先显示功能菜单，它显示**灯**。所以首屏要同时给出三种形态不同的答案：

| # | 问题 | 正确形态 | 读者动作 | 现实代价 |
|---|---|---|---|---|
| **Q1** | 有没有**卡住等我**的？ | **抢占**：一个数字 + 一个按钮 | 点一下就答 | agent 阻塞时进度是零，时钟在烧 |
| **Q2** | 我**不在的这段时间**发生了什么？ | **扫**：计数与增量 | 扫一眼 | 不知道就会一直惦记，等于没远程 |
| **Q3** | 我要走管的那条**现在怎么样**、我上次插的话**生效没有**？ | **读**：一行文字 | 读一行 | 读不到就重开 WebView，成本极高 |

三个问题的**形态不同**，所以它们不能由同一个控件回答。这是我全篇的结构起点：
**首屏需要三种形态，不是三个列表。**

### 0.2 从三问推出 5 条结构规则

| # | 规则 | 由哪一问推出 |
|---|---|---|
| R1 | **根屏必须同时是最重要的屏和永不空屏的屏** | Q2：变化会停（「它今天没动」也是答案），但「在跑 + 等你」全空的日子会出现 |
| R2 | **Q1 的位置必须恒定，不能靠排序争取** | Q1：393 条里靠置顶是概率，靠固定槽位是必然 |
| R3 | **切换器不是目的地** | Q2：换机器是换主语，不是换任务 |
| R4 | **每屏只回答一个问题，问错的问题用进不去代替空态** | Q3：转录回答 Q3，检索由根屏回答 |
| R5 | **屏幕成本按天付，点击次数按次付** —— 高频次级目的地必须抬进一级；低频目的地不许进一级 | 全部 |

R5 是本提案唯一的排序准则。下面每一条放置决定都引用它，不再引用 taste。

### 0.3 五个问题的正面回答

#### (1) 根目的地：会话列表，还是混合根？

**三个候选，逐个排除。**

**候选 A：参考客户端那种「根 = 单会话，列表在抽屉」。直接排除。**
理由是三条独立证据，不是一条：约束书 A 说「不是聊天 App」；
参考测绘 §2.2 记下它把唯一的分组能力放在一个**平时空着的 tab** 里
（`ChatProjections.kt:135` 的 `groupByTurn` 只被 `TrajectoryTab.kt:67` 用），
`chat.png` 证实默认转录一屏 19 条同构工具行、零结论；抽屉把「要被扫的东西」
藏起来，而本产品唯一的高频动作就是扫。**根屏必须是列表，这是结构问题。**

**候选 B：05 §5.2 / 01 §2.3 的「纯会话列表」。结构对，但答不全题。**
它答不了 Q2。平铺 393 条时，「有几家在跑」「我不在的这 3 小时有什么变化」
要靠用户用眼睛扫 44 屏去归纳。05 §3.3 给的答案是「把你置顶」，01 §4.5 补充
「超过 20 条就不置顶，靠筛选芯片」。**这两条互相打架，而且两条都答不了 Q2**
（置顶只解决「哪条要我管」，不解决「我不在的时候发生了什么」）。

**候选 C（本提案）：一屏混合根 = 看护带 + 列表。**
根屏仍然是会话列表（满足 A 的结构判断），但**列表顶部有一条恒定高度的看护带**，
它回答 Q1 与 Q2，下面的列表回答 Q3。

| 看护带行 | 服务 | 出现条件 | 中文文案（实际发货值） |
|---|---|---|---|
| 等你行 | Q1 | 等你 ≥ 1 | `等你 1 · Bash ls -la src/ · 已等 2h14m` + 按钮 `回答` |
| 在跑行 | Q2 | 在跑 ≥ 1 | `在跑 2 · 最久 11h35m · 部署测试环境` |
| 时间锚 | Q2 | **永远** | `你走后的 3 小时：新开 4 条 · 1 条跑完了` / `这 3 小时没有变化` |

看护带不是新数据源，也不是新目的地。它是**同一次 `session/list` 快照的纯投影**，
外加一个本地存的上次快照（`sessionId → {updatedAt, running}`）用来算增量。
零额外往返，且**不可能与下面的列表互相矛盾**——这是它比「筛选芯片」和
「置顶」都强的地方：它不改数据顺序，所以不会破坏用户对位置的记忆（01 §4.5
担心的正是这个）。

**为什么不是「仪表盘当根屏」**：R1。仪表盘在 0 在跑 0 等你那天是一张死屏，
而列表永不空屏。根屏必须永远有内容。

**R2 的推论，也是本提案对 01 §4.5 和 05 §3.3 共同的修正**：
`等你` **不从列表里移走，也不靠置顶**。它整条住在看护带里。
这样 393 条列表的内部顺序完全不动（01 的顾虑成立），而「等你」的位置恒定为
「第 1 行第 1 个控件」（05 的目的达成）。**01 §4.5 与 05 §3.3 的矛盾不是折中，
是被一个更好的位置消解了：固定槽位，而不是排序。**

#### (2) 一次 / 两次 / 永不

判据是 **R5 + 拇指可达性**：390×844 单手持握，舒适区是屏下 55%（y > 464dp），
最难区是左上与右上角。

| 层级 | 目的地 | 位置 | 为什么在这层 |
|---|---|---|---|
| **1 tap** | 会话详情 | 列表行（屏中带） | 唯一的主线动作 |
| 1 tap | **待答接管面板** | 看护带 `回答` 按钮（屏上带，56dp） | 跳过转录：用户在地铁上要的是**答**，不是先读 200 条消息。参数查不到再退化到转录（§4 S3） |
| 1 tap | 连接与这台电脑 `/machines` | **链路状态条** | 见 (5) |
| 1 tap | 停止 / 发送 / 插排切换 | 会话详情屏下 | 高频 × 拇指可达，C2/C3 要求它常驻 |
| 1 tap | 行操作（置顶/归档/复制 ID） | **长按** | 破坏性与低频（`workspace/pinSession` / `archiveSession`），不占可见控件（抄 01 §4.7，正确） |
| **2 tap** | 会话信息抽屉 | 详情页顶栏 `⋯` | 一周 0–2 次；抽屉形态而非全屏，符合它「被查」的属性 |
| 2 tap | 运行日志 | 机器页 | **每周 0–1 次**。R5：低频不许进一级 |
| 2 tap | 工作区文件 | 机器页 | 同上，且它不是主线 |
| 2 tap + 显式确认 | 终端 | 机器页 → gate sheet → 终端 | C9 要求默认关 + 显式开启 |
| 2 tap | 重命名 / 分叉 / 归档 | 会话信息抽屉 | 会话级、低频、破坏性，三层都在屏上：先要确认上下文 |
| **永不** | 搜索框 / 搜索页 | — | `session/search` 本部署 `openAt "never"`（05 §0.2.2）。**且它还消灭一个空态**（见 §3.4） |
| 永不 | 独立 Trajectory / 轮次顶层 tab | — | 约束书 B5 实测失败；`trajectory.png` 小轮次 65% 空白 |
| 永不 | 独立子 agent 面板 | — | 内联，见 (4) |
| 永不 | 独立设置页 | — | 见 (4) |
| 永不 | 权限档位编辑 | — | 约束书 D 标「待定」；`permissions.currentValue` **只读** |
| 永不 | goals / schedule / pluginManager / account / llm 发现 | — | 约束书 D |
| 永不 | 始终允许按钮 | — | 协议只有四个结局（05 §6.2 第 5 条） |

**不复刻参考客户端的 5 指标常驻底栏**（约束书 B5）：`sessionStats` 数据源确实存在
（探针样本：`turns/steps/ttftMs/llmMs`），但它是**被查**的，不是**被扫**的，
归会话信息抽屉的 `轮次 :: 1 轮 · 23 步 · 1m51s`。

#### (3) 393 条之前能 afford 几个目的地？

**算账（390×844，行高 66dp 下限，见 05 §4.2）：**

```
屏高 844 − AppBar 56 − 看护带 184 − 系统手势区 24 = 580dp → 580/66 = 8.8 → 一屏 8 行
看护带收起（只有时间锚 28dp）时：                       736/66 = 11 行
393 / 8.8 ≈ 45 屏
```

**45 屏平铺 = 不可扫。这个数字就是「只能有一个根」的论证**，也是为什么底部 tab
在本产品里必然是错的：一个为 `设置`（每周 0.5 次）预留的 tab，每天付 56dp 屏高
和一次误触的机会，而主线列表已经吃掉 22% 屏高。

**预算（本文的硬上限）：**

- **一级目的地 = 1**（根屏）
- **常驻导航控件 = 1**（链路状态条，它不是目的地，见 (5)）
- **底部 tab = 0**
- **抽屉 = 0**
- **二级目的地 = 6**（会话详情 / 机器页 / 文件 / 终端 / 日志 / 配对）
- **任何时刻用户需要记住的目的地名 ≤ 3**（`看护带`·`转录`·`这台机器`）

**ChatGPT 2026-03 扁平化反弹的正确读法。** 约束书 C8 记了它把能力入口抽成横 bar
（正确抽象），也记了扁平化后用户抱怨多项目不可扫。两件事要分开读：
**扁平化本身不是错，错的是扁平化 + 丢掉分组。** ChatGPT 丢掉的是项目层级，
用户失去的是「我上次在哪个项目」。我们有 393 条、更多，所以更不能靠「更扁」——
但正确的对策不是把项目树加回来（那是**深**的），而是加**便宜且被动**的两样：

1. **时间桶分组头**（带计数、可吸顶）：`今天 (6)` / `本周 (23)` / `7 月 (141)`
2. **位置锚**：用户始终知道自己在桶的哪一段

两者都是**零点击**的结构。这才是 393 条的可扫性方案。**代价说清楚**：
时间桶不解决「上周那个改鉴权的会话」——那是 §3.4 的诚实缺口。

#### (4) 哪个屏不该存在（状态该内联）

四个。各有独立证据。

| 被砍的屏 | 内联到哪 | 证据 |
|---|---|---|
| **独立设置页** | 并入 `/machines` 的三组：`这台机器` / `外观` / `关于` | 它的 4 条内容全是「关于机器或关于 App」的，与机器页同源。独立成屏 = 为 4 行文字付一个导航槽位。约束书 D 已把 `settings` 编辑标「待定」——我砍的是**屏**，不是编辑能力 |
| **独立子 agent 面板** | 会话详情顶栏下的 chip 行：`子任务 2 个进行中 · lead` | `agentTeam.members[].phase` 已在 `projections.values` 里（探针样本实测）。参考测绘 §11.3(3) 实测 12 条形态全同；我们 ≤ 3 个时内联，`> 3` 折叠成 `+N`。约束书 D 标「待定」 |
| **独立 Trajectory / 轮次 tab** | 转录内的折叠行：`23 步 · 1m51s`（点开才见明细） | 约束书 B5 实测失败 + `trajectory.png` 65% 空白。数据源现成（`sessionStats.steps` + `subagentTiming.settledMs`） |
| **独立「消息详情 / Details」屏** | 工具行就地展开 | 参考测绘 §5b 实测：Details 面板文案过期，叫用户「点工具行看输入输出」而那功能已搬到别的 tab。**拆分必然制造文案漂移** |

再加一条**状态级**的砍：**`失败` 不作为列表态存在**。
`session/list` 快照里没有轮次事件（05 §2 已实测论证），所以列表里永不出现失败色。
它只在转录里、**紧贴它修饰的那个轮次**显示 `这一轮中断`——因为参考测绘 §11.3(2)
实测 `Stopped` 药丸夹在两条 Bash 之间、无语境，正是状态词脱离修饰对象。

**B6 的 8 个 `No X` 空态，落到本方案的处理：**

| 8 个中的 5 个 | 处理 | 落点 |
|---|---|---|
| `No subagents` | **不渲染**（chip 行整体不出现） | `agentTeam.members` 为空 → 整个子任务行不渲染 |
| `No background jobs` | **不渲染** | 无面板（已砍） |
| `No pending turns` | **不渲染** | composer 无排队芯片 |
| `No active goal` | **不渲染** | 无 goal 面板（约束书 D） |
| `No recorded requests yet` | **不渲染** | 审批历史不做列表 |
| 另 3 个 | 不做 | — |

**关键区分（本提案的一条新判据）**：
**「没有后台任务」不需要被说；「此刻没有人在等你」必须被说**——因为后者是 Q1
的答案。空态是「一个事实的缺席」，而 Q1 的答案是「一个确定的事实」。
所以看护带全空时收敛成**一行时间锚**，而不是 `No pending interactions`。

#### (5) 终端与文件放哪（C9）

**裁决：机器级二级目的地，从链路状态条进，总 2 tap，与主线零竞争。**

```
根屏 ──1tap──▶ [链路状态条] ──1tap──▶ /machines 连接与这台电脑
                                            ├─ 2 tap ─▶ /machines/:id/files   工作区文件
                                            └─ 2 tap + 显式确认 ─▶ /machines/:id/terminal  终端
```

四条护栏，逐条对应 C9：

| C9 要求 | 本方案落法 |
|---|---|
| 终端入口**独立于会话** | 它在 `/machines` 下，路由里**没有任何会话 id**；会话详情里不存在终端入口 |
| 默认关 + 一次显式开启 | 每次进终端页先过 gate sheet：`终端会在你的电脑上直接运行命令，绕过 agent 的审批。` + `我明白，开启终端` / `取消`。**开关状态存在客户端，每次进入都要再确认一次**——不做「记住我的选择」 |
| 常驻可见的「终端已开」指示 | 指示挂在**链路状态条**（机器级），不在转录上浮动。转录里零终端元素 → 用户看转录时不会被提醒打断了谁 |
| 开启时明说不受审批保护 | gate sheet 的那句话本身就是**事实陈述**，不是恐吓文案。API 文档 §3.1 与 `api/terminal-controller/src/index.ts:151` 是它的出处 |
| 文件浏览标注是否在工作区内 | 每行前缀 `{工作区内}`（发丝描边）/ `{工作区之外}`（虚线描边 + 琥珀，**非仅颜色**）。越界读取需一次显式 tap 确认 |
| 两者都不许出现在「等你」里 | 看护带的等你行只由 `approval/request` 与 `userQuestions.active` 驱动，**代码路径上就没有终端/文件的入口** |

**为什么不放机器页的第 2 组（安全区）而是第 1 组**：终端和文件是**能力**，
安全与关于是**配置**。它们必须在同一屏的同一层，否则用户会把「开终端」
理解成一个设置项，而它是一个随时可能已经在跑的宿主进程。

## 1. 屏幕树

```
千寻 (App)
│
├─ 全局层（横切切面，不属于任何一屏，不是目的地）
│   ├─ 链路状态条 ..... 常驻。离线/重连中/在线；★ 通往 /machines 的唯一门
│   └─ 待答驻留条 ..... 仅在会话详情屏内；槽位常驻（约束书 B7）
│
├─ /                      根屏 = 看护带 + 会话列表        ← 唯一一级目的地
│   ├─ [弹层] 行操作 ..... 长按会话行：置顶 / 归档 / 复制 ID
│   └─ [接管] 待答面板 ... 1 tap 从看护带「回答」进，模态
│
├─ /pair                  配对引导（仅首启 / 无有效连接时）
│
└─ 二级
    ├─ /workspace/:id      会话详情（转录 + composer）
    │   ├─ [弹层] 会话信息 ... 2 tap，等宽指标区
    │   └─ [接管] 待答面板 ... 从本屏的待答驻留条进，模态
    │
    └─ /machines           连接与这台电脑
        ├─ /machines/:id/files      工作区文件（只读）
        ├─ /machines/:id/terminal   终端（默认关，显式开启）
        ├─ /logs                    运行日志
        └─ [弹层] 关于              版本 / 传输方式 / 协议限制
```

**返回规则**：只有根屏按返回退到系统（此时栈已空，退出是正确行为）；
其余每层都有可 pop 的上一页。根屏进二级**必须 `push` 不能 `go`**——
`go` 替换栈，按返回会直接杀进程（`app.dart:30-32` 已记录该 bug）。
（对 `sessions_screen.dart:47` 与 `app.dart:36` 的现有实现无改动。）

**深度上限 3**：根屏 → 会话详情 → 弹层。终端是 3 层（根 → 机器页 → 终端），
是唯一到 3 层的 push 目标；它多一层是因为它多一道**安全确认**，不是因为结构需要。

## 2. 全屏清单（约束书 E1）

### S1 `/` 根屏 —— 看护带 + 会话列表

- **入口**：冷启动默认落点（`app.dart:19` 已如此）；通知深链；任何二级页的返回
- **退出**：`push` 到 `/workspace/:id` / `/pair` / `/machines`；按返回退到系统
- **承载的信息**：Q1 + Q2 + Q3 的答案，以及「共 393 条」这个规模事实

**看护带（自上而下）**

| 元素 | 精确中文文案 | 数据源 |
|---|---|---|
| 等你行（条件渲染） | `等你 1 · Bash ls -la src/ · 已等 2h14m`　`[回答]` | `approval/request` pending / `projections.values.userQuestions.active` |
| 在跑行（条件渲染） | `在跑 2 · 最久 11h35m · 部署测试环境` | `running == true` + `turnOutline.last` |
| 时间锚（永远） | `你走后的 3 小时：新开 4 条 · 1 条跑完了` | 本地上次快照 vs 本次 `session/list` |
| 时间锚（无变化） | `这 3 小时没有变化` | 同上 |

**会话行（3 行 + 轨，行高 66dp 下限）**

```

└─┴──────────────────────────────────────────────┘
```

- **行1**：`subagent.label` 优先（探针样本实测 `"Survey qianxun judge model usage"`，
  是人写的标签），否则 `projections.values.title`，maxLines 2。
  ⚠️ 探针样本里 `title` 就是用户 prompt 的截断原文（`"You are analyzing the local"`），
  所以行1 常常是**英文长句**——必须截断到 2 行 + 尾 `…`，不能让它换行撑高。
  但它仍是正确的检索键：**用户记得住自己说过的话**，所以它留在行1；
  「agent 做了什么」归行2（05 §4.3 的规则对，行1 是另一回事）。
- **行2**（`mono`，maxLines 1）：在跑 → `turnOutline.last` 的当前工具（探针样本的
  `sessionStats` 不含工具名，工具名来自 `session/follow` 事件流；**查不到就不渲染**，
  不放占位符）。刚结束 → `turnOutline.last.response` 首行。查不到 → **不渲染**
- **行3 四格**（`Row` + `Expanded`，溢出 `…`，**禁用 `Wrap`**）：
  `[状态词 + 时长] · [cwd 末段] · [第 N 轮] · [相对时间]`
  - 状态词集合**逐字**：运行中 / 等你 / 已完成 / 父会话已结束（对齐 05 §2）
  - 状态词自带时长（C5）：`在跑 11h35m`、`等你 已等 2h14m`
  - `第 N 轮` ← `sessionStats.turns`（探针样本实测存在）
  - 相对时间格**就是**新鲜度标注（B3 #6）：正常态 `4 秒前`；
    超阈值原地升级为 `15 分钟前 · 链路重连中`（C1 原句）

| 态 | 中文文案 | 数据源 / 判据 |
|---|---|---|

### 3.2 探针样本新发现：`projections.kind == "cached"`

`projections` 有 `kind`（样本值 `"cached"`）与 `asOfSeq`（样本 `169`），
05 §0.2.3 未记录这两个键。**这是第二条新鲜度通道**，且是逐会话的：

- `kind == "cached"` → 该会话的第二行/轮次数据来自缓存投影

  `投影缓存 · 数据截至第 169 步`

## 4. 首屏倒推（约束书 E3）

冷启动 3 秒，屏上**每一个元素**都必须能指认自己服务的那个问题。
指认不出来的元素，本方案不放上去。

| 屏上元素 | 服务 | 它**不**服务 |
|---|---|---|
| 链路状态条 `台式机 · 在线` | Q2 的前提（数据是不是真的） | 不显示任何指标 |
| 机器 bar（C8，2 台才出现） | R3 换主语 | 不是目的地 |
| 等你行 `等你 1 · … · 已等 2h14m` + `回答` | **Q1** | 不展开转录 |
| 在跑行 `在跑 2 · 最久 11h35m` | **Q2** | 不列会话名（那是下面的事） |
| 时间锚 `你走后的 3 小时：新开 4 条` | **Q2** | 不承诺 agent 的意图 |
| 时间桶分组头 `今天 (6)` | Q2 的延续 | 不做筛选控件（被动） |
| 会话行 行1 `title` | **Q3** 的检索键 | 不是状态 |
| 会话行 行2 `Bash ./deploy.sh` | **Q3**「它在干嘛」 | 不是时间戳 |
| 会话行 行3 `在跑 11h35m · … · 4 秒前` | **Q3** + 新鲜度（B3 #6） | 不放 ctx 数字（C10 <70% 不显示） |
| 底部无 tab | — | **刻意空着**：45 屏列表已经吃掉 22% 屏高 |

**3 秒的物理检验**：三个答案全部在**首屏不滚动可见区**内；
状态词 ≥ 13sp、时长用等宽 `tnum`（否则 `11h35m` 与 `4h07m` 宽度不同会抖）；
强光可读 = 不依赖色（B3 #1）。

## 6. 成本与退化（E5）

### 6.1 复杂度

| 项 | 成本 | 说明 |
|---|---|---|
| 看护带 | **低** | 不是新数据源：同一次 `session/list` 快照的纯投影 + 一个本地 `sessionId → {updatedAt, running}` 快照。零额外往返，**不可能与列表矛盾** |
| 时间桶 | 低 | 纯 `updatedAt` 分组 + `sticky header` |
| 固定槽位替代置顶 | **零** | 比排序实现更简单（少一个 comparator 分支），且修掉 01 §4.5 与 05 §3.3 的矛盾 |
| 终端 | **高** | 需直读 `terminal-controller` 的 10 个方法名 + WebSocket 流 + 生命周期管理 + 关闭语义。**最后做** |
| 新鲜度 | 中 | 每屏一个 `snapshotAt` + 一张阈值表（§3）。**注意 `projections.kind` 只观测到一个取值** |

### 6.2 屏幕空间（有账）

```
根屏 844dp：AppBar 56 + 看护带 184 + 列表 → 一屏 8 行
看护带收敛（0 等你 0 在跑）= 28dp → 一屏 11 行
393 / 8.8 = 45 屏
```

**看护带花掉 22% 屏高 = 约 2 屏滚动深度，换「等你」从「要扫 45 屏」变成「第 1 个控件」。**
若实测「同时在跑 + 等你」长期为 0，看护带应自动收敛为一行时间锚（28dp），
一屏回到 11 行——**这是设计内的降级，不是缺陷**。

### 6.3 学习曲线

用户要学的手势共 **3 个**：点行（进转录）/ 长按行（行操作）/ 点状态条（这台机器）。
**要学的新概念：0 个**（无 tab、无抽屉、无层级菜单）。
对比参考客户端：它要用户学会「抽屉里有列表」+「另一个 tab 里才有轮次分组」。

### 6.4 拿不到数据时怎么退化（逐项）

| 缺失 | 退化 |
|---|---|
| `userQuestions.active` 不可用 | 看护带少「等你」行；**等你仍由 `approval/request` waterfall 兜底**（它更权威，是请求本身） |
| `lastPromptAt` 不可用 | 分桶退回 `updatedAt`（item 级，零嵌套成本） |
| `projections.kind` 未知取值 | 按 `cached` 处理（最保守） |
| `contextPressure` 不可用 | 退回 `contextBreakdown` 三段求和（探针实测 1550+11773+67555 = 80878，**注意它 ≠ pressureTokens 98478**，差 17600 —— 所以两者口径不同，**不可互换**，见 §10(3)） |
| socket 断 | 根屏/详情页全部转「N 分钟前的状态」，轨去流光，实时动作禁用；缓存照常可读 |
| `terminal/*` 全不可用 | 机器页的 `终端` 行右侧显示 `不可用` 并置灰，**入口仍在**（诚实报告能力边界，参考测绘 §4 规律） |

## 8. 一处明确反对：01 §4.6 的「21 条以上按 cwd 分项目」

01 §4.6 提议超过 21 条按 `cwd` 末段分组吸顶。**我反对把 cwd 当主轴**，三条理由：

1. **cwd 是技术键，不是心智键。** 探针样本的 cwd 是
   `E:\develop\dsh-workspace\qianxun` —— 末段 `qianxun` 对用户没有检索价值，
   他记得的是「上周那个改鉴权的会话」。而**时间**是本产品唯一确定的心智键：
   「我走的时候它在跑第 12 轮」——这是遥控器场景的天然连续性。
2. **它会破坏「我不在的这段时间发生了什么」。** 按项目分组后，3 小时前开始的
   4 条新会话会散落在 30 个项目组里，Q2 被重新打碎。而 Q2 是看护带存在的全部理由。
3. **`sessionListMetadata.lastPromptAt` 给了免费的时间键**，cwd 末段要给的话得先
   自己切路径字符串。

**保留的部分**：01 的结论「**不**按项目分组少于 21 条的列表」完全正确，采纳。
本提案把分组**推迟到 101 条**才启用，且主轴是时间。代价：跨项目的「找那条会话」
更难——写进已知缺口，见下。

## 9. 一个不解决的缺口：393 条里「上周那个改鉴权的会话」不可达

**这是本方案唯一一个我认为无法用 IA 解决的检索缺口，明写出来，不假装解决。**

- 时间桶让「最近那条」和「这 3 小时」可达，**不**让「特定那条」可达。
- 不加搜索框：`session/search` 本部署 `openAt "never"`（05 §0.2.2），
  服务端搜索根本不存在。
- 不加客户端过滤（对齐 05 §11.1 的立场）：`title` / `cwd` / `turnOutline` 在内存里，
  客户端过滤零协议成本，但**它会让「搜索」这个词在这个 App 里含义不明**
  （搜得到标题、搜不到正文）。参考测绘 §5h 已实测过同类问题：搜索能力关闭的提示
  出现在**打字之后**。

**会翻转这个判断的证据**（先埋点，再决定）：

1. 列表行打开事件的**时间桶分布**：若 `7 月` 及更早的桶贡献了 > 15% 的打开量，
   说明「找特定那条」是真需求 → 那时应当加**明确命名为「按标题筛」的**控件，
   而不是搜索框（05 §11.1 反对的是后者）
2. 滚动深度分布：若 P90 的打开发生在第 15 屏以上，说明一屏 8–11 行不够
3. 开工前必做的一条探针（本方案**没有数据**）：全量 `session/list` 的
   `updatedAt` 直方图 —— 它决定时间桶默认展开哪几段。**探针样本只给了 1 条 item，
   393 条的分布未采集，本文不猜。**

## 10. 与既有裁决的分歧（逐条给反证条件）

### (1) 上下文计量的位置：站 composer，不站抽屉

- **05 §3.4** 判给会话信息抽屉，理由「列表行是被扫的，指标微栅是被查的」
- **参考客户端**（`ContextMeter.kt:34-40`）的判据是反的：「上下文压力是你**写下一条消息时就要
  处理**的东西，不是一轮跑砸之后再去找的东西」，且 `chat.png` 证实它**同时**出现在
  composer 右侧与详情抽屉
- **约束书 C10 自己写明了位置**：`70–85%` composer 右侧灰字、`>85%` 琥珀 + 条

**本方案站 composer**，理由是 C10 是约束书且其门控描述本身隐含了这个位置；
再加上 C10 的阶梯（8 格 → 4 格 → `Ctx 87%` → 隐藏）本质上是**为窄空间设计的降级**，
放进抽屉就没有降级的必要——抽屉有整屏宽度。

**会裁决它的证据**：会话详情页打开后 30 秒内的发送率；以及 >85% 状态下
用户是否自救（发消息 / 插话 / 主动去翻抽屉）。若打开详情却极少发送，
说明「查」占主导，应双处并存（composer 精简 `Ctx 87%` + 抽屉全表）。

### (2) 「等你」的提升不随列表长度取消（对 01 §4.5）

01 §4.5 写「超过 20 条不提升，靠筛选芯片」。**反对**，理由见 §0.3(1)：
置顶与筛选都在赌「用户会扫到那里」，而看护带是**恒定坐标**。
取消置顶在 393 条时等于让「等你」沉到第 300 行——这正是约束书 C8 警告的
「靠更扁解决可扫性」。

### (3) `contextPressure` 与 `contextBreakdown` 口径不同，不可互换

探针样本同时给了两者，且**数值不等**：
`contextBreakdown` 三段求和 = 1550 + 11773 + 67555 = **80878**，
而 `contextPressure.pressureTokens` = **98478**，差 17600（21.8%）。
（两者都很小，是子会话，**不足以判断哪个是「正确口径」**。）
本文的立场：C10 的百分比阈值必须用 `pressureTokens / contextWindow`
（分母只有它给），三段图例只用于**定性**展示 System/Tools/Messages 占比。

**会裁决它的证据**：在一条长会话上同时读两个值，看哪个等于服务端在 UI 上报的百分比。
**这是实现前必须补的第二个探针**，理由写在这里以免被当成已知项。
