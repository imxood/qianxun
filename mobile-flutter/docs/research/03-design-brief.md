> 这是**多 Agent 设计讨论的共同基础**。所有设计提案必须逐条对照本文，
> 明确说清「本方案满足/违反/规避了哪一条」，不接受只讲好处的提案。
>

---

## A. 产品是什么（一句话）

**一个遥控器，附带条件在场。** 用户不在电脑前，用一只手端着手机，
确认家里那个 agent 还在不在跑、刚做了什么、是不是卡在等他。

**不是**聊天 App。用户不跟 agent 聊天，用户**看**它工作、必要时**改**它。

---

## B. 硬约束（不可违反）

### B1. 竞品现状：OpenAI 已做同一件事
2026-05-14 Codex 随 ChatGPT 移动端发布。官方定义
`monitor → steer → approve`，定位在通勤/等待语境。

**推论**：我们不能靠「做得像 ChatGPT」取胜。差异化必须在下面 C 组。

### B2. 协议事实（已入库，非猜测）
- 141 个 Remote 方法 / 29 命名空间。线格式见 `../api/dsh-remote-api.md`。
- `projections.values` 有 **19 个字段**，我们只读了 5 个。已确证可用的：
  `contextBreakdown`（三段 token）、`imageLimits`（附件硬限制）、
  `permissions.currentValue`、`inbox`（待发队列）、`todos`、`plan`、`goal`、
  `agentTeam`、`subagentCatalog`、`modelSelection`、`sessionListMetadata`。
- `agentAvailable` 在本部署 393 条里 392 条为 false，**不可作状态判据**。
- 事件只有 2 个是 waterfall（`approval/request`、`user-questions/request`），
  **重连后只有仍 pending 的 waterfall 会重放**，单向通知不重放
  → **断线重连后必须重新拉一次全量**。

### B3. 不可协商的交互约束
| # | 约束 | 理由 |
|---|---|---|
| 1 | **绝不用颜色单独表意** | 每态必有可见中文词 + 独立形状/运动通道 |
| 2 | **默认态树内零无限动画** | 否则 `pumpAndSettle` 永久超时。运行中的彗尾是**唯一**例外 |
| 3 | **触控区 ≥ 48dp**，间隔 ≥ 8dp | 拇指区，不是鼠标 |
| 4 | **字号缩放 0.9–2.0 全程不裁内容** | 05 §9.5 第 4 条；等宽数据层锁 1.0x |
| 5 | **所有状态必须可被读屏念出** | 户外强光 / 色觉障碍 / 屏幕朗读 |
| 6 | **任何状态必须标注其数据新鲜度** | 见 C1，这是本产品最重要的设计律 |

### B4. 竞品的旗舰失败（我们不能重犯）
Codex 官方 issue #28340，用户实机复现：
```
任务卡：  Pursuing goal — 11h 35m              ← 说它在跑
主机：    MacBook-Pro-4.local is reconnecting  ← 说链路断了
点进去：  Error loading messages                ← 消息打不开
```
> "makes Codex mobile **unreliable for monitoring** … the user may see that
> the task is still running but cannot read or interact"

**「显示对了但按下去是死的」会训练用户不再相信界面。**

### B5. 参考客户端的实测失败（不抄）
| 不抄 | 出处 |
|---|---|
| 一屏 19 行同构工具行、零结论 | `chat.png` |
| 5 个指标常驻底栏、不可关闭 | `chat.png` |
| Chat / Trajectory 双顶层 tab | `chat.png` / `trajectory.png` |
| Trajectory 在小轮次下 65% 屏高空白 | `trajectory.png` |
| `Stopped` 药丸夹在两条工具行之间、无语境 | `chat.png` |
| 12 条子 agent 行形态全同 | `subagent.png` |
| 配对页 30% 屏高给 logo + 重说 App 名的副标题 | `home.png` |
| 排队的 turn 聚合在**另一个平时空着的 tab** 里 | `ChatNodeItem.kt:408` vs `ChatProjections.kt:135` |

### B6. 8 个 `No X` 空态是反模式
一个会话没有后台作业是**常态，不是状态**。
这 8 个里**至少 5 个不该是空态而该是不渲染**：`No subagents` /
`No background jobs` / `No pending turns` / `No active goal` /
`No recorded requests yet`。

### B7. 移动端专属物理律
> "A dock that pops into existence mid-turn **shoves the transcript and the
> composer around** while you are reading or typing."（`Docks.kt:54-62`）

**任何会自己出现/消失的条状元素都会推动用户正在读的内容。**
我们 Batch 1 的「常驻待答条」方向对，但必须保证**槽位常驻、内容不跳**。

## C. 设计律（差异化所在）

### C1. 状态保质期 —— **P0**
每个状态渲染携带 `snapshotAt`。`now - snapshotAt > N` 或 socket 非 CONNECTED 时：
- 轨**去掉流光**（静止是诚实的）
- 标签变成 `15 分钟前 · 链路重连中`
- **禁用**任何依赖实时性的动作
- 点进加载失败时**保留上一次成功的转录**，给
  `3 分钟前的状态 · 下面是最后一次成功读取的内容`
- **离线态永不显示「运行中」**

反推自 B4。对照 MiniMax：它把 startup/loading/reconnecting/retrying/
compaction/stopping **六种不确定全部塌缩成 `run`** —— 宁可说「忙」也不谎称空闲。

### C2. 引导 / 排队是两个一等动词 —— **P0**
只有 MiniMax 做对了（`Enter` steer / `Alt+Enter` queue）。
Codex **禁止排队**（issue #6590）；DSH 协议有 `agent.steer()` 但**输入框锁死**
（作者自认 TODO）。

**手机上没有 `Alt+Enter`**，所以要做成：
- composer 上方常驻分段芯片：`插到当前轮 · 排到下一轮`
- **发送键文案随模式改**：`插入当前任务` / `排入下一轮`
- 切换有**触觉反馈**（用户往往不看它）

### C3. 打断带撤销窗口 —— **P1**
MiniMax：模型尚未开口时打断，消息**退回输入框**。
手机误触是必然事件；确认弹窗在拇指区还要点准，还训练出「见弹窗点第一个」。

「停止」常驻（不藏在 ⋯ 里）。若本轮尚无回复，停止后输入框自动回填。

### C4. 「这一轮结束」≠「活干完了」
MiniMax 明确：`state=done ... background=1` 意为「根轮次结束但有后台工作
会唤醒 agent」，并诚实记录 10–60ms 抖动窗口，规定自动化消费者**必须连续两次
读到 `done + background=0`** 才算真结束。

状态词二选一：真完成 `已完成 · 4 轮` / 轮次完但待唤醒
`已收工 · 1 个后台任务`（**中性灰，不是绿**）。
**拿不到证据就只显示真完成** —— 宁可少说，不可说错。

### C5. 状态词 = 进行时动词短语 + 已运行时长
Codex 的 `Pursuing goal — 11h 35m` 一行给了三件事：它在干嘛、还活着、跑了多久。
中文：`在跑 · 部署测试环境 · 11h35m`。
**时长是长任务最缺的属性** —— 离开三小时回来，最想知道的是
「它是不是已经卡在那里三小时了」。

### C6. 待办集合是顶层对象，不是会话分组
三家 peer 全空白。监督者真正要排的序是「先解哪个最省事/最解锁其它」。
列表顶部常驻「等你」区，每条带**阻塞时长**（`已等 2h14m`）。

⚠️ **阻塞时长有数据源；依赖关系没有** → 第一版只做时长排序，
**拿不到数据不要先画这个 UI**。

### C7. 改道要有回执
三家全无。转录里 `你插入的消息` 用引用块标在**实际生效的轮次位置**，
右侧小状态词。**拿不到注入点就只做「已送达」，不编造吸收点。**

### C8. 机器切换器用横 bar
ChatGPT 2026-03 把能力入口抽成横 bar 放列表上方（正确抽象）。
机器（host）和会话是同层上下文选择器，**不是设置项**。
单台时整行隐藏 —— 不为一个目的地永久缴税。

⚠️ ChatGPT 扁平化侧边栏后引发用户抱怨多项目不可扫。
**我们有 393 条会话，比它更多，不能靠「更扁」解决可扫性。**
只能靠**位置**（等你置顶）+ **形状**（信号轨）。

### C9. 终端与文件浏览：**做，但必须有护栏**（产品负责人决定）
`terminal/*` 是宿主上的真实进程执行，**且刻意绕过 agent 沙箱与审批**
（`api/terminal-controller/src/index.ts:151`）——**它不会出现在「等你回答」里**。
`workspaceFiles/read` **允许读工作区根之外的路径**。

因此必须有：
- 终端入口**独立于会话**，需要一次显式开启（默认关）+ 常驻可见的「终端已开」指示
- 开启时**明说它不受审批保护**（不是恐吓文案，是事实）
- 文件浏览**明确标注路径是否在工作区内**，越界时用不同视觉
- 两者都不许出现在「等你回答」里（它们不是待办）

### C10. 上下文计量按严重度门控
05 §3.4 与参考客户端冲突未决。MiniMax 给第三条路：**降级阶梯 + 优先级序**。
- `<70%` **不显示**（离开前不关心）
- `70–85%` composer 右侧灰字
- `>85%` 琥珀 + 条
- 降级台阶：条8格 → 条4格 → `Ctx 87%` → 隐藏
- 优先级：**权限 > 上下文告警 > 模型 > 会话标题**（按序丢，不按加入顺序丢）

## D. 范围（产品负责人已定）

**做**：
1. 盯状态（列表 + 详情）
2. 介入（引导 / 排队 / 审批 / 提问 / 中断 / 发送消息与附件）
3. 终端 + 工作区文件浏览（含 C9 护栏）
4. 连接与配对
5. 诊断（运行日志）

**不做**（列出但标「待定」不展开）：`goals` / `job` / `schedule` /
`subagent` 面板 / `pluginManager` / `settings` 编辑 / `account` / `llm` 模型发现。

**明确不做**：搜索框（本部署 `session/search` 禁用，05 §11.1 已记为缺口）。

## E. 提交要求

每份设计提案必须包含：

1. **全屏清单** —— 每屏：入口、退出、承载的信息、成功/失败/空/加载四态
2. **状态矩阵** —— 每个状态 × （数据源 API / 新鲜度规则 / 文案 / 非颜色通道 / 可用动作）
3. **首屏倒推** —— 用户冷启动 3 秒内要回答哪 3 个问题？屏上每个元素为哪个问题服务？
4. **逐条对照 B/C** —— 明确说本方案满足/违反/规避了哪几条，以及为什么
5. **成本** —— 复杂度、屏幕空间、学习曲线；以及**拿不到数据时怎么退化**
6. **不做清单** —— 本方案主动砍掉了什么，理由

**不接受**：占位符文案、照抄参考客户端的布局、没有 API 出处的状态。
